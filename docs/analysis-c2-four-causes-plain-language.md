# C2 为什么没有转化为性能:四个原因、逐个说清

## 背景:C2 的机制与它的负结果

**C2 想做的事**:从调参数据里找出「性能提升斜率最大、但取值域被资源上限截断」的那个参数,
把这件事告诉模型,引导它改写算子结构(多花别的资源,腾出这个被顶住的维度)。

**实现 = 2e**,三个动作:`find_walls` 找截断 → `tail_gain` 量斜率 → `for_prompt` 写进 prompt。

**结果**:改写**确实**腾出了那个维度(唯一被归因的墙 `BLOCK_N=128`,共享内存从 122880 B
降到 77824 / 45056–98304 B,都在 101376 B 上限内;对照臂离线找到 7 个墙、0 个被腾出)。
**但端到端更慢**:同箱同配置、只差 2e 的两臂,关掉 2e 的那臂快 8.0%。

---

## 原因一:斜率算出来的时候,这个候选的调参已经结束了

**在讲什么。** 2e 跑在调参循环**之外**。orchestrator 自己的注释就是这么写的
(`orchestrator.py:1710`):"outside the tuning loop, so it cannot touch the trial budget or
what the sampler sees"(在调参循环之外,所以它既不能动 trial 预算,也不能影响采样器看到什么)。
这个隔离**当初是故意的** —— 为了让三臂的 trial 预算严格对等、结果可比。

**怎么测的。** 对每个被找到的墙,数它所属候选在「墙被发现」前后各跑了多少 trial。

**测出什么。** 被归因的那个墙:发现**前 80 个 trial**,发现**后 0 个**。

**意味着什么。** 采样器永远看不到关于它自己的墙。这个候选把全部 80 次测量花在
「不知道哪个维度被顶住」的状态下,等知道了,已经没有 trial 可花了。

---

## 原因二:斜率只用来说服模型,从不改变「测什么」(这条最关键)

**在讲什么。** 斜率这个量,其实**在调参过程中就已经存在**。
`find_walls` 读的是 `stats.param_stats[].latency_by_value` —— 逐取值的中位延迟表,
**而这张表是调参器自己建的**。也就是说:调参器建了表 → 表被丢掉 → 事后重新算出斜率 →
写进 prompt → 交给改写。

**怎么测的。** 看最陡的那个参数,它的最高取值被采样了多少次。

**测出什么。** `cand-dc87a93a` 结束时最陡的参数是 `NUM_WARPS`(斜率 25.6%),
而它的最高取值只被 **7/80** 次 trial 采到过。

**意味着什么。** 斜率唯一的作用是**说服模型**,它从不改变**测了什么**。
所以即使模型完全照做(而 A3 证明它照做了),收益也只能来自那一次改写 ——
而那次改写的父代已经把预算花完了。**这就是你指出的那一点,代码层面确实如此。**

---

## 原因三:一次只有一个族收到墙信息,其他族什么都没有

**在讲什么。** 墙文本发给「被归因的那个候选所属族」的改写者。别的族收不到。

**怎么测的。** 数这个 run 里有几个族、几个族有墙、几个族的墙被归因(=真的收到了文本)。

**测出什么。** 4 个族;2 个有墙;**1 个**被归因。整个 run 只有一个改写沙箱里有
`analysis/resource_walls.md`。

**意味着什么。** 覆盖率 **25%**,另外 3 个族改写时完全没有墙信息。
而墙是**候选级**的事实 —— 别的族的候选也有自己的墙(这个 run 里就有 2 个族有墙),
只是没被投递。这是最便宜的改进点。

---

## 原因四(我一度以为成立,已否证):可归因的墙恰好是最不值钱的那个

**在讲什么。** 2e 只对「单调且斜率为正」的墙做探针,再要求编译探针确认。
怀疑是:这层过滤恰好把值钱的墙筛掉了。

**为什么怀疑。** arm3 看起来正是如此:被归因的墙斜率只有 **7.5%**,
而 60.7% / 25.6% / 10.7% 三个更陡的都没被归因。

**怎么测的。** 用出厂 `find_walls` 在四个 run 上离线重跑,比较「通过过滤」与「被过滤掉」两组的斜率。

**测出什么。** 通过过滤的斜率是 7.5 / 25.6 / 25.6 / 25.7 / 45.3 / 56.0%;
被过滤掉的是 −359 / −178 / −0.7 / 10.7 / 11.2 / 12.3 / 16.3 / 57.9%。
三个有墙的 run 里,**2 个**保留了当时最陡的那个墙。

**意味着什么。** **这条不成立** —— 过滤器没有系统性地筛掉值钱的墙,
arm3 的 7.5% 是**那一个 run 的运气**。我差点把它报成通则,记在这里以免重犯。

## 你指出的第二点:调参不是"找到墙就结束"

**我先前的说法是错的。** 我写"半程就有可探针的墙,还剩 40 个 trial 可花",
隐含把"找到墙"当成了终点。**不是** —— 找到墙只是探索路线要平衡的**一个**因素。
真实的探索方向应当同时考虑至少三件事:

1. **优先探索斜率大的参数的空间**(那里可能有值钱的资源瓶颈);
2. **优先探索未知空间**(没测过的地方,信息增益大);
3. **优先探索更可能拿到高性能的空间**(利用已知的好区域)。

这比 UCB 复杂:UCB 平衡的是「均值」与「不确定性」两项,这里至少三项,
而且第 1 项(斜率/敏感度)不是 UCB 框架里的标准成分。

### 先测了一件事:这三个信号到底是不是同一件事

如果三者高度相关,那任何单信号采样器已经会去那里,做复合毫无价值。
本项目已经两次被这种"其实只是延迟的改写"坑过
(speed-of-light 头寸与 1/latency 的 ρ=+1.000;边界饱和度 ρ 只有 −0.11…+0.24)。

在 4 个 run、48 个候选、**479 个(候选,参数)行**上实测 Spearman:

| 信号对 | ρ | 读法 |
|---|---|---|
| 斜率 vs 覆盖度(未探索程度) | **−0.431** | 中度相关 |
| 斜率 vs 利用价值 | **−0.027** | **基本独立 ⇒ 复合有价值** |
| 覆盖度 vs 利用价值 | **+0.095** | **基本独立 ⇒ 复合有价值** |

(「利用价值」= 该参数最优取值比其典型取值快多少 %。)

⇒ **斜率与"哪里能拿到性能"确实是两件不同的事**,所以复合是有依据的,不是叠概念。

### 但有一个结果对"用斜率引导"不利,必须先说

斜率与覆盖度**负相关(−0.431)**,机制上说得通:一个被资源上限截断的参数,
必然有它从未测过的取值。于是**一个朴素的"先测没测过的"规则,本身就指向墙**:

| | 覆盖度中位数 | 数量 |
|---|---|---|
| 有墙的参数 | **0.78** | 14 |
| 其余参数 | **1.00** | 465 |

而且**覆盖度 < 1.0 的参数只有 24 个,其中 14 个(58%)有墙**。

⇒ 一个廉价的"探索未知优先"规则,用很小的预算就能找到大部分墙,**不需要斜率模型**。
这**削弱**了"斜率作为引导信号"的必要性,但**不削弱**"斜率作为排序信号"的价值 ——
14 个有墙参数的斜率从 −359% 到 +58%,**覆盖度告诉你去哪看,只有斜率告诉你看了值不值**。

## 当前采样器(TPE)能不能表达这些:两个实测限制

### 限制一:它对"取值有序"是盲的

我们的参数是有序的(BLOCK_N 16/32/64/128),但用 `suggest_categorical` 声明,
而 TPE 默认把类别当**无序**处理(除非给 `categorical_distance_func`)。

**怎么测的。** 如果采样器在"向外走"逼近上限,那么有墙参数的**最高取值应该在后期**才被采到。
测 7 个有墙参数的平均归一化位置。

**测出什么。** 平均 **0.52**(个别 0.39–0.74)—— 均匀分布在整个 pass 里。

**意味着什么。** 采样器**不是**定向逼近墙的,它是**撞**上去的。
而这是空间**声明方式**的问题,不是 TPE 聪明不聪明:知道 64 好,对这个模型来说
完全不暗示 128 会怎样。

### 限制二:把不可行报成 PRUNED,对 TPE 的教育作用很弱

我们故意把硬性共享内存拒绝报成 `PRUNED` 而不是 `FAIL`,因为 Optuna 会把 pruned 留在 TPE 模型里、
把 failed 丢掉(实测:12 个 FAIL 只留下 1 个可见,同样 12 个 PRUNED 留下 13 个)。

**怎么测的。** 每个 pass 里,前半 vs 后半的不可行比例。

**测出什么。** 26 个 pass:**12 个下降、5 个持平、9 个上升**。

**意味着什么。** 这个通道**没有**明显把采样器推离不可行区 —— 9/26 个 pass 的后半比前半更不可行。
⇒ 一个**显式的约束模型**是真实的增益,而不只是对已有机制的微调。

**还有一个冲突要先解决**:Optuna 4.9 的内建 `constraints_func`(TPESampler / GPSampler /
NSGAIISampler 都支持,我们一个都没用)文档明确说**不会对 pruned 或 failed 的 trial 调用**。
所以「内建约束」与「我们把不可行报成 PRUNED」这两条路**互斥**,不能同时是机制。

## 下一步

算法选择(TPE 是否够用、有没有更合适的方法)**已完成调研,结论在
[`docs/analysis-sampler-algorithm-choice.md`](analysis-sampler-algorithm-choice.md)**。三句话版本:

1. **TPE 不能完整表达你要的三项**:「高性能优先」它本来就在做,「未知优先」没有方差项可挂
   (但朴素覆盖度规则已能找到 58% 的墙),「斜率优先」完全不表达。
2. **你描述的问题在文献里有名字**:约束边界 / 水平集主动学习 + 优化。BE-CBO(ICML 2024)
   的核心观察就是「最优解在可行/不可行边界上」—— 与我们独立实测到的一致,
   所以**这个观察不能作为我们的新颖性**;但它花大力气**学**边界,而我们的约束可在编译时便宜判定,
   这一半在我们这儿几乎免费。
3. **检索未找到先例的是「用调参实测的斜率去引导算子结构改写」** —— 最近的「重要性引导 BO」
   (MetaSHAP, ICTAI 2025)用的是跨 900 万条历史 pipeline 的 meta-learning,不是本次调参的实测斜率,
   且引导的是超参搜索而非被优化对象的结构。⇒ **C2 该写成「用调参反馈驱动结构搜索」,
   而不是「采样器改进」** —— 后者是个拥挤且成熟的领域。

**建议次序**:先做零风险的「墙文本发给所有族」,再做 `categorical_distance_func`
(唯一前提已实测成立、不动预算、不删取值、不需对照臂的改动),S7 与显式约束模型需你批准。
