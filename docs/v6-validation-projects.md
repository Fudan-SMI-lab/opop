# v6 真实项目、目标切换与反馈验证方案

日期：2026-10-20。代码基线：`v6`，继承 `v5-C3@8de73b4`。本次新增验证任务包，没有修改旧单算子优化路径。以下三类模型均已在 box4-2 上真实运行；“可运行任务基线”与“已实现通用 C3 自动优化”是不同的交付状态。

## 1 任务与目标矩阵

准备三类项目、五种开发 workload、八个目标配置。目标和质量约束属于合法的任务输入，算子组、候选、瓶颈排序、局部评测代码和回装位置应由后续框架产生。

| 项目 | 固定 workload | 独立优化目标 | 作用 |
|---|---|---|---|
| Qwen3-4B 自回归推理 | BF16 SDPA，batch=1，prompt=256，输出=32 | Q1 最小 TTFT；Q2 最大 cached decode tokens/s | 同一项目、同一输入切换目标，区分 prefill 和 decode 对目标的影响 |
| 同一 Qwen 项目 | batch=8，prompt=256，输出=32 | Q3 最大端到端生成 tokens/s | 批量负载下重新发现、测量和选组；不沿用单流结论 |
| ResNet-18 图像分类 | FP32 NCHW，batch=1，224×224，真实图片 | R1 最小模型调用延迟 | 非 Transformer、非语言模型入口，作为首个通用流程开发案例 |
| 同一 ResNet 项目 | batch=32，224×224，相同图片池 | R2 最大 images/s；R3 最小 allocated 峰值，images/s ≥ 原基线 95% | 同一负载的性能／资源约束切换；防止只能按时间占比选组 |
| GPT-2 124M 双卡 DDP 训练 | FP32；2 rank；microbatch=1；序列=128；累积=4；有效 batch=8；SGD | D1 最小训练步时；D2 最小逐 rank NCCL kernel 时间总和的最大值，clean step ≤ 原基线 1.05 倍 | 反向、状态更新、梯度 bucket、多 rank 一致性，以及通信与整体性能的权衡 |

Q1/Q2、R2/R3、D1/D2 是同 workload 的目标切换。Q3、R1/R2 之间还改变 batch，必须分别报告，不把输入变化的效果归因于目标驱动能力。固定 workload 下 DDP step time 和 tokens/s 互为倒数，只算一个优化目标。

ResNet 使用 [microsoft/resnet-18 的预训练图像分类模型](https://huggingface.co/microsoft/resnet-18)，固定模型 revision 和图片源 commit。Qwen 使用已经核查的本机完整预训练权重。DDP 使用完整 GPT-2 124M 架构、确定性随机权重和合成 token，保留其系统实验定位；如果要研究真实数据上的训练质量或收敛，需另加预训练检查点／数据集和对应质量契约，不能由本次验证外推。

预留但本轮未用于采样／调参的 workload：Qwen batch=2、prompt=768、生成16；ResNet batch=7；DDP 序列256、累积2、每步仍1024 token。保留集当前还没有实现 Agent 访问隔离，正式验收须以受限任务输入包与独立评测目录隔离，不能声称已经完成盲测。

### 2.1 本轮基线结果

以下是短程就绪检查的中位数，不是优化后成绩，也不是正式 p95／置信区间。所有推理指标排除加载、输入预处理、H2D、排队和网络，测量 GPU 输入已准备好的完整模型执行；Qwen 计时明确包含首 token 同步边界。训练步时排除权重恢复和测量前控制 barrier。

| Workload | 实测主指标 | PyTorch allocated 峰值 |
|---|---|---|
| Qwen interactive | TTFT **25.267 ms**；cached decode **44.450 tokens/s**；总耗时722.530 ms | 8,168,429,568 bytes |
| Qwen offline | 总生成吞吐 **260.762 tokens/s**；总耗时981.737 ms | 8,573,849,600 bytes |
| ResNet online | 模型延迟 **1.328 ms** | 86,366,208 bytes |
| ResNet offline | 吞吐 **7,632.169 images/s**；每批延迟4.193 ms | 282,264,064 bytes |
| GPT-2 DDP | 跨 rank 最大步时 **147.598 ms**；1,024 token/step，即6,937.741 tokens/s | 各 rank 峰值的最大值1,981,017,088 bytes |

Qwen 的32个输出包含首 token，因此 cached decode 只计31步；其 batch=8 cached decode 吞吐另为289.399 tokens/s，不能混作总生成吞吐。显存数字只包含 PyTorch allocated，不代表整卡、reserved 或 NCCL／驱动分配。

### 2.2 正确性与通信证据

Qwen 两个 workload 均通过完整 logits 重放和逐步 greedy token 一致性，重放最大绝对差为0；固定容差为 BF16 logits `atol=0.02, rtol=0.02`。ResNet 通过完整 logits 和 top-1 重放，最大绝对差为0，固定容差 `atol=1e-4, rtol=1e-4`。三张图片用于参考一致性检查，不构成 ImageNet 准确率评测。

DDP 基线已经使用前三次 microbatch `no_sync()`，没有把 sync-each 当成性能起点。完整梯度对照串行处理同一全局 batch 的单卡参考，最大绝对差 `7.4505806e-9`；更新后参数最大绝对差 `3.7252903e-9`，均通过既定 `atol=1e-6, rtol=1e-4`。两个 rank 的完整梯度完全相同。每个任务的校验器均拒绝人为加1的损坏输出；此负控制尚不等价于未来框架自动生成／回装错误候选后的完整拒绝测试。

DDP 独立 inventory 每 rank 每步记录 **13 次 allreduce、497,759,232 bytes 逻辑 payload**。两个 rank 的计数和字节一致。实际 NCCL transport 日志为 `SHM/direct/direct`，peer-access 双向为 false；不假定 box4-2 有可用 P2P／NVLink。

三次诊断中，各 rank 的 NCCL kernel duration 总和取最大值后分别为77.921、75.306、67.316 ms，中位数 **75.306 ms**。它包含设备等待，不等于线上的传输时间，也不等于关键路径上暴露的通信。不能将其与 clean step 的147.598 ms直接相减来估计计算时间，因为采集方式和重叠口径不同。这一维度波动明显，正式通信目标试验必须先增加标定采样、评估 profiling 扰动，再固定判胜规则。

Qwen 和 ResNet 的实际 trace 均有 CUDA kernel，NCCL kernel 计数为0。此结果证明单卡案例不依赖分布式通信；未来框架的“自动判定并关闭通信采集”仍属于待实现功能。

## 3 从基线走向框架验收

每个目标的正式输入应从干净的项目请求开始：执行入口、允许的资产定位、当前 workload、目标／约束、质量标准和预算。框架必须自行产出适配、评测／采集、执行关系、动态分组、搜索范围、优化候选、回装和归因；不能仅证明三个脚本能跑，或为三个模型各手写一组替换逻辑。优化范围包含单组、多组联合、计算区域和执行计划，最终按完整项目判断效果。

每个项目验收以下完整过程：

1. **独立评测生成。** 真实 Project/Eval Agent 只看允许的项目输入，生成 evaluator。与本任务包的独立参考核对计时边界、模型状态、质量门槛、有效 batch、输入范围与输出完成条件。既有手写基线不能冒充此步骤已经自动完成。
2. **发现与选择。** 保存实际 trace、module／functional 调用、状态和执行依赖、候选区域及合法性依据；没有人工 targets 文件或模型名映射。单组与联合机会均依据目标相关测量和真实试探，分组可随改写更新。
3. **真实优化与回装。** 局部任务复用原单算子内循环，其他范围走适配生成器；所有路径使用真实 provider 请求、候选和 GPU 执行。制品带 scope、父版本、执行计划／组版本、契约、读写闭包及 rank 协议，整个变更集合原子安装后验证。
4. **质量先于性能。** 失败输入、阶段、rank、状态、误差和参考进入反馈。训练检查梯度、参数更新与连续步骤，推理检查输出及缓存生命周期；局部非法的子编辑只暂存，完整候选闭合后才能执行。
5. **目标判定与归因。** 保存 clean 项目指标、局部／联合／计划指标和独立资源观察。接受依据是完整候选的目标与约束，约束继续锚定原始基线；不能累加多组收益或将共享通信按比例分摊。
6. **下一轮反馈。** 至少两轮真实请求，审计组／联合／计划 Agent 消费相应范围的反馈，包括负收益、交互、边界变化、缺测和通信。接受后重选或重分组，保存“证据→反馈→后续决策→结果”的链路。

### 3.1 如何验证目标驱动，而不是恰好加速

对 Q1/Q2、R2/R3、D1/D2 分别使用相同初始代码、输入、精度、质量约束和优化预算运行。冻结每次生成的候选，进行跨目标交叉评测，形成“目标 × 候选”的实测矩阵。只有符合各自约束的候选才进入该目标比较。

切换目标不要求一定换组或一定产生不同赢家。多个目标可能有共同瓶颈。要求的是选择理由能够由目标相关测量支持、替代选项经过合法比较、相同选择有解释，并且没有按目标名称硬编码结果。若框架总是选择相同组，也不立即判失败；先用交叉评测判断这是实际最优的近似，还是评价／资源反馈没有真正进入决策。

设置等预算对照：局部耗时选组 vs 目标试探选组；只有项目总分反馈 vs 加入分组／联合／通信反馈；可选通信观测关闭 vs 开启；固定分组、逐组接受 vs 允许联合／区域／执行计划的有界搜索。每条路径使用相同合法起点、质量门槛和总预算，计入重分组、分支及组合测量成本，报告全部目标与失败。正式性能比较用配对 AB/BA 和独立复核，采样／停止规则在看候选结果前固定。

### 3.2 怎样将验证失败用于下一轮框架开发

| 观察到的问题 | 反馈内容和处理位置 | 下一轮复核 |
|---|---|---|
| 无法理解新项目，或必须手写组名 | 入口、实际调用、无法适配的接口；修正通用 ProjectAdapter／项目理解提示 | 换项目名称、入口位置和负载后重跑；核心代码无模型特例 |
| 选中局部热点但项目目标不敏感 | 目标边界、调用频率、关键等待、试探结果 | 重做 shortlist 或改变预算；同一候选跨目标复测 |
| 微基准加速，回装后变慢 | 调用、copy／cast、布局、launch、状态／缓存及同步差异 | 从真实模型内测量修正组 fixture 和边界，而不是隐藏端到端退化 |
| 通信指标下降但整步退化 | logical bytes、次数、逐 rank kernel 时间、overlap、clean step 和环境能力 | 检查 D2 的非退化约束，拒绝越界候选并把证据送给组 Agent |
| 梯度／参数／token 错误 | 最早可定位的输入、阶段、rank、状态和误差 | 修正候选或自动 evaluator；质量失败不得进入性能候选排序 |
| 不同环境无法提供某维度 | unsupported／permission_denied／not_applicable 状态及替代来源 | 切换采集器或降级；不补零、不捏造带宽 |
| 目标切换始终无影响且交叉评测显示更好选择 | 请求中的目标与资源字段、候选评分、预算和控制流 | 修复目标传递或反馈消费；在三个项目上回归，不给单个模型加 if 分支 |
| 单项无收益或无法独立执行，联合机会被过早排除 | 编辑闭包、外部边界、探索分支和拒绝原因 | 区分未闭合子编辑与完整候选；验证联合搜索不要求单项先获益 |
| 多组各自有效，组合后退化或冲突 | 同一父版本上的子项／组合实测，接口、共享状态和调度差异 | 整体拒绝或重做联合任务；不将单组收益相加 |
| 改写后仍引用旧分组和旧 profile | 执行计划／组版本、调用对应、证据依赖 | 验证失效传播和重新采集，检查后续 Agent 没有收到过期结论 |

已有 Qwen TP2 和 greedy-head 通信原型保留为额外的分布式推理／负收益回归案例，不替代第三个独立项目。此前 TP2 对单卡参考的等价检查失败，需要先定位或显式采用 TP-relative 契约；不能带着未解决的质量问题进入“优化成功”矩阵。历史 greedy-head 逻辑通信量下降但整体变慢，适合检验拒绝与反馈链路，但手工历史候选不计作新框架自动生成成功。

### 3.3 多组与整个计算流程的验收

在原有三项目和八个目标上增加搜索范围这一维度，不把它当成新目标。保持 workload、输出／质量要求和计时边界固定，分别评价单组策略与完整项目策略。以下候选机会只是观察方向，不能预先指定必选组、融合点或成功收益；真正的作用范围由 Agent 和运行证据确定。

| 项目 | 多组与整流程检查重点 | 必须保存的项目证据 |
|---|---|---|
| ResNet | 多组共存；生产者／消费者边界、布局与中间物化、缓冲区生命周期等联合机会 | 完整 logits／top-1；外部输入布局保持契约；新增转换和复制计入原边界；区域覆盖及 allocated 峰值 |
| Qwen | 多组改动在 prefill／decode 场景中的组合；缓存、布局和执行策略跨阶段影响 | 完整生成序列与 teacher-forced logits；TTFT／decode／总耗时分列；缓存构建、消费、reset 与后续请求状态 |
| GPT-2 DDP | 多计算组与共享通信区域；梯度 bucket、就绪／消费、通信组织和重叠的合法联合变化 | 全 rank 候选／协议一致；完整梯度和更新；同一有效 batch；实际 collective／stream 证据及 clean step |

验收分为两层。每个项目须在同一隔离测试版本中同时执行至少两个组的自动候选，并检查组合覆盖、质量、项目评价与恢复；是否接受进入主版本仍由收益和约束决定。在三项目集合中，至少再完成一个需要联合修改边界的自动候选、一个执行计划候选、一次动态分组更新，并在 DDP 中验证跨 rank 原子安装和故障回收。联合边界与执行计划可以由同一候选覆盖，但须分别展示实际变化，不能只改变标签或重复测同一实现。

具体检查如下：

1. **联合合法性与探索。** 对完整候选列出子编辑及外部接口。只有子项自身合法时才运行单项对照；否则记录不能独立执行的原因，验证完整候选能绕过“子项必须先接受”的错误门槛。至少保留一次因边界变化需要联合修改的真实运行。质量合格但暂不获益的分支可以继续受限搜索，预算和退出原因可追溯。
2. **组合与交互。** 子项可拆分时，用相同父版本测原始、A、B、A+B，报告实测组合和不确定性；不可拆分时只报告合法整体结果，不构造虚假的单项收益。候选互相抵消、退化或不满足原始约束时，拒绝提交并将具体证据送入下一轮请求。
3. **动态边界。** 记录至少一次合并／拆分／区域重定界的提案、合法性检查和新组版本，证明调用可追溯、受影响 fixture／profile 失效并重新获取。旧候选的名称相同不能绕过父版本和边界检查。
4. **连续状态。** 新增状态专项检查，不替换已有基线证据。Qwen 检查完整 decode 缓存链、至少两个连续请求及请求间 reset；DDP 在不每步恢复初始权重的情况下，至少连续两步使用明确的不同输入，与同一全局 batch 序列的串行参考比较梯度、参数及存在的优化器状态；缓冲区复用检查跨调用污染。性能比较仍使用双方一致的既定 workload。
5. **事务与故障。** 注入部分编辑安装失败、旧父版本返回、提交记录写入前退出和一个 rank 未就绪／退出，验证没有半安装的接受版本，整个 worker 作业可回收。恢复父版本后重跑质量和受噪声约束的性能检查；已提交事务恢复不重复发布。再检查已接受版本在后续验证失败时的祖先回退、联合 bundle 整体撤销及后代失效，不能仅删除一个组映射。
6. **计时与范围。** 固定外部输入、完成条件、初始化／稳态口径和摊销次数。布局转换、物化、同步或缓存构建不能被候选移出原计时边界。D2 的通信改善必须同时满足相对于原始基线的整步约束；变化后的 rank 时间和共同通信继续按正确粒度统计。
7. **反馈闭环。** 保存联合候选 ID、影响组／调用、执行计划差异、共享资源、单项是否可测、整体结果和下一轮请求。检查相关 Agent 收到共同边界信息，协调器据此改变范围、重选、回退或停止；不可细分的收益不得分配为每组独立功劳。

预先构造的错误候选和故障注入用于验证协议控制，不计作自动发现或生成成功。可合法组合但没有收益时，可以完成安装／覆盖／质量这一层功能验证，性能结论必须保留为无改善或退化；若始终没有真实联合边界或执行计划候选运行，则对应功能验收仍未完成，不能用缺口说明替代通过。

每轮新增回执至少包含原始基线／父版本、scope、组注册表与执行计划前后版本、编辑影响闭包、bundle 哈希、安装／提交／终止记录、实际调用覆盖、质量与配对样本、约束判定、证据失效清单、预算和后续 Agent 请求引用。当前的 `result.json` 是就绪基线，尚不包含或证明这些未来工作流字段；不得向旧结果补填为已执行。

## 4 与实施阶段的衔接和交付状态

以下阶段安排和“就绪基线”描述是实施前的任务包记录。当前实现、逐阶段回执和未完成项以 [v6 执行记录](v6-execution.md) 为准；不能将本节原先的准备状态理解为当前代码仍全部未实现。

- **P0：已补齐本任务包的三项目真实就绪基线。** 正式旧行为回归、框架 worker 设备使用权和完整 Agent 成本记账仍按主计划完成。
- **P1：先定义多范围与事务基础。** 确定执行计划、动态组版本、完整候选及原子安装／回退，使用真实控制任务验证；不等到最终多项目验收才补这些接口。
- **P2–P4：先 ResNet，再 Qwen。** P2 生成支持边界和连续状态检查的 evaluator；P3 贯通最小联合候选、分组更新和有界分支；P4 接通旧资源响应、执行计划候选和项目反馈。转入 Qwen 前冻结核心版本并记录哈希，审计新增任务是否需要改核心。八个目标配置不等于八次优化已执行。
- **P5：用 GPT-2 DDP 接入真实通信目标。** 从已通过质量检查的 `no_sync` 基线开始，完成跨 rank 联合事务、通信与执行计划、动态缺测、连续训练质量及整步反馈；Qwen TP2 作为后续扩展。
- **P6：完成三项目多组／整流程矩阵、目标切换、等预算对照和保留 workload 复核。** 审计组合归因、负收益及故障恢复；新增案例不能靠修改核心里的模型名分支。三种结构覆盖仍不等于对任意项目证明泛化。

当前已完成：任务与目标定义、资产准备、真实基线、基础正确性／负控制、原始 CUDA／NCCL 诊断和回执。尚未完成：自动项目理解与动态分组选组、Agent 生成 evaluator／候选、多组／执行计划搜索、事务回装及联合反馈、正式优化收益和泛化验收。本次补充设计没有改变已有实测结果，也没有将新增验收标成已通过。
