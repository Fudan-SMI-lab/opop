## P7 · `analyst→假设` 的断点,而 prompt 文字是 v3 时代的

### 问题

rewriter 的 prompt(`modules.py:1275`)要求每个改写针对 **bottleneck report 里的某条假设**
(`hypothesis_id` 必填),而那份 report 是 **analyst** 写的。所以:

> **简报只能经 analyst 写进假设,才能真正引导改写。**

复验发现简报**已经**进了 analyst 的 `digest_text`(`orchestrator.py:2049`)⇒ **不是缺路径**。
真正的断点是:analyst 的 prompt 里关于简报只说了它是"shared memory 挡住哪个参数",
**从未说明方向(inward / outward)该怎么用** —— 这段文字写于 v3 时代,**早于方向 token 存在**。

实测(窗口 1 P1):`NUM_STAGES` / `inward` 这道墙**没有任何一条假设指向它**。

### 我们设想的修法

改 analyst 的 prompt(`modules.py:1059-1088` 一带),让它:
1. 知道 `inward` 与 `outward` 的 v4.1 语义(不是 v3 的"被挡住");
2. 对每道**过门**的墙,必须产出至少一条假设并写明方向;
3. **未过门 / unresolved 的墙不得产出假设**(否则它会凑数)。

### 我们已识别的风险 —— 这条是全部 15 条里最高的

| 风险 | 说明 |
|---|---|
| **analyst prompt 是 C1 与 C2 共用的入口** | 改它会同时改变 C1 的资源解释行为 ⇒ **两条 contribution 的证据同时失去可比性** |
| **可能强化"基线已能做"这个威胁** | 控制臂 analyst 已有 17% 的假设自带 C2 形状。把方向教给共用的 prompt,可能让 **off 臂也变强**,从而抹掉臂差 ⇒ **修引导端反而可能让 C2 更难证明** |
| 缓解本身带副作用 | 只在 `mode=active` 注入方向说明 ⇒ 两臂 prompt 长度不同,须在臂对等检查里声明为已知差异 |

**这是我们最想听你意见的一条。**

# 第二梯队:C2 的机制上限(P2 / P4)

这两条不是 bug,是**当前设计的天花板**。

## P2 · 斜率进不了采样器的决策,只能塞一个点

### 问题

`tuning/tpe.py:160` `enqueue()` 与 `:191` `enqueue_fresh()` 是 C2 对采样器的**唯一**接口 ——
往 Optuna 队列里塞一个具体配置。

**TPE 本身没有任何位置能挂斜率**:它只做"高性能优先",不表达方向,也没有"未知方向的方差项"
可挂。所以 C2 对采样的影响力上限就是"塞几个点"。

能塞几个由剂量决定:`f=0.125 ⇒ Q=5`,其中 **C4 源块占 4 个,E 动作只剩 1 个**。

### 实测

| 项 | m1-b | m2b-b |
|---|---|---|
| E 准入 | 2 | 2 |
| E 决策(20/21 个空间快照求和) | 79 | 79 |
| **同层竞争 ≥2** | **0** | **0** |
| RR vs gain 判决不同 | 0 | 0 |

**同层竞争恒为 0** ⇒ 一个空间最多 1 个 E 对比,**结构上不可能**产生"哪个方向更值得"的排序。
这不是负结果,是剂量的结构后果。

### 三条路,都有代价

| 路 | 做法 | 代价 |
|---|---|---|
| **A. 提高剂量** | f ≥ 0.225 ⇒ Q ≥ 9,可容纳 ≥2 个 E 对比 | **撞 B=40 红线** —— 22.5% 的 trial 变扫描槽 |
| **B. 把斜率接进采样器** | 让条件化斜率影响 TPE 的候选生成而非只塞点 | 我们的调研结论是 TPE 表达不了斜率;换采样器则整个 B 循环历史不可比 |
| **C. 降低 C4 槽位消耗** | C4 现吃 4 槽(发现对 2 + 验证对 2),若两对共享端点可降到 3 | **会破坏 P2′ 的留出独立性** —— 那正是唯一可守的地方,我们认为不可动 |

**我们的倾向:暂时不动,在论文里把"排序价值不可辨识"写成剂量的已知限制**,而不是待修缺陷。
理由:C 直接损害唯一的正结果;A 撞红线;B 让全部历史不可比,而 P2′ 的四个 run 复现是目前最贵
的资产。

**请评估这个取舍。** 特别是:有没有第四条路我们没想到?

## P4 · C2 只覆盖 8 个资源维度里的 1 个

### 问题

八个资源维度(`shared_bytes`、`n_regs`、`n_spills`、`occupancy`、`peak_alloc_bytes`、

`n_spills` 有第二种判据(软墙),且**每个 trial 都测到**。但 v4.1 的 compile-only 探针在

### 实测

| 项 | m1-b | m2b-b |
|---|---|---|
| 条件化墙 | `{'hard': 20}` | `{'hard': 13}` |
| **软墙** | **0** | **0** |

`soft=0` 是**结构性**的,不是运气 —— A1 的输出自己就这么标注。

软墙另有独立缺陷:它**恒指高侧**,所以已记录的 24 道软墙里 **11 道(45.8%)**因最优点已在域顶
而**无值可投**。读"零投递"时必须分 `no_wall` 与 `no_value` 两个计数器。

### 我们设想的修法

1. 让探针编译后读 cubin 的 regs/spills(硬墙路径已经这么做 —— `orchestrator.py:1885` 的

2. 软墙适用门是"最优 trial 自己要 spill",实测 79 个空间只有 30 个(38.0%)满足
   ⇒ **预算不能按空间数线性外推**;
3. 投递前分流 `no_wall` / `no_value`。

### 我们已识别的风险

### 问题

`_rewrite_round`(`orchestrator.py:2871`)每轮**遍历全部活跃族**,每族每轮消耗一次
`rewrite_rounds_used`。所以第 1 轮 = 4 个族各得第 **1 代**;第 2 代要等第 2 轮。而族边界的
墙钟检查(`:2892`)在第 2 轮的第 1–2 个族处就 `break`。

**6/6 个 run 一致**(窗口 1 四个:round1 完成 3/3/3/3、round2 完成 1/1/1/0;窗口 2 的
m1/m2b:8/8 个族各只有 1 条 `FAMILY_ROUND_RECORDED`)。

三个连带的判读陷阱:
1. `FAMILY_ROUND_RECORDED.round=2` 是**轮次位次不是血缘深度** —— 所有改写的父代都是种子(g1);
2. `latency_gain_pct` 是**相对种子的累计增益**,不是逐轮增量;
3. 每族只有 1 条记录 ⇒ **一个点,不是曲线**。

⇒ **"收敛速度更快"这个主张在当前配置下根本无法测量。**

成本结构(实测):GPU 只占 elapsed 的 **30–34%**,**66–70% 是 agent 调用**;
每族-轮约 **1.48h**;种子阶段占一个 12h run 的约 **54%**。

### 修法(已定为下一轮)

减族换深度:`max_seed_candidates: 2` / `max_families_active: 2` / **Loop D 关**。
用户已接受 (a) 放弃 Loop D 与 (b) 最终延迟可能更差。

⚠ `config.py` 的注释明确写着 `max_families_active: 3` 的**设计意图是相反的**:
"more families reach a first round before the clock stops, each getting fewer rounds"。
所以这是一次**有意的设计意图反转**,不是修 bug。

### 我们已识别的风险

| 风险 | 说明 |
|---|---|
| **最终延迟大概率更差** | 族数减半 ⇒ 结构多样性减半。已记录:L3:21 的赢家族种子是四个里**最差**的(20.4ms 垫底,最终 6.92ms)⇒ 任何减族/早停都会先杀掉它 |
| Loop D 证据归零 | D 刚刚才首次跑通 |
| 仍可能只有 1 代 | 2 族 × 1.48h/族-轮,若 agent 调用变慢仍可能排不到第 3 轮 |

**请评估:减族是不是拿到轮次深度的最佳手段?** 我们能想到的替代是加墙钟(翻倍 GPU 时间)或减
`trials_per_space`(**撞 B 红线,不可**)。有没有第四种?

## P5 · A1-3 / A1-5 无合格 tie 带

### 问题

我们的读数器 `a1_pair_comparability.py --final` 现在**故意拒绝给判决**,因为没有合格的同代码
A/A 标定。四把候选尺子每把都坏:

| 尺子 | 值 | 问题 |
|---|---|---|
| 原 13 对"A/A" | median 1.03% / p90 2.50% / max 5.33% | **0/13 跑了同代码** —— 配对键只固定种子 sha + 旋钮,而 parameterizer 是 **LLM 调用** ⇒ 两臂程序差 2–22 行。且**注册 sha 与空间 sha 都相同** ⇒ 按 sha 配对**结构上看不见**这个差异。另有 4 对两侧都带 reuse 标记,最大的 5.33% 与第二大的 2.69% 都来自这些对。**是混合量,不是噪声上界** |

### 三个选项

| 选项 | 内容 | 后果 |
|---|---|---|
| **A** | 沿用 4% 作**历史描述**,5.33% 作事后敏感性对照 | 两者**同判决**(投递点 4 输 2 平)⇒ 可以说"结论对阈值不敏感"。但 4% 的正当性仍待补 |
| **B** | 专门做一次同代码 A/A 标定:固定 artifact + 固定上下文重放 N 次 | 需 GPU(估 2–4h),换来第一把**合格**尺子。现有日志不足以完成该校准 |
| **C** | 永久以描述性方式报告差值,不设 tie 带 | 最保守,但审稿人会问"5.12% 算不算显著" |

| 风险 | 说明 |

**请特别评估:先定尺子再看数,在我们已经知道 +5.12% / +14.48% 的情况下还成立吗?**
我们担心这已经构成事后选择,想听你怎么处理。

## P6 · 收敛速度指标未预注册

### 问题

即便 P3 拿到第 2 代,`latency_gain_pct` **也不能直接用**:
- 它是**相对种子的累计值**,不是逐轮增量;
- 它与**起点强相关**:7.0635ms 起步降 53.83% vs 3.0003ms 起步降 1.76%
  ⇒ 跨族比较测的是**种子质量差异**,不是改写效率。

### 我们设想的指标

```
剩余距离比:  ratio_k = (best_k − best_final) / (best_seed − best_final)
```

`ratio_k` 从 1 单调降到 0,与起点无关。收敛速度 = 达到某 `ratio` 阈值所需的轮次或 GPU 墙钟。

⚠ 它测的是 **H2c(rewriter 的结构收益)**,**不是 C2 的预测精度**。两者不可混谈。

### 我们已识别的风险

| 风险 | 说明 |
|---|---|
| `best_final` 是**事后**量 | 分母用最终值 ⇒ 只能 post-run 计算,不能在线判读(可接受,但要写明) |
| **两臂 `best_final` 不同** | 分母不同 ⇒ 严格说两臂的 `ratio_k` 不在同一尺度。可能需用两臂**共同**最优作分母,或报告两种算法 |

**请评估这个指标,并指出更合适的替代(如果有)。** 它必须在下一轮 run 启动**之前**定下来。
