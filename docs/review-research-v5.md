# v5 方案审阅:问题清单与修订要求

> 日期:2026-09-15。评审对象:`docs/research-v5-unified-objective-framework.md`。
> 评审依据:**窗口 1 四个 12h run 的实测读数**(`docs/window1-results.md`,commit 12e925c)
> 与当前 checkout 的源码核查。**本文不否定 v5 的方法学方向**——它对单位、方向、
> 不确定性与约束的纪律是这一系列材料里最严的一份。本文只列必须修订的部分。

## 0. 一句话结论

**v5 的方法学纪律基本正确且应当保留,但它的能力快照停在窗口 1 之前,
导致它把两个已有答案的问题重新列为待检验假设,并把一项实施必需工作误记为"证据限制"。
在修订这三处之前,v5 不应进入实施。**

## 1. 必须修订(五条,按影响排序)

### 1.1 §2 的能力快照已过时,H2 的两半已被分别回答

**v5 现状**:§1 说能力描述"仅继承前序只读审计的两个快照:`7fc8a18` 与 `ff402aa`",
并自认"本文没有重新核验当前 HEAD"。§12 的 **H2** 写作:

> 固定搭档响应比混合搭档的边际历史更可靠,**并能在普通坐标测量之外改善方向判断
> 及后续结构改写**。

**实测已把这句话劈成两半,方向相反:**

| H2 的分句 | 窗口 1 实测 | 状态 |
|---|---|---|
| "比混合搭档的边际历史更可靠" | 条件化中位 \|误差\| **0.0039 vs 边际 0.1963**(l3:43,n=12,**50 倍**);**0.0031 vs 0.0802**(l3:21,n=11,**26 倍**);符号一致 **12/12 与 10/11** vs 边际 5/12 与 7/11 | **已确证**,两个独立 run、两个任务 |
| "并能…改善方向判断及后续结构改写" | 六个投递点终局 **0 赢 / 4 输 / 2 平**(败幅 5.4–8.8%,双侧 n≥2 真被测量) | **已否证** |

且边际的失败形状是**符号反转**而非量级偏差(最极端:`c4-aa93b3b0` COMPUTE_DTYPE
真值 −0.7362,边际读 **+0.5136**)⇒ 按边际行动会往相反方向投递。

**要求修订**:
1. H2 必须拆成 **H2a(测量可靠性)** 与 **H2b(行动收益)**。H2a 已有 n=23 的双任务证据,
   v5 若再列为"待检验",会花预算重新验证已知结论。H2b 已有反向证据,
   实施设计应针对"为什么测得准却投不对",而不是再测一次"是否投得对"。
2. §11 的 C2 证据义务栏写着"响应可校准,超越边际历史及普通坐标搜索,**收益覆盖成本**"。
   第三个分句在行动层**已知未满足**。保守措辞必须落到:
   **"更早、更可靠、定量更准"可主张;"因此投递的取值更好"不可主张。**
3. §1 那句"后续 v5 规划应刷新差距判断"要执行,不是备注:窗口 1 的读数是必读输入。

### 1.2 §6.1 说对了方向,但低估了严重程度——4% 的 τ 对延迟本身就已太小

**v5 现状**:§6.1 正确指出「旧 4% 门与每端两次 fresh trial 不能直接移植到内存、吞吐、
成功率或完整生成」,并正确指出「两次外层重复中各约 20 次内部 timing,不是足够的独立请求」。

**源码核对**:`src/kernel_optimizer/conditional/gates.py:34` — `BASE_TAU = 0.04`,
全局预注册常量;`τ = max(4%, ρ_F, ρ_N)`。简报正文自陈 "2 fresh trials/end, ~20 timings/trial"。

**但实测把这条推得更远**:N1 A/A 对(两臂 **125 个配置键逐位相同**、
读**同一个**冻结种子集、四个 `source_sha` 已逐位核对全同)测出:

- 逐候选配对噪声底 = **10.85%**(四个种子:0.51% / 1.41% / 4.97% / 10.85%,中位 3.19%)
- 端到端差 **−11.72%**

⇒ **τ = 4% 对延迟这个原生目标已经比真实配对噪声底小 2.7 倍。**
问题不是"4% 是延迟专用、不能移植",而是**"4% 从一开始就不是任何目标的合法阈值,
它是一个未经噪声标定的猜测"**。

**同时要如实记一条对 v5 有利的发现**:§6.1 担心的"负值不能进入旧的正值 log 门"
在实现上**已经是安全失败**,不是静默腐化——`gates.py:41-49` 的 `rho()` 对
`len<2` 或任何 `x<=0` 返回 `None`(UNKNOWN,不是 0),`gates.py:101-104` 对
非正复现值直接返回 `quality_ok=False` 且不出门。**所以 `J=−throughput` 的后果是
"拒绝出门",不是"算出错数"。** v5 应把这句从"风险"改成"已有的正确降级行为,
新目标要保持这个性质"。

**要求修订**:§6.1 把阈值来源从"目标特定"升级为"**每个目标 + 每个场地都必须由
配对 A/A pilot 标定,4% 不作为任何目标的缺省下限**";并明确 v5 的新阈值方案
必须复用 `rho()` 的 UNKNOWN 语义(缺复现 ⇒ 不出门,不补 epsilon)。

### 1.3 §5 把探针层拿不到的东西列成了"证据限制",实际是实施必做项

**v5 现状**:§5 的三类边界表把「**经验转折**:给定程序和搭档下的 spill、物化或访存行为
在哪里变化」列为 C1 的第三类边界。§2 则把这条记作"证据限制"("软墙缺数据时标未知")。

**实测**:两个 active pilot 的**软墙都是 0**,且这是**结构性的**——
compile-only 探针在 warmup 编译期读不到 `n_spills`(硬墙可用,软墙只能从真实 trial 读)。
硬墙则很健康:l3:43 **31 道 / 12 个已探空间(共 19)**,l3:21 **12 道 / 11 of 17**。

**这条对 v5 的后果比对 v4 更重**:v5 要把目标扩到内存,而 `peak_alloc_bytes` 与
`peak_reserved_bytes` 同样**只在真实 trial 的 profile 里**,探针不跑就没有。
⇒ 若 C1 要为内存目标提供"经验转折",**探针层必须先能拿到这些量**,
否则 C1 对内存的三类边界表里第三类恒为空,而 v5 §5 的收益论证依赖它。

**要求修订**:把这条从 §2 的"证据限制"移到 §8 的工作包,写明:
**"目标扩展到资源型指标时,探针层必须先具备该指标的采集能力;
compile-only 探针的能力边界要按指标逐项声明,不能假定沿用延迟探针的覆盖面。"**

### 1.4 §12.1 的二因子设计按当前实现不可执行,而 v5 把它列为首选

**v5 现状**:§12.1 首选 `C1 on/off × C2 on/off` 二因子;末尾给了退路
「若没有 C1 就无法定义 C2 域,改用嵌套三臂」。

**源码核对**:C4 的**轴域来自探针发现的墙**——没有 C1 的资源解释就没有 C2 的扫描轴。
而现有开关是单一的 `v4.conditional_scan.mode ∈ {off, observe, active}`
(`config.py` 的 `V4ConditionalScanConfig`,缺省 `off`),`mode=off` **同时**关掉
C1 的条件化解释与 C2 的响应测量 ⇒ **这是嵌套,不是因子**。
另有 `config.py:787` 的互斥约束:`mode=active` 与 `v3.slope_guide.enabled=true` 不可同开。

**所以 v5 的退路才是唯一可行路径。** 把二因子写成首选,实施时会先撞一次墙、
再回退到嵌套——纯浪费。

**要求修订**:§12.1 的首选与退路对调,并注明理由(轴域依赖 C1 ⇒ 因子不可分)。
同时 §12.1 说"C1 off 保留相同原始资源信息"——要写清这在实现上意味着什么:
`mode=off` 仍然journal资源向量(`DIMENSION_STATE` 无条件写盘),
但**不进 prompt**;这正是需要的"共有底座",应明确引用而不是重新设计。

### 1.5 §13 的八张面板远超可用预算,且 v5 没给最小集合

**v5 现状**:§13 列出 U / M / P / A / G / L / W / X 八张面板;§15 说
"不是把本文所有可选实验全部变成必做",但**没有给出优先序或最小集合**。

**实测代价基准**(窗口 1,四个 run):

| 量 | 实测 |
|---|---|
| 一个 12h run 的墙钟 | 12.24 – 12.97h(超时量 +0.24 … +0.97h) |
| 一个 12h run 的 **GPU 墙钟** | 3.86 – 4.16h(其余是 agent 与编译) |
| 一个 run 产出 | **一个场地、一个臂** |
| 可用硬件 | 两台 × 2 张 4090(24GB);**三张可用卡全是 4090,A800 拒连** |

⇒ **一个窗口 = 两台机器并行 = 最多 4 个臂**。按此换算:

- **M 面板**二因子 4 臂 = 1 个窗口(若改嵌套三臂 = 3 臂,仍 1 个窗口)
- **X 面板**"留出任务 × 后端 × 指标"要在 M 之上再乘一遍 ⇒ 至少 2–3 个窗口
- **L 面板**(Qwen3-8B 完整生成):bf16 8B ≈ 16GB 权重 + KV,**单卡 24GB 装得下但没有余量**;
  §13.3 要求"大模型加载与初始化单列,**计入搜索总成本**"⇒ 按窗口 1 的
  GPU 墙钟只占 32% 的结构,**加载可能吃掉一个臂相当大的比例**。
  另:box4 的 HF cache 为空,权重需先下载。
- **W 面板**(SDXL 完整出图)同理。

**要求修订**:§13 增加一栏"**优先级**",并给出明确的最小集合。建议的最小集合是
**U → P → M(嵌套三臂)**,理由:
- **U 面板 0 GPU**(合成/小任务的单位与方向检查),且它是其余一切的前置;
- **P 面板可在既有数据上离线做**(见下 §2.1),几乎 0 GPU;
- **M 面板**是唯一必须烧 GPU 的机制识别,且嵌套三臂 1 个窗口可完成。

G / L / W / X 应明确标为"**取决于 M 的结果**":若 M 显示 C1/C2 的增量为 0,
这四张面板的收益前提就不成立,应先改设计。

## 2. v5 不知道、但现在就能用的两项资产

### 2.1 §12.2 的"离线重评分基线"**今天就能跑,0 GPU**

**v5 现状**:§12.2 说"旧原始指标完整时,固定候选库的离线重评分是很强、很便宜的基线,
应先做而非故意略过"。这句完全正确,但 v5 把它写成了未来工作。

**实际上数据已经在盘上了。** 窗口 1 四个 run 共 **3,000 条 `TRIAL_DONE`**,
每条的 `trial.profile` 已带:

```
candidate_aten_bytes, candidate_aten_ops, peak_alloc_bytes, peak_reserved_bytes,
peak_above_resident_bytes, occupancy{occupancy, active_warps, blocks_per_sm, limiter,
by_regs, by_shared, by_warps}, threads_launched, n_regs, n_spills, shared_bytes,
sass{tensor_core, spill_store, global_load, ...}, compile_s, wall_ms,
cpu_issue_ms, overhead_gpu_ms
```

⇒ **"如果目标换成最小 peak memory,这四个 run 里谁会赢?与延迟赢家是同一个吗?"
这个问题现在就能回答,零 GPU。** 而它同时检验 v5 §10.2 推演的核心假设:
**目标切换会不会改变冠军**。

- 若**不会改变**:§13 的 G / W 面板价值大幅下降,应缩减;
- 若**会改变**:那是 v5 最强的一张图,而且**用已有数据就能画出来**。

**要求修订**:§12.2 与 §13 的 G 面板改写为"**已有数据的离线重评分先行,
且它是 v5 的第一项可交付**",并注明可用字段清单。

### 2.2 v5 §12.3 要求的两条纪律,现有实现**已经满足**——不要"修"它

**v5 §12.3**:「边际预测与条件预测使用同一历史截止时刻和相同发现/留出分离,
边际法不能偷看未来数据」+「保留 P2′ 的主要 legacy 分母和规则,
**不能只筛通过方向门的子集再评估校准**」。

**这两条现有实现都已做到**(`scripts/probes/v41_p2prime.py`):
- 边际预测用「该 C4 关闭**前**已有的 trial」重算(`prefix_at[c.scan_id]` 在追加该 contrast **之前**快照);
- 分母是**全部 fresh-complete C4**,包含 `unresolved`(未铸币)的那些;
- 三种拒绝原因分开计(`no_slope_at_cutoff` / `values_unsampled_at_cutoff` /
  `thin_bucket_at_cutoff`),不混进"边际误差"。

**要求**:v5 应**引用**这套实现作为既有正确基线,而不是重新设计校准协议。
新目标要另做按 pilot 标定的响应实验(v5 自己也这么说),
但**不得覆盖或重新解释旧 P2′**。

## 3. 实施时序:建议在全部实验结束后

三条理由,按强度排序。

**① prompt 与评分链是 M1 两臂的共享部分。**
v5 §8 的工作包"评价适配"与"比较与报告"要改的正是 `robust_ms` 评分链
(**53 处引用、11 个文件**;`latency_ms` 108 处、18 / 70 个文件)与 analyst/rewriter
的输入语义。M1 的自变量只有 `conditional_scan.mode` **一个键**
(两臂 125 个配置键逐位相同,已核对)。**任何改动共享部分都会让 M1 与窗口 1 不可比。**
这不是保守——step-4 的教训是两臂交付都是 0、自变量形同虚设,24 GPU·h 白跑。

**② M1 会直接回答 v5 §5 / §7 两个工作包的收益前提。**
新增的第五档(改写是否**测量上**解开了那道墙)在 pilot-p1 上是
**被简报父代 4 个改写解开 3 个**(拒绝率 24%→8%,best −17.0%,**赢家就在其中**),
但 **off 臂也解开 4/8**,而且两个 active pilot **方向相反**(p1 解 3/4 vs p2 解 0/4)。
⇒ **这一档的臂差只有 M1(同机同任务)能测。** 若臂差为 0,
v5 §5「C1 资源解释」与 §7「C1/C2 如何进入结构搜索」的收益前提不成立,应先改设计。

**③ 但 §2.1 的离线重评分现在就该做,零成本零风险**——它不碰运行中的任何代码。

**建议顺序**:

| 阶段 | 内容 | GPU |
|---|---|---|
| 现在 | 窗口 2:M1(box4)∥ M2b(box1) | 2 × 12h,并行 |
| 现在(并行) | v5 §12.2 离线重评分:四个 run × 3,000 trial 的内存/占用维度交叉选优 | **0** |
| 窗口 2 后 | A1 分析 + §11 重议 + 论文表格 | 0 |
| A1 后 | v5 §8 的**前两个**工作包(目标表达、评价适配)——只做协议与单元层,**不动 prompt** | 0 |
| 论文投出后 | §13 的 M / P / A 面板;G / L / W / X 视 M1 结果再定 | 需重新预算 |

## 4. 不需要修订的部分(明确保留,避免外部 agent 改坏)
