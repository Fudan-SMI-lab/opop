## Qwen：数值差异与绑定开销是两项独立问题

原第三轮候选 `trial-recovered-19ccfe875f` 替换了 prefill 的 145 个 RMSNorm 站点。
在其第一次活跃 gate 内增加旁路表达式比较，保持原返回值、gate、容差和回退逻辑，
完整模型仍复现原来的 `4.09375` 最大误差和 `1,884,096 / 4,861,952` 个 logits 超差。
该诊断包含额外 GPU 算术与同步，耗时不作性能证据。

第一个调用是 `model.model.layers.0.input_layernorm`。同输入下：

| 算术路径 | 与该站点父实现不相等的元素 | 最大绝对差 |
|---|---:|---:|
| 原加权融合 RMSNorm | 171,331 / 655,360 | 0.0078125 |
| 按源代码分解的表达式 | 0 | 0 |
| 先 FP32 乘权重、再转 BF16 | 171,331 / 655,360 | 0.0078125 |
| 无权重融合 RMSNorm 的 BF16 输出，再乘 BF16 权重 | 0 | 0 |

在这个首站点，原融合结果与“先乘权重再舍入”逐位一致，直接隔离出了舍入位置差异。
145 个当前候选输入上的旁路比较中，源表达式全部逐位一致；无权重融合后再乘权重仅
133 个站点逐位一致，其余 12 个站点共 192 个元素不同。不能把首站点结论扩展为所有
站点均只有同一种算术差异；后续站点的输入也是候选轨迹上的输入，不是独立原模型轨迹。

随后只在 gate 和常规调用两处，将加权融合表达式改成“无权重融合输出再乘权重”。
这是开发者算术干预，不是 Agent 修复结果。完整模型仍失败：最大误差 `2.625`，
`1,189,170 / 4,861,952` 个 logits 超差（约 24.5%）。仅改这个舍入位置不足以修复模型。

另用原候选实际执行 `binding_cost`：父版本及纯透传四端点质量均通过。完整调用耗时
包含全部 32 个生成 token，不能代替 TTFT；同一端点的真实 TTFT 如下：

| 对照 | 父路径 TTFT（ms） | 纯透传 TTFT（ms） | 差值（ms） |
|---|---:|---:|---:|
| AB | 24.971102 | 27.484254 | +2.513152 |
| BA | 24.938721 | 28.265191 | +3.326470 |

直接绑定不等于零成本。上述读数包含实际包装、组合和测量波动，不能当作可从候选分数中
扣除的固定值，也不能与侵入式 kernel 时间相减来断言某个优化必然无收益。
但它说明后续选择边界需要考虑 145 个细粒度站点的安装代价，不能只处理数值正确性。
此项新证据未注入已经启动的 Qwen 修复对照。

## DDP：同一个候选的可行性随端点波动，通信收益仍未通过

保持第三轮 barrier 候选 `03c5e5ab…`、原 adapter、完整参考和合同不变，预先固定
父路径／直接透传／候选／候选／直接透传／父路径六端点顺序。每端点独立 worker，
原两步连续质量检查、两次预热、五个 clean 样本，以及三次单独通信采样。
没有重测到通过或发布该候选。

| 顺序 | 路径 | 整步（ms） | 最大 rank 通信 kernel 总时长（ms） |
|---|---|---:|---:|
| 1 | 父路径 | 136.870036 | 80.490097 |
| 2 | 直接透传 | 135.649765 | 66.918269 |
| 3 | barrier 候选 | 137.085769 | 63.554964 |
| 4 | barrier 候选 | 138.223983 | 63.956863 |
| 5 | 直接透传 | 142.525142 | 70.019031 |
| 6 | 父路径 | 148.547318 | 71.880084 |

所有质量检查通过。本次两个候选端点都满足原 `138.6598437 ms` 整步上限，与先前
`144.138116 ms` 的筛查不同；原筛查拒绝记录不变。父路径自身相差约 11.68 ms，
纯透传相对父路径的差值也变成 `-1.220271 / -6.022176 ms`，不能解释成稳定的负绑定成本。
这些结果证明现有端点波动足以影响可行性判断，未隔离波动的具体硬件或主机原因。

取六端点中父路径与候选做诊断性配对判定：通信均值 `76.1850905 → 63.7559135 ms`，
配对收益 `16.935133 / 7.923221 ms`，噪声界 `9.545292 / 8.189040 ms`。
第二对仍未越过噪声界，按原规则仍不通过。该顺序夹有透传端点，属于固定三臂隔离，
不能冒充一次全新的标准四端点正式提交，也不能把 NCCL kernel 总时长当作链路传输时间。

## DDP 合同：基线实现选择不应自动变成优化禁令

只读来源审计确认：源代码设置了 DDP flags，忠实的基线 adapter 应保留；源 workload
和 README 定义了工作量、数值要求与目标约束，但没有明确禁止优化 bucket 或通信 hook。
“DDP construction flags are frozen” 首次出现于 evaluator 生成的 understanding，
框架将该数组原样写入 `ProjectContract`。提示中“不要为了被动 inventory 安装 hook”
也不能推导成“所有优化都禁止使用 hook”。原合同没有在原实验中被静默修改。

对原 evaluator 生成前快照建立两次真实会话，模型、工具设置和声明输入相同；实验组
只增加通用说明：区分任务语义与实现选择，说明不变量的来源，将纯实现选择放入 assumptions。

- 对照组再次冻结 DDP wrapper／bucket 参数。
- 实验组将这些参数和调度选择归入基线实现说明，保留完整工作量、梯度／参数一致性、
  rank 梯度完全相同、精度和整步约束；基线代码本身仍使用源 DDP 配置。
- 人工核对两份 adapter 的执行与观察字段后，分别进行双卡独立核验：两次连续更新，
  再 reset 回放第一步；每 rank 每次比较完整 `248,879,617` 个共享观察元素，均为零误差，
  `124,439,808` 个梯度元素的跨 rank 副本也逐位相同。参考来自先前已对原项目独立核验的
  完整参考；对照组额外输出的 microbatch losses 另行比较，实验组保留源任务要求的总 loss。

这个结果支持增加该通用提示，但不证明 Agent 能完美区分所有项目的语义与实现。
实验组仍将部分后端选择混在架构说明中；新任务合同仍需检查，既有冻结任务不会自动改写。

## 采集规划：按实测误读逐项补充说明

全部对照使用原 Qwen post-screening 规划快照，保留原输入，不预设失败类型或采集选择。
先做“无 functional replacements 不等于没有直接替换”的两会话对照，两组仍选同样的
`candidate_diagnostics` 和 `nsys`，没有证明实际采集改善，不单独推广这句提示。

随后观察到 control 声称 `candidate_diagnostics` 能测每站点误差、定位首个数值分歧，
而当前提示未描述该工具能力。新增一个自适应实验臂，只说明它记录候选 Python 调用、
异常及传播的库内 traceback、少量标量返回，不进行中间张量比较。新回复正确将数值分歧
列为不可采集项。这是沿用此前 control 的小范围自适应对照，没有新的独立 control 或统计显著性主张。

该回复仍把直接绑定误判为无法测成本。再仅追加 additive 的精确定义：保留父 bundle
并增加新 bundle；直接 module／project 绑定也适用，移除原 bundle 才不适用。
新回复选择了 `binding_cost`，实际原候选的四端点采集也成功。DDP 冻结规划的跨任务检查
同样正确识别直接绑定适用性，并继续选择通信相关采集项。两项事实说明已加入规划提示。

跨任务回复仍曾误用某个 rank 的参考值，声称全项目通信指标基本没变。为此另做一个
固定快照实验：仅在 `original_reference` 增加按现有目标聚合规则算出的参考目标值，
保留所有原字段和提示。新回复正确比较 `74.676 → 64.149 ms` 的最大 rank 通信指标，
并单独指出整步超限。该字段已接入 post-evaluation 规划输入，复用现有验收的 rank
聚合规则，缺测则保留 unknown；不新增指标、采集器或验收条件。

上述真实回复仍有解释过度的地方，例如把局部无计算重叠的区间称为暴露通信，或将
reference calibration 推导成等待／传输的界限。这些不是本轮新增字段能证明的事实，
没有将这些解释写入测量结论，也不声称本轮已消除 Agent 的所有推理错误。

## Qwen 真实修复对照

两次新候选会话基于同一个实际失败实现、第三轮常规反馈、原选组边界和合同。
实验组只额外获得上述旁路比较及舍入干预的紧凑测量摘要，不提供手工修复代码或指定算法。
生成前快照核验确认：prompt、模型、公开工具设置、框架源码和其他声明输入全部相同；
只有 `previous-feedback.txt` 的 `supplemental_evidence` 从空值变为实测摘要，增加 4,691 字节。
两组输出均交给原参数筛查、完整输出检查和 AB/BA；接受版本另做一次独立整版本验证。
此对照为开发者诊断辅助，不与原入口自主结果合并。

两组均保留原 ATen 均值归约，在周围实现平方及归一化尾部 kernel；对照使用 Triton，
实验组使用 CUDA 扩展。两者还存在缓冲复用、向量化和 Python 调用结构等差异，不能把
性能差别单独归因于语言或某一种优化。所有筛查及正式配对端点的完整质量检查均通过：
两个连续步骤各比较 `4,862,240` 个元素，最大绝对误差为零，原数值门槛未放宽。

| 修复臂 | 父版本 TTFT（两端点，ms） | 修复版本 TTFT（两端点，ms） | 正式判定 |
|---|---|---|---|
| 常规反馈 | 25.019123 / 24.885732 | 32.047240 / 30.977627 | 正确，但性能退化，拒绝 |
| 常规反馈 + 紧凑数值证据 | 25.047855 / 24.611580 | 23.911944 / 23.233821 | 正确，配对收益通过 |

正常评测的原生 trace 确认：对照执行 `_sq_f32_kernel`、`_rms_tail_kernel`，实验组执行
`rms_sq_kernel`、`rms_apply_kernel`，每种各 145 次。它们确实执行了新计算；该 trace 是
单独的侵入式采样，不用于性能打分。候选注释中关于旧失败“导致 greedy token 分歧”的
表述没有证据支持：旧记录中 input IDs 和生成 tokens 已通过比较，失败发生在 logits。

一次 control／treatment 无法证明补充证据必然改善生成，也不能说它是正确性修复的必要
条件，因为 control 同样修复了数值问题。本轮证明的是：提供少量真实诊断后，Agent
产出了一个可通过完整质量和本轮性能检查的候选。独立整版本结果另列，不能以此轮局部
接受直接替代最终验证。

第一次独立验证原本计划比较完整两 bundle 版本与原始基线，其原始读数如下；后续原生
核验发现这次启动环境有差异，因此这些数据**不能验证新 RMSNorm 实现的性能**：

| 对照 | 原始基线 TTFT（ms） | 完整候选 TTFT（ms） | 收益（ms） | 噪声界（ms） |
|---|---:|---:|---:|---:|
| AB | 29.420211 | 27.363015 | +2.057196 | 9.361456 |
| BA | 24.997769 | 27.695433 | −2.697664 | 1.423390 |

质量及 bundle 调用覆盖检查虽然通过，但每个候选端点的 728 次 norm 路由均为
`parent-fallback:setup-failure:no-extension`，Nsight 中也没有新 norm kernel。
开发者启动器为缓解磁盘压力设置了 `TMPDIR=/dev/shm`；候选用临时目录缓存 CUDA 扩展，
而该挂载具有 `noexec`。直接导入缓存的 `.so` 复现 `failed to map segment from shared object`，
同一源码在原 `/tmp` 缓存中的扩展可正常加载。根因来自开发者验证启动环境，不是本轮
候选数值实现再次失败，也不能据此推断新 kernel 的性能退化。

首次 raw 判定及完整记录仍保留在 `qwen-independent`，额外审计为
`qwen-independent-tempdir-audit.json`。修正启动器使 `TMPDIR` 与原实验一样未设置，
在 `qwen-independent-matched` 做一次独立 AB/BA 及原生核验；候选、合同、阈值不改。
这次重做基于已复现的执行路径失效，不是根据分数重复采样直到通过。

恢复原环境后的有效独立结果如下：

| 对照 | 原始基线 TTFT（ms） | 完整候选 TTFT（ms） | 收益（ms） | 噪声界（ms） |
|---|---:|---:|---:|---:|
| AB | 24.427023 | 24.036326 | +0.390697 | 0.920202 |
| BA | 24.618941 | 24.573830 | +0.045111 | 0.071280 |

平均值 `24.522982 → 24.305078 ms`，约下降 0.89%，但两对收益均未超过噪声界，
因此正式判定仍为拒绝。所有完整质量检查零误差、bundle 覆盖通过；两个候选端点均记录
`bitexact-composite: 583` 和 `bitexact-composite-gated: 145`，新 norm 路径不再全部回退。
对该精确完整版本的单独 Nsight 核验也观察到 `rms_sq_kernel`、`rms_apply_kernel` 各 145 次。
有效复测与第一次局部接受仍有差异，尚未证明稳定整项目加速；两种判定都保留，不推广候选。

## 下一步边界

1. 保留这个质量通过、实际执行新 kernel 的 Qwen 候选，先审阅现有 clean 样本、原生
   trace 和绑定对照，设计固定候选的计时稳定性／宿主开销最小实验。暂不继续生成更多
   融合候选，也不把绑定成本当作固定常数扣分；根据实际缺测再增加少量观测。
2. 用已验证的通用合同提示重新启动独立 DDP 原入口任务，确认新合同保留任务语义而不
   自动冻结源实现选择，再沿原流程测试真实通信优化。旧合同和旧实验结果保持可追溯。
   双卡通信 kernel 时间包含等待，优化仍须同时满足原完整质量和整步约束。
3. 新提示和参考聚合字段已通过角色级真实调用及针对性测试，但尚未完成新代码下的完整
   三任务自主重跑。下一次原入口验证应与本轮诊断辅助结果分开统计，不以此轮修复成功
   证明通用工作流已自动具备同等诊断能力。
