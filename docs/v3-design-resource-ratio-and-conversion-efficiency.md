# v3 设计:以资源比例与转化效率为核心的算子优化框架

**状态**:设计稿,2026-09-09。v3 分支从 v2 的 `8772831` 继承全部代码,`D:\Pyhon_projects\opop\v3`(git worktree,同仓库分支 v3)。v2 分支继续跑完当前两个实验,box 1 完成后转为 v3 的实验平台。

本文档只定**整体思路、项目逻辑与改造路线**,不逐行规定代码怎么改。每条判据都写明"用什么证据算通过",这是 v2 立下的规矩:改动必须泛化、必须有会失败的反向对照。

## 一、核心思想

### 1.1 一句话

一个算子(或一个模型)在每个资源维度上有自己的**消耗向量**;一台硬件在每个维度上有自己的**供给向量**。两者方向不一致时,某个维度先撞顶而其余维度闲置——这就是瓶颈。**算子优化的本质是在资源维度之间做交换,把消耗向量的方向转向供给向量的方向。**

例:算子融合 = 用存储/内存占用,换掉启动开销、传输开销、通信开销。降精度 = 用数值精度,换算力吞吐与带宽。两者在 v2 里是"两种互不相干的技巧",在 v3 的模型里是**同一类操作的两个实例**——都是资源维度间的重新分配。

### 1.2 但"利用率均衡"不是目标

严格讲最优是**延迟最小**,不是利用率均衡。一个打满带宽、算力空转的 kernel,若已达该任务的物理下界,它的"比例失衡"是**物理性质而非缺陷**——继续"均衡"只会更慢。

已有实测反例(必须内建进设计,否则框架会去优化一个已经到底的 kernel):

- **L3:48 是带宽墙**:固定 1.351 GB 流量,1.64 ms 已达实测 911 GB/s 屋顶的 **90.4%**。平台期是物理不是噪声,只剩约 10% 靠减少流量。
- v2 曾因缺 fp16 天花板,把候选读成 **107.8% 已到顶**,指令直接反转(该候选实际约 54–60%)。

**所以 v3 必须以"每个维度的下界"为锚**,而不是以"均衡"为目标。`task_cost.py` 的 `compulsory_bytes`(任何实现都躲不掉的流量)已是流量维度的下界雏形,v3 把它推广到每个维度。

### 1.3 资源不是可自由兑换的:软资源 vs 硬墙

- **软资源**(可交换、有成本):DRAM 流量、算力、启动次数、寄存器压力、occupancy、溢出流量、(未来)通信量。
- **硬墙**(越界即不可运行,不是"效率低"):shared memory > 101376 B、寄存器 > 255/thread。v2 实测有 62 个 trial 直接死在 shared memory 上。

模型里必须区分这两类,**不能都当成成本项加权求和**——硬墙是可行性判定,由编译期真值裁决(v2 的 F5 compile screen 已在做且正确率 100%),软资源才进交换计算。

### 1.4 资源转化效率:v3 最有价值也最新的部分

让一个算子达到资源上限的方法几乎无限多。评判优劣不能只看"到没到顶",还要看**在资源转化上的效率**:

- **资源转化效率**:降低 1 单位瓶颈资源,付出了多少其他维度的开销。
- **性能转化效率**:增加的开销换来了多少实际性能提升,即 `Δ性能 / Δ开销`。

现有文献(roofline、各类 auto-tuner)基本只关心"到没到屋顶",不关心"你花了多大代价挪到屋顶"。把效率当成一等**信号**,能区分两种终点相同、过程质量完全不同的优化;它也正是"用参数调优反馈引导结构搜索"缺的那一半——**现在的反馈只有"更快/更慢",没有"以什么代价"**。

### 1.5 效率指标的噪声纪律(踩过坑换来的)

比值的分母小时,比值本身就是噪声。已有实测:**L3:48 每 trial 的 std 占均值 16%,而 33 个近平局的跨度只有 9%**——那种噪声下算 Δ性能/Δ开销,分子分母都是噪声,得到的"效率"是幻觉。

**硬规则:效应量未显著超过噪声底时,效率一律报 `unknown`,不报数字。** 这条不写进设计,这个指标会系统性骗人。

## 二、v2 与该思想的差距(全部在 v2 代码里复验过)

差距不在"有没有做优化",而在**框架根本不度量"资源转化"这件事**。

### 缺口 1(最致命):候选实际消耗的资源从未被测量,只有任务的下界

`v2 orchestrator.py:1421` 把 `byte_count=cost.compulsory_bytes` 传给分类器——**任务的强制流量,对所有候选是同一个常数**。后果:

- 框架**无法知道任何候选实际移动了多少字节**。融合掉一半中间张量的候选与不融合的,在分类器眼里流量完全相同。
- 于是**"这次优化把流量换成了算力"在框架里根本不可观测**——而这正是 v3 的核心量。
- 现有 `pct_of_dram_peak` 实际是"下界流量 ÷ 时间",是**该候选达到的下界带宽**,不是真实带宽利用率;真实流量更大 → 真实利用率更高 → 真实可优化空间更小。**这个偏差在融合差的候选上最大**,恰好在最需要准确判断的地方最不准。

**这是其余一切的前提。** 没有 per-candidate 资源向量,"资源比例"与"转化效率"都无法计算。

### 缺口 2:瓶颈判决是单标签,不是资源向量

`classify()` 返回单个 `kind`,取值 8 种之一(`memory_bound`/`compute_bound`/`resource_limited`/`launch_bound`/`latency_bound`/`overhead_floor`/`mixed`/`unknown`)。"每个维度的消耗比例"被**压缩成一个词**。

好消息:分量大多已算出来了。`evidence` 里已有 `pct_of_dram_peak`、`pct_of_compute_peak`、`occupancy`(带 `occupancy_limiter`)、`n_regs`、`n_spills`、`shared_bytes`、`arithmetic_intensity`、`ridge_flop_per_byte`、`uses_tensor_cores`。**向量已经存在,只是最后被 if-else 链塌缩成标签。**

代价的实证:**L3:21 的 20 份报告里 19 份是 `resource_limited`**,几乎没有区分度。它字面意思正是"某资源接近硬限但两个屋顶都没到"——最该被量化的"比例失衡"情形,却给了 agent 最少的信息。

### 缺口 3:资源维度覆盖面窄

| 维度 | v2 现状 |
|---|---|
| 算力 | ✅ 实测四档屋顶(fp32/tf32/fp16/bf16) |
| 内存带宽 | ⚠️ 已测,但分子是下界(缺口 1) |
| 存储/容量 | ⚠️ shared/regs 有硬限检查,但**仅作布尔**,不作可交换成本 |
| 启动开销 | ⚠️ 测了 `empty_launch_floor_ms`,但 `launch_bound` 判决 **848/848 trial 从未触发**(缺 `cpu_issue_ms`,P2 至今未修) |
| 通信 | ❌ **完全不存在**(grep `nccl|nvlink|multi_gpu|dist.` 零命中) |
| 多卡 | ❌ 不存在 |

### 缺口 4:"效率"从未被计算,搜索目标是单一延迟

- 目标函数是 `robust_ms`(`tpe.py:100`),纯延迟。**Δ性能/Δ开销 在任何地方都不被计算。**
- 改写推进判据 `min_improvement_pct: 2.0` 只看性能变化,不看代价。框架**无法区分**"用 2 倍 shared memory 换 2% 提升"与"零额外开销换 2% 提升"——按 v3 思想后者显然更优。
- 中间步骤效率无记录:rewrite/expansion 只记 best_ms 变化,不记资源向量变化,**事后也无法重建**。

## 三、v3 改造路线

按依赖顺序。前两项是地基,缺了后面全做不了。

### 第 1 步:测量候选自己的资源向量(必做,一切前提)

每个 trial 记录 `ResourceVector`,而非只记延迟:

- **实际 DRAM 流量** — 最难的一项。不需要 counter 的路径:从 SASS 数 LDG/STG 指令数与宽度(**v2 已在做**:`statics.py` 已解析 `.128/.64/.32` 宽度用于判向量化),乘 grid 尺寸得请求字节数。
  - **诚实交代**:这是**请求流量**而非 DRAM 流量(不含 cache 命中),因此是**上界**。配合已有 `l2_bytes` 与"L2 是否装得下"的判断,足以区分"融合了/没融合"。报告里必须标清是哪个量,否则重演"把下界当利用率"的错误。
  - **为什么走这条路**:counter 在租用容器里**永久不可用**(`ERR_NVGPUCTRPERM`,需要容器内无法设置的 host 侧内核模块参数)。任何建立在 ncu 上的方案在真实实验箱上返回空。
- **算力**:已有(FLOP 由任务决定,常数)。
- **容量类**:`shared_bytes`、`n_regs` — 已有,改为成本项而非仅布尔。
- **启动/调度**:kernel 数 × 空启动地板 — `kernel_names` 已有,便宜且真实,可立即算。
- **溢出流量**:`n_spills` 已有,STL/LDL 已能数出。

**判据(必须有反向对照)**:同一任务上,一个明确融合更好的候选,其测得流量必须显著低于融合差的候选。L3:21 有现成对照——获胜的全融合 fp16 流水线 vs 10.198 ms 的分离实现。**若新度量分不出这两者,该度量即为坏的。**

### 第 2 步:判决从标签改为向量 + 保留标签作摘要

`BottleneckVerdict` 增加 `utilization: dict[str, float]`(每维:实际/该维屋顶)与 `headroom: dict[str, float]`。`kind` 保留(向后兼容 20 个 run 的记录、报告可读性),但**给 agent 的 prompt 主体改成向量**。

理由:"你在带宽 91%、算力 12%、occupancy 8% 且被 shared memory 限制"对写 kernel 的人,信息量远高于 `resource_limited`。顺带解决 19/20 同标签的区分度问题。

### 第 3 步:算出每个维度的**下界**,作为"还有多少空间"的锚

- 流量下界 = `compulsory_bytes` / DRAM 屋顶(材料已有)
- 算力下界 = 任务必需 FLOP / 该精度屋顶(材料已有)
- 启动下界 = 最少 kernel 数 × 空启动地板

**三者取最大值 = 该任务在该卡上的物理下界。** 比它更快意味着算错了——这同时是一个比现有粗糙 `excessive_speedup` 10× 阈值更好的诚实性检查。有了下界才能回答"还剩多少空间",而不是去"均衡"一个已到底的 kernel(直接治好 §1.2 的风险)。

### 第 4 步:资源转化效率,作为**报告与 prompt 信号**,不作搜索目标

对每次 rewrite / 空间扩展,计算并记录 `Δlatency / Δ(每个资源维度)`——这次改动用什么换来了什么。

**三条硬约束,每条都来自已踩的坑:**

1. **绝不作为 TPE 目标函数。** 目标仍是 `robust_ms`。比值目标会奖励"两边都很小"的无意义改动,且放大噪声。
2. **效应量必须超噪声底才允许计算**(§1.5)。Δlatency 小于该候选 combined SEM 时报 `unknown`。
3. **绝不作筛选/剪枝。** 与 v2 一贯规则一致(agent 建议永不 gate),且有实测反例:**L2:37 上最慢的种子所属族改善最多(−30.5%)**,按效率剪枝会杀掉赢家。

真正用途是喂给 rewriter:"上一轮你用 2.1 倍 shared memory 换来 2% 提升,而另一族用零额外资源换来 16%"——这才是让 agent 学会**挑更高效交换方向**的信号,也正是论文主张缺的那一半。

### 第 5 步(为多卡/异构预留):通信作为第 N 个维度

现在完全不存在,单卡任务也不需要。但若多卡在路线图上,应在**第 1 步设计向量时就留出位置**(维度可扩展、屋顶可缺失),而非事后硬塞。

## 四、异构显卡与该思想的关系

选卡不只是"支持更多硬件",而是**在哪张卡上这套资源比例思想第一次真正起作用**。

已实测的关键事实:**4090(Ada)上 tf32 ≈ fp32 速率**(实测 88.1 vs 54.8 TFLOP/s,1.61×;而外部团队误以为两者相等)。这导致精度这一维在 4090 上的交换价值被压缩。

| 卡 | 架构 | 对 v3 的价值 |
|---|---|---|
| **A100-40GB** | Ampere sm_80 | **验证"精度作为算力维度交换"最佳**:tf32 约 8×、bf16 约 16× fp32(规格估算),精度从"可有可无"变成第一杠杆。全功能卡,四档精度都真实存在,首次异构移植不踩坑 |
| **H20-96GB** | Hopper sm_90 | **这套资源比例思想最好的试验台**:算力被阉割、带宽极高(4TB/s)——**极端不平衡卡**,比例失配最严重、最易暴露框架盲区。也是唯一有 TMA/wgmma 的卡(CuTe 主场)。注意:结果不可外推到 H100/H800 |
| **V100-32GB** | Volta sm_70 | 鲁棒性破坏测试:**无 tf32、无 bf16**,直接顶破框架"这卡有这些精度"的隐含假设,检验校准 schema 能否优雅降级。Triton 的 Volta 支持最弱,后端对比不公平 |
| **RTX 5090** | Blackwell sm_120 | **信息量最低**:与已测的 5080 Laptop / 4090 同族同故事,几乎不产生新可移植性信息 |

**CUTLASS/CuTe 的现实约束**:worker 环境未安装,也没有 prompt / pitfalls / 每后端编译错误分类(v2 契约明确写着"不可用,不要使用")。且实测**手写 CUDA 比 Triton 慢 0.874×**,KernelPro 的 1.23× 来自 **CuTe(Hopper)** 而非裸 CUDA。所以 CUTLASS 生成应推迟到 H 卡,在 4090 上写它**测不出收益、无判据**。已完成的地基:后端中立 profiling(`cuobjdump -res-usage` 覆盖 CUDA/CUTLASS/CuTe)、`structural_signature` 含后端前缀。

## 五、代价、风险与纪律

- **第 1 步是真正的工程量**,且请求流量 ≠ DRAM 流量(cache 命中致偏高)。足以区分融合好坏,但**不得声称是精确 DRAM 字节数**。
- **第 2、3 步性价比最高**(原料齐备,主要是暴露已有数值 + 三个下界的算术),**建议先做**。
- **第 4 步价值完全取决于第 1 步质量**:没有可信资源向量,"转化效率"就是拿噪声除噪声。
- 全部改动**泛化**(不针对任何 task/candidate),符合既定修复标准。
- **第 1、2 步改变 agent 看到的信息 → 改动前后 run 不可直接比较。** 必须在两箱空窗时统一上线,并明确记下这条分界线。

### 从 v2 继承且不重做的东西(已验证承重,勿动)

fp64 相对门(救回 ratio<1 的候选,对抗缺陷以 28–290× 被拒);cosine 溢出修复(float64+归一化);四档精度实测天花板 + 校准 schema 版本;F5 编译期 shared-memory 判定(正确率 100%,已前移进 `guard_ok`);median 作为调参目标(排序正确率 93.2% vs mean 64.8%);厂商库许可;artifact rescue;后端由源码裁决而非声明。

### v2 遗留的开放项(v3 需决定是否继承其修法)

D1 死值 FAIL→PRUNED 升级(bf16 在 L3:21 两轮 0-for-100,占 8.8% 预算;但同一 bf16 在 L3:43 是**获胜精度**——证明门正确、不可做 dtype 禁令);P6-C per-precision 最优上报;P9 ieee `tl.dot` 标定 yardstick(已复验未落地,标定只测 `torch.matmul`=cuBLAS);P2 `launch_bound` 不可达;固定 0.99 门 vs 三任务噪声底(0.9554/0.9767/0.9778)全低于它;Loop D 在 L3 上因墙钟从未被调度。
