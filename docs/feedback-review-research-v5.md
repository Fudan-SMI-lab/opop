## 2. 问题一：P2′ 的增益方向和分母不同，优先级最高

**证据锚点：** `src/kernel_optimizer/conditional/scanner.py:419-422`；`scripts/probes/v41_p2prime.py:97-123`。
当前 scanner 对完整 C4 的发现对定义 `g_d = 1 - N_d/F_d`，留出对定义 `y = 1 - N_v/F_v`。
两者均为延迟最小化下从 F 到 N 的相对改善，正数表示 N 更快。
当前 reader 却由中位端点返回 `g_m = (N_med-F_med)/N_med`。
这不仅符号相反，分母也不同；reader 的“same sign convention”注释与实际公式不一致。
逻辑反例：若发现对、边际中位端点对及留出对均满足 F=10、N=8，则 `g_d=y=0.20`。
旧边际式给出 `g_m=-0.25`，从而制造 `|g_m-y|=0.45` 的表观误差。
上述 0.45 来自已核验的纯算术，不是任何 pilot 的误差测量，也不证明所有旧误差都由此造成。
比较中位端点时，应使用同口径的 `1 - N_med/F_med`，不能只把旧值乘以负一。
若仅作代数换算，旧 `g_m` 对应的新量为 `-g_m/(1-g_m)`，前提是有效正值端点与同一历史池。
由于下述历史范围和泄漏问题，不能靠换算已发表汇总数字完成修复，必须重建正确历史再算。
**意义：** 50 倍／26 倍、边际符号一致率及“边际必然指错方向”都直接依赖这项比较。
对 `docs/window1-results.md:21-40` 与 `docs/review-research-v5.md:33-47` 的强结论应暂停引用。
暂停不表示这些差异修正后必然消失，也不表示条件预测没有价值；当前证据不支持预判更正方向。
先把生成该表的实际 reader 版本、命令、输入 run 和输出文件对应起来，才能归因历史数字。

## 3. 问题二：P2′ 历史池跨候选混合，不能代表已声明的 legacy 基线

**证据锚点：** `scripts/probes/v41_p2prime.py:64`、`:138-157`、`:162-163`。
reader 将整个 run 中所有 `status=complete` 的 `TRIAL_DONE` 加入同一个 trials 列表。
`Contrast.candidate_id` 被读取，但调用 `_marginal_slope` 时未用于过滤，也没有 space 过滤。
同名 BK 或 COMPUTE_DTYPE 因此可能混入不同候选实现的延迟，比较对象已不只是搭档参数边际化。
**意义：** 若实现、工作量或参数语义不同，混池误差不能直接归因“边际历史不可靠”。
不要随意补成“仅当前 space”或“候选所有 space”就宣称复现旧 analyst 的真实信息。
当前调用锚点为 `src/kernel_optimizer/control/orchestrator.py:1033`、`:1504`、`:1959`，均向 analyzer 传入 space 与 `crun.trials`。
仍需核对实际历史版本的 analyzer、caller 和数据生命周期，恢复当时 candidate／space 的真实作用域。
修核时固定任务、实现身份、端点语义、允许精度和合法历史范围。
在有效范围内，边际法仍应有意对其他 partner knobs 作边际聚合；不要改成固定搭档后冒充旧基线。
扩展空间是否可合并取决于历史语义与实现规则，而不是哪种池能让某个方法更好看。

## 4. 问题三：C4 关闭前的前缀不等于无留出泄漏

**证据锚点：** `src/kernel_optimizer/control/orchestrator.py:1323-1335`；`src/kernel_optimizer/conditional/bridge.py:103-114`、`:283-318`。
生产链先写 `TRIAL_DONE`，然后才调用 bridge；bridge 折入扫描结果后才写 `SCAN_BLOCK_DONE`。
因此 reader 在 `SCAN_BLOCK_DONE` 前保存的 trials 前缀，已经包含该 C4 的 validation trials。
`scripts/probes/v41_p2prime.py:152-157` 的“追加 contrast 之前快照”不能排除这种泄漏。
**意义：** 外部评审 `docs/review-research-v5.md:179-193` 宣称“已有正确无泄漏基线”不能成立。
当前完整 C4 的 `g_d` 仅用 discovery roles，源码本身没有把 validation 混进 `g_d`。
`g_m` 吃到 validation 是独立问题；不能说它必然偏向反对边际法，偏差方向需复算判断。
先明确预测时点：例如发现对完成后、验证开始前，但这一时点必须与真实随机执行顺序一致。
角色不能由到达顺序猜测；须核对实际 F_d／N_d／F_v／N_v 标记与 trial ID。
若验证先于发现完成，不能虚构一个实际不存在的在线时刻，应显式说明角色留出重分析的协议差异。
另一可选分析是 C4 准入前的边际基线；它的信息预算不同，应另命名，不能静默替换预注册估计目标。
按 role、trial ID 和截止事件排除留出与未来数据，核对发现数据在两种预测中的可用性。
缓存复制记录应保留来源与计数，但不能当作新的独立样本或增加重复数。
保留全部 fresh-complete C4 的主分母，包括未铸 token 的 unresolved，不只筛通过方向门的例子。
另报可比交集、每端有效独立样本数和缺失原因；missing 不算错误，也不算条件法自动获胜。
保留 no_slope、values_unsampled、thin_bucket 与日志缺端点等原因，不能压成一个失败数。
旧计算产物应原样保留并标“不可用于该可比性结论”；新分析必须附旧／新定义及数字差异。
23 个 contrasts 来自两个 run，不是 23 次独立搜索重复，任务内和候选内相关性须披露。
预测准确度本身也不证明“更早”，该词还需要共同信息时点或成本到达时间的证据。

## 5. 问题四：H2 应分三层，终局 E 负结果不能替代结构收益检验

建议拆为 H2a：响应预测可靠性；H2b：sampler 的行动效用；H2c：rewriter 的结构改写收益。
**证据锚点：** `scripts/probes/did_the_enqueued_point_win.py:206-226`、`:251-255`；`docs/window1-results.md:104-118`。
终局 reader 在同一 space 内按轴值分桶，比较投递值的最小延迟与所有其他值的最小延迟。
它混合 partners，且两侧机会数不同，如 n=5 对 25、n=2 对 25；极小值受到搜索机会数影响。
“双侧 n≥2”只是桶内 trial 计数，不等于同一个完整配置有两次 fresh 独立重复。
因此 0 赢／4 输／2 平是既定终局按值指标的描述性负结果，应保留，不用新终点把它冲掉。
但它不等于 exact committed-partner E 点相对 source anchor 的局部响应，更不等于结构改写干预。
也不能由该表直接推断探针、LLM、采样机会成本都已超过收益。
将“收益覆盖成本已知未满足”改为“收益覆盖成本尚未建立”，避免把未建立写成已知否定。
**阈值锚点：** 同一脚本 `:288-300`、`:459-463` 默认用 4% 将小幅差异归为 tie。
这是一条描述性分桶带，不是统计等效检验，不能证明两侧性能等价。
一边宣称 4% 在任何场合都不合法，一边据此确定两例平局并普遍否证行动收益，论证不一致。
后续可另列固定 committed partners 的 E 与 source anchor 比较，说明其局部目标和重复条件。
搜索净效用另需配对搜索臂、共同预算与完整成本；结构效用另需提案、完整复评及对应对照。
这些是补充证据路线，不是本文件授权新增实验或追溯改写原终局指标。

## 6. 问题五：N1 反映搜索结果差异，不提供 C4 通用噪声阈值

**证据锚点：** `scripts/probes/v41_n1_noise_floor.py:71-83`；`src/kernel_optimizer/control/orchestrator.py:1339`、`:1362-1375`。
N1 reader 用每个 candidate 最后出现的非空 `TUNING_DONE.best_ms` 覆盖前值。
生产端该事件记录当前 space 的 tuner best，而 candidate 跨空间最优另由 `crun.best_ms` 维护。
最后一次空间调参结果不保证是候选历史全局最优，需先核对报告实际 reader 和扩展路径。
四个 source SHA 相同只固定种子源码，不固定参数、搜索轨迹、实际实现路径或测量精度。
`docs/window1-results.md:124-127` 已列 N1 两个终局赢家分别为 fp16 与 bf16，且来自不同 rewrite。
这可属于旧放宽精度语义下的合法搜索，但不能称为同一固定配置的硬件计时 A/A。
将 10.85% 说明为报告中四个种子调参读数差异的最大绝对值，不能称总体噪声分布。
将 11.72% 说明为一个 A/A 搜索对的终局差异，不能称所有计时器的噪声底或 MDE。
`docs/window1-results.md:147-155` 中 `11.72%-10.85%` 不是方差分解，不能把差额因果归为搜索路径。
既有“超过 2% 则 P3 降级为描述性”的预声明规则可以作为本次保守规则遵守。
但遵守该规则不证明 11.72% 是统计阈值，也不证明小于它的所有真实效应不存在。
**门锚点：** `src/kernel_optimizer/conditional/gates.py:34`、`:106-108`，实际 `tau=max(4%,rho_F,rho_N)`，并非始终等于 4%。
应分清方法的最小效应下限和测量噪声控制；一个搜索 A/A 最大差不能直接替代端点 rho。
拒绝“4% 普遍无效”不等于认证“4% 已有效”；当前证据不足以给出任一普遍裁决。
不要用上述错误推导追溯修改 legacy 的 4% 门或终局 tie 规则。
v5 应按目标、上下文和测量层级校准，可先用可负担的固定配置重复与端点响应对照。
若研究算法收益，再按需要取得独立搜索重复；不强制每个指标乘每个场地都跑 12h A/A。

## 7. 问题六：非正值安全拒绝是局部优点，不等于一般目标支持完毕

**证据锚点：** `src/kernel_optimizer/conditional/gates.py:41-49`、`:97-104`；`src/kernel_optimizer/conditional/scanner.py:395-403`。
`rho` 遇不足重复或非正值返回 None，gate 在 log 计算前拒绝这些输入，这一点应明确采纳。
scanner.tell 也会将非正延迟标为失败，且完整增益链另有 log 运算，不能只凭 gates 宣称全链支持负目标。
对 `J=-throughput` 的 legacy 路径，应写“不支持时清楚拒绝”，而非“一般目标已完成正确适配”。
v5 仍需定义最大化、零基线、单位和响应尺度；unknown／missing 不能补零或 epsilon。

## 8. 问题七：相关资源测量应进工作包，但不是所有任务都必须有软墙

**证据锚点：** `docs/window1-results.md:42-53`；`src/kernel_optimizer/conditional/bridge.py:98-133`；v5 草案 `:104-122`、`:163-171`。
采纳 compile-only 探针对运行期 spill 或 peak memory 有能力边界的提醒。
当前 bridge step 接收 trial 后处理延迟及拒绝，没有在该路径把 trial spill profile 馈入软墙发现。
因此若要声称识别运行期软墙，需要补足相关观测接线，而非只把缺数据写成小注脚。
但 runtime profiling 或完整任务 evaluator 都可收集内存，不必强迫每次编译探针执行完整任务。
C1 的三种边界是可选解释类别，不要求每个任务同时拥有硬墙、吞吐包络和经验转折。
内存目标也不意味着必然存在 spill 边界，甚至不要求存在任何有用软墙。
workspace、每块／每 SM shared memory 与整卡 VRAM 分开解释，不能相互代称。
将目标所需测量能力提升为有限工作包即可，不扩大为全指标强制采集或新安全平台。

## 9. 问题八：真实开关语义与实验处理定义需要拆开

**证据锚点：** `src/kernel_optimizer/config.py:412-423`；`src/kernel_optimizer/control/orchestrator.py:2147-2167`。
`v3.diagnosis.mode=label/vector` 决定资源向量解释是否进入 prompt，独立于 `v4.conditional_scan.mode`。
证据构造成功时两种 diagnosis 模式都可记录 DIMENSION_STATE；异常路径也可能记录 FAILED，不能说无条件必有向量。
关闭 conditional 并不等于关闭 C1 vector，不能从 off 名字推断 prompt 没有任何资源解释。
**补充锚点：** `src/kernel_optimizer/control/orchestrator.py:1437-1442`；`src/kernel_optimizer/conditional/bridge.py:115-133`。
条件简报仅 active 交付；observe 不准入 C4，也不交付条件 prompt，并非天然的“只有 C1”臂。
所以 off／observe／active 不是自动成立的 baseline／C1／C1+C2 三臂。
先定义 C1 指“解释”还是“墙与轴的取得”，再列共有测量、轴域、提示内容和 C2 使用的处理矩阵。
当前耦合使前瞻性嵌套设计较容易，这是可采纳的工程优先项。
若共享轴／测量提供方，再分开控制解释与 C2 消费，二因子仍可能成立，不是理论上不可识别。
不建议仅为凑齐因子形式重构；选当前最小可执行设计，并准确声明只能识别哪些增量。

## 10. 问题九：离线资产有价值，但覆盖、测量边界及可比性尚未确认

**覆盖锚点：** `src/kernel_optimizer/models/core.py:325`；`src/kernel_optimizer/control/orchestrator.py:1320-1324`；`docs/window1-results.md:10-15`。
profile 是 optional，TRIAL_DONE 包含失败，也可能是缓存复制；schema 能表达不等于每条日志都实有全部字段。
四 run 的 trial 汇总为 720+840+760+680=3,000，不是 `docs/review-research-v5.md:222` 所写“四个 run × 3,000”。
先按 run、status、backend、precision、metric、collector version 和 validity 做覆盖表，缺失不补零。
同时列缓存／独立测量计数、有效候选交集与不能比较的原因，避免只留下最方便的成功记录。
**测量锚点：** `src/kernel_optimizer/gpu/worker_main.py:412-450`、`:498-540`。
当前 cost helper 新建候选模型和输入，warmup 后 reset peak，读取 resident，再单独 forward 测 peak。
`peak_alloc_bytes` 是进程 allocator 的峰值，可能包含同时驻留的其他模型与输入，不是候选独占 VRAM。
外层 metadata 模型在第 498 行构造，调用第 540 行 cost helper 时仍存活，helper 又构造一份模型。
`peak_above_resident_bytes` 扣除了 resident，其中也含候选权重与输入，因此不是“完整候选显存”。
profile 路径 `.to(device)` 没显式匹配计时 precision，需核对实际 dtype、源码内部转换和 collector 政策。
L2 cache flush 属计时路径，不能说它直接污染了这个独立 pass 的 peak；allocator reserved 历史仍需解释。
只有完成边界及精度审计，才可把这些 runtime peak 用作明确 proxy 范围内的离线比较。
重评分分组须固定任务／模型语义、输入、环境、精度和采集政策，并使用同一有效候选交集。
可以跨结构候选比较合法目标，但须防止将不同机器、不同任务的四个 run 混评为一个全局冠军；这是分析边界提醒，并非外部原文提出的做法。
COMPUTE_DTYPE 搜索在旧放宽语义下可能合法，却不是固定 BF16 任务的纯内存目标切换。
不同精度血缘不能未经限定就归为“只换了目标”；同精度 speedup 也不能抹去任务政策差异。
赢家变化只描述延迟驱动、被记录候选 bank 内的目标偏好，必须报告选择偏差及覆盖率。
赢家不变不否定通用内存搜索价值，候选库可能根本没探索到对应结构。
“无需新增 GPU”不等于零成本或零风险，CPU 分析、版本核对和错误解释的成本仍需承认。

## 11. 问题十：拒绝率代理与 P1 个案要保留，但不能直接称墙因果证据

**证据锚点：** `scripts/probes/v41_refusal_delta.py:49-64`、`:71-81`、`:94-98`；`docs/window1-results.md:78-100`。
reader 的 relieved 是聚合采样拒绝率差 `dr<0`，父子可能具有不同参数域、partners 和采样分布。
它只纳入有 complete best 的 rewrite，并选择第一个 parent；这些选择条件必须随分母披露。
briefed 是全程曾收到简报的集合，若用于归因还须核对交付是否早于相关改写，不能预先断言历史确有时序错误。
因此先称“采样拒绝率代理下降”，不称“同一物理墙已被解除”。
P1 个案的 24%→8%、BN=256 通过率变化及 best 改善是值得保留的提示性测量对照。
要提升为墙级主张，还需匹配具体边界、上下文及父子配置，不将 3/4 直接当方法因果胜率。
同机同任务联合处理臂的比较能帮助估计总效应，但不单独证明是哪道墙或哪个解释造成效果。
off 也有下降、两个 active pilot 方向不同都应保留；不抹掉好例子，也不由一个例子证明完整机制。

## 12. 工作顺序、运行保护与预算边界

采纳最小集合和优先级，但 U 只有纯逻辑部分可断言 0 GPU，小任务实际执行未必如此。
P 的既有数据重分析应优先，不写成“协议已正确、分析已完成”；G 的廉价重评分可在 M 之前。
M 后再决定昂贵扩展是预算选项，不把 G／L／W／X 全部设成依赖 M 非零的硬门。
X 可选代表性留出任务／后端／指标，不必完整笛卡尔积；单样本零增量或低功效不否定全部应用泛化。
外部材料同时写“三张可用卡”与“四个并行臂槽”，可用容量存在内部不一致。
同机配对约束下，一台两卡机器不能同时容纳三个臂且自动消除机器混杂，需另行阻断或排程设计。
一个窗口也不等于具有独立搜索重复的研究；本文件不指定 GPU 排期、新计时或硬件安装。
8B 权重约 16GB 不能保证完整任务适配 24GB，KV、shape、workspace、并发及精度都未定。
历史 GPU 墙钟约 3.86h 对总时长约 12h，不能推导未来加载成本占比，更不能据此承诺容量。
保护实际运行中的共享 prompts、scorer 和代码版本，不改变对照实验正在使用的处理。
独立分支上的设计或不接触运行版本的 CPU 分析可先行，但本次不执行任何 git 操作。
科学证据不要求所有设计都等到论文投稿后；需要等待的是依赖结果的决策或会污染在跑版本的改动。

| 优先级 | 有界下一步 | 完成标准 |
|---|---|---|
| P0 | 先对应实际 run／raw logs／reader 版本，再提出 P2′ 修核及微型解析 fixtures | 同公式、合法历史池、无留出／未来泄漏，旧新分析分开 |
