# 三机工具链能否统一 —— 能,而且 box 1 / box 2 已经统一了

**日期** 2026-09-11 · **结论:box 1 与 box 2 可以并行跑一对对照 run;box 3 不能加入那一对** · **判据是实测的资源图摘要,不是版本号推理**

## 一、结论先行

| | box 1 | box 2 | box 3 |
|---|---|---|---|
| GPU | RTX 4090 24564 MiB | RTX 4090 24564 MiB | A800 80GB PCIe |
| 功耗上限 / 最大 SM 频率 | 450 W / 3105 MHz | 450 W / 3105 MHz | 300 W / 1410 MHz |
| compute capability | **8.9** | **8.9** | **8.0** |
| CPU | Xeon 8358P ×128 | Xeon 8358P ×128 | Xeon 6348 ×112 |

| 驱动 | 580.105.08(CUDA 13.0) | 580.142(CUDA 13.0) | 595.71.05(CUDA 13.2) |

**box 1 与 box 2 是同一款卡、同一款 CPU、同一个 CUDA 主版本。** 硬件侧没有障碍。

**而工具链侧的关键发现:两台机上已经各有一个完全相同的 `torch 2.13.0+cu129 / triton 3.7.1` 环境** —— box 1 在 `orch-venv`,box 2 在 `kernel-opt-venv`。**不需要安装任何东西。**

## 二、判据:资源图摘要,不是版本号

**为什么不能靠版本号判断**:「版本号相同 ⇒ 编译结果相同」是一个假设。而本项目要比的量(寄存器、shared、spill、能否启动)恰恰是 Triton 编译器的分配决策,**且已实测为非单调**(13 条非单调切片,BK 16→32 掉 58 寄存器、32→64 涨 87 并顶到 255 上限)**且不可分离**(10 个单步 Δ 零个一致)。所以两个编译器可以在一个 tile 上一致而在两个 tile 之外分歧。

**要比的是调参器实际采样的那片空间上的整张图。** `scripts/sweep_resource_map.py` 扫 162 个配置(BM×BN×BK×warps×精度 = 3×3×3×3×2),记录每个配置的 `(n_regs, shared, n_spills)` 或启动失败类型,输出一个摘要。

### 实测结果

| box | 工具链 | 启动失败 | 摘要 |
|---|---|---|---|
| **box 1** | 2.13.0+cu129 / 3.7.1 | 6 | `dd3eca5acd8ce656aa98160eb3d1b16c` |
| **box 2** | 2.13.0+cu129 / 3.7.1 | 6 | `dd3eca5acd8ce656aa98160eb3d1b16c` ✅ **逐字节相同** |
| **box 3** | 2.8.0+cu128 / 3.4.0 | **0** | `d565c810253c8f1fbd5b4f978c638ea4` ✗ **不同** |

**162 个配置全部一致,包括同样的 6 个启动失败。**

### 这个摘要不是空的(否则一致毫无意义)

| 检查 | 实测 |
|---|---|
| 不同的 `(regs, shared, spills)` 三元组 | **122** 个(共 162 行)|
| 寄存器跨度 | **38 – 255**(顶到硬上限)|
| shared 跨度 | 至 **98304 B** |
| 有 spill 的行 | **19** |

**一张全同或全失败的表会平凡地一致。** 这张不会:122 个不同三元组意味着摘要真的在比较东西。脚本把这几个数字与摘要一起打印,正是为了让「一致」可以被当作论断而不是被信任。

### 负对照成立 —— 这是这个判据可信的前提

**只会返回好消息的探针与正确的探针在输出上长得一样**,而本项目已经把探针自身故障读成过五个阴性结果。所以:

**A800 必须不同,而它确实不同。** 摘要不同,且**启动失败 0 个对 4090 的 6 个** —— 那正是物理差异(166912 B vs 101376 B 的 shared 上限)在数据里的样子。**如果 A800 曾与 4090 摘要相同,那说明脚本坏了,而不是两台机相同。**

## 三、所以对照 run 可以并行,但只在 box 1 + box 2 之间

```
box 1 (4090, 2.13.0/3.7.1, orch-venv)        ── 对照臂 ──┐
                                                          ├── 12h,而不是 24h
box 2 (4090, 2.13.0/3.7.1, kernel-opt-venv)  ── 处理臂 ──┘

box 3 (A800, 2.8.0/3.4.0)  ── 另一件独立实验(不属于这一对)
```

**墙钟从 24h 压到 12h,而 A800 同时可以跑第三件事。**

**box 3 为什么不能加入那一对**:两个原因各自独立成立 ——
1. **工具链**:triton 3.4.0 vs 3.7.1,摘要实测不同;
2. **硬件**:sm_80 vs sm_89,shared 上限 1.65 倍,**6 个在 4090 上无法启动的 tile 在 A800 上可以启动**。第 2 条不可能靠装软件消除。

**要不要把 A800 也升到 3.7.1**:可以做,但**不会让它加入这一对** —— 硬件差异仍在。它的价值是别的:让 A800 与 4090 的**判决模式**在同一个编译器下比较,从而把 G12(异构按维度比较)的共变因素从两个减到一个。**不在关键路径上,建议放在对照 run 之后。**

## 四、两臂放在两台机上,还要守住什么

**「同机」这条约束的真正内容是「除开关外一切相同」。** 换成两台机之后,原先由「同一台机」免费保证的东西必须逐条显式检查:

| 项 | 状态 |
|---|---|
| GPU 型号 / 显存 / 功耗上限 / 最大频率 | ✅ 实测相同 |
| compute capability | ✅ 8.9 / 8.9 |
| torch / triton | ✅ 2.13.0+cu129 / 3.7.1,**且资源图摘要逐字节相同** |
| 驱动 | ⚠️ 580.105.08 vs 580.142(同一 CUDA 13.0)。**未实测其影响**,但资源图摘要一致说明编译侧无差异 |
| `device:` 配置块 | **必须两臂相同** —— 两台机都是 101376 B,可共用 |
| 标定 | ⚠️ **两台机各自标定,数值不会完全相同**(屋顶是实测值,有测量噪声)⇒ 见下 |
| 两臂 config 只差两个键 | ✅ 已有测试守着(`test_the_shipped_a800_arm_pair_differs_in_exactly_the_two_switches` 的同形) |

### 一个必须承认的残余风险

**两台机各自标定 ⇒ 屋顶数字有测量噪声上的差异**,而 S2/S3 的每维判决拿屋顶当分母。这不是工具链问题,装软件解决不了。

**处置**:两臂启动前**在两台机上各跑一次标定并比对数字**;若某个屋顶差异超过任务噪声底,则**那一对 run 不可跨机**,退回 A800 单机串行 24h。这一步必须在启动前做,而不是事后解释差异 —— **否则「终局变差」会有两个候选解释而无法区分**。

**顺带一个卫生问题**:box 2 的 `/tmp/nt.py` 会遮蔽标准库的 `ntpath`,让解释器在 `main()` 之前就崩。属于另一个会话留下的污染,已绕开(在 `~/probe-clean` 下运行),**未删除他人文件**。box 1 上另有一个 4 天前的孤儿监视循环(PID 16978,每 20s 轮询一个已死的 run),同样未动。

## 五、两个 pre-flight 途中查明的疑点(都不是缺陷,但都会让人走弯路)

### (1) `linux-server/*.linux.py` 是**过期快照**,不需要在任何 Linux 机上套用

三个变体文件与主线各差 29 / 351 / 176 行,读起来像「主线版本不得覆盖」的那条纪律的对象。**但方向是反的:主线是超集。**

主线已有:
- `worker_client._wsl_hop_needed()` —— **按 orchestrator 自己的 OS** 决定要不要跨进 WSL(不是按 config,也不是探测 `wsl.exe` 是否存在:一台原生 Linux 机即使 PATH 上有 `wsl.exe` 也必须走原生路径);
- `runtime._shell_for_opencode()` —— Windows 上 opencode 是 `.cmd` shim 必须走 shell,**POSIX 上传 `shell=True` 反而是 bug**(list argv 会让 `--hostname`/`--port` 被静默丢弃);
- 变体里没有的额外错误处理。

**实证**:A800 上三个文件**都是主线版本、工作区干净**,而它已经跑通标定、真实 agent 调用与 668 项测试。

**结论**:Linux 修复早已折进主线,`linux-server/` 下是当时的快照。**box 1 / box 2 都不需要套用。** 那条「有变体的文件主线版本不得覆盖」的纪律仍然成立 —— 它防的是**反向**覆盖(用主线覆盖某台机器上的本地改动),而不是要求把这些快照装回去。

### (2) 一次我自己造成的假 "PULL OK"

box 2 的 GitHub 访问在这段时间反复超时(`GnuTLS recv error -110`、`Failed to connect ... after 130385 ms`)。我先 scp 了配置文件,随后监视器的完成条件写成「配置文件存在」⇒ 它立刻报 `PULL OK`,**而 commit 仍是 `669aebe`**。

**这是一个自证条件**:文件之所以存在是因为我放的,不是因为 pull 成功了。**判据必须验证被声称的那件事**(此处应查 commit),而不是查一个我自己刚满足过的副作用。记在此处是因为它与本项目「探针只会返回好消息」那一族同形。

**处置**:box 2 的两份配置与两个脚本经 scp 落地(**只新增文件,未覆盖任何东西** —— `git status` 显示四个 `??`),GitHub 恢复后再补 pull。

## 六、标定门:先判 NO-GO,查明成因后用「共用一份标定」消除,而不是放宽容差

**这是 §四 那个残余风险的实际处置,全过程留档。**

### (1) 门的判决:NO-GO,只差一个量

两台机各自标定后运行 `scripts/compare_calibrations.py`(容差 = L3:43 噪声底 2.35%):

| 类别 | 结果 |
|---|---|
| 硬件身份(device/cap/SM/L2) | ✅ **完全相同** |
| 十个实测屋顶 | ✅ 全部 ≤ **1.87%**(DRAM 0.04%、fp16 0.05%、fp32 0.39%、tf32 0.92%) |
| `dram_saturated_frac` / `compute_saturated_frac` / `launch_bound_cpu_ratio` | ✅ 0.47% / 2.17% / 2.20% |
| **`idle_frac`** | ❌ **2.51% > 2.35%** ⇒ **NO-GO** |

**我没有直接放宽容差,也没有直接放弃并行。** 先查这个阈值管什么。

### (2) 它管什么:`latency_bound` 与 `mixed` 的分界

`bottleneck.py:679` 用 `frac_bw < idle_frac and frac_fl < idle_frac` 判 `latency_bound`。

**而 `frac_bw` / `frac_fl` 正是已被查明为「1/延迟」的那两个量**(分子是任务级常数)。所以这个阈值坐在本项目已经折价过的那条轴上 —— **但它确实会翻转判决**,而处理臂正是读判决的那一臂,所以不能就此放过。

### (3) 实测影响:**在现有全部语料上为 0**

```
分类判决(两个 fraction 都在)  : 68
两台机 idle_frac 会给出不同判决 : 0
   max(frac_bw, frac_fl) 从未落入 [0.1628, 0.1670)
```

跨九个 run(box 1 五个 + box 2 四个)的 68 份判决,**没有一份会因这个差异而不同**。

**但「在历史数据上无害」不等于「安全」** —— 下一个 run 的候选是新的。所以不采纳「差异可忽略」这个理由。

### (4) 处置:两臂**共用同一份标定**,让分母从「接近」变成「相同」

`load_cached` 的复用判据是**身份字符串**,而两台机的身份**逐字节相同**:

```
box1  NVIDIA GeForce RTX 4090|8.9|128|2.13.0+cu129|12.9|3.7.1
box2  NVIDIA GeForce RTX 4090|8.9|128|2.13.0+cu129|12.9|3.7.1   ← 完全一致
a800  NVIDIA A800 80GB PCIe|8.0|108|2.8.0+cu128|12.8|3.4.0
```

**注意 `driver_version` 记的是 CUDA 运行时(12.9)而不是内核驱动**,所以 580.105 vs 580.142 的差别不进身份 —— 而这一点是**查出来的,不是假定的**:那两个内核驱动版本号不同,但资源图摘要逐字节相同,说明编译侧确实无差异。

**已实测该共用被接受**:box 2 加载 box 1 的文件,`measured_at` 显示 box 1 的时间戳(证明用的是共享文件而非静默重测),而 box 2 **为自己算出的身份与文件里的身份一致**,`load_cached(path, identity)` 返回非 None。

共用后门判 **GO**,全部量 0.00%。

**box 2 自己的测量保留为 `calibration.box2-own.json.bak`** —— 差异是**记录下来的事实**,不是被擦掉的。这两份文件本身就是「同一款卡两次独立标定的散布」这一事实的证据。

### (5) 这个做法的代价,必须写明

**共用标定意味着 box 2 的屋顶用的是 box 1 的实测值。** 若两台 4090 之间存在真实的持续性能差异(散热、功耗墙、显存颗粒),box 2 的百分比读数会有系统性偏移。

**为什么仍然可接受**:
- 十个屋顶的实测差异全部 ≤1.87%,而**任务噪声底是 2.35%** ⇒ 真实差异本就在噪声底以内;
- 对照实验要的是**两臂分母相同**,而不是每臂分母各自最准。J2-5 问「终局是否变差」,分母只要一致就不会污染这个比较;
- **绝对性能仍由 `final_reeval_ms` 判定,那是墙钟实测,与标定无关。**

**不适用的场合**:任何要报告「box 2 达到其屋顶百分之几」的绝对结论 —— 那必须用 `calibration.box2-own.json.bak`。

## 七、启动前最后一个被抓到的问题:**驱动解释器与 worker 解释器不是同一个**

**这个问题只在启动命令这一层显形,而它会让整对 run 在第一秒就死。**

`wsl.venv` 只跑 **GPU worker**(每次评测、每次计时、每次标定测量);**orchestrator 跑在启动 CLI 的那个解释器里**。两者在 box 2 上**必须不同**:

| | 驱动(orchestrator) | worker(`wsl.venv`) |
|---|---|---|
| **box 1** | `orch-venv` | `orch-venv` —— **同一个** |
| **box 2** | `orch-venv`(有 optuna) | **`kernel-opt-venv`** —— 匹配的工具链 |

**box 2 的匹配 venv 没有 optuna**,`from kernel_optimizer.control.orchestrator import Orchestrator` 在那里直接 `ModuleNotFoundError`。所以 box 2 的启动命令必须用 `orch-venv` 当驱动。

**这也纠正了我先前一处不严谨的报告**:我说过 box 2「681 passed」—— 那是 `orch-venv`(torch 2.14 / triton 3.8)跑的,**不是**这一对要用的那个 venv。`kernel-opt-venv` 里没有 pytest,所以那个数字并不能说明匹配 venv 可用。

**为什么这不影响配对的有效性**:驱动的 torch/triton **不参与任何测量** —— 它既不编译也不计时候选。真正决定测量的是 `wsl.venv`,而 box 2 已经产出的那份标定**正是经 `kernel-opt-venv` 测的**,这也是它的屋顶与 box 1 相差 ≤1.87% 的原因。已实测:两台机各自的「驱动 + worker」组合都能导入 orchestrator 并加载正确的开关。

**两份配置里都写明了各自的启动命令,并互相点名对方是反的** —— 因为两台机 venv 名字相反,复制启动命令是这一对最容易犯的错。
