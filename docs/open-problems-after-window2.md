# 第一梯队:C2 引导端的三个断点(P1 / P7 / P8)

这三条是**同一个断点的三个切面**,必须一起改、一起测,否则改了一条另两条会把效果吃掉。

## P1 · 简报到改写之间隔着一个不受约束的 LLM

### 问题是什么

条件简报建好之后走两条路(`orchestrator.py:2039-2049`、`:3210`):

```
2039  conditioned_text = self._conditional_brief(crun)
2049  digest_text = f"{digest_text}\n\n{wall_text}"     → analyst 的 prompt
3210  wall_text=parent_crun.wall_text                    → rewriter 的 sandbox
```

`modules.py:1188` 把它写成 `analysis/resource_walls.md`。同一个沙箱里还有:
`candidate/best.py`、`analysis/bottleneck.json`、`history/prediction_ledger.md`(或
`failed_hypotheses.json`)、`docs/candidate_contract.md`、`docs/triton_pitfalls.md`、
`docs/device.md`、`task/eval_semantics.md` —— **简报是第 8 个平权文件**。

prompt(`modules.py:1198-1215`)确实点名了它,并说"where it disagrees with
`analysis/bottleneck.json`, it is the one to trust"。但这是**措辞层面的优先级**,不是机制:

- 框架**不检查**改写是否使用了简报;
- **不重试**没用简报的改写;
- **不拒绝**任何改写。

### 实测后果

| 档 | m1-b (L3:43) | m2b-b (L3:21) | 窗口 1 pilot |
|---|---|---|---|
| ① 简报交付 | 13 | 9 | 12 / 11 |
| ④ 改写**点名**该轴 | **1/5** | **1/4** | **0** / **0** |

⇒ 通路存在且被走通,但**内容基本没进改写正文**。第四档在窗口 1 两个 pilot 上都读 0,窗口 2 才
第一次非零,而分母是 5 和 4。

### 怎么解决

三个层次,从低风险到高风险:

**(a) 只加测量,不改行为(零风险)。** 在 `REWRITE_PRODUCED` 里记录简报的哪些轴出现在改写的
`change_summary` / `expectations` 里 —— 现在这件事只能靠事后跑 `v41_axis_uptake.py` 从文本
grep,而 grep 漏掉措辞与"agent 没做"在输出上不可区分(这是已记录的探针陷阱)。落盘一个结构化
字段,让第四档不再依赖正则。

**(b) 让简报进 analyst 的假设生成(中高风险)。** 见 P7 —— 简报现在**已经**进 analyst 的
`digest_text`(`:2049`),但 analyst 的 prompt 从未说明"方向该怎么用",所以它写出的假设不指向
简报的轴。改 analyst prompt 让它必须为每道 gate-passing 墙产出**至少一条**假设。

**(c) 让 rewriter 的输出被校验(高风险)。** 见 P8。

### 收益

- C2 的第三个动词("引导")从**不保证**变成**可验证**。当前如果审稿人问"你的机制如何保证简报被
  使用",诚实答案是"不保证" —— 这必须自己先写清楚而不是被问出来。
- 第四档若从 1/5 提到 3/5 以上,②→③→④→⑤ 的归因链才第一次完整。

### 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| **历史结果不可比** | 改 prompt 后窗口 1/2 的四个 run 与新 run 不在同一 prompt 版本上 ⇒ 不能并表 | 改动必须落在一个**新的对照对**里,旧数据只作历史;绝不追溯解释 |
| **过度约束会造出假阳性** | 强制 agent 提到某个轴,它会为了满足格式而提到,而不是因为真的用了 ⇒ ④ 档变成 100% 而 ⑤ 档不动 | **必须同时读 ⑤ 档(拒绝率实测)**;④ 升 ⑤ 不升就是格式满足而非机制生效 |
| **prompt 是全局变量** | 同一份 prompt 服务全部任务,改它会改变每个族的行为,不只是被简报的族 | 用 config 开关而非直接改文字,让 off 臂保持 v3 措辞 |
| 与 B 红线无关 | 这条不动 trial 预算 | — |

## P7 · `analyst→假设` 的断点,prompt 文字是 v3 时代的

### 问题是什么

rewriter 的 prompt(`modules.py:1275`)要求每个改写针对 **bottleneck report 里的某条假设**
(`hypothesis_id` 必填)。那份 report 是 **analyst** 写的。所以:

> **简报只能经 analyst 写进假设,才能真正引导改写。**

而 analyst 的 prompt 里,关于简报只说了它是"shared memory 挡住哪个参数",**从未说明方向
(inward/outward)该怎么用** —— 这段文字是 v3 时代写的,当时还没有方向 token。

实测(窗口 1 P1):`NUM_STAGES` / `inward` 这道墙**没有任何一条假设指向它** ⇒ 断点定位在
`analyst→假设`,不在 `简报→沙箱`。

### 怎么解决

改 analyst 的 prompt(`modules.py:1059-1088` 一带),让它:
1. 明确知道 `inward` 与 `outward` 的语义差别(v4.1 的方向 token 语义,不是 v3 的"被挡住");
2. 对每道 **gate-passing** 墙,必须产出至少一条假设并在假设里写明方向;
3. 未过门 / unresolved 的墙不得产出假设(避免它为了凑数而编)。

### 收益

这是 P1 的**上游**。不修这条,P1 的 (c) 会失效:rewriter 被强制指向假设,而假设里根本没有简报的轴。

### 风险

| 风险 | 说明 |
|---|---|
| **最高的一条** | analyst 的 prompt 是 C1 与 C2 共用的入口。改它会同时改变 C1 的资源解释行为 ⇒ 两条 contribution 的证据同时失去可比性 |
| **可能强化"基线已能做"这个威胁** | 控制臂 analyst 24 个假设里已有 4 个(17%)自己做出 C2 形状的推理。把方向教给它,可能让**控制臂**也变强(如果 off 臂共用这份 prompt),从而抹掉臂差 |
| 缓解 | 方向说明只在 `mode=active` 时注入,off 臂保持原文 ⇒ 但这会让两臂的 prompt 长度不同,须在臂对等检查里声明为已知差异 |

## P8 · `hypothesis_id` 全代码零校验

### 问题是什么

复验结果(`grep -rn hypothesis_id src/`):

| 位置 | 内容 |
|---|---|
| `models/reports.py:176` | `hypothesis_id: str = ""` —— 默认空串 |
| `agents/modules.py:1332` | 注释原文:"narration the pipeline does not gate on" |
| `agents/modules.py:1361` | rescue 路径直接填 `hypothesis_id=""` |
| `control/orchestrator.py:2771/2781` | 读取时 `ev.payload.get("hypothesis_id") or ""` |
| `control/orchestrator.py:484` | 注释承认:"both candidates of a round carried `hypothesis_id: ""`。Then nothing is filtered" |

⇒ **prompt 要求它必填,框架从不检查它是否指向一条真实存在的假设。** 空串合法,指向不存在的
`H9` 也合法。

### 怎么解决

在 `RewriteResult` 的校验里(`modules.py` 的 `validate` 一带)加一条:`hypothesis_id` 必须
命中 `crun.report.hypotheses` 里的某个 id,否则走已有的"带错误反馈重试"路径(≤2 次)。

**必须同时保留 rescue 路径的豁免**:`:1361` 的空串是**故意**的,它标记"这个候选是从沙箱救回的、
agent 的叙述随连接一起丢了"。把 rescue 也一起卡住会让超时的改写直接被丢弃 —— 那是已记录过的
`false-converged` 事故成因(超时丢改写 ⇒ 判 converged 但从未评测)。

### 收益

让"每个改写针对一条具体假设"从**叙述**变成**约束**。这直接影响 P1 的 ⑤ 档能否归因:现在
`hypothesis_id` 不可信,所以"改写针对的是哪条假设"只能靠读文本推测。

### 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 增加改写失败率 | 多一道校验就多一次重试机会被消耗,而 agent 调用占 66–70% 的 elapsed | 重试上限已是 2;先在 smoke 上量失败率 |
| **rescue 豁免写错会造成静默丢弃** | 若把 rescue 也卡住,超时的改写会被丢,族记录 0 改善后被判 converged | 单测必须覆盖"rescue 的空串仍被接受" |
| 历史不可比 | 同 P1 | 落在新对照对里 |

# 第二梯队:C2 的机制上限(P2 / P4)

这两条不是 bug,是**当前设计的天花板**。

## P2 · 斜率进不了采样器的决策,只能塞一个点

### 问题是什么

`tuning/tpe.py:160` `enqueue()` 与 `:191` `enqueue_fresh()` 是 C2 对采样器的**唯一**接口 ——
往 Optuna 的队列里塞一个具体配置。

**TPE 本身没有任何位置能挂斜率**:它只做"高性能优先",不表达方向,也没有"未知方向的方差项"
可以挂。所以 C2 对采样的影响力上限就是"塞几个点"。

而能塞几个点由剂量决定:`f=0.125 ⇒ Q=5`,其中 **C4 源块占 4 个,E 动作只剩 1 个**。

### 实测后果

| 项 | m1-b | m2b-b |
|---|---|---|
| E 准入 | 2 | 2 |
| E 决策(20/21 个空间快照求和) | 79 | 79 |
| **同层竞争 ≥2** | **0** | **0** |
| RR vs gain 判决不同 | 0 | 0 |

**同层竞争恒为 0** ⇒ 一个空间最多 1 个 E 对比,**结构上不可能**产生"哪个方向更值得"的排序。
这不是负结果,是剂量的结构后果 —— 门 2 因此只能选 M2b(复制对),排序价值在此样本量下不可辨识。

### 怎么解决

三条路,**都有代价**:

| 路 | 做法 | 代价 |
|---|---|---|
| **A. 提高剂量** | f ≥ 0.225 ⇒ Q ≥ 9,能容纳 ≥2 个 E 对比 | **与 B=40 不变红线冲突** —— 9/40 = 22.5% 的 trial 变成扫描槽。用户已否决"为控成本收紧搜索空间",这是反方向但同性质的改动 |
| **B. 把斜率接进采样器** | 让条件化斜率影响 TPE 的候选生成(而非只塞点) | 需要改 sampler。已记录的调研结论是 TPE 表达不了斜率;要换采样器则整个 B 循环的历史结果不可比 |
| **C. 降低 C4 的槽位消耗** | C4 现在吃 4 个槽(发现对 2 + 验证对 2)。若发现对与验证对能共享端点,可降到 3 | 会破坏 P2′ 的留出独立性 —— 那正是 P2′ 唯一可守的地方,**不可动** |

**我的建议是暂时不动,并在论文里把"排序价值不可辨识"写成剂量的已知限制**,而不是当成待修缺陷。
理由:C 直接损害唯一的正结果;A 撞红线;B 让全部历史不可比,而 P2′ 的 4 个 run 复现是目前最贵的资产。

### 收益(若做 A)

同层竞争 > 0 ⇒ 第一次能测"斜率能否给出正确的**方向排序**",这是 C2 声称的核心能力之一,目前
**从未被测过**。

### 风险

| 风险 | 说明 |
|---|---|
| **红线** | B=40 是用户明确的不变量。动它需要显式裁决 |
| 成本 | 22.5% 的 trial 变扫描 ⇒ 同墙钟下有效搜索少约 1/5,端到端延迟大概率进一步变差,而它已经在两个任务上更慢了 |
| 可能仍读 0 | Q=9 只保证"能容纳",不保证 planner 真的会在同一空间发现 ≥2 个有效轴 |

## P4 · C2 只覆盖 8 个资源维度里的 1 个

### 问题是什么

八个资源维度里,**只有 `shared_bytes` 有拒绝判据** ⇒ 只有它能产生"硬墙"(编译器拒绝 = 客观事实)。
其余维度(`n_regs`、`n_spills`、`occupancy`、`peak_alloc_bytes`、`threads_launched`、
`candidate_aten_bytes`、`candidate_aten_ops`)没有"被拒绝"这个事件,所以 `find_walls` 的唯一
输入(被拒参数集)对它们不存在。

`n_spills` 有第二种判据(软墙),且**每个 trial 都测到**。但 v4.1 的 compile-only 探针在
warmup 编译时 `n_regs`/`n_spills` 恒为 `None` ⇒ **软墙在探针层拿不到**。

### 实测后果

| 项 | m1-b | m2b-b |
|---|---|---|
| 条件化墙 | `{'hard': 20}` | `{'hard': 13}` |
| **软墙** | **0** | **0** |

`soft=0` 是**结构性**的,不是这两个 run 的运气 —— A1 的输出自己就这么标注。

另外软墙有个独立缺陷:它**恒指高侧**,所以已记录的 24 道软墙里 **11 道(45.8%)** 因最优点已在
域顶而**无值可投**。读到"零投递"时必须分 `no_wall` 与 `no_value` 两个计数器,否则会把"没机会"
读成"没找到"。

### 怎么解决

1. 让探针在编译后**读 cubin 的 regs/spills**(硬墙路径已经这么做了 —— `orchestrator.py:1885`
   的 `screen_cache_entry` 拿 `max_shared`),把同一条路扩展到 spills;
2. 软墙的适用门是"最优 trial 自己要 spill",实测 79 个空间里只有 30 个(38.0%)满足 ⇒
   **预算不能按空间数线性外推**;
3. 投递前分流 `no_wall` / `no_value`。

### 收益

墙的产出量约翻倍(38% 的空间多一类墙),可归因面从 1 个维度扩到 2 个。这也是回应
"C2 只对 shared memory 有效"这个必然会被问到的问题。

### 风险

| 风险 | 说明 |
|---|---|
| 探针成本上升 | 现在探针只花 run 的 0.067%,读 cubin 会更贵;但仍远低于 trial |
| **软墙没有投递路径** | 已记录:软墙**只落盘、无投递路径**,`applicable` 才是判决。所以光让探针能读到还不够,得同时接上投递 ⇒ 改动面比看起来大 |
| 两种墙同名 | 硬墙与软墙都写进 `resource_walls.md` ⇒ 必须读内容不能数文件名。加软墙会让这个混淆变严重 |

# 第三梯队:实验形态与判读(P3 / P5 / P6)

## P3 · 12h 只买到 1 代改写

### 问题是什么

`_rewrite_round`(`orchestrator.py:2871`)每轮**遍历全部活跃族**,每族每轮消耗一次
`rewrite_rounds_used`。所以第 1 轮 = 4 个族各得第 **1 代**;第 2 代要等第 2 轮。而族边界的墙钟
检查(`:2892`)在第 2 轮的第 1–2 个族处就 `break`。

**4/4 个 run 一致**(n1-a/n1-b/pilot-p1/pilot-p2 的 round1 完成族数 3/3/3/3、round2 完成
1/1/1/0),窗口 2 的 m1/m2b 同形状(8/8 族各只有 1 条 `FAMILY_ROUND_RECORDED`)。

三个连带的判读陷阱(全部已复验):
1. `FAMILY_ROUND_RECORDED.round=2` 是**轮次位次不是血缘深度** —— 所有改写的父代都是种子(g1);
2. `latency_gain_pct` 是**相对种子的累计增益**,不是逐轮增量;
3. 每族只有 1 条记录 ⇒ **一个点,不是曲线**。

⇒ **"收敛速度更快"这个主张,在当前配置下根本无法测量。**

### 怎么解决

减族换深度:`max_seed_candidates: 2` / `max_families_active: 2` / **Loop D 关**。同墙钟下每族
能排到第 2、3 轮。用户已接受 (a) 放弃 Loop D 与 (b) 最终延迟可能更差。

⚠ `config.py` 的注释明确写着 `max_families_active: 3` 的**设计意图是相反的**:"more families
reach a first round before the clock stops, each getting fewer rounds"。所以这是一次有意的
设计意图反转,不是修 bug。

### 收益

- 第一次可能拿到**每族 ≥2 轮**的曲线 ⇒ 收敛速度可测;
- 引导端有了**迭代机会**:第 1 代的结果能反馈进第 2 代的简报,而这正是 C2 声称的过程,目前只
  执行了第一步。

### 风险

| 风险 | 说明 |
|---|---|
| **最终延迟大概率更差** | 族数减半 ⇒ 覆盖的结构多样性减半。已记录:L3:21 的赢家族种子是四个里**最差**的(20.4 垫底),任何早停/减族都会先杀掉它 |
| Loop D 证据归零 | D 刚刚才首次跑通 |
| 仍可能只有 1 代 | 2 族 × 1.48h/族-轮,若 agent 调用变慢仍可能排不到第 3 轮 |

## P5 · A1-3 / A1-5 无合格 tie 带 ⇒ **需用户裁决**

### 问题是什么

`a1_pair_comparability.py --final` 现在**故意拒绝给判决**,因为没有合格的同代码 A/A 标定。
四把候选尺子,每把都有问题:

| 尺子 | 值 | 问题 |
|---|---|---|
| 原 13 对 "A/A" | median 1.03% / p90 2.50% / max 5.33% | **0/13 跑了同代码** —— 配对键只固定种子 sha + 旋钮,parameterizer 是 LLM 调用 ⇒ 两臂程序差 2–22 行。且 4 对两侧都带 reuse 标记,最大的 5.33% 与第二大的 2.69% 都来自这些对。**是混合量,不是噪声上界** |
| 新协议 n=9 | median 1.0311% / nearest-rank p90 = observed max 2.5005% | 排除标记 reuse、按注册 source + backend + typed params 匹配。**但注册 SHA 不是物化产物证明** |
| 10.85% | — | **已证伪** —— 是搜索轨迹差(两臂最优配置差 11 个 knob 含 bf16 vs tf32),不是测量噪声 |
| 真同代码 A/A | 3 例(0.06%),离散度 0.0618/0.0390/0.0674% | n=3,且三组未标 reuse 的记录全在一个臂、分属三个候选、跨 40× 延迟范围 |

⇒ 投递点(A1-3)与端到端(A1-5)的"赢/输/平"目前**无法判决**。历史上我用 4% 判过 tie,而同时
论证 4% 不合法(该自相矛盾成立);改用 10.85% 也是错的。

### 怎么解决(三个选项,请你裁决)

| 选项 | 内容 | 后果 |
|---|---|---|
| **A** | 沿用原 4% 作**历史描述**,5.33% 作事后敏感性对照 | 两者**同判决**(投递点 4 输 2 平)⇒ 结论对阈值不敏感,这是能说的最强话。但 4% 的正当性仍待补 |
| **B** | 花一次专门的同代码 A/A 标定:固定 artifact + 固定上下文重放 N 次 | 需 GPU 机时(估 2–4h),换来第一把**合格**的尺子。现有日志不足以完成该校准 |
| **C** | 不设 tie 带,永久以描述性方式报告差值 | 最保守,但审稿人会问"这个 5.12% 算不算显著" |

我的建议是 **A + 在下一轮实验里附带做 B**(同一 run 里插入 N 次同 artifact 重放,边际成本低)。

### 收益

有了合格 tie 带,A1-5 的 +5.12% / +14.48% 才能从"描述"变成"判决",P3 也才有资格降级/保留。

### 风险

| 风险 | 说明 |
|---|---|
| B 的标定只对**那个目标 × 那个场地**有效 | v5 的正确要求是"每个目标 × 每个场地都要有自己的同配置 A/A 标定,4% 不能默认外推" |
| 标定值可能比 4% 大 | 若真噪声底 > 5.12%,则 m1 对的结论从"active 更慢"变成"不可分" —— 这对我们**有利**,所以更要先定尺子再看数,不能反过来 |

## P6 · 收敛速度指标未预注册 ⇒ **需用户裁决,且必须在 run 前**

### 问题是什么

即便 P3 拿到第 2 代,`latency_gain_pct` **也不能直接用**:

- 它是**相对种子的累计值**,不是逐轮增量;
- 它与**起点强相关**:7.0635ms 起步降 53.83% vs 3.0003ms 起步降 1.76% ⇒ 跨族比较测的是**种子
  质量差异**,不是改写效率。

### 怎么解决

预注册一个**归一化**指标。候选:

```
剩余距离比:  ratio_k = (best_k − best_final) / (best_seed − best_final)
```

`ratio_k` 从 1 单调降到 0,与起点无关。收敛速度 = 达到某个 `ratio` 阈值所需的轮次或 GPU 墙钟。

⚠ 它测的是 **H2c(rewriter 的结构收益)**,**不是 C2 的预测精度**。两者不可混谈。

### 收益

P3 的实验才有主终点。没有预注册的指标,跑完之后无论什么结果都可以被解释成想要的方向 —— 这正是
预注册要防的。

### 风险

| 风险 | 说明 |
|---|---|
| `best_final` 是**事后**量 | 用最终值做分母,意味着指标只能在 run 结束后计算,不能在线判读。这是可接受的(A1 本来就是 post-run),但要写明 |
| 两臂的 `best_final` 不同 | 分母不同 ⇒ 严格说两臂的 `ratio_k` 不在同一尺度。可能需要用**两臂共同的**最优作分母,或者报告两种算法 |
| 你已明确说"暂时不用"写预注册文本 | 所以这条是**待办**,但 P3 的 run **不能在它之前启动** |

# 第四梯队:读数器与生产侧定义(P9–P12)

## P9 · 第三个 wall origin 会静默覆盖 second_origin —— **已修,但机制值得记住**

复验 `orchestrator.py:1885-1905`:现在 `origin_verdicts[oname]` / `origin_max_shared[oname]`
**先写、无条件写**,下面的分支只把两个 entry 镜像到旧的标量字段。注释自己写明修复前的形状:

> "Before this, a third origin overwrote the second's verdict in the single `second_origin`
> field -- silently, with a plausible value and a normal event log, which is the failure shape
> this project has recorded as the dangerous one."

**残留风险**:`second_origin` / `second_origin_max_shared` 两个标量仍在,注释说是
"Replay compatibility, not a second source of truth"。任何新读数器若读这两个字段而不读
`origin_verdicts`,会在 K > 2 时读到不完整的图景。

**解决**:在读数器侧统一改读 dict;标量字段加 deprecation 注释。**收益**低但**风险也低**。

## P10 · N1 reader 的 last-vs-min 脆弱点

reader 用**最后一次** `TUNING_DONE` 覆盖前值,可能漏掉全局最优(如果某个空间的最优出现在
中间一次 tuning 而非最后一次)。

**在本批日志上不成立** —— 8/8 个候选 LAST == MIN,已实测。但**逻辑成立**,是待修脆弱点。
外部评审提这条时我复验后确认它在这批数据上不咬人,所以降级为待修。

**解决**:改成取 min 而非 last。**风险**:极低(纯读侧)。**收益**:防止未来某批日志上静默出错。

⚠ 8/8 只是**本批**外部报告,不证明 reader 在其他日志不存在覆盖旧最优的通用脆弱点。

## P11 · `v41_p2prime.py:43` `_typed()` 死函数 + 误导注释

复验:`grep -n "_typed"` 只有定义那一行,**零调用点**。而它的 docstring 说
"Kept for the wall-payload fallback" —— 描述了一个不存在的用途。

**解决**:删掉,或者若确实要留作 fallback 就接上调用点。**风险**:极低。**收益**:清理一处会
让下一个读代码的人相信有 fallback 而实际没有的注释。

## P12 · published `speedups` 是 3 位量化 —— **生产侧,高风险**

### 问题是什么

链条(全部复验):

```
KernelBench timing.py:614   "mean": float(f"{np.mean(elapsed_times):.3g}")   ← 源头只留 3 位
orchestrator.py:3474        speedups[kind] = round(baseline.mean / cand.mean, 4)  ← mean/mean
orchestrator.py:136-163     _honest_verdict 直接取 speedups[compile_key]
```

实测:n1-b(median 2.537472、tf32 baseline 10.948608)与 m1-a(2.539456、10.948544)**publish
出完全相同的 4.3307**,因为两侧都被压成 `11.0 / 2.54`。

分辨率地板:分母 ulp `0.01/2.54 = 0.39%` + 分子 ulp `0.1/11.0 = 0.91%` ⇒ **≈1.3%**。
而 m1 对的真实臂差是 **0.08%**,低一个数量级。

### 怎么解决

**探针侧已修**(`a1_pair_comparability.py --final` 现在两个约定并排、各带臂差、撞值时报警)。
**生产侧未动**,三个选项:

| 选项 | 内容 | 后果 |
|---|---|---|
| A | 不动 published 数字,只在论文里用 `final_reeval_median_ms` 与 `speedups_median` | 零风险。已发表的加速比不变 |
| B | 让 `speedups` 改用未量化的 mean | **每个已发表加速比都会变动** —— 这正是 `speedups_median` 那段注释警告的"每个 published speedup 上升而没有任何 kernel 变快" |
| C | 修 KernelBench 的 `.3g` | 改外部依赖,且 KernelBench 是 pin 在 `423217d` 的 |

**建议 A。** 理由:B 的代价是所有历史数字重算,而收益只是让一个我们已经决定不用作差的字段变准。

### 风险(若选 B)

| 风险 | 说明 |
|---|---|
| **每个已发表加速比变动** | 3.647x / 3.80x / 4.3307x / 9.29x 全部要重算,而它们已进入多份文档 |
| 方向不确定 | 量化可能高估也可能低估,不是单向的 |
