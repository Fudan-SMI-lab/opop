# `split3` 的首次生产测量:1 胜 3 负,而这正好验证了"做成 knob 而非建议"

**日期** 2026-09-11 · box2 处理臂 `run-l3-43-20260911-052630`(115 trial)+ box1 对照 `run-l3-43-20260911-053020`(40 trial)· 脚本 `scripts/audit_split3_payoff.py`

低精度契约改动把补偿 dot 作为 `DOT_MODE: ["plain","split3"]` 引入。语料侧的对照是硬的:**0 / 48 个改动前候选含任何形式的补偿 dot**(五种独立搜法)。所以这是它第一次被真实测量。

## 逐精度同类比较(box2)

只在**同一 `COMPUTE_DTYPE` 内**比,避免拿 split3@bf16 去比 plain@fp16。

| `COMPUTE_DTYPE` | plain | split3 | 比值 |
|---|---|---|---|
| bf16 | 3.2128 ms | 4.3633 ms | 1.36× |
| fp16 | 3.3905 ms | 4.3197 ms | 1.27× |
| **ieee** | 13.8588 ms | **12.6490 ms** | **0.91×(split3 胜)** |
| tf32 | 6.2695 ms | 21.7083 ms | 3.46× |

**1 胜 3 负。** box1 只有 fp16 一对可比,+28.27%,与 box2 的 +27.41% 一致(两台机器上同一现象)。

## 三个比值各自说明什么

`split3` 发 3 次 MMA 换 1 次,所以纯 MMA 受限的 kernel 应当读出约 **3.00×**。

- **bf16 1.36× / fp16 1.27×** —— 远低于 3×,说明这些配置**不是 MMA 受限**,多出的 MMA 被部分掩盖。仍然是净损失,但幅度不大。
- **ieee 0.91×** —— split3 **更快**。ieee 没有张量核通路,`plain` 走的是慢的标量回退,而 split3 的 fp16 操作数**能进张量核**。这是"3 次便宜 MMA 打赢 1 次昂贵非 MMA dot"的唯一情形。
- **tf32 3.46×** —— **比 3× 的 MMA 下界还差**,说明有 MMA 数量之外的开销(tf32 下 split3 要逐 tile 计算 fp32 残差再拆分)。

## 结论:knob 的判断被数据支持

- 一个**推荐** split3 的契约会让 bf16/fp16 慢 27–36%、tf32 慢 3.5×。
- 一个**不提供** split3 的契约会丢掉 ieee 那一档 8.7% 的改善。
- **只有一个被实测的 knob 同时拿对这两件事。**

这也是当初把它写成 `"DOT_MODE": "plain"  # ["plain","split3"] -- arithmetic only, NOT a code path` 而不是"总是用三项分裂"的理由,现在有了生产数据。

## 附:预筛没有把 split3 排除出搜索

曾怀疑 `CONFIG_SCREENED_INFEASIBLE`(box2 28 次、box1 8 次)在系统性删掉 split3 —— 它确实会让操作数 tile 翻倍。实测不是:

| | plain 被筛比例 | split3 被筛比例 | split3 完成的 trial |
|---|---|---|---|
| box1 | 16% | 38% | 5 |
| box2 | 20% | 38% | 16 |

38% vs 16–20% 正是 tile 翻倍应有的差别,且**两台机器完全一致**。split3 有 5 和 16 个完成态 trial,**确实在被测量**,不存在"tuner 报告一个它从未测过的取值"这个缺陷。
