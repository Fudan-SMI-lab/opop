# 正对照结果:判据误判 2/5,且 dram/compute 两个"维度"其实就是 1/延迟

**状态**:2026-09-10。工具 `scripts/probe_binding_criterion_control.py`,box 1(RTX 4090)。**这份结果推翻了我在 `result-a1-no-ranking-rule-...md` §四 给出的机制解释。**

---

## 一、为什么要做这个对照

A-1 的实测发现是:14 次超噪声底的成功改写里,**8 次没缓解任何"绑定"维度**,其中 6 次反而把某维朝墙推。我把它读成"**赢的动作是填有余量的资源**"。

**但这个解释有一个前提:我用利用率判定的"绑定 / 有余量"标签是对的。** 而 Balakrishnan & Cheng(*IJPR* 38(6), 2000,已复核全文)的算例正好说明利用率不是好判据 —— 那里**利用率不满的资源 B 影子价格 $1.8,而被选中的资源 A 只有 $0.6**。

**于是同一批数据有两种读法,而它们用历史数据分不开**(因为我的"绑定"标签本身就是利用率):

| 读法 | 说的是什么 |
|---|---|
| A(我先前写的) | 改写把**真正有余量**的资源用起来了 → "填空隙"是新机制 |
| B(文献支持的) | 我标成"有余量"的维度**本来就是真约束**,改写是在正确地缓解它 → 没有新机制,只是我的判据不可靠 |

**唯一能分开的办法是造几个"我们按构造就知道答案"的 kernel。** 这份文档是那个实验。

---

## 二、五个 kernel 与结果

每个 kernel 都按构造让**一个**维度成为限制。天花板在同一台机器上现测(DRAM 915.3 GB/s、fp32 ieee 54.1 TFLOP/s)。压强归一到 `1.0 = 贴着墙`,占用率反向。

| kernel | 构造意图 | ms | regs | occ | dram | compute | occ压 | shared | regs压 | 判据说 |
|---|---|---|---|---|---|---|---|---|---|---|
| A stream | DRAM 受限 | 0.587 | 18 | 1.00 | **1.00** | 0.00 | 0.00 | 0.00 | 0.07 | ✅ dram |
| B occupancy | 占用率受限 | 0.035 | 52 | 0.81 | **1.05** | 0.27 | 0.19 | 0.04 | 0.20 | ❌ **说 dram** |
| C compute | 算力受限 | 0.017 | 22 | 1.00 | 0.55 | **1.14** | 0.00 | 0.00 | 0.09 | ✅ compute |
| D shared | shared 容量受限 | 3.694 | 64 | 0.67 | 0.08 | 0.01 | 0.33 | **0.65** | 0.25 | ✅ shared |
| **E stream-in-L2** | **不该是 DRAM 受限** | 0.013 | 18 | 1.00 | **2.87** | 0.01 | 0.00 | 0.00 | 0.07 | ❌ **说 dram 287%** |

**5 个里判对 3 个。**

## 三、根因:判据分不清 L2 命中的流量与 DRAM 流量

**E 是"对照的对照"** —— 它和 A 是**同一个 kernel**,只是数据量缩小到能装进 4090 的 72 MiB L2。它的流量由缓存供给,**按构造就不是 DRAM 受限**。

**它读出 DRAM 屋顶的 287%。** 一个物理上不可能的数字。

**根因**:我们的 DRAM 压强 = `字节数 / 时间 / DRAM屋顶`,而"字节数"是**逻辑访问量**,不是**实际到 DRAM 的字节数**。L2 命中时,逻辑字节照算,时间却短得多 → 压强虚高,可以任意超过 1.0。

**这同时解释了 B 为什么被误判**:B 的数据也在 L2 里(我为了让它不是带宽受限才这么设计),于是它同样读出虚高的 dram 1.05,把真正的信号(占用率 0.81)压了下去。**B 的误判和 E 是同一个缺陷的两个表现。**

**顺带,C 读出 114% 也是同一族问题的另一面**(算力侧):我的 flop 计数把一次 fma 当两个 flop,而分母是用 `torch.mm` 测的、以 fma 为单位。>105% 这条 sanity 检查把三处都抓出来了。

---

## 四、结论:两个,方向相反

### (1) A-1 的机制解释不成立 —— 收回"填空隙"

**判据在已知答案的 case 上误判了 2/5,所以它在历史数据上打的"绑定 / 有余量"标签不可信。** 于是 §二 的读法 A 失去支撑,**读法 B 更可能是对的**:我标成"有余量"的维度里,至少有一部分本来就是真约束(尤其凡是数据能进 L2 的候选,其 dram 压强都被虚高地读成"绑定",而真正的约束被压下去)。

**必须收回的说法**:"赢的改写在填有余量的资源"。**这句话现在没有证据支持。**

**仍然站得住的说法**(它们不依赖标签的正确性):
- **没有排序规则打得过对照**(R1 7.1% vs 最好对照 21.4%)—— 这条只依赖"规则和对照用同一套标签",标签错也不影响相对比较;
- **不要按利用率排序** —— 现在有了**两条独立依据**:文献的影子价格算例,以及本次实测(利用率判据本身会误判);
- **S2 要并列输出多类维度而不是选一个头条** —— 单标签强迫做没依据的选择,这一点不变。

### (2) 但这个对照发现了一个具体可修的度量缺陷 —— **而它今天还没伤到我们**

**`pct_of_dram_peak` 在数据能进 L2 时会虚高、可超 100%,并压掉真正的信号。** 这不是设计缺口,是**一个具体的、可修的度量缺陷**,而它就在 v2 **已上线**的判决路径里 —— `bottleneck.py:298`:

```python
achieved_tbs = byte_count / (gpu_ms * 1e-3) / 1e12
frac_bw = achieved_tbs / peaks.dram_tbs
```

**先把严重程度说准,因为我第一版写得过重了。** 我原写"小工作集的任务会中招,而我们无法事先知道哪些候选的工作集小"。**去查了 `byte_count` 到底是什么之后,这句话有两处要改**:

1. **`byte_count` 是 `compulsory_bytes`(`orchestrator.py:1421`),不是候选的逻辑访问量。** 它是**任务级**的量(不同输入+参数+输出各计一次),在参考实现上算的,**对同一任务的所有候选是同一个常数**。所以它不随候选变 —— 我说的"无法事先知道哪些候选工作集小"是错的:**它是任务的性质,而且是事先就能算的。**
2. **我们三个真实任务全都远大于 L2**(72 MiB):

   | 任务 | compulsory_bytes | 相对 L2 |
   |---|---|---|
   | L3:21 | **307.1 MiB** | 4.3× |
   | L3:43 | **397.0 MiB** | 5.5× |
   | L3:48 | 1.351 GB | 19× |

   **所以这个缺陷今天没有污染任何一份实际判决**,L3:48 那个 94.6% 是可信的。

**并且 `task_cost.py:33` 的 docstring 早就写明了这个限制**:"`reference_bytes` is materialized-tensor traffic, **not measured DRAM traffic**"。**警告一直在,只是分类器没有据此动作** —— 这是"已知的限制没有被下游执行"这一类问题,不是新发现的未知。

**所以正确的定性是**:一个**当前休眠、但会随任务变大而醒来**的缺陷。修它的理由不是救火,是**在扩大任务范围之前把门装好** —— 而我们确实计划扩大范围,届时 level1/level2 的小任务很可能落进 L2。

**可执行的修法(按代价排序)**:
1. **压强 > 1.05 时不报"绑定",报 `unknown` 并注明分母可疑。** 零新测量,一条判据。**它比既有的 clamp 处理更强**:Nsight 那条是"百分比可以超 100%,clamp 后仍可用";这里是**超限说明分子分母语义不匹配,该数不能当信号**。
2. **`compulsory_bytes` 与 L2 容量比较,作为 dram 维度 `applicable` 的前置。** 能进 L2 时 DRAM 维度**不适用**(而非"值为 0")—— 正是 `applicable` 一等字段的用途。**而且因为它是任务级常数,这个判定在 run 开始时就能做一次,零 per-trial 成本。**
3. 真正测到 DRAM 的字节数 —— 这是 B-1(候选真实流量),仍然测不到。

**第 1、2 条都便宜且泛化,已排进 S2 的硬门 J2-8。**

## 四b、追查上一节时发现了更严重的一件事:dram 与 compute 两个"维度"就是 1/延迟

**去核实 `byte_count` 是什么的时候,顺手做了一个检验,结果它比 L2 那件事严重得多。**

如果 `byte_count` 与 `flop_count` 都是**任务级常数**(而 §四(2) 已经确认它们是),那么按 `bottleneck.py:298` 的公式:

```
achieved_tbs   = byte_count / gpu_ms        →  ∝ 1 / gpu_ms
achieved_tflops = flop_count / gpu_ms       →  ∝ 1 / gpu_ms
```

**两个"维度"都只是延迟的倒数换了个刻度。** 检验方法:若如此,`gpu_ms × achieved_tbs` 必须在同一 run 内恒定。实测三个 run 的全部 66 份判决:

| run | n | `gpu_ms × achieved_tbs` 范围 | `gpu_ms × achieved_tflops` 范围 |
|---|---|---|---|
| L3:21 | 18 | 0.321637 – 0.322794(**变动 0.36%**) | 112.1106 – 112.1196(**0.008%**) |
| L3:43 r1 | 27 | 0.415764 – 0.416694(**0.22%**) | 412.3129 – 412.3239(**0.003%**) |
| L3:43 r2 | 21 | 0.416157 – 0.416452(**0.07%**) | 412.3152 – 412.3186(**0.001%**) |

**恒定到小数点后三位。确认无疑。**

### 这直接推翻了 A-1 §四 那张表的读法

那张表的核心观察是"6/8 次成功改写把 dram 或 compute **朝墙推**,同时吞吐上升"。而现在:

> **改写变快 ⇒ gpu_ms 下降 ⇒ dram 与 compute 压强必然上升。这是恒等式,不是发现。**

**所以"朝墙推"这个观察不含任何超出"它变快了"的信息。** 我把同一个量测了两次,然后把两次读数之间的一致性当成了一个机制。这比 L2 那个缺陷严重 —— L2 缺陷只影响一部分任务,**这个是恒等式,影响每一次判决**。

### 哪些维度不受影响

**关键的区分**:`occupancy`、`n_regs`、`n_spills`、`shared_bytes` 都是**编译/启动期读出来的**,与 gpu_ms **无关**。所以:

| 维度 | 是否独立于延迟 |
|---|---|
| dram_bandwidth | ❌ **就是 1/延迟** |
| compute | ❌ **就是 1/延迟** |
| occupancy | ✅ 独立(编译期读数) |
| register_pressure | ✅ 独立 |
| shared_capacity | ✅ 独立 |

**这解释了 A-1 表格里一个我当时没解释的现象**:那 8 次里 ΔP_occ 与 ΔP_reg 绝大多数是 **+0.00**,只有 dram/compute 在动。**当时我以为那是"改写没碰占用率";实际上是只有那两个随延迟自动变的量在动。**

### 这对 v3 设计的后果

1. **`pct_of_dram_peak` / `pct_of_compute_peak` 不是独立维度,是延迟的重新表述。** 它们**仍然有用** —— 与屋顶比较回答"离物理上限还有多远"(L3:48 的 94.6% 是真实且有意义的),**但它们不能作为"多维绑定"里的两个独立维度**,否则等于把延迟算两票。
2. **S2 的"多维同时绑定"统计必须重做**:先前 90%/45% 的多维绑定率里,`compute + occupancy + register_pressure` 这类组合中的 compute 是自动跟随延迟的,**不构成独立证据**。
3. **真正独立的资源维度只有编译期那几个**(occupancy / registers / shared),**而这恰好就是 S2c 局部资源地图测的那些** —— 地图直接测 Δresource,不经过"某个量 ÷ 延迟 ÷ 屋顶",**所以 S2c 不受这个缺陷影响**。这是第二次出现同一个模式:**实测的 Δ 比推导的比值稳健**。
4. **要得到真正独立的带宽维度,需要候选真实流量**(B-1),而它测不到。**在那之前,诚实的做法是把 dram/compute 标为"延迟的派生量",而不是当成两个资源维度。**

## 五、这次我自己犯的四个错(形态比结论重要)

**四个都不报错,每个都给出一张读起来合理的表。**

1. **flop 计数把 fma 当 2 个 flop** → B 的第一版读出算力屋顶的 **125%**。sanity 检查抓住了。
2. **第一版 B 做 512 fma/元素** → 它**真的**是算力受限,判据说 compute 是**对的**,是我把一个算力受限的 kernel 贴上了"占用率受限"的标签。**判据没错,我的对照错了。**
3. **第二版 B 的流量与 A 相同** → 读出 dram 1.00、耗时 0.584 ms(与 A 完全一样)。判据又是**对的**:A 已经打满带宽,B 也就是带宽受限。**教训:占用率只有在"掩盖不住延迟"时才绑定**,所以占用率对照必须同时满足流量远低于屋顶、驻留 warp 足够少、算术足够轻。
4. **我的一次编辑删掉了执行循环** → 0 个 kernel 运行,而结论块打印"在**全部 0 个** kernel 上判对了……**这支持**把 A-1 读作填空隙"。**一个空集被当成通过。** 已修:运行数少于用例数时强制报 INCONCLUSIVE 并返回 2。

**第 4 条与既有纪律 `a constant reading is a broken probe` 同族**:探针最危险的失败不是报错,是给出一个可信的、支持你已有结论的输出。**这次它甚至支持了我想要的方向**,这是我必须特别记下它的原因。

**而第 2、3 条是一个更值得记的模式**:我三次把"判据判对了"读成"判据判错了",因为我对自己构造的 kernel 的瓶颈判断是错的。**正对照的价值恰恰在这里 —— 它检验的不只是被测对象,也检验我对被测对象的理解。**
