## 零、清单的分类原则

| 类型 | 含义 | 处理方式 |
|---|---|---|
| **算错了** | 有这个量,但算法产出的数不是它声称的东西 | **必须修**,优先级最高 |
| **方向错了** | 目标函数或判据的层级关系不对 | **必须修**,优先级最高 |
| **缺失** | 这个量根本不存在 | 按成本与收益排 |
| **测不到** | 知道该测什么,但没有可行手段 | 记录 + 找替代下界/上界 |
| **未验证** | 知道怎么做,但没有证据说明有效 | 只能靠实验,不能靠设计 |

## 二、逐条

### G1 搬运开销的分子是任务级常数 —— 算错了

**症状**:`bottleneck.py:296-307` 算 `achieved_tbs = byte_count / gpu_ms`,而 `orchestrator.py:1421` 传入的 `byte_count = cost.compulsory_bytes` 是**任务级常数**。约掉之后这个量就是 `常数 / 耗时`。

**磁盘复验(5 个 run,从存盘的 `achieved_tbs × gpu_ms` 反解分子)**:

| run | `gpu_ms` 跨度 | 反解 `byte_count` 跨度 |
|---|---|---|
| L3:21 box1 | 2.8× | 0.183% |
| L3:21 box2 | **4.3×** | 0.359% |
| L3:43 r1 | **4.6×** | 0.185% |
| L3:43 r2 | 1.3× | 0.069% |
| L3:48 | 2.5× | 0.010% |

耗时变 4.6 倍而分子变 0.36%(那 0.36% 只是 4 位小数舍入)。

**根因不是 bug,是用错了地方。** `task_cost.py` docstring 明写这是刻意设计:`compulsory_bytes` 是**去重后的输入+参数+输出**,是任何正确实现的**下界**,而 `flop_count / compulsory_bytes` 回答"这个任务在这张卡上有没有可能算力受限"——**这是任何单候选测量都答不了的问题**。缺陷在于把任务级下界当候选级实测量除以耗时。

**修法(不是替换,是并存 + 分开命名)**:
- 任务级量保留,改名为 `task_floor_bytes`,只用于"任务有多少余量"这一问;
- 新增候选级量 `candidate_bytes_lower`(见 G6),用于"这个候选搬了多少";
- **`pct_of_dram_peak` 这个名字要废掉** —— 它同时暗示了"候选的""DRAM 的"两件都不成立的事。

**为什么不能直接换成候选级**:那会毁掉唯一能回答"L3:48 有 1.351 GB 固定流量、只剩 10% 空间"的那个量,而这是整个项目最硬的物理结论。

**状态**:🔧 分子已有候选级下界(G6 实测通过),命名与用途分离待实现。

### G2 算力开销的分子同上 —— 算错了

**同一个式子的另一半**:`achieved_tflops = flop_count / gpu_ms`,`flop_count` 也是任务级常数(反解跨度 ≤0.008%)。

**候选级 FLOP 能不能测?实测结论:aten 层测不到。** 用 `FlopCounterMode` 作用在候选上(box 1,L3:21):

| 候选 | FLOP | 相对参考 |
|---|---|---|
| cand-8a5dcef3(冠军,全融合 Triton) | **0** | 0.0000× |
| cand-2d4e1574(全融合 Triton) | **0** | 0.0000× |
| cand-37572704(混合,两个 1×1 交给 cuDNN) | 120,503,484,416 | **1.0748×** |

**读出 0 不是故障,是正确答案**:算术全在 Triton kernel 内部,dispatcher 看不见。而那个混合候选读出 1.07× 参考,因为它把两个卷积交回了 aten。

**所以 `FlopCounterMode` 在候选上测到的是"没融合掉的那部分"** —— 这本身是一个有用的量(它给出融合程度),但**绝不能当作候选的总 FLOP**。

**修法**:候选级 FLOP 只能靠**解析计算**(tile 形状 × grid × 每 tile 的 MAC 数),或者接受"算力维度只有任务级上界"。**倾向后者**:算力的任务级上界(`flop_count`)本来就是对的东西 —— 一个候选不可能比任务要求的算得更少(除了减少冗余计算),而它算得更多是可以从 aten 层的 0 和 sass 指令混合看出来的。

**状态**:🔧 已确定 aten 路不通并测出原因;解析路待评估。

### G3 "资源→性能"没有强制兑现 —— 方向错了

**用户原话**:"v3 里的效率不仅是指资源之间的转换效率,也指资源和性能之间的转化效率(如果单纯资源间转换而性能没有提升,那完全没有意义)"。

**这条纠正的是目标函数的层级。** 我的文档里定义了 `转化效率 = Δ耗时 / Δ资源`(这确实是资源→性能),但**另外还写了"资源之间的替代率"(用容量换流量),而那部分没有要求兑现成性能**。

**为什么严重**:一个改动可以让共享内存降 40%、寄存器降 30 个、占用率翻倍,而**耗时一点不动** —— 按"资源间替代率"记法它是成功的,实际毫无价值。而这不是假想:今天实测 **23 次超噪声底的成功改写里,11 次(约一半)没有缓解任何绑定的资源维度**,却确实变快了;反向的情形(资源改善而耗时不动)必然也存在,而框架**没有任何机制把它标出来**。

**修法(三条,改的是层级不是指标)**:
1. **唯一最终判据是耗时。** 资源分析是**手段**,不是目标。
2. **每次资源替代都必须报告兑现了多少性能**:"共享内存 +2048 字节 → 耗时 −0.3 ms(超噪声底)",或者"资源变了而耗时没动 = **本次替代无效**"。
3. **新增输出类别「资源改善但性能没动」**。这类结果现在被当中性丢掉,其实**最有信息量** —— 它直接证明那个资源不是当前瓶颈,比任何利用率标签都可靠。
4. **"资源→性能转化率"本身要被追踪**:同一维度上的历史记录("这个任务上共享内存每多用 1 KB 平均换来多少 ms")才是能引导下次改写的东西。

**状态**:✅ **已实现**(`src/kernel_optimizer/evaluation/conversion.py`,接进 `FAMILY_ROUND_RECORDED`)。

**落地形态**:每个改写轮次现在都在事件日志里记录一个 `conversion` 判决:

| 判决 | 含义 |
|---|---|
| `improved` | 耗时下降超过噪声底 —— 附带列出同时改善了哪些资源 |
| **`no_conversion`** | **某个资源实质改善了而耗时没动** ⇒ **那个资源不是当前的限制**(最有信息量的一类) |
| `regressed` | 耗时上升 —— 任何资源改善都不能抵消 |
| `flat` | 耗时和资源都没有实质变化 |
| `unknown` | 前后耗时无法比较 |

**同时报告每个维度自己的 Δ**(前值、后值、变化量、相对变化、单位、方向),**并且不做跨维度排序**(遵守 G8 的纪律)。占用率的极性单独声明(高才算好),并有专门的反验证测试 —— 把它写反不会报错,只会给出一张干净的错表。

**反向验证**(两项,都实测会失败):(a) 把占用率极性写反 ⇒ 测试捕获;(b) 让"仅资源改善"返回 `improved` ⇒ 测试捕获并打印出那条断言。

### G4 显存峰值维度缺失 —— 已实测可行

**先前状态**:全仓库零 `max_memory_allocated` / `peak_memory` 引用(已复验)。

**实测(box 1,`scripts/probe_per_candidate_cost.py`,2.2–4.3 秒/候选)**:

| 任务 | 显存峰值区间 | 跨候选跨度 |
|---|---|---|
| L3:48 | 1288 – 1424 MiB | **9.55%** |
| L3:21 | 1206 – 2055 MiB | **41.3%** |

**两个任务上冠军都是显存峰值最低的那个。** 与耗时的秩相关 Kendall **τ=+0.64**(9 一致 / 2 相反,n=11 对)。

**必须标注的局限**:`max_memory_allocated` 是**缓存分配器**视角(分配器缓存的空闲块不计),不是真实设备显存。但**"会不会 OOM"问的正是 `max_memory_reserved`**,而"候选之间谁更省"问的正是 `allocated` —— 所以两个都记录。

**状态**:✅ 探针实测通过,待接进 worker。

### G6 候选真实 DRAM 流量测不到 —— 已有下界+上界

**三条旧路仍然不通**(已在代码里逐一证实):数汇编指令是静态文本计数(K 循环 100 次的 GEMM 其读指令可能只出现 2–3 条);aten 级拦截**融合越好越低报**;现有 profile 无 grid/启动次数。硬件计数器被 `ERR_NVGPUCTRPERM` 永久封死。

**但"完全没有"过于悲观。实测拿到了两个界**:

| 记号 | 方法 | 是什么 | L3:21 跨候选跨度 |
|---|---|---|---|
| **下界** | `__torch_dispatch__` 拦截**候选** | aten 层物化流量。**对融合进 kernel 内部的搬运瞎** ⇒ 低报 | **81.9%**(990 – 5465 MiB) |
| **上界** | `task_cost.reference_bytes` | 参考物化的全部流量(含留在 L2 的中间量) ⇒ 高报 | 任务级 |
| **启动几何** | 包装 `JITFunction.run` | blocks × warps × 32。**实测 27/27 次启动的 grid 都是真元组**,拿得到 | 16.3%–75% |

`候选下界 ≤ 真实流量 ≤ 参考上界`。与耗时秩相关 **τ=+0.82**(10 一致 / 1 相反)。

**注意方向相反**:`reference_bytes` 的局限是**上界**(把 L2 里的也算上),候选 aten 流量的局限是**下界**(把融合掉的漏掉)。两个界一起用才有意义。

**状态**:🟡 有界且跨候选可比;精确值仍需 L2 建模(见 G7)。

### G7 L2 命中被算成 DRAM 流量 —— 待改

正对照实测:5 个按构造已知瓶颈的 kernel,判据**误判 2 个**;一个数据全在 L2 内的流式 kernel 读出 DRAM 屋顶的 **287%**(物理不可能)。

**今天休眠**:三个真实任务的工作集全部远超 72 MiB L2(L3:21 307 MiB / L3:43 397 MiB / L3:48 1.351 GB),所以当前零污染。**扩大任务范围(level1/2 小任务)前必须修。**

**两条修法(都便宜且泛化)**:(a) 压强 > 1.05 报 `unknown` 并注明"疑似 L2 命中" —— 超限说明**分母不适用**,比 clamp 更强;(b) 工作集 vs L2 容量作为该维度 `applicable` 的前置。

**状态**:⏳ 修法明确,待实现。

### G8 禁止跨维度比"谁变化最大" —— 已登记为纪律

23 次超噪声底成功改写上实测的**摆幅**:共享内存中位 **0.162**、寄存器中位 **0.012**、占用率中位 **0.000**。共享内存的中位摆幅是寄存器的 **13.5 倍**,纯粹因为归一化分母不同(`shared_bytes/101376` 一改 tile 就动几万字节)。

**造成的实际错误**:重新打分后"最佳对照"变成"永远挑共享内存"= 61.5%,它什么都没发现,只是叫出了摆得最宽那一维的名字。

**纪律**:禁止用跨维度 `argmax |Δ|` 做(a)打标签、(b)排序、(c)报告给 agent。**替代:每个维度只和自己的历史分布比。**

**状态**:✅ 已登记(A-3b),且 S2c 的资源地图本来就走原始量、只在同维度内比较,不受影响。

### G16 `n_spills` 与 SASS 的 STL/LDL 是两个不同的量 —— 算错了(✅ 已修)

**先前的断言**(`statics.py:13` 与 `bottleneck.py:20`):

> "spills VISIBLE as STL/LDL, **cross-validated** against Triton's own n_spills (STL=2/LDL=1 against n_spills=2, **agreeing exactly**)"

**这句是论文引用的"无计数器信号的双源交叉验证"依据,所以必须实测而不是靠推理。**

**box 1 实测**(`scripts/probe_n_spills_semantics.py`,5 个寄存器压强递增的 kernel,**全部访存宽度都是 `.32`**):

| n_regs | `n_spills` | STL+LDL | 比值 |
|---|---|---|---|
| 30 | 8 | 80 | 10.0× |
| 128 | 20 | 651 | 32.6× |
| 168 | 560 | 4025 | 7.2× |
| 168 | 1336 | 8531 | 6.4× |
| 168 | 2432 | 15250 | 6.3× |

**5/5 不符,差 4–33 倍,而且比值不是常数** —— 所以两者互相推不出来。

**原因从数字本身就能看出**:`n_spills` 是**局部内存的占用量**(`CU_FUNC_ATTRIBUTE_LOCAL_SIZE_BYTES / 4`,即 32 位槽数,且统计**全部**局部内存而不只是溢出);STL/LDL 是**访存次数**。**同一个槽在循环里会被反复读写**,所以访存次数随循环次数增长而占用量不变。

**原断言为什么会看起来成立**:它建立在**一个** kernel 上,而且是**可能的最小量级**(STL=2/LDL=1 vs n_spills=2)。在最小量级上任何两个小整数都容易巧合。

**修复**:两处 docstring 改为明确说明这是**两个不同的量、不可互证**,并附实测表。**两个量都继续采集** —— 它们是真正互补的两个视角:一个说局部内存**流量**多大,一个说局部内存**需求**多大。

### G17 反汇编器只在 CUDA toolkit 里找,而 Triton 自带一份 —— 缺失(✅ 已修)

`find_cuda_tool` 先查 PATH,再查 `/usr/local/cuda` 等 toolkit 目录。**box 1 实测 Triton 自己就带着这三个二进制**:

```
triton/backends/nvidia/bin/cuobjdump
triton/backends/nvidia/bin/nvdisasm
triton/backends/nvidia/bin/ptxas
```

**这是比 CUDA toolkit 更强的保证**:Triton 自己产出 SASS 时就调用它们,所以**只要 Triton 候选能编译,它们就一定存在** —— 而 toolkit 在很多容器镜像里是缺的,那种情况下整个 Tier 1 信号会静默消失(只留一条 `statics_note`,与"这个 kernel 没有张量核"长得一样)。

**修复**:在 PATH 之后、toolkit 之前查 Triton 的 `backends/nvidia/bin/`,路径从**已安装的 package 定位**而不是猜,所以跟着 venv 走。顺序保留 PATH 优先,这样运维刻意放在 PATH 上的特定版本仍然胜出。
