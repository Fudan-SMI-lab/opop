### 1a. 筛查期限不再借用真 trial 的编译预算(即 D9)

**做什么。** `compile_screen`(`correctness.py:268`)当前把 `build_timeout_s`(1200 s)传给
`run_job`,而姊妹函数 `prescreen_batch`(第 180 行)用的是专用的 `prescreen_timeout_s`。
新增:

```python
def screen_timeout_s(cfg: EvalConfig) -> float:
    return max(prescreen_timeout_s(cfg, 1), float(cfg.screen_floor_timeout_s))
```

配一个新 config 字段 `screen_floor_timeout_s: float = 120.0`。

**为什么 120 而不是别的。** 三箱 1243 次单配置筛查实测 p50 11.4–13.6 s、p90 26.5–28.5 s、
p99 38.7–105.0 s ⇒ **现有截止线是自身 p99 的 11 倍**。120 s 仍能答出 99.0 / 99.6 / 99.7%
「本来会答出来的」筛查。而 `prescreen_timeout_s(cfg, 1)` = 33 s 只比实测 p90 低 4.5–6.5 s,
所以 floor 是必需的而不是装饰。

**产出。** box 1 那类 run 回收 **约 2.1 h(12 h 预算的 17–20%)**;box 2 / box 3 各 0.02 / 0.01 h。

**成功判据。** 5 个守卫:`screen_timeout_s < build_timeout_s` 恒成立;它 ≥ 实测 p99 下限;
两个 revert 变体(恢复 `build_timeout_s` / floor 置 0)必须被抓到;
一个 grep 测试断言**任何筛查的 `run_job` 都不再出现 `build_timeout_s`** ——
这是本缺陷的可泛化形式,因为 `59d5a71` 修了一个调用点却漏了姊妹函数。

**风险。** 唯一实质风险是 run 间不可比(中)。**误杀候选:无** —— 筛查只缓存答案,
超时留空缓存 ⇒ `cached_shared_verdict` 返回 `None` ⇒ 该配置照样拿到完整 `build_timeout_s`
的真 trial。**判据被削弱:无** —— 实测两臂 225 次拒绝没有一次是边缘的(最紧超限 5%,
中位超 62%)、0 漏判 ⇒ 逻辑对、只有期限错。

### 2c(新增,取代 2a):~~按声明准确率分配**定向核验**预算~~ —— **已取消(用户 2026-09-12 批准)**

> **状态:取消,不实施。第 3 步第三臂改为 2e(资源墙归因),见 `spec-2e-resource-wall-attribution.md` §11.1。**
>
> **取消的理由是落盘读码发现的一个硬事实:2c 想分配的那笔预算不存在。**
> `reconcile()`(`evaluation/reconcile.py:141`)的签名是
> `reconcile(expectations, resource_deltas, hypothesis_id=...)` ——
> 它读的是那一轮**已经测好的** `resource_deltas`,**不调用任何
> evaluator / run_job / prescreen / compile_screen**(在整个 `_reconcile_round`
> 调用段上 grep 过,0 命中)。而那份 profile **免费覆盖全部 8 个维度**:
> 落盘核实 box2 **12/12**、A800 **6/6**,`declared but never reconciled = 0`。
>
> ⇒ **8 个维度已经在每一轮被全部、免费地核验。** 「把机时投到 shared_bytes
> 而不是 aten_ops」在当前实现下**省不下任何东西**,因为两者是同一份 profile 的两个字段。
> 要让 2c 成立,必须先**人为地停测某些维度**造出稀缺性,再来分配它 ——
> 那与它自己引用的 Coverage-Not-Credit(`arXiv:2608.28011`)论证直接冲突。
>
> **另一个理由是它不服务当前的任何一个 contribution。** 2e 才是 contribution 2
> (「找出斜率最大但被资源截断的维度,并据此引导结构改写」)的机制本身 ——
> `find_walls` 找截断、`tail_gain` 量斜率、`for_prompt` 引导改写,A3 检验最后那个动词。
> 2c 属于第三个尚未定型的 contribution(信息获取效率)。
>
> 下面的原文保留作记录,**不是待办**。

**做什么。** 账本按维度累积历史命中率。改写落地后,harness 对该改写声明过的维度
**按 (1 − 该维准确率) 加权抽样**做一次定向测量去核验;高准确率维度得到**小而非零**的份额。
测量用 compile-only 探针,中位 11.4–13.6 s(一个真 trial 是分钟级)。

**为什么不是阈值开关。** Coverage-Not-Credit(`arXiv:2608.28011`)测到:
把反馈只投给"看起来最值钱"的样本会让被覆盖的分布收缩、长期更差。
在这里后果很具体:`aten_ops` 的 88% 是**在它一直被测**的条件下成立的,
一旦停测,它退化时我们不会知道 —— 而分配依据就是这个准确率,**会自我锁死**。
加权而非开关也顺带满足「不用硬编码缩小探索空间」:没有任何维度被永久排除。

**为什么它是"效率"。** 它把有限的验证机时投到**信息增益最大**处:
在 aten_ops 上核验一次的期望收益 ≈0,在 shared_bytes 上 ≈0.64–0.80。
即"每单位机时买到多少信息"。

若定向核验改变了 agent 的选择偏好,"准确率上升"会与"被测集合变了"混在一起。

**依赖。** ~~必须在 2d 之后~~ —— 已取消,依赖关系随之作废。

### 2d(新增,纯只读,原先于 2c):给 miss 加 `under-converged` 标签

**做什么。** 现有三种 miss 形状**全都默认调参已收敛**。加第四个标签:
若该候选的最终 best 是在其 trial 序列的最后一段才首次达到(即预算耗尽时仍在改善),
则它的"说会动、结果没动"**不计入死杠杆**。只读已有 trial 序列,不需要新测量。

**已实测的量级与三个陷阱**(`conversion-efficiency-redesign.md` 机制二):
**2/11 个候选 = 18%**,且**不跨箱复现**(box2 2/6、A800 0/5)。
必须避开:① **按行算会被伪复制放大** —— 每个改写声明全部 8 维,26 行只来自 11 个候选,
A800 某阈值下的"50%"全部来自一个候选贡献的 6 行;② **绝对水平随阈值动**(21/50/71%);
③ 唯一稳定的是**比值** —— dead-lever 行的污染率在每个切点都约为 hit 行的 3 倍,
**这需要 hit 行作对照组才能说**。

**成功判据。** 报告必须给**候选级**的 n 与**阈值敏感性表**,而不是单一百分比。

**为什么值得做(理由已修正)。** 不是"大部分死杠杆是假的",而是
**18% 落在最坏的区间** —— 既不能忽略又不占多数,而在没有标签的情况下
**无法把它界定在 0% 与 50% 之间**。且它与"剩余增益不可预测"不矛盾:
**事后**判断"是否还在改善"免费,**事前**预测"还剩多少"才是不可能的。

**机时。** 纯代码,0 GPU 小时。

## 第 3 步:三臂实验,验证"资源维度对齐"与"资源墙归因"(2e)

**做什么。** 同一任务三臂,**必须同卡型**(2e 在 A800 上无输入,见 spec 风险 5):

| 臂 | `mode` | 2e | agent 看到什么 | 检验哪个概念 |
|---|---|---|---|---|
| 对照 | `label` | 关 | 一个瓶颈标签 | 基线 |
| 处理 1 | `vector` | 关 | 每维度一行判断 | **资源维度对齐** |
| 处理 2 | `vector` | **`enabled` + `in_prompt`** | 同上 + **实测的共享内存墙归因** | **A3:墙归因 → 改写腾出该维** |

**第三臂已两次改动,当前定义以本表为准。** 原为 `vector_rate`(2a,已取消);
其后改为 `vector` + 定向核验(2c);**2c 亦已取消**(它要分配的验证预算不存在,见 2c 段)。
**现在是 2e。** 自变量 = 「prompt 里关于哪个 knob 被共享内存顶住的那句话,是 agent 猜的还是 harness 实测的」。
已量过 agent 那一侧的质量:**53 条 `parameter_limits` 声明只有 8 条被确认**,
且有 `blocked_by` 归错资源、声明不存在的墙、`predicted_gain_pct` 符号相反三类误报。

**为什么必须三臂而不是两臂。** 「维度对齐 vs 标签」已经有 −8.68% 的单边判决;
新问题是「在维度对齐之上,把被顶住的那一维**实测**归因出来有没有增量」。
拿现有 `vector` 数据当第二臂不行 —— 那是**不同的 run**,只能作参考不能作对照
(而且第 1 步的修复已经让它不可比了)。

**这一臂的主结果不是延迟。** A3 的可证伪预测是
**「被归因的墙所指向的改写,确实腾出了那一维」** —— 落盘判据有两条,都是客观量:
改写后该候选的 `shared_bytes` 是否下降,以及**那个 knob 被拒的取值是否重新变得可行**
(同一个 compile-only 探针,在新源码上重跑一次即可回答)。
若维度腾出了而延迟没改善,则**墙不是真瓶颈** —— 那个负结果同样是结论。
⇒ **样本量要求因此下降**:主结果是逐墙的二值判定(每个被归因的墙一条),不是族级延迟。

**必须同时记录**:每臂的 `RESOURCE_WALL_ATTRIBUTED` 计数与 `probe_total_s`
(后者使探针机时可以在报告里被减掉,而不是被假定为零)。

**样本量的诚实预期(对延迟这个次要观测)。** 现有配对是 3–4 族/臂,而这一臂与 `vector` 臂的
预期延迟差异**小于** `vector` 与 `label` 的差异(G9 那次:`verdict` 与 `rich` 差 4.19%
而臂内跨度 4.72%,未分离)⇒ 延迟上**很可能测不出分离**,应事先这样声明,
而不是事后解释。

**产出。** contribution 2 的第一份实验证据(不论正负)。

**成功判据。** 三臂的解析后 config **只差 `mode` 与 2e 的两个开关**,由
`test_config_strictness.py` 的配对测试守住(上一轮已有 5 个这样的测试);
三臂标定文件 md5 相同或差异 ≤2% 并写明。

**机时。** 3 × 12 h。**两张 4090(box1 + box2)排三臂 ⇒ 24 h 墙钟**;
不开第四台机器,因为它只把 24 h 压成 12 h,而代价是一套新环境 + 一份新标定
(成功判据要求三臂标定 md5 相同或差异 ≤2%,新机器必然不同)。

## 第 5 步:解决"一次调参吃掉半个预算"的结构性问题

**做什么。** 这是第 0 步要绕开、而大批量前必须正面解决的问题。

**根因(落盘 + 读码确认)。** `orchestrator.py:656`:

```python
self._pipeline_batch(list(self.runs))     # ← 把【所有】种子逐个跑完
...
while True:                                # ← 改写循环从这里才开始
    progressed = self._rewrite_round(round_no)
```

`_pipeline_batch` 的墙钟检查是**按候选**的(第 2790 行)⇒ **只能在候选之间停,
不能在候选内部停**。所以任何一个种子调参慢,后面所有种子和整个改写循环都在它后面排队。

**为什么第 1 步修完还不够。** 假设 1a 回收 2.1 h、1b 之后的闸再省 3.5 h,这一 run 够跑改写循环。
**但结构仍在**:只要某个候选恰好更慢一点,同样的事会再发生,而且表现为沉默。

**三个候选修法(需你选)。**

1. **给单个候选的调参阶段一个墙钟份额** —— 例如"任一候选的一次调参不得超过剩余预算的 X%",
   超出即结束该空间的调参(保留已测 trial,该族照常进改写循环)。
   泛化、不针对任何候选、**不缩小可行域**(不删任何取值,只是这一轮少测几个点)。
   X 必须由第 1b 步积累的 `job_wall_s` 语料导出,不能猜。
2. **把改写循环的第一轮提前到种子批完成之前** —— 首个族拿到 stats 就可以改写。
   更贴近论文的"反馈闭环"语义,但改动大、改变调度顺序。
3. **只做可见性** —— 即第 1c 步。不解决问题,但让它不再隐形。

**我的建议**:1c 已在第 1 步无风险上线;方案 1 在第 1b 有语料后实施;方案 2 留到 v4。

**产出。** 一个 run 的流程完整度不再取决于"最慢的那个种子有多慢"。

**风险。** 方案 1 改变每候选的 trial 数 ⇒ run 间不可比 ⇒ 必须在实验之间做,
且之后的 run 不能与之前合并。

**机时。** 代码 + 一次单任务验证跑(12 h)。

## 第 6 步:大批量 benchmark 的前置条件

**做什么。** 三件事,都不是"再修一个 bug",而是上量前必须先有的东西。

**6a. 任务集筛查。** 现在只有 3 个 L3 任务,且选择有硬约束:
forward 内含 `randn` 的任务(33 / 35 / 41)**不能用于正确性比对**。
要上量必须先扫一遍 KernelBench 判定哪些任务可用,这本身是一次扫描作业(纯 CPU + 少量 GPU)。

**6b. 单任务预算下界。** 12 h/任务在大批量下不现实。需要用第 1、5 步之后的语料回答
"多少小时能稳定走完四个循环"。**这个数字依赖第 1 步和第 5 步修完才有意义** ——
在当前代码上量出来的下界会把 D9/D8 的浪费固化进去。

**6c. 并行度规划。** 三台机器 × 12 h ⇒ 一天 6 个任务。20+ 任务需要重新规划或压缩单任务预算,
这取决于 6b 的结果。

**产出。** 一份可执行的大批量计划:任务清单、每任务预算、总机时、以及每个 run 的
流程完整度自检(第 1c 步)。
