# 低精度契约改动的首个正向实证:box3 L3:48 上 fp16 比 ieee 快 10.5 倍

**日期** 2026-09-11 · box3 (A800) `run-l3-48-20260911-052647`,resume 于 commit `b6315fa` · 主体为 24 trial 时的读数,末尾"追加"一节为 45 trial;全部来自 on-disk `events.jsonl`

此前对低精度契约改动的两份实证都是**间接**的:

- `docs/result-box2-precorpus-precision.md` —— 改动生效、8/8 候选正确,但真实收益是**补救**(0/48 改动前候选含补偿 dot),不是"拿到低精度"。
- `docs/result-split3-first-production-measurement.md` —— `split3` 1 胜 3 负,支持"做成 knob 而非建议",但那是 dot 模式的账,不是精度的账。

box3 给了第一个**直接**的:同一候选、同一 space、同一台机器,只换 `COMPUTE_DTYPE`。

## 逐精度最优(24 trial)

| `COMPUTE_DTYPE`/`DOT_MODE` | n | best ms |
|---|---|---|
| **fp16/plain** | 3 | **12.2844** |
| ieee/plain | 4 | 129.3809 |
| tf32/split3 | 1 | 308.9393 |
| bf16/split3 | 2 | 458.2641 |

**fp16 比 ieee 快 10.53×。** 两个最快的 trial 都是 fp16(12.28 / 24.94 ms),第三快才是 ieee 的 129.38 ms。

## 与基线的位置

| | median ms |
|---|---|
| eager | 13.9597 |
| eager_tf32 | 13.4349 |
| torch_compile | 8.5832 |
| torch_compile_tf32 | 8.0527 |
| 候选 best(fp16,24 trial 时) | **12.2844** |

24 trial 时已胜 eager(1.14×)、未胜 `torch_compile`(0.70×)。**这是中途读数** —— 见下方"追加"一节:45 trial 时 K 扩展把它推到 3.6055 ms,反超 `torch_compile` 2.38×。

关于纯带宽下界:A800 的 `dram_tbs = 1.686 TB/s` 是标定过的,按 4090 语料测得的同任务 1.351 GB 固定流量,**下界约 1.351 GB / 1.686 TB/s ≈ 0.80 ms**。这个 0.80 ms 是**下界不是目标**:它假设流量与 4090 上相同,而 fp16 的 B/C 张量本就更省字节,真实可达值需在本机实测,不能由此推断。

## 为什么这次是"精度的账"而不是别的

三点使归因干净:

1. **同一候选同一 space。** `cand-d2cf7928` / `sp-fc83f2bb`,只有 `COMPUTE_DTYPE` 不同,其余 6 个 knob 由 TPE 采样。fp16 的最优点(BL=64/BN=128/BP=64/NUM_WARPS=4/NUM_STAGES=2)与 ieee 的最优点(同 tile,NUM_WARPS=8/NUM_STAGES=2)几乎重合,所以差异不是 tile 选择带来的。
2. **10.53× 与 A800 实测屋顶比一致。** 本机 `calibration.json`(schema 5)测得:

   | 精度 | cuBLAS TFLOPS | Triton TFLOPS |
   |---|---|---|
   | fp32 | 19.01 | 18.08 |
   | tf32 | 111.46 | 100.99 |
   | fp16 | 226.17 | 193.35 |
   | bf16 | 233.96 | 199.78 |

   **fp32 → fp16 的屋顶比是 226.17 / 19.01 = 11.90×**(Triton 路径 10.70×),观测到的 10.53× 落在其内。所以这是**算力屋顶差**,一个数量级的加速不需要别的解释。

   注意一个我先写错又改掉的说法:A800 **有** TF32 张量核(实测 111.46 TFLOPS,是 fp32 的 5.86 倍),所以"ieee 慢是因为 A800 没有张量核通路"是错的 —— ieee 走的是 `input_precision="ieee"` 的真 fp32 路径,慢的原因就是那条路径的屋顶只有 19 TFLOPS。

3. **tf32 为什么没赢?** tf32 屋顶 111.46 TFLOPS 高于 fp32 的 5.86 倍,但表里 tf32 只有一个 `split3` 样本(308.94ms)、`tf32/plain` 的 2 次尝试全是 `correctness_mismatch`。这与记忆中 "tf32 0-for-172、根因是候选把 tf32 放在未补偿的 else 兜底" 一致 —— **tf32 的失败是候选侧的,不是屋顶侧的**,而它本该是这台机器上第二好的选择。这一条留给实验后统一分析。

4. **这个候选此前因 fp16 被拒过两次**(`witness_default_failed` tf32、`witness_minimal_failed` fp16),repair 第 3 次用指数重标定把它救回来。**如果见证门把这个候选丢掉,这 10.5× 就永远看不到** —— 这正是 `product-order-defeats-a-fallback` 那条修复要保护的东西。

## 追加(同日,45 trial):K 扩展再拿 3.41×,best 3.6055 ms

原空间 v3 的 tile 域是 `BL[64,128] BN[128,256] BP[64,128]`。analyst 读完瓶颈后,K 扩展在 **BL/BN/BP 三个 knob 上都朝 `min` 方向**加值,发布 v4:`BL[16,32,64,128] BN[32,64,128,256] BP[16,32,64,128]`、`NUM_STAGES[1,2,3,4]`。

新冠军 **3.6055 ms**(median,std 0.0807,n=20,空间 `sp-b2bab578`),配置 `BL=16 BN=32 BP=16 NUM_WARPS=2 NUM_STAGES=1 fp16`。**三个获胜取值全部是扩展新增的** —— 按本项目的归因判据(diff 空间版本 + 获胜配置是否用了新增值),这是一次**可归因**的 K 扩展成功。

| | median ms | vs 3.6055 |
|---|---|---|
| eager | 13.9597 | **3.872×** |
| eager_tf32 | 13.4349 | 3.726× |
| torch_compile | 8.5832 | **2.381×** |
| torch_compile_tf32 | 8.0527 | 2.233× |

`excessive_speedup` 硬失败门是 **10.0**,未触发(事件流中 0 次);2.0 只是"标记待查"级别,按已记录规则**速度不能否决正确性**。3.6055 ms 是本机带宽下界 0.80 ms 的 **4.50 倍**,物理上合理,不是测量假象。

### 读"为什么变快"时我两次读错,方向相反

1. **先否掉"spill 少更快"** —— 因为冠军自己带 298 个 spill 且顶在 255 寄存器上。**错**:绝对值不是判据,**排名**才是,`n_spills` 在两个群体内都是最强单一预测量(+0.882 / +0.696)。
2. **再否掉"共享内存解释了它"** —— 因为混池相关系数只有 +0.176。**也错**,错在混池本身。

`n_regs` 在这 22 个 trial 上是**双峰**的(32 或 128–255,中间没有值),且**所有慢于 100 ms 的都在 32 那组**。混池同时在两个方向上造出 Simpson 悖论:

| | 混池 (n=22) | regs≥128 (n=9) | regs<128 (n=13) |
|---|---|---|---|
| `shared_bytes` | **+0.176** | **+0.795** | **+0.676** |
| `n_spills` | +0.924 | +0.882 | +0.696 |
| `n_regs` | **−0.826** | +0.000 | 恒为 32 |

混池的 `shared_bytes` **掩盖了**两组内都强的效应;混池的 `n_spills` 被**夸大**;混池的 `n_regs` −0.826 是**纯群体假象**。脚本 `scripts/audit_k_expansion_win_mechanism.py` 现在先按寄存器类分组,并把混池行显式标注。

**机制(冠军 vs 亚军)**:shared 从 114944 降到 12288(9.35×),按 A800 的 166912 opt-in 上限算,**每 SM 可驻留块数从 1 变成 13**。这是小 tile 真正买到的东西,而且是实测的 —— 不是从 occupancy 推的(Triton 的 occupancy 是对着这个 kernel 无论如何都会顶到的寄存器上限报的)。

### 与 4090 语料的关系:平台期结论不可搬运,但比较要小心

A800 带宽 1.6858 TB/s 是 4090 的 **1.82 倍**,而当前 best 3.6055 ms 比 4090 语料的 1.41–1.55 ms **慢 2.33 倍**,且距自己的带宽下界还有 4.50 倍 ⇒ **A800 在这个任务上不是带宽受限的**,而 4090 是。所以"L3:48 已到 90–95% DRAM 屋顶、平台期是物理"这条结论是 **4090 专属**,不能搬到 A800。

**但这个比较本身有一个我必须声明的不对等**:3.6055 ms 是**第一个候选、45 个 trial、run 中途**的读数;1.41–1.55 ms 是**跑满 12h、多候选多族**的最终结果。所以"A800 比 4090 慢 2.33 倍"**不是硬件结论**,只说明这台机器上的搜索还远未收敛。可以断言的只有一句:**A800 距自己的带宽屋顶尚远,因此这里还有空间**,与 4090 的"只剩 ~10%"处境不同。
