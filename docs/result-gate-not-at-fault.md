## 一、我错在哪里

**我的推理**:三个任务的噪声底(0.9554 / 0.9767 / 0.9778)全部**低于** `relaxed_pass_frac = 0.99` ⇒ 低精度候选**无论多正确**都过不了绝对门 ⇒ 那 537 个里必然有被冤判的。

**前半段是真的,后半段不成立。** 因为绝对门**不是**唯一的判据 —— `fp64_relative_gate: true` 在三个 L3 配置里都开着,而它正是为这件事加的。所以正确的问题不是「绝对门够不够宽」,而是「**fp64 相对臂放过了它们吗**」。

**我把一个已经修好的缺陷当成了还在的缺陷。** 这与我在 S1 上犯的错同形:引用一个修法上线**之前**的数字(18% → 实际 4.42%),这次是引用一个**保护措施存在之前**的推理。

## 二、实测怎么做的

worker 写的失败信息本身带着两条臂各自用的数字(`worker_main.py:2314-2337`),所以归因不需要论证。一条真实记录:

```
relaxed mismatch on trial 2; gate needs frac_within_tol>0.99 AND cosine>=0.99985
  vs ieee ref: {'frac_within_tol': 0.97605, 'cosine': 0.99999995, ...}
  reference's OWN ieee-vs-tf32 spread (task noise floor, NOT a bug):
                {'frac_within_tol': 0.977768, ...}
  fp64-relative arm ALSO failed (...):
                {'reference_rmse_vs_fp64': '1.5110e+15',
                 'candidate_rmse_vs_fp64': '7.5286e+15',
                 'multiplier': 2.0, 'threshold': '3.0220e+15',
                 'ratio_to_reference': '4.982'}
```

**这一条把两种成因分得很干净**:候选 `frac_within_tol=0.97605` 确实低于 0.99(绝对门会拒),也确实低于任务噪声底 0.977768 —— 但 fp64 相对臂给出了独立判决:候选距 fp64 真值的 RMSE 是**参考自身的 4.982 倍**,门限是 2.0 倍。**这是对着真值的判决,不是两个不精确结果之间的比较。**

判据顺序(`audit_gate_vs_candidate.py`):

1. 候选误差 ≤ 参考自身的 ieee-vs-tf32 spread ⇒ **门的问题**(在任务噪声以内);
2. fp64 臂**没跑**(开关关或 golden 不可用)⇒ **门的问题(遗漏)**;
3. fp64 臂**跑了并拒绝** ⇒ **候选的问题**。

**537 个全部落在第 3 类。**

## 五、fp64 相对臂承重吗?承重,而且量很大

从它自己的计数器(`fp64_rescued_trials`,per-trial 落账):

```
带该计数器的 trial : 1714
仅靠相对臂救回的正确性 trial : 2790
```

**2790 次救援。** 这与「零误杀」是两个方向的同一件事:**门确实曾经会误杀大量正确候选,而那个缺陷已经被 fp64 相对臂修掉了** —— 这 537 个是它**放过之后仍然**被拒的。

（`fp64_rescued_trials` 的语义:每个 trial 的多次正确性检验中,有几次是**只有**相对臂接受的。所以 2790 > 1714 是正常的 —— 一个 trial 可以有多次。)

## 六、所以「要怎么修」——**门不用修。要修的是候选**

**门侧不做任何改动。** 三条判据(绝对门 / fp64 相对臂 / 乘数选择)在这份语料上都没有可归因的缺陷,任何放宽都会变成把 3.04–3766 倍误差的 kernel 收进来 —— 那是 reward hacking,不是修复。

**真正的问题在候选生成侧,而且根因早有记录**(`compensated-dot-passes-plain-dot-fails`):

| 成因 | 机制 | 实测 |
|---|---|---|
| **(A) 未补偿的 `dot`** | 低精度累加不做三项分裂/补偿 | 三项分裂过 12/12,单次全灭 11/11 |
| **(B) `PREC` 门控整个算法** | 非 fp16 落到未稳定化的 `else` 兜底分支 | — |

**这两个都是候选源码的性质,修法在 prompt 与候选契约,不在门。** 而且这正是 S1b 打的那一类的根因 —— S1b 已经把这类无条件失败**避开**(省 228 个),但避开不等于**解决**:一个会写补偿 `dot` 的候选本可以真的用上张量核。

**量级参考**:L3:48 上 8/8 张量核候选被拒、7/7 标量候选被收,2.09ms/8.90x 的成绩**完全没用上张量核**。所以这是「让低精度真正可用」的问题,不是「让门更宽」的问题。

## 七、这份实测没有验证什么

1. **只有 L3、只有 box 1 语料、只有 GLM、只有 5 个 run。** A800 上的 run 未纳入(那台机只跑过验证性 run)。
2. **只覆盖 `correctness_mismatch`。** `runtime_error`(67 个)未分类。
3. **归因依赖失败信息里的文本。** 537/537 都成功解析,但若将来 worker 改了那段格式,这两个脚本会静默读不到 —— 已在脚本里把「无法解析」作为一个显式类别输出(本次为 0),这样格式变化会表现为该类别变大而不是结论变形。
4. **「候选的问题」不等于「候选无救」。** 本文只说这 537 个按当前判据是候选侧的缺陷,**没有测**若候选写了补偿 `dot` 能拿到多少加速 —— 那是独立的一项。
5. **没有测 `relaxed_pass_frac`/`cosine_min` 本身是否过严**,因为在 fp64 相对臂存在的前提下这个问题不影响结局(第 3 类已经是对着真值判的)。若相对臂将来被关掉,这个问题会立刻回来。
