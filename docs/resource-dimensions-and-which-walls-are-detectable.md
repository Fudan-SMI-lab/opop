## 0. 先说清"墙"在本项目里的定义,以及它为什么比"超上限就 fail"窄

你举的例子(OOM、带宽到顶、算力到顶)对应的是**三种不同的东西**,混在一起会读错:

| 概念 | 含义 | 例子 | 本项目现状 |
|---|---|---|---|
| **硬失败** | 这个配置**跑不起来** | OOM、共享内存超限 | 有,是 `FailureKind` |
| **饱和** | 跑得起来,但某资源**用到了物理上限** | 带宽达到屋顶的 90% | 有,是 `verdict="binding"` |
| **墙(2e 的定义)** | 某个**参数**的取值域**被资源上限截断**,而它在被截断的方向上**还有性能斜率** | `BLOCK_N` 只能到 64,到 128 就被拒,而 32→64 延迟还在降 | **只有共享内存这一维有** |

**墙比"饱和"多两个要求**:①要能定位到**具体哪个参数**被顶住;②那个参数在被顶住的方向上**还有收益**(否则腾出来也不值钱)。
所以"带宽到顶"是饱和而不是墙 —— 它不指向任何一个参数的取值域。

**墙需要什么才能被检出。** `find_walls`(`wall_attribution.py:134`)的输入是
**"被拒绝的参数组列表"**。所以一个维度要能产生墙,必须先有一个**在采样时就能拒绝配置的判据**。
现在**只有共享内存有这个判据**(`_screen_config` → `compile_screen`),其余七维**结构上产生不了墙**,
不是因为没人写,而是因为没有拒绝事件可读。

## 1. 八个维度逐个说明

> "每线程 / 每 block / 整卡"这三个层级要分清:GPU 把线程按 32 个一组打包成 **warp**,
> 若干 warp 组成一个 **block**,block 被派到 **SM**(流多处理器,一张卡有几十个)上执行。
> 寄存器和共享内存是**每个 SM 上的固定家当**,由驻留其上的 block 分摊 —— 这是下面多条的关键。

### ① `n_regs` — 每个线程占用多少寄存器

**是什么。** 寄存器是**每个线程私有的、最快的一小块存储**(GPU 上离计算单元最近的一级)。
`n_regs` = 编译器为这个 kernel 的**每个线程**分配了多少个。上限是每线程 255 个(硬件规定)。

**为什么它是资源。** 一个 SM 的寄存器总数是固定的。每线程用得多 ⇒ 同时能驻留的线程就少
⇒ 硬件用来掩盖内存延迟的"备用工作"变少。**它不会让程序失败,只会让程序变慢。**

**墙能否检出:能检出"饱和",但不产生"墙"。**
- 现状:`dimensions.py:246` 读 `n_regs` 与 device query 的 `max_regs_per_thread`(255),
  ≥90% 判 `binding`。
- **但它不会拒绝配置**,所以没有被拒参数组 ⇒ `find_walls` 抓不到它。
- **更要紧的实测**:`triton-caps-regs-instead-of-spilling` —— **Triton 不会因为寄存器不够而失败,
  它会主动把每线程寄存器数压下来**。所以"超限"这个事件在 Triton 上**根本不发生**。
- 已实测的反例:`fixed-denominator-comparison-explains-nothing` —— 寄存器**同为 ≥250/255**
  的两个赢家,延迟仍差 **12.8x / 2.1x** ⇒ 寄存器打满**不解释**性能。

⇒ **这一维的可检出信号不是"寄存器超限",而是 ④ occupancy 下降。**

### ② `n_spills` — 寄存器装不下,溢出到慢速内存的次数

**是什么。** 当 kernel 需要的临时变量超过寄存器容量,编译器把一部分挪到
**local memory**(名字叫"本地",物理上在显存里,比寄存器慢**两个数量级**)。
`n_spills` = 发生了多少次这种搬迁。

**为什么它重要。** 它是**唯一一个"非零就是坏"的维度** —— 没有"70% 的不溢出"这种说法。
代码里的判据就是这么写的(`dimensions.py:265`):`verdict = "binding" if spills > 0 else "slack"`,
天花板写成 0。

**墙能否检出:能检出,而且这是最值得做的一个。**
- **它已经在编译探针里被采集了**(`worker_main.py:785`:`"n_spills": _opt_int(getattr(meta, "num_spills", None))`)
  —— 与共享内存**同一次探针、同一份返回值**,不需要额外 GPU 时间。
- **实测支持**:`only-n-spills-has-a-stable-conversion-rate` —— 八维里**只有 `n_spills`
  有稳定的资源→性能转化率**(其余七维跨候选差最多 15.4x,不可迁移)。
- **可行的判据**(与共享内存不同,不是"超上限"而是"从 0 变正"):
  某 knob 增大时 `n_spills` 由 0 变正 ⇒ 该 knob 的取值域被"寄存器容量"截断。
  **这是一个真正可写的检出规则**,因为 0 是一条硬边界,不需要标定阈值。

### ③ `shared_bytes` — 每个 block 用多少共享内存

**是什么。** 共享内存是**一个 block 内所有线程共用的一块高速暂存区**(比显存快得多,由程序显式管理)。
典型用法:把一小块矩阵搬进来反复用,避免反复读显存。
上限是**每 block** 的 opt-in 限额:4090 **101376 字节**,A800 **166912 字节**。

**墙能否检出:能,而且这是现在唯一实现了的。**
- **硬拒绝**:编译器填 `metadata.shared`,启动时只是拿它和上限比 ⇒ 超了**必然**
  `out of resource: shared memory`。box2 实测编译期数字与运行期 `Required:` **逐字节相同**。
- **代价**:L3:43 上 **180/1004 个 trial(18% 预算、0.93h)**死在这上面,而每一个都在启动前可判定
  ⇒ 这就是先做它的理由。
- **不能用公式代替**:`BLOCK_M*BLOCK_N*stages` 在 **15/15** 个候选上"失败的最小值 < 通过的最大值"
  ⇒ 可行集与不可行集在任何这类乘积上**重叠**;agent 手写的共享内存约束中位只有真值的 **32%**。

### ④ `occupancy` — SM 上实际驻留的线程占它能容纳的比例

**是什么。** 一个 SM 有固定数量的"线程席位"。occupancy = 实际坐了多少 / 总共有多少席位,是个 0~1 的比例。
**坐得满 ⇒ 一个 warp 等内存时,硬件能切到别的 warp 干活,延迟被掩盖。**

**极性是反的:低才算糟。** 这是八维里**唯一** `lower_is_better: False` 的
(`conversion.py:47`),判据也用单独一对阈值:**< 0.30 判 binding,< 0.50 判 near-binding**
(`dimensions.py:75`)。已记录:`a-dimension-must-declare-its-binding-polarity` ——
统一按"高=绑定"处理曾导致**零个**多维绑定被报出来,而反例就在输入里。

**墙能否检出:这是①的真正出口,但需要新判据。**
- **它是被 ① ② ③ 共同挤出来的结果** —— 编译探针返回的 `occupancy_limiter` 字段直接说明是谁在限制。
- 可行判据:某 knob 增大 ⇒ occupancy 单调下降且已触底(<0.30)⇒ 该 knob 被"SM 席位"截断。
- **陷阱**:`occupancy-is-nested-and-a-flat-read-fakes-unmeasured` —— 它在 profile 上是
  **嵌套字段**(`profile.occupancy["occupancy"]`),平读会把"已测"读成"未测"。

### ⑤ `peak_alloc_bytes` — 这个候选跑起来峰值占多少显存

**是什么。** 显存(VRAM)峰值占用。天花板是整卡显存(24GiB / 80GiB)。

**墙能否检出:硬失败已有(OOM),但对本任务不绑定。**
- **OOM 是一个独立的 `FailureKind`**(`models/core.py:23`),在**运行时**由 worker 检出
  (`worker_main.py:38`),不是编译期筛子。所以它**能**拒绝配置 ⇒ 理论上能产生墙。
- **但在我们的任务上它是 `slack`**:代码注释明说 peak 是真实的逐候选测量
  (候选间跳 9.6–41.3%),但"天花板是整卡显存,而这些任务离得远",所以**必然落在 slack**
  —— 这是**诚实的读数,不是隐藏**。
- 已记录的例外:`l1-oom-ceiling-is-not-the-candidates-fault` —— 24GiB 上
  **34/78 个 level1 任务不可评测**。⇒ 在**别的任务**上这一维会真的绑定。

### ⑥ `candidate_aten_bytes` — 这个候选在 PyTorch 算子层搬了多少字节

**是什么。** "aten" 是 PyTorch 的底层算子库。这个数是候选调用的 aten 算子搬运的字节数。
**它衡量的是"没被融合掉的数据搬运"** —— 每个未融合的算子都要把中间结果写回显存再读出来。

**墙能否检出:不能,而且它没有天花板。**
- 代码写明:`ceiling=None`,`confidence=0.5`,理由是**融合的 kernel 会低报**
  —— 一个把 10 个算子融成 1 个的候选,aten 层只看得到 1 个,数字**变小了但这是好事**。
  所以它是一个**下界**,不能界定天花板。
- 有意义的方向是**地板**(任务的必需字节数),而不是天花板。
- ⇒ **这一维不存在"撞墙"的概念**,它衡量的是"还有多少可以融掉"。

### ⑦ `candidate_aten_ops` — 同上,但数的是算子个数

**是什么。** 未融合的 aten 算子调用次数。地板是 1(完全融合)。

**墙能否检出:不能,同 ⑥。** `ceiling=None`,`confidence=0.5`。
- 相关实测:`task-cost-fusion-headroom` —— L3:43 的融合头寸 **69.09x**,是**任务级最大杠杆**。
  但这是"还能融多少"而不是"撞到什么墙"。
- 注意 `declaration-accuracy-is-per-dimension-not-global`:agent 对 `aten_ops` 的声明准确率
  **88%/100%**,是八维里最高的;而 `shared_bytes` 只有 **36%/20%** —— 跨度 52/80 个百分点。

### ⑧ `threads_launched` — 一共启动了多少线程

**是什么。** grid × block 的总线程数。

**墙能否检出:结构上不可能 —— 它没有好坏方向。**
- `conversion.py:44`:`"lower_is_better": None`。代码里对它的处理值得一读
  (`dimensions.py:339`):它被标成 `applicable=True`(维度存在且测到了)但
  `verdict="not-applicable"`(**没有档位可判**),并且注释明确拒绝了把它标成 `slack`:
  > *"`slack` would be the tempting default and it is the wrong one: it implies headroom in a
  > direction that does not exist."*
- ⇒ 线程多不是好也不是坏,**没有方向就没有墙**。

## 3. 三个必须说清的"不在这张表里"

**`num_warps` 不是一个维度 —— 我此前提到它是错的。**
`dimensions.py:365` 有一条专门的注释:它**不在** `classify()` 的 evidence 里(grep 0 次),
也不在 `_DIMENSIONS` 里,所以**没有东西可读**;并且刻意**不**用默认值给它造一条记录:
> *"a dimension fabricated from a missing key is exactly the 'confident constant' failure mode."*

它只是编译探针顺手返回的一个字段(`worker_main.py:786`),同时也常常是一个**可调 knob**
(`NUM_WARPS` 出现在参数空间里),但它**不是一个资源维度**。

**带宽 / 算力(你提到的"带宽到上限、算力到上限")不在八维里,而且是有意的。**
已实测 `dram-and-compute-pressure-are-latency-restated`:`pct_of_dram_peak` 与
`pct_of_compute_peak` 这两个"维度"**就是 1/gpu_ms 换个写法** —— 采纳它们不改变任何分配决定。
同一函数的第二个缺陷:`pct-of-dram-peak-counts-l2-hits-as-dram-traffic`,L2 命中会让它
**虚高到超过 100%**。
它们仍然作为**天花板/饱和度**出现在 bottleneck 分类里(L3:48 已达 DRAM 屋顶的 90.4%),
但不是这张表里的"可撞的墙"。

**"都吃满资源上限则谁快谁效率高"这个想法已被实测否证。**
`fixed-denominator-comparison-explains-nothing`:寄存器同为 ≥250/255 的两个赢家延迟仍差
12.8x / 2.1x,固定分母压掉的离散度为零。
以及 `leaner-resource-use-means-less-headroom-not-more`:"平局取资源更省者"的前提**方向是反的**
—— 4/4 个更省的候选剩余增益都**更少**(最极端 0.2% vs 47.0%)。
⇒ 扩展墙检出时**不能**顺手引入"资源用量越满越好/越省越好"的裁决规则。
