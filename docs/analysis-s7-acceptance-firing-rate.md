# S7(斜率引导采样)的验收测量:机制在真实语料上的**触发率**

> 复现命令(每条都是零 GPU、纯离线):
> ```bash
> RUNS=$(ls -d /d/Pyhon_projects/opop/v2/runs/run-l3-*/ | tr '\n' ' ')
> PYTHONIOENCODING=utf-8 uv run --offline --extra test --quiet \
>   python scripts/probes/s7_acceptance.py $RUNS --soft --out docs/s7-acceptance-soft.txt
> PYTHONIOENCODING=utf-8 uv run --offline --extra test --quiet \
>   python scripts/probes/s7_acceptance.py $RUNS       --out docs/s7-acceptance-hard.txt
> ```
> 原始输出即 `docs/s7-acceptance-soft.txt` / `docs/s7-acceptance-hard.txt`,本文是它的解读。

## 0. 这份测量回答的问题,以及它**不能**回答的问题

`s7_feasibility_replay.py` 回答的是"**墙**是否够早、够稳定,值得据此行动"(74% 半程可得、
53% 到最后仍成立)。它完全没有回答:**这套实现能不能把这样一道墙变成一个合法、有用、不重复的采样点**。
中间有四道门,每一道都可能把所有的墙悄悄吃掉:

1. 被截断 knob 的取值可能**已经全被采过**,那就没有可提的点;
2. 唯一没采过的取值可能落在**被拒值之外**,或落在**最优点的错误一侧**;
3. 提出的点可能是**调参器已经问过的**配置;
4. 最优点可能**不是当前空间的点**(扩展后重调参时会出现)。

所以本文给出的是**触发率**,并按"哪道门拒绝了"分解。它**不是性能声明**:
回放知道 trial 实际是什么,但**无法知道插入一个点之后采样器接下来会画什么**,
因此"这样会不会找到更好的配置"在结构上不可回答 —— 那只有一对 12h 能回答。

## 1. 硬墙(共享内存):**本机无法回答**,原因与之前一致

152 个候选里 **0 个**有 `infeasible_shared_memory` 记录 —— 本地备份的每个 run 都早于共享内存筛查,
而被拒参数集是 `find_walls` 的**唯一输入**。790 次重算全部报"无可行动的墙",
**这个 0 是输入的缺席,不是机制的性质**。

⇒ 硬墙版本必须在**带筛查的 run 上重测**,而这正是 12h 对照臂会提供的。

## 2. 软墙(`n_spills`):机制会触发,但**只在 10.5% 的候选上**

| 量 | 值 |
|---|---|
| 候选数(≥10 trial) | 152 |
| 重算次数 | 790 |
| **曾触发的候选** | **16 / 152 = 10.5%** |
| 会插入的点总数 | 48 |
| 首次触发位置(占该候选序列的比例)| **中位 0.25** |
| 被行动的 knob 的尾部斜率 | 中位 **+34.8%**,范围 +0.5% … +66.6% |

两道门的拒绝次数(**注意分母不同,不可相加**):

| 门 | 次数 | 分母 |
|---|---|---|
| 完全没有可行动的墙 | 751 | 790 次**重算** |
| walled 侧没有未采过的取值 | 194 | 逐 **knob** |
| 点已被问过 | 0 | 逐 knob |
| 最优点不属于该空间 | 0 | 790 次重算 |

一次重算若其唯一 walled knob 无未采取值,会同时给两类计数器 +1(行在解析目标时被丢掉,
随后空列表被报成"没有墙"),所以 751 + 194 > 790 不是矛盾。

**空间是从已采取值重建的**(这些 run 没有 `SPACE_PUBLISHED`),即 choices 是真实声明的**子集**。
所以"没有未采取值"是该项的**上界**,10.5% 是触发率的**下界** —— 对一个要论证花 12h 的探针来说,
这是保守方向。

## 3. 这三个数各自意味着什么

**(a) 0.25 的首次触发位置是好消息,而且是本轮唯一的直接好消息。**
中位 0.25 意味着机制在候选自己序列的四分之一处就有东西可提 —— 80 trial 的候选还剩 60 个 trial。
这正是 P1 需要的前置条件:2e 的负结果根因是"80 个 trial 全花在发现墙之前",而这里**不是**。

**(b) +34.8% 的中位斜率说明被选中的维度不是边角料。**
如果触发的都是 +1% 那种,机制即使生效也无意义。范围下端 +0.5% 存在,但中位在 +34.8%,
说明斜率过滤器(复用 `select_for_probing`,不是重写)在做实事。

**(c) 10.5% 是坏消息,而且它把 S7 的定位改了。**
"没有可行动的墙"占 790 次重算的 **95.1%**。也就是说:**瓶颈是判据,不是接线**。
S7 原本的论证是"墙来得太晚,所以斜率只进 prompt 不进采样器";
但在这个语料上,墙的问题不是**来得晚**(0.25 已经很早),而是**大多数时候根本不存在**。
这与 2e 的 25% 族覆盖率、以及 item 5 测出的"提高覆盖只能改判据"是**同一个结论从第三个角度出现**。

⇒ **S7 不修 C2 的覆盖率问题,它继承了这个问题。** 这一点必须写进论文而不是被 12h 的结果掩盖。

## 4. 对设计的影响:三处已据此固定,一处必须记录为局限

**已据此固定:**

1. **剂量上限保持 2。** 48 个点分布在 16 个候选、790 次重算上,平均每次触发的重算插 1.2 个点。
   `max_enqueued_per_recompute=2` 从未成为瓶颈("点已被问过" = 0 也说明这一点),
   所以没有理由为了触发率去放大剂量 —— 放大只会在**会触发的少数候选上**多花预算。
2. **`recompute_every=10` 保持。** 首次触发中位 0.25,80 trial 下即第 20 个 trial 左右,
   正是第二次重算。把 cadence 调密只会增加 751 次"无墙"里的空转,不会让墙更早出现。
3. **软判据必须与 item 2 的开关 AND**(已实现)。本机唯一能触发的判据就是软墙 ——
   若两个开关不联动,一个"只开 S7"的 run 会得到 0 触发,并被误读成"S7 无效",
   而真实原因是它唯一能用的信号被另一个开关关着。

**必须记录为局限,不在本轮修:**

`n_spills` 软墙在 152 个候选上只有 16 个能触发,而它是本机唯一可触发的判据。
这意味着**在 4090 语料上,S7 的可测样本量是 16**。一对 12h 若跑在带共享内存筛查的机器上,
硬墙会加入,样本量才可能上去 —— 但那时"S7 有没有用"的答案会同时依赖两种判据的混合,
`source` 字段(已实现)是事后能把它们分开的唯一手段。

## 5. P1–P4 在这份测量之后如何读

- **P1(墙归因首次出现提前)** —— 前置条件成立(0.25)。若 12h 后 P1 不成立,
  说明**插队的点没有产生新的 `latency_by_value` 覆盖**,那是实现问题而不是前提问题。
- **P2(每候选 probe-worthy 墙数增加)** —— 这是本测量**最可能失败**的一条:
  95.1% 的重算根本没有墙,插 1–2 个点不太可能把"无墙"变成"有墙"。
- **P3(族覆盖率从 25% 上升)** —— 与 P2 同理,且 item 5 已独立测出覆盖率受**四道门**限制而非投递范围。
- **P4(P1–P3 成立但延迟不改善 ⇒ 瓶颈在改写转化率)** —— 本测量给 P4 加了一个**新的第三种可能**:
  P1 成立、P2/P3 不成立、延迟不变 ⇒ 瓶颈**既不是时机也不是改写**,而是**判据的适用面**。
  这个读法在实现前就该写下来,否则事后会被归因到 S7 的剂量或时机上。

## 6. 一句话结论

机制可用、触发得足够早(0.25)、选中的维度斜率够大(+34.8%),但**只在 10.5% 的候选上触发**,
且 95.1% 的重算是因为"根本没有可行动的墙"。
⇒ 值得跑那对 12h(它同时是硬墙唯一可测的场地),但**必须事先声明 S7 不修覆盖率**,
否则 P2/P3 失败会被误读成 S7 的实现缺陷,而它其实是判据适用面的问题 —— 与 2e 和 item 5 同一个根因。
