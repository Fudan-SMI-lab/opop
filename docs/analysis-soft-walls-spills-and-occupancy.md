## 0. 结论先说

**相关性门槛:两个信号都通过了**(|ρ| < 0.9 对所有已有量),不是 `logical_bytes` 那种代数改写。

**但更严的一道检验把它们分开了** —— "这个建议在实测最优点处成立吗":

| | `n_spills` | `occupancy` |
|---|---|---|
| 独立性(最大 \|ρ\|) | **+0.339**(vs `n_regs`) ✅ | **−0.497**(vs `n_regs`) ✅ |
| 能否触发 | 43.8% trial 非零 ✅ | 87.6% trial < 0.30 ⚠️ 几乎恒为真 |
| 候选内是否随 knob 变化 | 56/56 变化 ✅ | 56/56 变化 ✅ |
| 关系形状 | 27 峰形 / **18 单调符合预期** / 6 反向 | **37 峰形** / 13 单调 / 3 反向 |
| **赢家在自己范围里的位置** | **中位 0.00,56/56 都在最低端** ✅ | **中位 0.33,只有 2/56 在顶端** ❌ |
| 判据可写? | ✅ **可写**(方向与最优点一致) | ❌ **不可写**(建议方向与最优点相反) |

⇒ **只做 `n_spills`,不要做 `occupancy`。**

## 1. 相关性(你要求先测的那一项)

门槛来自上一轮的教训:`logical_bytes` 对 tile 乘积 ρ=+0.978 被判为代数改写,
于是定下 **|ρ| ≥ 0.9 即不得实现**。

### `n_spills`

| 对比对象 | ρ | n | 读法 |
|---|---|---|---|
| `n_regs` | **+0.339** | 2788 | 中度相关 |
| `shared_bytes` | +0.257 | 2788 | 基本独立 |
| tile 乘积 | **−0.048** | 2749 | **几乎完全独立** |
| 延迟 | +0.275 | 2788 | 基本独立 |

### `occupancy`

| 对比对象 | ρ | n | 读法 |
|---|---|---|---|
| `n_regs` | **−0.497** | 2788 | 中度相关(合理:寄存器是首要限制者) |
| `shared_bytes` | −0.387 | 2788 | 中度相关 |
| tile 乘积 | +0.032 | 2749 | 几乎完全独立 |
| 延迟 | **−0.053** | 2788 | **几乎完全独立** |

### 两者之间

`n_spills` vs `occupancy` **ρ = −0.500** —— 中度相关但不互为改写,
所以"只做一个"的理由**不是**冗余,而是下面第 2 节的判据问题。

**⇒ 相关性这一关两个都过。** 与 `logical_bytes`(+0.978)、`pct_of_dram_peak`(+1.000)、
SOL 头寸(+1.000)形成明确对照 —— 这次的信号确实携带自己的信息。

## 2. 但 `occupancy` 过不了下一关:建议方向与实测最优点相反

相关性只说明"它不是别的量的改写",**不说明"照它行动是对的"**。所以追加了两项检验。

### 2.1 先看一个表面矛盾

- 候选**内部**比较:occupancy 最高的三分之一 trial 比最低的三分之一**快 23.1%**(中位;
  37/56 个候选是"高 occupancy 更快",p90 +60.3%);
- **但** 55/56 个候选**自己的最优 trial** 也在 0.30 以下。

两件事同时成立 ⇒ "occupancy 绑定"对赢家几乎总是真的。**一个在 55/56 个赢家上都触发的判据是常数,不是发现。**

### 2.2 矛盾的解:关系是峰形,赢家在中间

| 关系形状(逐候选) | 数量 |
|---|---|
| **峰形:中间最快** | **37** |
| 单调:越高越快 | 13 |
| 单调:越低越快 | 3 |
| 其他/非单调 | 3 |

**赢家在自己 occupancy 范围里的归一化位置:中位 0.33**;
在顶端(≥0.8)的只有 **2/56**,在底端(≤0.2)的有 **16/56**。

⇒ **"提高 occupancy"在实测最优点处是反向建议。** 平均趋势为正,但赢家并不坐在高 occupancy 处 ——
它坐在一个内部最优点上。把"occupancy 被顶住"报给改写者,会让它去追一个**测量显示并非最优**的方向。

### 2.3 顺带得到一个有用的事实:限制者是谁

编译器自己在赢家处的归因(`occupancy_limiter`):

| 限制者 | 赢家数 |
|---|---|
| `registers` | **38** |
| `shared_memory` | 18 |

这印证了 `triton-caps-regs-instead-of-spilling`:寄存器是首要限制者。
**但它不能变成 occupancy 墙** —— 见上。它的正确用途是**给 `n_spills` 墙提供"为什么"的说明文字**。

## 3. `n_spills` 通过了同一关

为公平起见,把完全相同的检验施加给 `n_spills`(否则结论会变成"我第二个测的那个赢"):

| | 结果 |
|---|---|
| 关系形状 | 27 峰形 / **18 单调符合预期(越多越慢)** / 6 反向 / 5 其他 |
| **赢家在自己 spill 范围的位置** | **中位 0.00** —— **56/56 全在最低端(≤0.2)** |
| 赢家 spill 为 0 的比例 | **32/56(57%)** |

**关键差别**:`n_spills` 的赢家**无例外地**坐在自己范围的最低端。
⇒ **"减少 spill"与实测最优点的方向一致**,这正是 occupancy 缺的那一条。
(峰形仍有 27 个,说明**不能**把它当成单调规律用;但"往下走"这个方向从不与最优点冲突,
因为最优点本身就在最低端。)

**一条要写进实现的限制**:32/56 个赢家 spill 为 **0** ⇒ 对这些候选,
**在最优点处没有 spill 墙可找**。所以这个检测器只能在**其余 43%** 的候选上产生结论,
报告必须写"多少候选适用",不能只报"找到几个墙"。

## 4. 墙形状:这个判据在真实数据上确实出现

判据形式:**某 knob 增大 ⇒ 信号单调恶化并进入绑定态,且延迟在该端仍在改善**。
(最后一条是 `tail_gain_pct > 0` 过滤,与共享内存墙同一条。)

在 454 个(候选, knob)对上:

| 信号 | 单调进入绑定态 | 其中延迟仍在改善 |
|---|---|---|
| `occupancy` | 152 | **69** |
| `n_spills` | 132 | **49** |

`n_spills` 的样例(斜率最大的几个):

| 候选 | knob | 取值数 | spills 变化 | 尾部斜率 |
|---|---|---|---|---|
| cand-36fea075 | `GEMM_NUM_WARPS` | 3 | 0 → 72 | **+54.1%** |
| cand-da341a61 | `ATTN_BLOCK_M` | 4 | 0 → 16 | +50.5% |
| cand-f997f04c | `GEMM_N_SPLIT` | 3 | 4 → 29 | +49.7% |
| cand-f49f5b32 | `ATTN_BLOCK_M` | 3 | 0 → 46 | +47.0% |
| cand-4f7b6838 | `GEMM_K` | 3 | 0 → 9 | +45.4% |

⇒ **判据不是空的**:49 个 (候选, knob) 对满足全部条件,分布在 **29/56 个候选**上。

### 4.1 与硬墙的产出对比 —— 只能给同底数字,不能给倍数

我本想写"比硬墙大一个数量级",**但那样比较是错的,已改掉**。
这五个 run 都在共享内存筛子(2e)**上线之前**,`RESOURCE_WALL_ATTRIBUTED` 事件数为 **0**(逐 run 核实),
而且用出厂 `find_walls` 离线重放同一份数据也得 **0 个墙 / 0 个 probe-worthy / 0-56 个候选**
—— 原因是没有 `infeasible_shared_memory` 的 trial 记录可读,不是判据无效。

| | 硬墙(共享内存) | 软墙(`n_spills`) |
|---|---|---|
| 本语料上的产出 | **0 / 56 候选**(该 run 时期无筛子记录 ⇒ **不可比**) | **29 / 56 候选**,49 个 (候选,knob) 对 |
| 三臂 run 上的产出(另一份语料) | 个位数;arm3 是 6 个墙 / 19 候选,1 个被归因 | 未测(三臂日志不在本机) |

⇒ **正确的说法是**:软墙在**这份 2788 trial 的语料上**能产出 49 条结论,而硬墙在**同一份语料上**
产出 0 条(因缺少筛子记录)。**两者的产出规模需要在同一个 run 上并行测量才能比较** ——
这应当作为实现后的第一项验收,而不是现在的断言。
(`box1-and-box4-have-different-cpus-so-trial-counts-are-not-comparable`:
跨语料比数字是本项目记过的错。)

## 5. 这两个软墙具体会怎么影响框架流程(你问的第二部分)

### 5.1 现在的硬墙流程(共享内存)

```
调参循环内:
  每个 trial → _screen_config() 编译期比 max_shared → 超限则
      TrialRecord(status="fail", failure_kind="infeasible_shared_memory")
      + 事件 CONFIG_SCREENED_INFEASIBLE
      + 告知 Optuna 为 PRUNED(留在 TPE 模型里)

调参结束后(_stats_and_analysis):
  _attribute_resource_walls()
    ← 读 crun.trials 里 failure_kind == "infeasible_shared_memory" 的 params  ← 关键输入
    → find_walls(stats, refused)            找"被拒值落在已测范围之外"的 knob
    → select_for_probing()                  只留 monotone 且 tail_gain > 0
    → _probe_walls()                        在 θ* 处做消融,一次批量编译探针
    → RESOURCE_WALL_ATTRIBUTED 事件
    → for_prompt() → crun.wall_text
  → 进 analyst 的 digest_text,并由 _do_rewrite 交给该族的 rewriter
```

### 5.2 软墙必须改哪些环节 —— 四处,而且**不能改前三处**

| 环节 | 硬墙 | 软墙(`n_spills`) | 影响 |
|---|---|---|---|
| **① trial 判定** | 配置被**拒绝**,记 `failure_kind` | **不拒绝** —— 配置正常完成,只是 profile 里 spills 非零 | **不改任何东西**:软墙**不产生失败**,不影响成功率、不影响预算、不影响 Optuna 收到的状态 |
| **② `find_walls` 的输入** | 被拒参数组列表 | **没有被拒参数组** ⇒ 现有函数**结构上读不到** | **必须新增一个判据函数**,不能给 `find_walls` 加参数 |
| **③ 探针(`_probe_walls`)** | 在 θ* 处改一个 knob,问编译器"还超限吗" | **无需探针** —— spills 已经在每个 trial 的 profile 里测过了 | **零 GPU 成本**;不需要 `prescreen_batch`,也不占 `probe_total_s` |
| **④ 输出** | `RESOURCE_WALL_ATTRIBUTED` + `for_prompt` 文本 | 同一条链路,新增一种 `kind` | 复用现有事件与投递路径 |

**最要紧的一点:软墙对调参循环是完全透明的。**
它不拒绝配置、不改变采样、不动 trial 预算、不改 Optuna 收到的状态 ——
所以它**不破坏 run 间的 trial 预算对等**,这是它与 S7 的根本区别(S7 改分配 ⇒ 必须配对照臂)。

### 5.3 新判据函数的形状

```
find_soft_walls(stats, trials) -> list[SoftWall]:
    对每个数值型 knob:
        按取值分桶,取每桶的 spills 中位数与延迟中位数
        要求 ① 单调不减 ② 末端进入绑定态(spills > 0)
              ③ 尾部延迟仍在改善(tail_gain_pct > 0)
        → SoftWall(param, values, spills_curve, tail_gain_pct, limiter_at_optimum)
```

三点与硬墙的必要差异:
1. **没有 `refused_value`** —— 软墙没有"被拒的那个取值",只有"恶化到绑定态的那个取值";
2. **没有 `verdict`/探针** —— 结论直接来自已测 profile,所以**也没有 `second_origin`**
   那种"换个原点复验"的动作。这是**弱点**,必须在文本里说明:
   硬墙的归因经过了一次独立的编译器确认,软墙没有;
3. **必须报"适用面"** —— 32/56 个赢家 spill 为 0,对它们无墙可找。

### 5.4 报给改写者的文本会是什么样

```
寄存器溢出墙(实测,来自逐 trial profile,未经独立探针确认):
  GEMM_NUM_WARPS:该 knob 从 4 增到 16 时,编译器的寄存器溢出从 0 增到 72 个槽位,
  而这一段上延迟仍在改善(尾部 +54.1%)。在该候选的最优点处,
  编译器报告限制驻留的是 registers。
  ⇒ 这一维仍有斜率,但继续增大会把中间结果挤到本地内存(比寄存器慢约两个数量级)。
  可考虑的方向:减少每线程活跃变量(拆分循环、缩小累加器、把部分中间量放共享内存)。
  这是一个提示,不是指令。
```

**刻意不写的**:不提 occupancy 数值(§2 已证"提高 occupancy"是反向建议),
不提资源向量、不提候选延迟绝对值(与 `for_prompt` 现有边界一致)。

### 5.5 风险清单

| 风险 | 说明 | 缓解 |
|---|---|---|
| **没有独立确认** | 硬墙有编译器探针二次确认,软墙只有一次观测 | 文本明写"未经独立探针确认";可选加一次 θ* 处消融探针(0.49s)看 spills 是否复现 |
| **27/56 是峰形** | spills-延迟关系并非普遍单调 | 判据要求**逐候选逐 knob 单调**,不套用全局规律;峰形候选自然不触发 |
| **适用面只有 43%** | 32/56 个赢家 spill 为 0 | 报告必须给分母;"没找到墙"与"不适用"要能区分 |
| **两个信号 ρ=−0.500** | `n_spills` 与 `occupancy` 中度相关 | 只做一个,避免同一现象报两次(这也是不做 occupancy 的附带理由) |
| 与共享内存墙同时出现 | 一个 knob 可能既溢出又超共享内存 | 分开报,不合并计数 —— `no-scalarization-of-resource-vector` 与 "verdicts stay plural" |

## 6. 建议

1. **实现 `n_spills` 软墙**:零 GPU 成本、对调参循环透明、不需对照臂,
   在这份 2788 trial 的语料上能产出 **49 条结论 / 29 个候选**。
   **不要**宣称"比硬墙多一个数量级" —— 见 §4.1,那需要在**同一个 run** 上并行测量,
   作为实现后的第一项验收。
2. **不要实现 `occupancy` 软墙** —— 峰形 37/56、赢家中位位置 0.33、仅 2/56 在顶端
   ⇒ 判据的建议方向与实测最优点相反。**这条应写进记忆,以免日后重提。**
3. `occupancy_limiter` **仍然有用**,但用途是给 `n_spills` 墙提供"为什么"的说明
   (赢家处 38 个是 registers、18 个是 shared_memory),不是自己当一个墙。
4. **先写测试再改**,至少三条:①判据在峰形曲线上**不**触发;②赢家 spill 为 0 的候选被记为
   "不适用"而非"无墙";③一个正对照 —— 构造一条单调进入绑定态且尾部斜率为正的曲线,
   断言它被检出(否则整个判据可能静默失效)。
