## 绑定方案及实验

`0566148` 增加可选 `binding_backend: scoped`，原默认 `legacy` 保留。
它仅在每个实际安装的 functional 站点都能解析到模块边界时，尝试在这些
模块执行期间启用分派。无模块边界的站点、多个 functional bundle 的模式
优先级仍沿用旧路径，安装回执记录原因。候选 build 接口、phase、动态
签名守卫、质量与覆盖检查不变。

三项目在相同候选字节和父版本上，分别比较 parent、passthrough、candidate；
每种条件使用 legacy/scoped 和反向顺序，共 12 个端点。运行入口为
`examples/v6_validation/run_binding_backends.py`，结果在 box4-2 的
`/root/autodl-tmp/dev/v6-work/stage2-binding-0566148`。这是开发者发起的
后端诊断，不发布候选，也不计为自主生成优化。

Qwen 当前父候选下，新 functional 站点的观测父边界均为整个 `model`，
因此局部启用没有消除大部分全局分派。不能因为单元测试中局部站点减少
了拦截次数就宣称真实模型获得收益。是否保留可选实现、是否切换默认，
分别由兼容性和完整项目实测决定。

首批 36 个端点全部通过原质量和覆盖。实际组合的两对端点中位数：
Qwen legacy/scoped 为 2351.461/2343.166 ms，DDP 为
216.134/221.434 ms，ResNet 为 3.131/2.693 ms。Qwen 配对方向不一致；
DDP 实际退回同一 global 后端，数字差异不能算 scoped 收益。ResNet 的
两对方向均有改善但幅度波动大。同一冻结源码的独立四对复测全部通过质量：
parent 为 1.611/1.604 ms，passthrough 为 3.587/2.497 ms，
candidate 为 3.678/2.622 ms，后两种条件的四对方向均一致。
这些组合仍比各自父版本慢，不能把绑定层差异当作整个优化方案已成功。

`6179733` 将 scoped 调用状态隔离到 ContextVar，并恢复 legacy hook
原有路径；`21897c1` 将实际后端与回退原因加入下一轮反馈。最终源码另做
独立四对绑定复测。首次复测在任何端点开始前撞到旧实验的同名 job 目录，
保留错误后改用唯一输出名重启；诊断入口随后采用完整输出路径的哈希命名，
避免不同目录中相同 basename 再次冲突。这不改变正在运行的框架或 Agent 会话。

`21897c1` 的四对复测已经完成，24 个端点全部通过质量。parent 为
1.604/1.528 ms，passthrough 为 3.244/2.939 ms，candidate 为
3.624/2.764 ms（均依次为 legacy/scoped 的端点中位数）。
candidate 四对均改善，passthrough 三对改善、一对变慢；原始 parent 的
波动说明不能忽略环境噪声。组合仍慢于 parent，scoped 保留为可选项。

## 通信观测进入反馈

`0e4c751` 为附加采集结果记录版本、父版本、bundle、请求、目标、设备
及框架来源。对进入完整配对评价并通过质量和覆盖的候选，重跑 Collector Agent 已选择的
采集器，保留父版本和候选的独立观测。

参数筛查阶段已被约束淘汰的候选没有进入这一步；其反馈仍保留完整筛查回执、
约束结果和已经执行的参数／回退诊断，不能声称每个淘汰端点都已重新采集所有后端。

Selection/Candidate 输入采用索引与完整 JSON 附件。索引包含版本和
采样窗口；完整字段、原始路径和不可用原因均保留，不按失败类别隐藏
数据。参数和 bucket 所属关系链接到实际组，保持多对多，不分摊共享
通信时间，也不把跨次采样的 bucket 顺序当作同一次事件身份。

GPU 输入就绪、消费完成和等待/传输分离仍必须由实际可用的关联信息
支持。当前 trace 的部分同步 API 只给出运行时关联号，没有足以恢复
唯一 event/stream 依赖的标识；这些数据不能补成已经证明的因果链。

## 冻结版本的全新输入验证

开发批次冻结在 `0e4c751`，目录为
`/root/autodl-tmp/dev/v6-work/stage2-autonomy-0e4c751`；
修复后的显存任务单独冻结在 `be51164`。统一验收批次的六条运行全部冻结在
`21897c1`，目录为 `/root/opop-v6-stage2/stage2-autonomy-final-21897c1`。
统一批次放在系统盘以分散磁盘空间占用，仍使用同一设备租约避免 GPU 测量相互干扰。
不导入历史 prepared run、分组、评测适配或成功候选。输入为已有
三项目源程序任务包、资产路径、固定 workload、目标和质量要求。
额外声明 observe 的字段结构，供独立源程序核对；没有提供实现或算子目标。

| 项目 | 两个目标 | 共同 workload |
|---|---|---|
| Qwen3-4B | TTFT、完整生成吞吐 | batch=1，prompt=256，生成32 token |
| ResNet-18 | 延迟、allocated 峰值（带吞吐约束） | batch=32，224×224 |
| GPT-2 DDP | 整步耗时、带整步约束的通信目标 | 2 rank，序列128，累积4 |

相同项目两目标使用相同任务输入和质量要求。与历史矩阵相比，ResNet
延迟使用 batch=32，以免把 batch 差异混作目标切换；Qwen 吞吐使用全部
32 个生成 token，与 cached decode 的31步口径区分。

每条运行执行：真实 Agent 生成适配 → 框架 controls → 独立源程序
输出核对 → 自动发现和采集选择 → 两轮真实选组、候选和评价 → 下一轮
读取上一轮反馈。两轮是实验协议，不限制 API 请求、token、费用或角色修复次数。
通信目标保留整步约束与新的 profiler 准备协议。

运行中发现问题不修改冻结代码、不补充人工消息。保存完整失败后，
在后续版本修复并启动新运行，不能把开发恢复称为原运行无人干预成功。
自动化是否完成、候选质量是否通过、是否获得可靠收益分别报告。

验证入口为 `examples/v6_validation/run_autonomous.py`。独立核对失败时
停止该条验收，保留失败任务，不在已经改变的任务上继续报优化收益。
核心检查 `21897c1` 为 33 passed，包含并发调用上下文、兼容回退、附件、
契约及后端反馈；不与历史重叠用例累加。真实运行结果须以完成回执为准。

## 冷启动发现的契约缺口

首批 ResNet 显存任务在 prepare 阶段失败：真实 Agent 把 `state_protocol`
写成对象，实际 ProjectContract 要求非空字符串。旧校验只检查字段存在，
导致错误在离开 Agent 自动修复循环后才暴露。原失败及会话完整保留。

`be51164` 给项目理解输出提供正式 schema，并在现有输出验证器中构造
完整契约。类型错误现在进入已有的契约修复机制；没有按失败类别增加
搜索路由。相关 5 项检查在本地和 box4-2 通过。该显存任务已在
`stage2-autonomy-be51164/resnet-memory` 从全新输入重跑，原首批其他任务
继续使用 `0e4c751`，不混写源码版本或把失败改成成功。

## 开发批次的中间证据

以下是已经结束的首轮，尚不代表对应两轮协议或统一六任务验收已经完成：

* ResNet 延迟：自主选择 8 组区域，候选通过完整质量，配对
  4.233575 → 3.6331685 ms，约降低 14.2%，接受。
* 修复后新开的 ResNet 显存任务：自主选择 10 组区域，allocated 峰值
  282,103,808 → 205,033,472 bytes，降低约 27.3%，吞吐不低于原始
  95% 的约束通过，接受。候选把 stem 分块处理，仍处理完整 32 个样本。
* Qwen TTFT 首轮区域候选未通过 logits 质量，拒绝。
* DDP 通信首轮候选完整质量精确通过，但整步约 235 ms 未通过原始约束，
  拒绝。候选尝试用 CPU barrier 移出 NCCL kernel 内的等待；
  kernel 累计时间降低不能解释为物理传输加速。

读取真实 OpenCode 数据库已确认第二轮 ResNet 延迟与 DDP 通信 Selection
会话读取上一轮反馈。附件中保留前后不同 revision 的完整采集结果。审计
“路径出现次数”包含列目录和写文件，不等同于读取次数，更不等同于正确理解；
最终证据需要结合具体工具输入与候选理由判断。
