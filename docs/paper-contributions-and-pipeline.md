## 1. 一句话总览

让 agent 优化 GPU 算子时不再盲目试错,而是沿着**资源**这条主线层层递进:
先知道**墙在哪**(C1),再知道**怎么用资源换性能**(C2),
最后知道**换来的"性能"应该用什么目标来度量**(C3)。

三条是一个递进链,不是三件独立的事:

```
C1:算子 ↔ 硬件资源维度对齐          →  告诉你「优化空间还剩多少、剩在哪一维」
        ↓ 建立在 C1 之上
C2:资源-性能斜率引导结构改写        →  告诉你「怎么改结构,才能把一份资源消耗换成更多性能」
        ↓ 建立在 C2 之上
C3:目标引导的算子优化              →  把 C2 的「资源→性能」转化,推广成「资源→端到端目标指标」转化
```

## 2. 三条 Contribution

### C1 · 资源维度对齐:在不断"撞墙"中把算子的资源形状对齐到硬件

**主张。** 对齐不是一次性的分析,而是一个**可观测的迭代过程**:调参 → 撞墙 → 换维改写 →
再调参……每一轮都让算子的资源消耗形状更贴合硬件的资源边界(寄存器 / shared memory /
DRAM 带宽 / 算力峰值 / occupancy),直到停在**实测的物理上限**附近,而不是停在"预算用完"。

**对齐具体怎么发生(一轮循环,四件事)。**

1. **调参即测量**:每个 trial 在记录延迟的同时记录各资源维度的消耗(n_regs / n_spills /
   shared_bytes / DRAM 与 tensor-core 占用)。所以调完一个参数空间,算子在每一维上
   "用了多少、离本机实测上限还有多远"就有了完整画像——不需要额外的 profiling 阶段。
2. **发现墙**:参数/性能斜率显示某个参数方向**仍有较大提升空间**(例如 BLOCK_N 增大方向
   单调变快),但沿这个方向再走一步就超出某一维的硬件上限(shared 装不下 / 寄存器溢出)。
   这就是一面"墙":**提升空间明明存在,却被单一资源维度堵死,调参在域内怎么走都够不到。**
3. **换维改写**:参数翻不过结构墙,所以框架改变**算子结构**:降低被顶住那一维的消耗,
   代价通常是提高其他仍有余量的维度的消耗——用富余的维换出稀缺的维。
   实例:full-K 单发 GEMM(shared 65 KB ⇒ 每 SM 只驻 1 个 block,寄存器 255 顶满 + 108 次
   spill)改成 K 循环分块,寄存器 255→140、spill 108→0,代价是多轮 shared 装载。
4. **对齐加深**:墙被推开后调参重新展开,原来不可达的取值域现在可达,算子**整体能用上
   更多资源**——不再被一维卡死,而是同时逼近多面墙。循环重复,直到剩下的墙是**物理的**
   (带宽 / 算力峰值,本机实测:下限 = max(必须流量/实测带宽, 必须算力/**该设备各精度与后端
   实测所得的最高峰值**)),
   对齐完成:此时"还能不能更快"第一次变成可核算的问题——离墙还有百分之几、顶住的是哪一维。

> ⚠ **峰值口径**(2026-09-24 修正):分母是**最高实测峰值**,不是 TF32 峰值。
> 三台设备分别为 A800 **233.9**、RTX 4090 **158.6**、RTX 5090 **214.85** TFLOP/s
> (均为张量核低精度档)。用 TF32 算会把 L3:43 的参照比例从 75.0% 错算成 153%。
> 流量侧按"输入+参数+输出各计一次"(compulsory traffic),
> 故**存在片上复用时候选可以略快于该下限**,这是定义边界不是测量错误。

**过程证据(一条实测轨迹,L2:16 的一个族)。** 种子 4.008 ms(shared 12 KB、寄存器 166);
第 1 轮改写用 **3.3× shared + 寄存器打满(255)** 换到 3.134 ms(改善 **21.8%**);第 2 轮换
**精度维**(fp16)并**主动接受 60 次 spill**,到该族全局最优(相对种子累计改善 **30.9%**)。
同轮两个失败的改写恰好从两侧夹出真墙:
继续加 shared 到 53 KB 反而变慢、削到 8 KB 灾难性变慢 3.6× ⇒ shared 已饱和,真墙在 DRAM
流量侧——与该任务 dram-bound 的独立判定一致。⇒ **资源是被交换的,不是被单调增加的;
连失败的改写都在定位墙。**

> ⚠ **只用相对改善,不要引用轨迹终点的绝对值**(2026-09-24)。该终点 2.770 ms 是
> **tuned_ms**(搜索循环内值),同一候选 final re-eval 为 2.87,而主表 A800/L2:16 是 2.790。
> 抄绝对值会让正文与主表自相矛盾(review 的 N5)。main.tex 已改为只写 21.8% / 30.9%。
> 一般规则:**tuned_ms 系统性乐观 1.5–6.7%,任何对外数字只能取 final re-eval**(见 §6 ⑧)。

**终点证据(对齐真的到了墙上)。**
- L3:48 的定稿候选 final re-eval **0.799 ms** 对参照 0.8024 ms = **100.4%**,
  即**已触及带宽墙**(4090 上为 107.1%);外部框架手写 CUDA、纯 fp32 的最优停在 **97.6%**
  (0.822 ms,其源码自述"≈实际混合读写带宽的 94%")——
  两条独立技术路线收敛到同一面墙,说明墙是真的。
  越过 100% 的部分由上面的 compulsory-traffic 口径解释(该任务 130 个 op,存在跨 op 复用),
  **写 paper 时必须同时给出这个口径**,否则"超过自己给出的物理下限"会被直接质疑。
- L2:59 的 fp32 下限(**2.609 ms**)已经贴住外部最强结果(**2.649 ms**):
  纯 fp32 即使做到理论极限也只领先 1.5%,落在噪声带内 ⇒ **fp32 这条路线没有可用余量**。
  框架读出"99.2% 流量被权重钉死、权重可量化",把 dtype 当作显式资源维度换掉,
  int8 做到 1.05 ms(2.52×)。⇒ 对齐不只用于"别越界",还能**发现哪一维必须被改变**。

**诚实边界**:对齐 ≠ 已达上限(L3:21 只到 10.7%,是当前余量最大的一格,但仍胜外部 1.248×)。
注意该比例**同时混入两件事**——候选离下限多远(我方本事)、下限对该任务多紧(任务性质,
对所有框架相同)。同一格最强对手只有 8.5%,所以 10.7% 是**胜格**,不是惨败;
写 paper 时若给出该比例,必须同时给出对手的比例,否则读者会当成效率排行榜。

### C2 · 资源-性能斜率引导结构改写(建立在 C1 上)

**主张。** C1 的循环里,"换维改写"是翻墙的那一步——但面对同一面墙,agent 会想出**好几种
不同的改法**,各自动不同的资源维,转化效率天差地别。C2 回答的就是"几种改法里选哪一种"。
关键约束是:**不能只是让算子占用更多资源——每一份新增的资源消耗,必须换回更多的性能。**
所以引导信号不是"哪个参数动了性能变多少"(性能斜率),而是**资源-性能转化响应**:
每个参数轴上,固定其他旋钮实测两端点,同时记录性能怎么变**和**各资源维度怎么被换掉
(资源斜率)。资源斜率告诉 agent **哪一维现在最该动、往哪个方向换是划算的**,
于是选中转化效率最高的那种改法。

**为什么必须建立在 C1 上。** 斜率只有对着"哪一维顶住了"这张图才有意义:
没有 C1 的资源画像与实测上限,"寄存器斜率 −0.027"只是个数字;
有了"寄存器已顶满 255、spill 108 次"这个背景,它才读作"这一维可以靠 tile 形状换出来"。

**最硬的证据(G0/G1/G2 消融,自变量只有"给 agent 看多少")。**
- G0 无斜率、G1 只有**性能**斜率、G2 加上**资源**斜率。结果:G2 对 G0 **4/4 胜**、
  对 G1 **3/4 胜**。关键对照是 G1:它连性能斜率都有(与 G2 逐位相同)仍然不及 G2
  ⇒ 主张被收窄到"资源斜率"这一件事上,而不是"信息越多越好"。
- 机制案例:父代被两面夹住(shared 65KB 致 1 block/SM,寄存器 255 满 + 108 spill)。
  只有拿到资源斜率的 G2 冲着那个 kernel 改结构(寄存器 255→140、spill 108→0,4.100 ms);
  G1 被性能斜率最大但资源无关的轴吸走注意力,只降了存储精度、108-spill 结构原封不动
  (5.076 ms,三组最差)。**"消耗资源换性能"与"白占资源"的分界,正是资源斜率给出的。**

**诚实边界**:资源斜率提高选对方向的概率(3/4),不是保证(有一格 G1 更好,已如实保留)。

### C3 · 目标引导的算子优化(建立在 C2 上)

**主张。** C2 的转化目标端始终是**算子自身 latency**。C3 把它推广:优化的目的从来不是
"这个算子更快",而是**用户声明的端到端目标指标 J**(TTFT / 单流吞吐 / 并发吞吐)。
于是 C2 的「资源→性能」转化效率变成「**资源→目标指标**」转化效率,带来两个推论:

1. **不同目标该优化的算子组不同**——同一份搜索资源(GPU 时 + agent 额度),投给哪个算子组,
   由该目标下的实测优化空间决定,而不是由"哪个算子最耗时"决定;
2. **判据必须是端到端目标指标**——算子单测更慢但目标指标更好,是合法且核心的接受理由。

**为什么必须建立在 C2 上。** "资源→目标指标"的转化链比"资源→latency"多一跳
(算子变化 → 整模型行为变化 → 目标指标变化),只有 C2 已经把"资源→性能"这一跳做成
可测量、可引导的,加长的链条才不至于失控:站点排名里的实测探针增益(probed_gain_frac)
就是 C2 的斜率思想在"算子组选择"层的同构复用——先花小钱实测转化响应,再投大钱。

**最硬的三个证据。**
- **3×3 矩阵**(3 个目标各自优化出 kernel × 3 个指标下测量):对角全正
  (+3.56% / +12.51% / +9.29%),离对角显著为负(ttft-kernel 在 single/multi 上
  −10.64% / −14.17%)⇒ **错配即伤害**,目标特异性不是"随便优化都变快"。
  ⚠ 九格来自三个 run,**基线各异**(TTFT 那一列的基线是 284.83 ms);
  正文只能写"各列基线在对应负载下分别测得",不能给一个统一基线。
  single 对角在两次独立运行测得 +12.51% 与 +9.42%,此处取前者(该次 single/multi 同源自洽)。
- **承载 ≠ 空间**:single 目标下 RMSNorm 站点承载的 CUDA 时间最小(2383 μs)增益却最高
  (+12.51%);承载最大的 **gate_proj 与 up_proj(同一站点)** 88822 μs 增益 ≈ 0 ——
  按耗时排序会选错算子组,按实测转化空间排序才对。
- **算子更慢、目标更好**:同一个 kernel 算子单测 0.98×(慢 1–2%),端到端 TTFT **+3.32%**
  (launch −219 次、显存流量 −7.13 GB,孤立微基准看不到这两笔)。全设备扫出 **291 个**
  同类 fixture ⇒ 用传统算子基准做判据,这些冠军会被整批误杀。

> ⚠ **两处必须照口径写**(2026-09-24):
> ① **gate_proj 与 up_proj 是同一个 site**(同一 `family_key`:72 个模块,
> 同为 `nn.Linear` 2560→9728,88821.9 μs)。88822 与 92975 **不是两个算子**,
> 而是**同一站点在 ttft 与 multi 两个负载下**的承载读数;
> 早期版本把 92975 当成 up_proj 的 TTFT 时间是事实错误(review 的 L7)。
> 因此 C3 第一个证据的表是**三行**:RMSNorm(73 模块)/ gate_proj 与 up_proj(72 模块)/
> SiLU(36 模块),两个负结果的机制不同——GEMM 的归约无法交给现有库实现、改写未过等价检查;
> SiLU 已是单个访存受限的向量化 kernel,没有可合并的启动或可复用的中间结果。
> ② **TTFT 改善有两个合法口径**:**+3.56%**(F4 密封矩阵,基线 284.829)与
> **+3.32%**(lane 定稿,基线 282.818),用在不同表里时必须分别标明基线。
> 曾出现的第三个值 **4.46% 无任何原始支持**(该候选落盘实测 −0.12%),已从 paper 删除,
> **不要再使用**。

## 3. 框架流程(不含 C3):输入是一个算子任务

输入 = 一段参考实现 + 固定输入形状(KernelBench 式)。八个主步,前两步一次性,③–⑦ 循环;
另有两个挂载步(④′ 扩域、⑦′ novelty)与贯穿全程的 ③′ 低成本测试,详见 §6:

```
①设备标定+基线 → ②种子生成(agent) → ③正确性门(+修复agent) → ④参数调参 →(④′扩域)
      ↑                                                            ↓
      └──── ⑦结构改写(agent) ← ⑥斜率采集 ← ⑤资源画像与瓶颈判定 ←──┘
      └──── ⑦′新族注入(novelty,占 6 个族名额中的 2 个)
                                          (③–⑦按族循环:每族 5 轮 / 连续 2 轮改善<2% 冻结
                                           / 12h 墙钟兜底;③′ 的三档评测贯穿全部评测点)
                              → ⑧最终独立复评
```

| # | 步骤 | 做什么 | 为什么需要这一步 |
|---|---|---|---|
| ① | **设备标定 + 基线** | 本机实测带宽 / 各精度峰值 / 空 launch 地板;测 eager、torch_compile、tf32 变体基线 | 对齐的对象是"这台机器的资源边界",所以边界必须先被实测出来:墙的位置决定后面每一步"还有多少空间、顶没顶住"的判断,基线定义"提升"相对谁而言。没有这一步,对齐没有靶,提升没有分母 |
| ② | **种子生成(agent)** | agent 写出若干**结构互异**的候选,每个带 `PARAMS` 旋钮字典(tile 形状 / 精度档 / stage 数…) | 一个结构就是一种"资源消耗形状"的假设:它决定各资源维的可达范围,参数只能在其中挪动。多个结构互异的种子 = 多个不同起点,避免搜索被第一个假设锁死;把 tile/精度/stage 做成显式旋钮,后面的测量与引导才有明确的"轴"可依(精度入轴也是 C1 把 dtype 当资源维度的入口) |
| ③ | **正确性门(+修复 agent)** | 双见证宽容门(99% 元素在 1% 相对误差内 + 余弦 ≥ 0.99985)或 fp64 相对门(遵循 `torch._dynamo.utils.same()`,倍数 2.0 / 3.0,详见 §6 ③);数值不达标交独立修复 agent,反馈携带门限判据与噪声底 | 精度本身是一个可交换的资源维(用 fp16/bf16 换速度),但交换必须有硬边界,否则"更快"可以靠算错换来。门要同时做到两件事:挡住真错的、不冤杀"比 fp32 参考更准"的低精度候选(fp64 相对门的作用)。反馈带具体差距,是为了把"精度不达标"从死刑变成可修复状态(补偿 / 换精度档) |
| ④ | **参数调参** | 每候选在其参数空间采样(每空间 40 trial,可扩域),记录延迟**和资源画像**(n_regs / n_spills / shared_bytes) | 两个目的:①公平比较——结构的好坏只能在它的旋钮空间被探索后判断,拿没调过的和调好的比会选错结构;②调参本身就是对齐的测量仪——带着资源记录走一遍参数空间,才知道每一维在哪里饱和、哪个方向被堵。⑤ 的"墙"不是静态分析出来的,是调参撞出来的 |
| ⑤ | **资源画像与瓶颈判定(C1 落地)** | 对照①的实测上限算各维占用,标出"哪个旋钮的哪个方向被哪一维资源顶住"(墙) | 延迟数字分不清两种"慢":已经贴住物理墙(没救了),还是被某一维人为堵死、其他维还空着(有救)。这一步把"它慢"翻译成"它被 X 维顶住",改写才有靶子;也只有它能判断"该停了"——剩下的墙若是物理的,继续烧预算就是浪费 |
| ⑥ | **斜率采集(C2 落地)** | 逐参数轴:固定其他旋钮,实测两端点,得性能斜率 + 各资源维斜率 | 光知道"哪一维被顶住"(⑤)还不够——解开一面墙不代表值得解:一次改写完全可能腾出了资源却换不来性能(只是在挪资源)。斜率把每个参数方向的**性能响应**和**资源响应**成对测出,回答的正是"在这一维上花/省一份资源,能换回多少性能"——它区分**值得做的资源交换**与**单纯增加资源消耗**,防止为了对齐而对齐;⑦ 里几种改法选哪种,靠的就是这份定价 |
| ⑦ | **结构改写(agent)** | 把资源画像 + 墙 + 斜率写进简报交给 rewriter,产出新结构:**花掉有余量的维,换出被顶住的维** | 墙是长在结构里的,参数在域内怎么走都跨不过去;改写是唯一能改变"资源消耗形状"本身的杠杆。它消费 ⑤⑥ 的产出:冲着被顶住的那一维去,用斜率说"有余量且划算"的维来支付——"每份新增资源消耗必须换回更多性能"这条约束就落地在这一步 |
| ⑧ | **最终独立复评** | 全新进程、100 采样,取 `final_reeval` 中位数为唯一报告值 | 冠军是"因为测得好才被选中"的,选择过程本身会让循环内的数字偏乐观(选择偏差)——所以选它的数字不能同时用来报告它。独立新进程重测,让报告值在搜索循环之外可复现;对外主张的一切加速比只从这里读 |

## 4. 含 C3 的扩展:输入变成"一个整模型 + 一句目标"

C3 不替换上面的回路,而是在**前面加五步**(把模型级输入转成算子任务)、在**验收处换判据**:

```
⓪a 目标合同化 → ⓪b 短窗口profile → ⓪c 算子分组+资格门 → ⓪d 站点排名与选择 → ⓪e 任务包
                                                                        ↓
                                              进入 §3 的核心回路(②–⑦)
                                                                        ↓
                                    验收:端到端目标指标 + 自校准精度 floor(不看算子 latency)
```

| # | 步骤 | 做什么 | 为什么需要这一步 |
|---|---|---|---|
| ⓪a | **目标合同化** | 用户目标("prefill 快些")→ GoalSpec:方向 / 单位 / 负载形状 / 冻结 prompt 集 | 自然语言目标无法测量、无法比较、无法验收;合同把它固定成"在什么负载下测什么数、往哪个方向"。负载形状必须进合同,因为**同一个模块的重要性随负载完全不同**(prefill 重的目标和 decode 重的目标,热点根本不在同一处)——目标不定形,后面选哪个算子组就无从谈起 |
| ⓪b | **短窗口 profile** | 按合同负载真跑一遍模型,逐模块记录:路径、类源码、权重几何、张量形状、每个 CUDA kernel 的归属与耗时 | 该优化什么必须**问模型本身**,而不是靠人对架构的印象——印象既不知道这个具体负载下热点在哪,也枚举不全模块。跑一次、全记录,之后所有分类和排名都只读这份文件:贵的测量做一次,便宜的决策做无数次 |
| ⓪c | **算子分组 + 资格门** | family = sha256(模块源码+权重几何+属性)——代码和几何一样的就是同一种算子,36 个 MLP 自动归组;再过五道门(叶子 / KV-cache 纯度 / 几何代表 / 不嵌套 / 实测容量) | 分组解决"优化一个 = 优化一类":一份 kernel 要替换全部同类实例,所以"同类"必须有严格定义——按身份(代码+几何)分组零手写规则,换模型照样成立。资格门解决"别选一个做不成的":有些组根本无法打包成任务(带 KV cache、形状不唯一),让它们在排名前就出局,搜索预算才不会烧在注定失败的对象上 |
| ⓪d | **站点排名与选择(C3 落地)** | 三层排序:短探针**实测增益** > (可达性 + 承载) > 实测无空间;每 goal 独立排,跨 goal 冲突自动消解 | 这是"资源→目标指标"转化效率的定价步:搜索资源(GPU 时 + agent 额度)投给哪个算子组,回报差异巨大,而**最直觉的判据——谁最耗时——是错的**(耗时大只说明它承载多,不说明它有可优化空间:可能已被 cuBLAS 调到峰值)。所以用小额探针先实测"这个目标在这个组上有多少油水",再决定大额投入——与 C2 用斜率给改法定价是同一个思想,只是抬到了选组层 |
| ⓪e | **任务包生成** | 选定站点打包成自包含 OperatorBrief:参考源码 + 代表张量形状 + 数值语义口径 + 证据指纹 | 让"模型里的一个算子组"变成核心回路能直接消费的任务(与 KernelBench 任务同构),核心回路一行不改——C3 因此是纯前置扩展而非重写。数值语义口径必须随任务走(正确性的标准是任务的一部分);证据指纹保证任何后续结果都能对回"当时选的是什么、依据是什么" |
| — | **验收换判据** | 接受与否看**端到端目标指标**(J 相对 baseline 的增益)+ 自校准精度 floor(站点 1-ULP 差异在 logits 上的实测放大值定门限,NLL 双保险) | 用户要的是目标指标,不是算子跑分——而两者会**真实地背离**:算子孤立测更慢、放进整模型目标反而更好(融合省掉的 launch 和中间张量往返,孤立基准根本看不到)。若沿用算子 latency 做判据,这类冠军会被整批误杀,所以判据必须换。精度门用自校准 floor,是因为固定容差对不同站点/不同序列几何不公平——门限本身也应当被测出来,而不是拍出来 |

| 支撑机制(不单独成条 contribution) | ①′候选契约与后端、③′低成本测试、④′扩域、⑦′novelty、⑧独立复评 | 搜索空间怎么界定?成本怎么控?路线从哪来?报告值可信吗? |

最后一行这些机制**不要写成 contribution**——它们是让上面三条成立的工程条件。
但 method 必须写:少了它们,读者无法判断搜索空间的边界、成本口径和报告值的可复现性。

与 paper 三条主线的对应(main.tex:232–234)是一一对齐的:
资源对齐 → C1;信息消融 → C2;模型级目标驱动 → C3。三个 `\subsection` 同序同措辞。

递进关系再说一遍(这是论文叙事的主轴):
**C1 没有 C2 就只是诊断**(知道墙在哪但翻不过去);
**C2 没有 C1 就没有靶子**(斜率对着空气没有意义);
**C3 没有 C2 就不敢加长转化链**(资源→算子→模型→目标,中间那跳必须先被证明可引导)。
反过来,C3 也回头改变了 C1/C2 的意义:同一面资源墙、同一条斜率,在不同目标下值不值得攻,
答案不同——**资源的价值由目标定价**。

## 6. 各步骤的具体做法(method 级细节,可直接支撑论文 Method 章)

> 编号对应 §3 / §4 的表。每小节给出:机制、判据(含默认值)、以及实现位置(便于核对)。
> 判据里的数字是**设计参数**(门槛/预算),不是实验结果——写 method 需要它们。
>
> 两条使用说明:
> ① **本节的默认值已于 2026-09-24 逐项核对 `src/kernel_optimizer/config.py`**,可直接引用。
> ② 本节少数条目附有**支撑该设计选择的离线统计**(如"中位数排序正确率 93.2%"、
> "44.7% 的旋钮不一致")。这些是**设计依据,不是实验结果**,main.tex 中一处也没有出现,
> **也不应写进正文**——否则会把 method 写成实验报告。它们只用于回答审稿人
> "为什么这么设计"一类质询,适合放进 rebuttal 或附录。

### ① 设备标定 + 基线

- **实测三类边界**:DRAM 带宽(大块拷贝)、各精度档(fp32/tf32/fp16/bf16)GEMM 峰值、
  空 kernel 的 launch 地板。全部在本机测,任何阈值(如 DRAM 饱和判定线)从标定值**推导**,
  不使用手册常数。
- **任务成本核算**:在参考实现上测出 required arithmetic(GFLOP)与 unavoidable traffic
  (输入+参数+输出各计一次的字节数),得物理下限
  `floor = max(traffic/实测带宽, FLOPs/该设备各精度与后端实测的最高峰值)`
  与融合余量(参考实现实际搬运量 / 必须量)。
  **峰值取最高档**(A800 233.9 / 4090 158.6 / 5090 214.85 TFLOP/s),不是 TF32;
  流量口径为 compulsory traffic,故有片上复用时候选可略快于该下限。
- **基线**:eager、eager_tf32、torch_compile、torch_compile_tf32 各 100 个计时样本,
  与候选同一计时方法(CUDA event)。报告口径:同精度加速比对 `torch_compile_tf32`。
  三台设备的标定值见 main.tex 的 `tab:hardware_resources`
  (带宽 1683.1 / 907.1 / 1512.3 GB/s;fp32 18.97 / 54.92 / 66.11;
  tf32 114.5 / 89.76 / 113.88 TFLOP/s)。

### ①′ 候选契约与后端集合(原缺;审稿人第一批问题之一)

> §3/§4 通篇没说候选是用什么语言写的,main.tex 里 `Triton`/`CUDA` 也零命中。
> Method 必须声明这两件事,否则"结构搜索"的搜索空间是不定义的。
> 实现:`agents/prompts/candidate_contract.md`(323 行,随每次 agent 调用注入)+
> `models/core.py:22`。

- **允许的后端集合**:`Backend = Literal["triton", "cuda"]`——Triton kernel 或
  手写 CUDA/C++ 扩展,二者皆为一等公民,profiler 对两者都给出真实资源读数。
  后端进入结构签名(见 ⑦),所以"同一算法改用 CUDA 重写"算一个**新结构**而非重复候选。
- **候选契约的硬性条款**(机械校验,违反即自动拒收):单文件、KernelBench solution 格式、
  `class ModelNew(nn.Module)` 且 `__init__`/`forward` 签名与参考一致、
  禁止自定义 `get_inputs`/`get_init_inputs`(一律用参考自带的输入工厂)、
  模块级禁止网络与文件系统访问、**必须且只能有一个模块级 `PARAMS` 字典字面量**
  (不改变任何行为的 PARAMS 项会被拒)。
- **精度条款(与 ③ 的门配套,须一起写)**:**输出 dtype 与形状必须与参考一致**,
  而**内部计算精度是自由设计维**——契约明确告诉 agent 不要在源码里锁定某一精度,
  由调参依据实测决定;并明确"保持输出 dtype 的低精度计算路径是一等、被接受的策略"。
  这正是 C1 把 dtype 当作显式资源维度(L2:59 的 int8)的**制度前提**。
  ⚠ **两个版本并存,主表跨机不一致**:旧版第 45 行写的是
  "fp32 unless the reference uses another dtype; do not silently downcast"(字面禁止降精度,
  与鼓励张量核的章节矛盾),已于 2026-09-23 00:56 在三台 4090 与 5090 上改写,
  **A800 故意未改**。主表的 A800 六格用旧版、4090 十二格与 5090 六格用新版
  ——已逐份取证,详见 §9 第 2 条;是否写入正文见 §0.4。
- **契约何时生效**:`agents/modules.py:53 _contract_doc()` 在**每次构建 agent sandbox 时读盘**,
  并把副本写进该 sandbox 的 `docs/candidate_contract.md`。
  ⇒ 改契约对随后的每次调用立即生效(不需要重启 run),
  且**每个 run 留有它当时真正收到的契约副本**,是审计契约版本的权威记录。

### ② 种子生成

- generator agent 一次产出 **4 个结构互异**的种子(`max_seed_candidates=4`)。每个候选必须
  自带 `PARAMS` 字典(tile 形状 / warps / stages / 精度档等旋钮及默认值)。
- **参数化**:parameterizer agent 把每个种子转成 `ParameterSpace`——逐旋钮的**离散取值表**
  (choice grid),即每个旋钮列出 3–6 个候选取值,而非连续区间。
- **入场检查**(不花 GPU 或只花一次编译):AST/lint 验证 → 静态 guard(按取值组合估算
  shared memory 等,超限组合直接标不可行)→ 两个 witness 配置实际编译运行
  (default = PARAMS 默认值;minimal = 每旋钮取 `choices[0]` 的角落配置,专抓 fp16 角落错误)。
- **族**:每个种子创建一个"族"(family);结构签名 = AST 规范化(去注释/docstring/字面量
  规整)后的哈希,签名相同判为重复候选拒收。

### ③ 正确性门 + 修复

- **门的两条通路**(顺序判,第二条只用于救回):
  1. 宽容双见证门(`correctness_mode: dual_witness_relaxed`):候选输出对 tf32 **或** ieee
     两份参考之一满足"≥99% 元素相对误差 <1%" 且 cosine ≥ 0.99985
     (`cosine_min`)。"双见证"指的就是 tf32 与 ieee 这两份参考;
  2. fp64 相对门(仅当 1 失败时判):以 fp64 金标准为准,
     `候选误差 ≤ multiplier × 参考自身误差 + tol/10`,multiplier = 2.0(fp32 候选)/
     3.0(fp16/bf16 候选)。**只能救回,不能否决**——比 fp32 参考更准的低精度候选由此通过。
- **这条通路的可信度论据(建议写进 method)**:第二条路径**遵循 PyTorch 的
  `torch._dynamo.utils.same()`**,倍数 2.0 / 3.0 与 PyTorch 使用的一致
  (实现见 `src/kernel_optimizer/config.py:327-347`,注释已明写 "following")。
  而 KernelBench 官方按精度放宽容差(`KernelBench/src/kernelbench/eval.py:83-102`:
  fp32 用 1e-4,**fp16/bf16 用 1e-2**,自述 "inspired by torchbench");
  本框架对**所有**候选用同一组条件,因此对低精度候选的要求**严于**该基准所允许的范围。
  ⇒ 这不是"我们把门放宽了",而是"我们对低精度比官方更严",写 method 时应正面给出。
- **另一种模式**:`correctness_mode: strict` 走 KernelBench 官方
  `eval_kernel_against_ref`(fp32 下 allclose 1e-4)。两种模式是配置项,实验用哪个须声明。
- **失败路由**:数值不符(witness_* 类)→ 独立 repair agent,最多 `repair_attempts=2` 次;
  其他失败(编译/OOM/超速嫌疑)→ 作为文本反馈回 parameterizer。
- **修复反馈的内容**:frac_within_tol / cosine / max_abs_diff / p99 相对误差 / 参考噪声底 /
  fp64 RMSE 比值,外加三分支数值诊断(尾数不足 → hi/lo split 补偿配方;按精度档分支的算法;
  fp16 溢出 → 建议 bf16),并携带此前尝试记录防止在两个方案间来回翻转。

### ③′ 低成本测试(评测的三档成本梯度)

> 这一节原本缺失,但它是框架控制搜索成本的主要手段之一,**method 必须写**。
> 实现位置:`evaluation/correctness.py`(`screen` / `quick_test` / `full_eval` /
> `prescreen_batch`),预算见 `EvalConfig`。

- **三档评测,按成本升序**,同一套正确性判据只改采样数:
  | 档 | 正确性样本 | 计时样本 | 用在哪 |
  |---|---:|---:|---|
  | `screen` | 3(`quick_correctness_trials`) | 0 | 只判对错,共享 GPU 通道、可并发 |
  | `quick_test` | 3 | 20(`quick_perf_trials`) | **每个调参 trial**(一次 run 数百次) |
  | `full_eval` | 5(`correctness_trials`) | 100(`perf_trials`) | 候选定档、最终复评 |
  ⇒ 贵的测量只在少数决策点做。launch 开销等附加测量只挂在 `full_eval` 上
  (它已经跑 100 个样本,多约 150 次调用可忽略),不进 `quick_test`。
- **批量预筛(prescreen)**:一批参数取值组合先共用一次编译筛查,自己的截止时间是
  `prescreen_base_timeout_s=30 s + 3 s/配置`,并受 `build_timeout_s=1200 s` 上限约束;
  单配置筛查另有 `screen_floor_timeout_s=120 s` 的下限。
- **关键性质(写 method 时值得明说):预筛超时不会丢弃任何候选。** 预筛**只缓存答案**,
  超时则该键缺席、`cached_shared_verdict` 返回 `None`(三值语义),
  该配置照样获得一次完整的真实 trial。⇒ 低成本档只能**省时间**,不能**改变结论**。
- **静态 guard 更便宜**:按取值组合估算 shared memory 等,超限组合直接判不可行,
  **零 GPU 成本**(见 ④ 的不可行区学习)。
- **诚实边界**:低成本测试降低风险,不保证保留最终最好的结构——20 个样本的排序
  与 100 个样本的排序可能不同,这是该设计已知的代价。

### ④ 参数调参:探索策略的直接回答

- **采样器**:Optuna TPE,`multivariate=True, group=True`(联合建模旋钮间相关,而非逐旋钮
  独立),随机种子固定。**前 10 个 trial 为随机启动**(纯探索),之后由 TPE 的后验平衡
  利用与探索。每空间预算 **40 trial**。
- **优先级问题的答案:采样目标始终是最优性能,不显式"找墙"。**
  墙是**免费副产品**:guard 拒绝、编译失败、OOM 的 trial 全部落盘,墙从这些记录里**读出来**
  (见⑤),不花采样预算去撞。探索由启动期与 TPE 后验负责,没有单独的"探索未知区"目标。
- **不可行区的学习**:guard 拒绝的抽样以 PRUNED 状态告知 sampler 并重抽(每次 ask 上限
  64 次)——sampler 学会避开不可行区,且这些拒绝**不花 GPU 时间**。
- **锚点**:已知好配置(如改写候选继承父代的获胜配置)通过 `enqueue_trial` 插队优先实测,
  保证"新结构至少在旧最优点上被测过"。
- **有序 categorical**:数值梯子型旋钮(BLOCK_N ∈ {32,64,128,256})向 sampler 声明相邻关系,
  使"64 和 128 比 64 和 256 更近"这一结构可被利用。
- **每 trial 记录**:延迟(取稳健统计;分析与调参读同一统计,按选值聚合用**中位数**——
  实测中位数对"哪个取值更好"的排序正确率 93.2%,均值只有 64.8%)+ 资源画像
  (n_regs / n_spills / shared_bytes,来自编译器报告,零额外成本)。
- **斜率默认不引导采样**(见⑥):诊断产物进 analyst/rewriter 的简报,不改变 TPE 的队列。
  存在一个可选机制(S7 slope_guide)把墙检测移进调参循环:每 10 个完成 trial 重算一次墙,
  向 TPE 队列**建议性**插入至多 2 个朝墙方向的点(不删值、不缩域、不加预算);
  它与⑥的四槽扫描互斥,二者不得同时开。

### ⑤ 资源画像与瓶颈判定

- **两级测量**:每 trial 的编译器级画像(寄存器/溢出/shared)免费全量;最优 trial 另跑
  profiler 得 DRAM 占用、张量核占用、launch 计数。
- **瓶颈四分类**(阈值由①的标定推导):`memory_bound`(DRAM 占用超饱和线)/
  `compute_bound`(算力侧超线)/ `launch_bound`(接近空 launch 地板)/
  `resource_limited`(寄存器或 shared 压住 occupancy,两侧都上不去)。
- **硬墙判据**(`find_walls`):某旋钮存在**被拒绝的取值落在已测范围之外**(即"再走一步
  就被资格挡住"),且已测范围**尾部 ≤3 个取值的中位延迟单调向墙变好**——两个条件同时成立
  才算"提升空间被截断"。随墙记录 `tail_gain_pct`(尾部单调段的改善幅度,即墙前斜率的大小)。
- **墙的筛选**:按 tail_gain 从大到小排序;**平坦或变差方向的墙不值得解**(解开买不到性能),
  被跳过——这是"避免为对齐而对齐"在墙这一层的体现。
- **软墙**:spill 数随某旋钮单调上升的曲线,单独归因(证据强度低于硬墙,在简报中分开标注)。
- **边界锚点**:判断"最优点是否在测量域边缘"时,锚定**获胜 trial 实际使用的取值**,而非
  中位数曲线的最优取值——两者在 44.7% 的旋钮上不一致,锚错会把扩域指向反方向
  (实测错向扩域成功率 2.6%,对向 21.8%)。

### ⑥ 斜率采集:计算方式与协议

- **一轴对比(one-axis contrast)**:每次只动一个旋钮,**其余全部旋钮冻结在准入时刻的
  取值上**(伙伴配置一经冻结不再随后续更优解更新——否则两端点各自搭配不同伙伴,差值
  就不再归属于这个轴)。
- **端点选择**:F = 远离墙的内点,N = 墙侧点(当前测量域内最靠近被拒值的可行取值);
  若最优点已在边界上,N 取边界值本身、F 取向内的对照点。
- **测量协议(四槽)**:每端点测 discovery + validation 两对,**顺序内部随机化,明确禁止
  ABBA 镜像顺序**(在线性时间漂移下镜像顺序会制造 −(bΔ)² 的假协方差);四个端点**全部
  新鲜测量**,不复用历史上的任何读数(包括曾经的最优 trial)。
- **斜率计算**(端点差商,不做拟合):
  - `parameter_slope = ΔJ / Δθ`(J = 目标值,θ = 该轴取值;仅对数值轴定义);
  - `resource_deltas[r] = r(N) − r(F)`(r ∈ {n_regs, n_spills, shared_bytes, …});
  - `resource_slopes[r] = ΔJ / Δr`——**每变化一单位资源 r,换回多少目标改善**。
    这就是"资源-性能转化定价":比值好 = 值得交换,资源动了 J 不动 = 单纯挪资源。
- ⚠ **两类斜率都是未归一化的原始差商,跨轴不可比较——method 必须写明这一句。**
  `parameter_slope` 随 θ 的单位缩放:一个取值为 {1,2,4} 的小整数轴与一个取值为
  {32,64,128,256} 的轴,即使端点延迟改善相同,斜率也差一个数量级。
  实验部分正靠这一点论证:`SPLIT_M` 性能斜率 −0.787、`BLOCK_N` −0.031,**差 25 倍**,
  而两轴端点降幅只差约 3 倍(85.3% vs 28.2%)。
  ⇒ 若把斜率当成"影响力排行",会得出与本文主张**相反**的结论
  (本文的主张恰恰是:**大的性能斜率不一定指向该改的结构**)。
  斜率的用途是**方向与配对**(该轴往哪走、同时换掉了哪一维资源),不是跨轴排序;
  轴间比较一律用 ⑤ 的 `tail_gain_pct` 或端点降幅百分比。
  同理 `resource_slopes[r]` 的量纲是"目标单位 / 资源单位",只在同一个 r 上可比。
- **探哪些轴**:不是全部轴,只探⑤筛出的高 tail_gain 墙(按分排序取前几个)。
- **预算**:诊断槽位从调参预算里**原子预留 10%**(Q = ⌊0.1×B⌋ = 4 个 trial/空间),
  用不完退回给 TPE;诊断 trial 永不参与最优解评选(fresh-measurement 隔离)。
- **去向**:结果组装成结构化响应(含端点参数、有效性、ΔJ、gain、两类斜率、
  resource_status)写进 analyst / rewriter 的简报——即 C2 消融里 G1/G2 之差的那个字段块。

### ④′ 扩域(挂在调参之后,回答"扩哪个、朝哪、谁来扩")

- **扩哪个旋钮**——六个条件全部满足才请求(`boundary_knobs_to_expand`):
  1. 获胜 trial 的取值在已测范围的**边缘**;
  2. 中位曲线尾部单调**向该边缘变好**(趋势同意"外面可能更好");
  3. 该旋钮效应 ≥ 2%(`min_effect_pct`;平坦曲面上"最优在边缘"是噪声,扩了也没用);
  4. **有序数值轴**(categorical 如精度档没有"下一个值",不可扩);
  5. 边缘之外**不是硬件地板/天花板**(内置墙表按名字后缀匹配:NUM_WARPS 下限 1、
     `tl.dot` 收缩维 BLOCK_K 下限 16 等——向硬件墙外要值,agent 只能拒绝或用掩码模拟,
     两者都必输);
  6. **至少一维资源仍有余量**:该维占用低于本机实测上限的 **80%**
     (`space_expansion_idle_frac=0.8`,上限来自①的标定)——资源已全饱和时扩域只会
     OOM/spill,此时正确动作是交给⑦结构改写,而不是扩域。
- **朝什么方向**:向获胜取值所在的那一侧边缘之外(方向由锚点+趋势共同决定,见⑤末条)。
- **谁来扩**:请求发给 **parameterizer agent**,形式是聚焦的扩域请求——只为点名的旋钮
  **追加取值**(结构与其他旋钮原样保留),产物重新过 validation + guard + witness,
  然后**再调参一轮**(又一个 40-trial 空间)。
- **同轮偏好**:边缘取值已经高失败率的旋钮,让位给同轮里更健康的旋钮
  (`max_edge_failure_frac=0.30`)——**是偏好不是过滤**,同轮没有替代者时照常执行。
  这个区别是实测决定的:作为过滤会在 177 次扩域中的 8 次把请求列表清空,
  而空列表会直接取消整次扩域(连同新的调参预算一起丢掉),其中 2 次是该 run 的最优候选。
- **预算**:`space_expansions_per_candidate` = 每个候选最多申请几次扩域
  (每次扩域后再跑一个完整的 40-trial 空间)。**代码默认 0(关),但本文全部实验一律为 1**
  ——已于 2026-09-24 核对五台机器上 60 个非 smoke run 的 `manifest.json` 配置快照:
  `space_expansions_per_candidate=1`、`trials_per_space=40`、`wall_clock_hours=12.0`
  三项无一例外(唯一的 0 是 box4 的一个 L1 冒烟 run,不在主表内)。
  ⇒ **写 method 时直接写 1,不要写默认值 0**。
  注意 1 是**上限不是必然**:六个条件全满足才会真正触发一次扩域。

### ⑦ 结构改写

- **rewriter 输入**(一份简报,全部来自④⑤⑥的落盘产物):获胜 trial 的**物化源码**
  (把最优 PARAMS 写回默认值,agent 看到的是"调好的"版本)、analyst 报告(瓶颈判决+
  资源画像+达上限%)、墙文本与⑥的斜率响应、该族**失败假设列表**(此前改写试过且没赢的
  方向,防止来回试同一个想法)、设备标定。
- **产出与准入**:每轮产 `n_candidates`(默认 4)个新结构;按**结构签名**去重(定义见下);
  **新族门槛**:与所有现存族锚点的**规范化源码文本**相似度 < 0.85 才允许立新族
  (`novelty_max_similarity=0.85`,`difflib.SequenceMatcher`;否则归入最近族,
  占该族的改写名额)。注意这是**文本**相似度,与签名的 AST 哈希是两道独立的门。
- **结构签名的确切定义**(`control/families.py:87 structural_signature`):
  对候选源码做 AST 规范化(去 docstring、`PARAMS` 字面量归零)后取 sha256,
  **并以 backend 作前缀**(如 `cuda:9f3a…`)。
  backend 是**结构轴而不是偶然差异**:同一个算法用 Triton 与 CUDA C++ 写出来,
  性能上限不同,若签名相同会被当作重复候选拒收。
  ⚠ 曾有表述称签名使用"源码和 IR 特征"——**代码中没有任何 IR/PTX/TTIR 成分**
  (已全量 grep 确认),写 method 时须写成"AST 规范化哈希 + backend",不要提 IR。
- **族调度**:同时活跃至多 3 族(`max_families_active=3`),**从未改写过的族优先**排队
  (`rewrite_rounds_used == 0` 的族排在最前,保证每个结构假设至少被改一次,
  而不是最好的族垄断全部轮次);每族改写轮数上限 5(`rewrite_rounds_per_family`);
  族总数上限 6(`max_families_total` / `max_families_total_hard`)。
  已死的族(无正确产物且已冻结)不再占名额(`productive_family_count`)。
- **子代路径**:改写产物继承父族,回到③门→④调参(锚点带上父代获胜配置)。
- **停止准则(原缺,method 必须写)**:三条并存,任一触发即停该族或整个 run——
  1. **收敛**:一个族连续 `no_improve_rounds=2` 轮相对改善低于
     `min_improvement_pct=2.0`%(相对判据)即冻结;
  2. **轮数**:每族 5 轮上限;
  3. **墙钟**:`wall_clock_hours=12.0` 作为硬兜底。
  墙钟在若干工作边界处检查而非调用中途,故实际结束时间可能超出 12 h
  (已观察到 12.82 h 的 run)。⇒ 正文写"12 小时预算"时应理解为软预算。
- **记账约束**:一轮改写的返回值是"是否有产物**真的被评测**"——改写 agent 三次尝试全失败
  的轮次不得记为"未改善"(否则平的 best_history 会被上面第 1 条误判为收敛)。
  这条约束存在的唯一目的就是保护收敛判据。

### ⑦′ 新族注入(novelty,"多路线"从哪里来)

> 这一节原本缺失。§3 的流程图里没有它,但它是"同时维护若干结构路线"这一主张的
> **唯一新路线来源**——种子只在开头产生一次,之后所有候选都继承父族。
> 实现:`agents/modules.py:1486 NoveltyGeneratorAgent` + `control/families.py:222
> accept_novel_seed`;预算 `novelty: AgentModuleConfig(n_candidates=2)`。

- **机制**:在族调度之外,另有一条回路请求 agent 提出**与现存全部族都不同**的新结构,
  一次 2 个。它不继承任何父代,因此能跳出"改写只能沿既有结构走"的限制。
- **准入两道门**(见 `accept_novel_seed`):
  1. 结构签名与任一现存族锚点相同 → `duplicate_signature` 拒;
  2. 规范化源码文本相似度 ≥ 0.85 → `too_similar` 拒(附上相似度与被比对的族)。
  通过后以 `origin="novelty"` 注册,自建新族,再走 ③门 → ④调参。
- **名额来自哪里**:`max_families_total=6` = 4 个种子族 + **为 novelty 预留 2 个**。
  (该值曾为 3,导致 4 个种子族一产生就填满名额,novelty 门永远为真 → 从不触发。)
- ⚠ **实验现状必须如实写**:该回路在 L1 smoke 上端到端跑通过一次,
  但**在全部 L3 run 上执行次数为 0**——novelty 排在改写之后,且"墙钟到就不启动新一轮",
  12 h 预算被 10–14 个候选的调参耗尽,调度不到它
  (定案见 `docs/assessment-2026-09-09-defects-and-next-steps.md` 的 P-D:
  这是**实验设计/调度问题,不是缺陷**)。
  ⇒ 写 method 时可以描述该机制,但**不能暗示主实验的结果依赖它**;
  "多路线"在主实验中实际由**4 个结构互异的种子族 + 族调度的公平排队**承载。
  若正文需要"多路线"的证据,应指向种子族而非 novelty。

### ⑧ 最终独立复评

- run 结束后取全程最优 trial,**全新进程**重新加载源码与参数,5 次正确性 + **100 个计时
  样本**,报告值 = 中位数(`final_reeval_median_ms`)。与基线同计时方法。
- 搜索循环内的任何数字(tuned_ms)不进入对外报告;胜负、加速比、达上限 % 全部只从
  复评值计算。

### C3 前置链的具体做法(⓪a–⓪e)

完整细节在 `docs/c3-site-classification-and-selection-explained.md`(含实现文件与行号),
此处只列 method 要点:

- **⓪a 目标合同**:GoalSpec = {方向, 单位, input/output tokens, 并发请求数, 冻结的
  search/final prompt 集}。三个内置目标:ttft(minimize ms)、single / multi(maximize tok/s)。
- **⓪b profile**:按合同负载预热一轮后真跑一遍,`torch.profiler` + 逐模块 forward 包装,
  记录模块路径/类源码/权重几何/张量形状/每 CUDA kernel 的归属与耗时;每 goal 至多 3 个
  短窗口(admission 限制);之后全部决策只读这份 JSON。
- **⓪c 分组+资格门**:family = sha256(模块源码+权重形状+属性);site = 同 family 全部
  模块路径的哈希。五道门:叶子(复合站点需显式开启且 children 计时并入)/ KV-cache 纯度
  (forward 签名含 cache 参数即拒)/ 几何代表(ttft 需恰 1 个无歧义代表调用,decode 目标
  需 step 0 与 127 两个)/ 成员不嵌套 / fixture 容量(按 `mem_get_info` 空闲量 10% 实测推导,
  进程内测一次)。
- **⓪d 排名选择**:三层序——实测探针增益(`probed_gain_frac`,每 goal 独立)降序 >
  无探针者按(可达性判定, 承载 CUDA 时间)> 实测无空间者垫底但可强选;可达性 = 在站点上
  绑数值等价替换、读生产 quality 门的分数(旁置必须读 0.0 的 torch 对照);跨 goal 站点
  必须相同或不相交,被包含者提升到包含者并记录原因。
- **⓪e 任务包**:自包含 reference(类源码+实录 forward+children 定义按需一次+AST 递归
  补齐同文件依赖)、代表张量形状、数值语义口径、profile 指纹;campaign 启动时重建 target
  并核对 site_id,不一致即报错。
- **验收**:端到端 J 相对 baseline 的增益(双测量确认)+ 自校准精度 floor(站点 1-ULP
  实现差在 logits 上的实测放大值为门限)+ 逐算子忠实度门(local L2,拦 identity/zeros 类
  假 kernel)+ paired NLL delta 双保险。

### 7.1 形式记号映射(main.tex:44–72 立的记号 → 实现)

paper 已定义 $S$(算法结构)、$\theta$(可调参数)、$\Theta(S)$(合法参数范围)、
$T(S,\theta)$(运行时间),并给出式 (1):$T^*(S)=\min_{\theta\in\Theta(S)}T(S,\theta)$。
Method 必须用这套记号,映射如下:

| paper 记号 | 实现中的对应物 |
|---|---|
| 算法结构 $S$ | 一个**族**(family)的锚点结构;等价类由结构签名定义 = AST 规范化哈希 + backend 前缀(⑦) |
| 参数 $\theta$ | 候选源码里的 `PARAMS` 字典(tile 形状 / warps / stages / **精度档**) |
| 合法参数范围 $\Theta(S)$ | `ParameterSpace` 的逐旋钮离散取值表(choice grid,每旋钮 3–6 个值)**∩** 静态 guard 判定可行的组合;由 parameterizer agent 给出,可经 ④′ 扩域 |
| $T(S,\theta)$ | 该配置的实测延迟(CUDA event,稳健统计;调参与分析读同一统计,按取值聚合用中位数) |
| $T^*(S)$ | **不可直接观测**;可操作代理 = 该族 40-trial TPE 搜索的最好值。paper L70–71 已声明"实际调参只能给出已测配置中的最好结果,不能据此认定已达结构上限"——Method 应在同一处呼应,并说明每族 5 轮改写共享这一预算 |
| 可行结构空间 $\mathcal{S}$ | 不显式枚举;由 agent 生成 + 签名去重 + 相似度门(0.85)构成的**可达子集**;4 个种子族 + 至多 2 个 novelty 族,族总数上限 6 |

**一个必须点明的边界**:$\Theta(S)$ 在实现里是**离散且随扩域变化**的,不是固定集合。
式 (1) 的 $\min$ 在 method 里应表述为"在当前 choice grid ∩ guard 可行集上的最好实测值",
否则 ④′ 扩域(往 grid 里追加取值)这一机制在形式框架里无处安放。

### 7.3 与 MAP-Elites 的关系(paper §2.3 的落点,原缺)

main.tex §2.3(`sec:map_elites_analysis`,L132–166)用一整个 subsection、一张六面板图
(`fig:structure_space`)和一张划分敏感性表(`tab:map_grid_experiment`:KernelFoundry 在
L2:37 上固定模型/硬件/尝试数、仅改归档划分,中等划分最好)论证:**保留哪些路线与
充分改进这些路线之间存在取舍**。Method 必须回答"那本文用的是什么",而本文档原先零提及。

**本文的做法不是描述符网格归档**,对照如下:

| | MAP-Elites | 本文 |
|---|---|---|
| 保留单位 | 描述符空间的 cell,每 cell 留一个 elite | **族**(结构签名等价类),每族留自己的最好候选 |
| 划分依据 | 预先选定的描述符维度 + 网格粒度 | 候选**自身的结构身份**(AST+backend),无需预设描述符或粒度 |
| 谁被淘汰 | 落入已占用 cell 且更慢者 | 签名重复者、文本相似度 ≥0.85 者;连续 2 轮改善 <2% 的族被冻结 |
| 预算分配 | 由采样/选择规则决定 | 至多 3 个活跃槽位轮转,**未改写过的族优先** |

⇒ 可写的主张:本文**回避了粒度选择问题**——不需要选 cell 数,因为等价类由结构自身给出;
代价是族的边界依赖签名这一可操作近似(相同算法的两种写法可能分成两族,反之亦然)。
`tab:map_grid_experiment` 那个实验因此是**对现有做法的动机性观察**,不是本文方法的消融。

### 7.4 组织建议

paper 标题是 *Guiding GPU Kernel Structure Search with **Parameter Tuning Feedback***,
而本文档 §1–5 的组织主轴是"资源对齐"。这两套说法指同一件事
(调参记录 → 资源画像与墙 → 斜率 → 结构改写),但**Method 应沿标题的说法组织**:
以"从调参过程中提取什么信息 → 这些信息如何决定下一个结构"为主线,
把资源对齐作为**信息的内容**而非章节骨架。否则 Method 的组织原则会与标题、
与 Background 的问题陈述(L194–224:如何判断该继续调参还是改结构)错位。
