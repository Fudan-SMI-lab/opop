# C1 · 资源维度对齐

## C1(a) 主实验:6 任务 × 3 环境 × 4 个外部框架

**主张。** 框架能在**不同 kernel 资源需求**(6 个任务)× **不同环境资源**(3 张卡)的组合上,
稳定对齐到各自的资源边界 —— 所以它不是针对某张卡或某类算子的调优技巧。

**为什么这个设计能支撑"资源维度对齐"。** 6 个任务被选中正是因为它们的**绑定维度不同**
(下表 `floor_kind` 一列:3 个 dram-bound、3 个 compute-bound,融合余量从 3.0× 到 68.2×);
3 张卡的**资源上限不同**(带宽、SM 数、shared memory 上限、是否有 sm_120 新指令)。
如果框架只会一种优化套路,它必然在某一格塌掉。跨 18 格都成立,才说明它对齐的是**资源维度本身**。

### 必须随表携带的口径(否则这张表会被合理质疑)

1. **终值一律取 `final independent re-eval`**,不用搜索期的 `tuned_ms`。后者实测偏乐观 0.4%–8.9%;
   A800 L2:16 的偏差(3.6%)刚好跨过胜负线 —— 用 `tuned_ms` 会把这一格误报成"已超对手"。
2. **预算严重不对等,且对我们不利。** 我们每 run **12 h 墙钟**;外部每任务 128 次尝试、
   API 累计 **16.5–64.7 h**(中位约 46 h)。任何领先都要附这个前提。
3. **加速比列不可横比,候选耗时才是硬列。** 四个外部框架各用自己的 adapter 和基线
   (它们的 README 自己说明),所以本文统一比**绝对候选耗时**,并另附我们自测的同卡 eager。

   (**8685.6 μs**,其实测 8533.5 更快,故仍取自报值),**我方 2.7628 ms 领先 3.144× 不变**。

   ⚠ **我此前的理论论证已被取代,不应再写进论文。** 早先我基于 FLOP 计数论证
   "两个 fp32 投影(309.24 GFLOP)在 4090 上即便走 TF32 也需 1.872 ms",
   方向虽正确,但它依赖"该候选真的按自己声明的 fp32 路径执行"这一假设;
   **实测不需要任何假设,结论也更强**(9286.9 μs 是同卡同门量到的)。
   同样地,更早的"多流未同步计时假象"判定也已撤回(它的
   `current_stream().wait_event()` 同步是正确的)。
   ⇒ **论文只写实测结论**:自报 1.000 ms,同卡复核 9.287 ms,与同任务其余候选同档,正确性通过。

   旁证(可作脚注):`evaluation.json` 里该值是整数 `latency_ms: 1.0`,疑似舍入或占位。

   逐格数据见附 E;原始记录
   `external_files/4090_52_experiments_results_and_best_sources/_retest_2026-09-24/res_l343.json`。

8. **形状可比性已核实(这一条决定 L3:43 那行能不能并表)。**
   `box2` 保留冠军的 `report.md` 有一处 analyst 文本写着 "B=16, T=2048, C=1024, 16 heads" ——

   ⇒ 我方冠军与外部候选跑的是同一个任务、同一形状,绝对值可比。

## C1(b) 到达物理上限 —— 这才是"对齐"的直接证据

**主张。** 大部分优化后的算子**停在物理上限附近**,而不是停在"搜索预算用完"。

**为什么这份数据能支撑"资源维度对齐"。** 逻辑链是这样的:
如果框架只是盲目搜索,候选的终点会散落在离物理下限很远、且彼此无规律的位置;
而如果它真的把算子与资源维度对齐了,候选就会**贴着某一维的墙停下**,
并且**这个墙可以被独立算出来**。所以"达上限 %"是对齐的可验证形式。
下限的推导是可核算的,不是估计:

```
floor = max( 必须搬运流量 / 实测带宽 ,  必须算力 / 实测峰值 )
```

两项都**在本机实测**(不是查手册),流量是"输入+参数+输出各计一次"的 compulsory traffic。

### 六任务的达上限比例(A800,实测)

| 任务 | 物理下限 | 绑定侧 | 本框架最佳 | **达上限 %** | 参考 / 下限 = 理论天花板 |
|---|---:|---|---:|---:|---:|
| **L3:48** | 0.8024 ms | dram | **0.799 ms** | **100.4%** ⚠见① | 17.32× |
| **L3:43** | 1.7629 ms | compute | 2.35 ms | **75.0%** | 17.02× |
| **L2:16** | 1.5924 ms | dram | 2.79 ms | 57.1% | 22.54× |
| **L2:61** | 0.9525 ms | compute | 1.89 ms | 50.4% | 30.24× |
| **L2:59** | 2.609 ms (fp32) | dram | 1.05 ms (int8) | **见下** | 6.36× |
| **L3:21** | 0.4605 ms | compute | 4.32 ms | 10.7% | 32.14× |

**三个必须讲清楚的点:**

**① L3:48 达到 100.4% —— 略微越过下限,这需要如实解释,不是测量错误。**
该任务的下限来自 1.3506 GB compulsory traffic / 1.6831 TB/s 实测带宽 = 0.8024 ms,
而 resume 轮的最终候选 final re-eval 测得 **0.799 ms**。
**为什么能略低于下限:** compulsory traffic 的定义是"输入 + 参数 + 输出**各计一次**",
它假设每个字节只过一次 DRAM。真实 kernel 若在 L2 上复用了部分数据(该任务有 130 个 op、
存在跨 op 的张量复用),有效 DRAM 流量就会**小于** compulsory 值,于是实测可以略快于该下限。
⇒ **这个下限是一个"在无 cache 复用假设下的保守下界",越过它 0.4% 不构成矛盾**,
但**必须在论文里写明这个定义边界**,否则"超过自己给出的物理下限"会被直接质疑。
该候选的实测瓶颈判定为 `memory_bound — 97%+ DRAM`,即它确实把 DRAM 打满了。
**更强的旁证是外部对手也停在同一面墙上:** KernelFoundry 的 0.822 ms = 下限的 **97.6%**,
而它是**手写 CUDA、纯 fp32**(`cp.async` 三重缓冲 + `__stcs` 流式存 + 每 tile 仅一次
`__syncthreads()`),源码自述"0.823 ms ≈ 实际混合读写带宽的 94%"。
⇒ **两个独立框架、两条完全不同的技术路线,收敛到同一个物理下限的 97–100%** ——
这是"该任务的物理上限已被确认"的最强形式。
⚠ 该格在第一轮曾是 0.856 ms(下限的 93.7%、负对手 4.1%),**resume 轮把它推过了对手也推到了墙上**。

**② L2:59 是一个更有力的案例:下限本身证明"纯 fp32 这条路线没有可用余量"。**
该任务 99.2% 的必须流量是权重(4.295 GB / 4.329 GB 总量),所以 fp32 下限 = **2.609 ms**,
而外部最强是 **2.649 ms** —— 即**对手已经贴到了 fp32 下限的 98.5%**,
纯 fp32 即使做到理论极限也只能领先 1.5%,落在噪声带内。
⇒ **fp32 路线上没有可争取的空间**,必须换维。
框架读出"流量被权重钉死、且权重可量化"这一资源结构,选了 **int8**,做到 **1.05 ms**。
⇒ 这证明资源对齐**不只用于"别越界",还用于"发现哪一维必须被改变"** ——
把 dtype 当作显式资源维度,是这一格从"无余量"变成 2.52× 领先的唯一途径。

> ⚠ **2026-09-24 修正**:本段原写"fp32 下限(2.609)**高于**外部最强(2.649)⇒ 纯 fp32
> 物理上追不上",**算术反了**(2.609 < 2.649,下限当然低于任何实际耗时)。
> 原句照抄进 paper 是一眼可破的假陈述。正确的论证是上面的"对手已达下限 98.5%、
> 余量仅 1.5%",结论(必须换精度维)不变,但理由必须改。

**③ L3:21 只有 10.7%,必须如实写,而且它有解释。** 它是 compute-bound、
最高算术强度 348 FLOP/byte(ridge 的 30 倍),但最优候选实测 **仅 11.1% tensor-core、4.5% DRAM**,
判定为 `resource_limited`,occupancy 被寄存器顶住。
它同时是 6 个任务里参数轴最多的(**34 个轴**,横跨 BN / GEMM / DW / MOM / COV 等 8 个子 kernel)。
⇒ 这一格说明的是"**资源余量大 ≠ 已对齐**",它是当前方法余量最大的一格,
也是 C1 的诚实边界。**不要把它写成失败,它是 32.14× 天花板下的 3.43× —— 仍然领先外部 1.248×。**

# C2 · 资源-性能斜率引导算子结构改写

## C2(a) G0/G1/G2 消融 —— 主结果

**主张。** 引导信号必须包含**资源侧的转化响应**(资源斜率),**光有性能斜率不够**。

**实验设计(自变量只有一个:交付视图的屏蔽范围)。**
先做一次 **acquisition**:对若干参数轴,固定其他旋钮不动,在该轴上取两个端点各实测一次,
得到"这个轴从 a 走到 b,性能与资源分别怎么变"。三组**共享同一批采集结果**,只改给 agent 看多少:

| 组 | 能看到 | 看不到 |
|---|---|---|
| **G0** | 只有普通历史信息:此前 trial 的参数与延迟、已有静态资源约束 | **完全没有**本次采集的端点信息 |
| **G1** | 端点参数取值、该端点是否有效、**J**、**delta-J**、**gain**、**性能斜率 `parameter_slope`** | 端点的 **`resource_deltas` / `resource_slopes`** 与 fresh metrics;`resource_status` 置为 `unknown` |
| **G2** | 上述**全部**(未经遮蔽的完整原生响应) | — |

- **J** = 该端点实测的目标值(本组即延迟 ms,越低越好)
- **delta-J** = 两端点间 J 的差
- **gain** = 同一差值的归一化形式
- **`parameter_slope`** = delta-J 相对该轴取值变化的斜率,即**性能斜率**
- **`resource_slopes`** = 各资源维度(n_regs / n_spills / shared_bytes)相对该轴的斜率,即**资源斜率**

⇒ **G1 与 G2 之差是「资源斜率」这一整块,不是"有无斜率"。**
G1 已经知道"这个轴走一步、性能变多少",G2 额外知道"同时哪一维资源被换掉了"。
**所以这组消融检验的是:光有性能斜率是否够用。**

⚠ 这一点与 `paper-positive-evidence.md` 的表述不同。该文档把 G1 描述为"只拿到标量增益",
但从 12 个 cell 的 `actual-delivered-response-views.json` 逐字段读出,**G1 的 `parameter_slope`
是有值的**(例:L3:21/P1 的 `SPLIT_M = −0.78650`,G1 与 G2 逐位相同)。
本文按落盘事实描述,详见 C2(b) 的案例 1。

**控制条件**:三组同一批 acquisition、同一父状态、同一 B40 协议、同一 sampler seed;
prompt / 契约完全未改(连 `wall_text` 措辞在 G1 与 G2 都一致);**组名不写进 agent 输入**;
无 G2 专属指令、无强制引用某轴、无修复 campaign、无额外提案循环。

**规模**:固定 **4 个真实父状态**(2 任务 × 每任务 2 父)× 3 组 = **12 次独立 fresh proposal**
(analyst → rewriter → parameterizer),每次接一个 native B40 调参。父状态按注册顺序取前两个合格状态,
**不按新 child 表现挑选**。P、C 各为三个 fresh full block median 的中位数,**R = C/P**(越低越好)。
12 行全部产出 selected child,无 fallback。

| 主机/任务 | 父 | 组 | Candidate | P (ms) | C (ms) | **R** |
|---|---|---|---|---:|---:|---:|

## C2(b) 斜率如何引导方法选择 —— 一个完整案例走通

**要证明的那一句。** 面对同一个算子,agent 会想出**好几种不同的改法**;每种改法会动到不同的资源维度。
**资源斜率告诉它"哪一维现在最该动"**,于是它选中对的那一种改法,**改写后确实更快**。

### 先看这个算子哪里有问题(父代的实测资源画像)

任务 L3:21(EfficientNet MBConv),父代算子 **8.47 ms**(三个 fresh block 的中位)。它的 expand GEMM 用的是
"full-K 单发"设计:一次把整个 K 维(K_PAD)搬进 shared memory 再算。实测资源:

| 资源维度 | 父代实测值 | 硬件上限 | 状态 |
|---|---:|---:|---|
| shared memory | **65536 B** | 101376 B | 占 65%,**且它是当前的 occupancy 限制者** |
| 寄存器 / 线程 | **255** | 255 | **顶满** |
| 寄存器溢出(spill) | **108** | 0 才健康 | **溢出到显存,每次访问慢 ~100 倍** |
| occupancy | **8.3%** | — | 每个 SM 只能驻留 1 个 block |

**读法**:这个算子被**两面夹住** —— shared memory 太大导致一个 SM 只放得下 1 个 block,
寄存器顶满导致 108 次溢出。但**光看延迟数字看不出该先动哪一维**。

### 三种改法,以及每种改法动了哪些资源维度

同一个父代,三组 agent 各自想出了自己的改法(同一份采集数据、同一提示词,**只有斜率视图不同**):

| | **改法 A**(G0 组采用) | **改法 B**(G1 组采用) | **改法 C**(G2 组采用) |
|---|---|---|---|
| **一句话** | 把 full-K 单发改成 **K 循环**,顺带重写 project GEMM | **保留** full-K 单发结构,**只把中间结果存成 fp16** | 把 full-K 单发换成 **标准 K 循环分块 GEMM**,并把中间结果存 fp16 |
| **动的是哪一维** | shared memory + 寄存器 + spill | **只动显存流量(存储精度)** | shared memory + 寄存器 + spill + 显存流量 |
| **碰没碰那个有 108 spill 的 kernel** | 换掉了 | **原封不动留着** | 换掉了 |
| shared memory | 65536 → **41472 B** | 65536 → 32768 B | 65536 → **30208 B** |
| 寄存器 | 255 → **236** | 255 → **255(仍顶满)** | 255 → **140** |
| **spill** | 108 → **0** | 108 → **0**(靠调参绕过,不是靠结构) | 108 → **0** |
| occupancy | 8.3% → 16.7% | 8.3% → 16.7% | 8.3% → 12.5%,但 **3 blocks/SM** |
| 显存流量 | 不变(fp16 仅作为可调开关) | 降一半 | **1.69 GB → 0.84 GB** |
| **改写后延迟** | 8.467 → **4.672 ms** | 8.366 → **5.076 ms** | 8.466 → **4.100 ms** |
| **R = 子/父**(越低越好) | 0.5517 | **0.6068(最差)** | **0.4843(最好)** |

> 三组的代码可直接核对:`generated--rewriter-*__rewrites__rw_1.py` 里,
> **只有 G1 那份仍然定义 `_gemm_fullk_atomic`**(那个 108-spill 的结构),
> G0 换成了 `_gemm_kloop`、G2 换成了 `_expand_gemm`。这不是解读,是文件里有没有那个函数名的事实。

### 斜率是怎么引导这个选择的

三组看到的斜率信息如下。**注意 G1 和 G2 看到的性能斜率是逐位相同的**(我逐字段比对过):

| 参数轴 | 改这个轴,延迟怎么变(**性能斜率**) | 改这个轴,资源怎么变(**资源斜率**) | G0 看到 | G1 看到 | G2 看到 |
|---|---|---|:---:|:---:|:---:|
| SPLIT_M | 58.09 → 8.54 ms,斜率 **−0.787**(最大) | 资源无变化 | ✗ | ✓ | ✓ |
| SPLIT_K | 7.31 → 10.23 ms,斜率 +0.417 | 资源无变化 | ✗ | ✓ | ✓ |
| **BLOCK_N** | 12.22 → 8.77 ms,斜率 −0.031 | **寄存器 −0.027 / spill −0.032 / shared −7e−5** | ✗ | ✗ | **✓** |
| BLOCK_M | 10.28 → 9.46 ms,斜率 −0.007 | **spill −0.0022** | ✗ | ✗ | **✓** |
| BLOCK_K | 8.36 → 9.29 ms,斜率 +0.019 | 资源无变化 | ✗ | ✓ | ✓ |
| STATS_BLOCK_M | 8.734 → 8.737 ms,斜率 +0.00002 | 资源无变化 | ✗ | ✓ | ✓ |

**关键在 `BLOCK_N` 那一行。** 它的资源斜率说的是:**把 BLOCK_N 调大,寄存器和 spill 会一起降下来**
—— 也就是"**spill 是可以靠结构换掉的,而且换的方向就在 tile 形状这一维上**"。

- **G2 看到了这条**,于是它的改法直接冲着那个 kernel 去:把 full-K 单发换成 K 循环分块,
  寄存器 255→140、spill 108→0。它的改写说明里逐字引用了 **"64KB single B-tile, 1 block/SM,
  96-block grid, 255 regs + 108 spills"** —— 这正是资源斜率暴露的那组数字。
- **G1 看不到资源侧**(`resource_status = unknown`,资源字典为空)。它手上最醒目的信号是
  `SPLIT_M` 的性能斜率 −0.787,但那一维**动了也不改变任何资源**。
  于是它退回到一个通用手法:**把中间结果存成 fp16**,降显存流量 —— 结构一动不动,
  那个 108-spill 的 `_gemm_fullk_atomic` 被完整保留,寄存器仍然顶在 255。**结果三组最差。**
- **G0 什么斜率都看不到**,但它凭历史 trial 也猜到了该改 GEMM 结构(改法 A),所以比 G1 好。
  **这说明 G1 的问题不是"信息少",而是"信息偏了"** —— 只给性能侧,会把注意力吸到
  斜率最大但资源无关的那一维上。

**一句话总结这个案例**:同一个算子、三种改法;**只有拿到资源斜率的那一组,
才把力气花在真正被顶住的那一维上**(shared memory + 寄存器),改写后最快(4.100 ms,
比只降精度的 G1 快 **19.2%**,比无斜率的 G0 快 **12.2%**)。

### 第二个案例:当性能斜率毫无区分力时,资源斜率仍然指得出方向

同任务另一个父状态(父代三个 block 中位 **9.038 ms**)。这一格的特点是:**所有参数轴的性能斜率都接近零**
(最大的 `STATS_STAGES` 只有 −0.0022),**光看性能,无从判断该改哪里**。

| | **改法**(G1 组) | **改法**(G2 组) |
|---|---|---|
| 一句话 | 中间结果全部留 fp16,去掉 `.float()` 上转 | **用 Triton tensor-core GEMM 替换 expand 的 cuBLAS matmul**,并合并独立的 stats pass |
| 动的维度 | 只动存储精度 / 显存流量 | 计算单元(上张量核)+ 融合掉一趟全张量读写 |
| **R** | 0.4685 | **0.3906** |

G2 额外看到三个轴的资源斜率(`STATS_BLOCK_M`: 寄存器 −0.0067 / shared −0.0008;
`STATS_BLOCK_C`: 寄存器 +0.0004 / shared +0.00003;`STATS_WARPS`: 寄存器 +0.00007)。
这些数值虽小,但它们告诉 agent:**资源侧还有可交换的余量**,值得做结构性改动,
而不是止步于降精度。结果 G2 好 **16.7%**(4.237 → 3.530 ms)。

⇒ **这一格证明资源斜率不是"性能斜率的附属信息"**:性能斜率归零时它仍然有效。

### 第三个案例(反例,如实保留):资源斜率也会指错

L3:43 的一个父状态上,**G1 反而最好**(R=0.8042,G2 为 0.9735,高 21.04%)。
机制可解释:G1 选了**两种改法的组合**,G2 只做了其中一种 —— 多出的资源信息让 G2 更保守地聚焦单一假设。
⇒ **资源斜率提高的是"选对方向"的概率,不是保证。** 4 个父状态里 G2 胜 G1 是 **3/4**。

# C3 · 目标引导算子优化

**主张。** 把优化目标从"算子延迟"一般化为**任意声明目标 J**(TTFT / 单流吞吐 / 并发吞吐),
并且:(a) 不同目标该优化的**算子组不同**;(b) 判据必须是**端到端目标指标**,不是算子自身 latency。

## C3(a) Qwen3-4B 三目标 × 三指标矩阵

**主结果表(增益 vs baseline,正 = 更好;对角线加粗)**

| 优化目标 ↓ \ 测量 → | **ttft**(延迟↓) | **single**(吞吐↑) | **multi**(吞吐↑) |
|---|---:|---:|---:|
| **ttft**-kernel | **+3.56%** | −10.64% | −14.17% |
| **single**-kernel | −0.05% ⚠精度拒 | **+12.51%** | +8.35% |
| **multi**-kernel | −0.10% ⚠精度拒 | +11.03% | **+9.29%** |

baseline:ttft **283.99 ms** / single 26.00 tok/s / multi 197.46 tok/s。

**目标声明与测量协议:**

| 目标 | 输入规格 | 输出 |
|---|---|---|
| TTFT | 4 × 4096-token | 每请求 1 token |
| Single | 2 × 256-token | 每请求 128 tokens |
| Multi | 8 × 512-token(同步 wave) | 每请求 128 tokens |

质量规则:local `.02/.02`;per-prompt logits relative L2 `.01`;paired mean NLL delta `.02 nat/token`。
非 thinking、greedy、seed 0,fresh KV/state + warmup。

**这张表为什么能支撑"目标引导"。** 两件事同时成立才算证明:
1. **对角线全部为正**(+3.56% / +12.51% / +9.29%,均 device-proven、logits < floor)
   ⇒ 每个 kernel 在**自己优化的目标**上都拿到收益。
2. **离对角显著为负** —— ttft-kernel 在 single / multi 上是 **−10.64% / −14.17%**
   ⇒ **错配即伤害**,不是"随便优化都普遍变快"。
   若离对角也为正,这张表就只能证明"优化有效",不能证明"目标特异性"。
   **第 2 点才是 C3 不可替代性的证据。**

**来源**:ttft 行(kernel `214c971b`)= `results/c3-fast-kernel-iteration/F4-matrix/matrix.json`;
single/multi 对角与离对角 = `synth-matrix-3rows-0922/matrix.json`;
ttft 列的 single/multi-kernel latency = `synth-matrix-3rows-full-0922/matrix.json`。
全 box4 RTX4090、RMSNorm 站点 `pure-727f184a…`、contract `2c0e2fc7…`。

**⚠ 三点必须随表声明的诚实标注:**
1. **ttft 列的两个离对角格被精度门拒**(worst logits 0.0193 / 0.0237 > floor 0.0162)。
   根因是**评测序列长度与 floor 校准长度不匹配**:floor 在 64-token 校准 prompt 上测得,
   而 ttft 只解码 4 token,同样扰动摊在极少的 continuation logits 上 → 相对 L2 结构性偏大。
   逐算子忠实度 local=1.0 全过、NLL 全过,只栽 logits 放大门 ⇒ **不是 kernel 错误**,
   而是 floor 应按目标序列几何分别校准的方法学细节。表中如实给出 latency 并标 `correctness_failed`。
2. **该表由三处 device-only 实测合成**(同站点、同 contract、同设备、同 baseline 口径),
   差异仅在各 kernel 出自不同 framework 搜索版本。合成驱动去掉了 framework_id 身份匹配,
   但**完整保留正确性门**。此点应作为方法学脚注写入论文。
3. **一个已知测量波动**:single 对角在两次独立运行分别测得 +12.51% 与 +9.42%(差约 3pp),
   来自不同 baseline 与笔记本级 GPU 计时噪声(block 离散度 2–3%);两次均远超噪声带、方向一致。

### 另一组同类证据(源改写路线,36 cell 全 valid)

## C3(b) 站点选择:优化空间 = 相关性 × 承载 × 实现余地

**主张。** "该优化哪个算子组"不是随意的,也**不是选最耗时的那个**。

**① 同一站点在三个目标下承载完全不同**(实测 `associated_cuda_us`):

| 目标 | RMSNorm 承载 CUDA | 该目标下的对角增益 |
|---|---:|---:|
| ttft(4-token 预填) | 14041 µs | +3.56% |
| single(256-token 单流解码) | **2383 µs**(最小) | **+12.51%**(最高) |
| multi(1024-token×8 并发) | 15036 µs(最大) | +9.29% |

**反直觉现象:承载最小的 single 拿到最高增益** ⇒ **相关性优先于承载**。
single 是纯 decode,每步只算 1 token,GEMM 等大算子开销被摊薄,
RMSNorm 的逐 token 归约 + launch 开销占比反而最高。**若只按承载排序,single 会去优化 GEMM 而错失 +12.51%。**

**② 承载最大的站点增益≈0**(同一 ttft 目标,换不同算子组):

| 站点(算子组) | 承载 CUDA | kernel 组成 | 状态 | ttft 增益 |
|---|---:|---|---|---:|
| **input_layernorm (RMSNorm,73 模块)** | 14041 µs | **8 种分散 kernel** | accepted | **+3.56%**(F4)/ **+3.32%**(lane) |
| **gate_proj 与 up_proj(同一站点,72 模块)** | **88822 µs(最大)** | 每模块 1 个 cuBLAS tensor-core GEMM | accepted | +0.22%(噪声内) |
| act_fn (SiLU,36 模块) | 5095 µs | 1 个向量化 kernel | censored | 0 |

> ⚠ **2026-09-24 两处修正**(原表是四行,其中两处为事实错误):
> ① **`gate_proj` 与 `up_proj` 是同一个 site**,不是两个算子——同一 `family_key`
> (72 个模块,同为 `nn.Linear` 2560→9728,88821.9 µs)。
> 原表把 **92975 µs** 当成 up_proj 的 ttft 承载,但那是**同一站点在 multi 负载下**的读数,
> 属跨负载串入(已独立复现族分组确认)。
> ② ttft 增益的 **4.46% 无任何原始支持**(该候选 `453b09ee` 落盘实测 −0.12%,
> 三个 ttft 格全部 `correctness_failed`),已从 paper 删除,**不要再使用**。
> 合法的两个口径是 **+3.56%**(F4 密封矩阵,基线 284.829)与
> **+3.32%**(lane 定稿,基线 282.818),引用时必须各自标明基线。
> ③ 两个负结果的机制不同,写正文时应分开说:GEMM 的归约无法交给现有库实现、
> 改写后未过等价检查;SiLU 已是单个访存受限的向量化 kernel,
> 没有可合并的启动或可复用的中间结果。

差别在 **kernel 组成揭示的"实现余地"**:RMSNorm 被 torch 拆成 8 个独立小 kernel,
每个都要单独 launch、每个中间结果(如 [1,4096,2560] fp32 = 41.9 MB)都要写回再读出 ⇒ **余地来自"未融合"**;
GEMM 已是单个 cuBLAS `s1688gemm`(NVIDIA 手工调优到接近硬件峰值)⇒ **承载大但零余地**。

⇒ **C3 的判据是"相关性 × 承载 × 实现余地",三者缺一即零。** 这解释了为什么换目标就该换算子组。

## C3(c) 度量哲学:算子单测更慢,但目标指标提升(C3 与传统算子基准的分水岭)

同一个 device-proven kernel `214c971b`:

| 度量 | 数值 | 说明 |
|---|---|---|
| 算子级 paired micro-benchmark | **0.980 ~ 0.988×**(算子本身**更慢** 1–2%) | 孤立测这一个 RMSNorm,新 kernel 比原始还慢 |
| 端到端 TTFT | 282.818 → 273.433 ms = **+3.32%(更快)** | 放进整模型,首 token 延迟显著下降 |
| launch 数 | **−219 次** | 8-kernel 融合成 2 个 |
| 显存流量 | **−7.13 GB** | 省掉多个 [1,4096,2560] fp32 中间张量往返 |

**机制**:孤立微基准克隆单次调用、分配器已热、无邻居竞争,它只测"这一次调用的算术耗时",
而新 kernel 的算术确实略多(多了融合逻辑);但它**看不到**跨 73 个模块累积的 219 次 launch
与 7.13 GB 显存往返 —— 而这两笔正是 ttft 延迟的大头。**所以孤立基准把赢家判成输家。**

**规模确认(不是孤例)**:全 box4 扫出 **291 个**"算子级 speedup < 1 却通过正确性门"的 fixture ——
o_proj 低至 **0.37×**、复合 mlp 融合 0.71×、gate_proj 0.75×、act_fn 0.74× 均通过。

⇒ **若用算子孤立 latency 做判据(传统做法),这个 +3.32% 的 ttft 冠军会被直接淘汰。**
这是 C3 坚持用项目/模型级目标指标做判据的**不可替代性**证据。

> **两条方法学脚注**(原为独立小节,收在此处;它们不支撑主张本身,只挡住两个必来的质疑):
> **① 收益不是替换路径的副作用。** 同进程交错对照(interleaved passthrough arm):
> 不带 kernel 的 torch passthrough 臂停在基线 **−0.13%**,kernel 臂 **+2.93%**
> ⇒ 增益来自 authored kernel。**这条在审稿时是必需的**,否则"把算子换掉"本身就可能改变时序。
> **② 精度门是自校准的、且不放水。** floor = 该站点 1-ULP 实现差异在 logits 上的实测放大值
> (RMSNorm 73 模块 = 0.01616,两次自校准逐位复现);identity / zeros / 丢权重的错误 kernel
> 全被逐算子忠实度门(local=0.0)拦下 —— floor 只抬 logits 放大门,从不放行不忠实的 kernel。
