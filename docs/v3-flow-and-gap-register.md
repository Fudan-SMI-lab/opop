## 第一部分:v3 的整体框架流程

### 1.1 从 v2 继承的骨架(已在 `orchestrator.py` 复验)

外环状态机,每步以 `step_key` 幂等(replay 时跳过已完成步):

```
_calibrate           实测本机四档精度天花板 + DRAM 屋顶 + 启动地板
   ↓                 (必须在 baseline 之前:候选编译中测出的天花板会系统性偏低)
_baseline            eager / eager_tf32 / torch_compile / torch_compile_tf32,各 100 采样
   ↓
_generate_seeds      → Loop 起点:generator agent 产出 N 个种子候选
   ↓
_pipeline_batch      对每个候选跑 _candidate_pipeline:
   │                    _parameterize_with_repair   ← Loop A(修复),含双见证门
   │                    _tune                       ← Loop B(Optuna TPE)
   │                    _stats_and_analysis         ← 确定性统计 + analyst agent
   │                    _maybe_expand_space         ← K 扩展(边界旋钮扩域)
   ↓
_restore_family_control_state
   ↓
while global_verdict != freeze:          ← 墙钟 / 族状态决定
   │   _rewrite_round                    ← Loop C(结构改写),对活跃族
   │      ↓ 若无进展
   │   _novelty_round                    ← Loop D(新族探索)
   │      ↓ 若也无进展 → idle_rounds++,达上限则 OUTER_LOOP_STUCK 退出
   ↓
_finalize            θ_best 独立新进程复测(final_reeval)+ 报告
   ↓
RUN_FINISHED
```

**四个循环的分工**:A 修复(候选坏了就修)、B 调参(Optuna TPE,内环)、C 改写(结构变化,LLM agent)、D 新族(结构上足够不同的新起点)。**外环是 LLM agent,内环是 TPE。**

**这个骨架 v3 不改。** v3 改的是**沿着这条流水线流动的信息**。

### 1.2 v3 在流程上加/改什么

按阶段标注(S1…S6),**粗体是本次修订后的定稿形态**:

```

        (依据:Roofline 原文在 SpMV 上推翻自己的 ceiling 顺序;
         我们的 L3:48 8/8 张量核候选撞死在一条天生不可用的屋顶上)
   ↓

   ↓
_generate_seeds                              不变(prompt 内容由 S2 的消化层改)
   ↓
_candidate_pipeline
   │  _parameterize_with_repair
   │     + S1:空间生成时把编译期可知的不可行「声明掉」(依赖域收缩)
   │            ——不是抽出再拒
   │  _tune
   │     + S1b:无条件失败的取值降权(非黑名单,需先过历史重放)

   │     ★ S2:判决从单标签 → 每维一条独立记录 + 消化层
   │     ★ S2c:θ_best 邻域局部资源地图(每 knob ±1 步,批量编译 + 一次 launch)
   │            实测代价表取代 agent 对资源影响的预测
   │            带 measured_at 有效范围;按 (候选, structural_signature) 键入
   │     + S3:每维下界作「还剩多少空间」的锚
   │     + S4:成对观测 (Δ维度i, Δ维度j, Δ延迟) 记录但不聚合
   │  _maybe_expand_space
   │     + S4:扩展方向按 S=ΔQ/ΔF 排序
   ↓
_rewrite_round (Loop C)
   ★ S2:改写简报改为「多份并列的按维度诊断」经消化层
```

**两者的风险不同,所以开关必须独立**:S2 的风险在 agent 对多份判决的反应(A-6,外部有反向先例);S2c 的风险在成本与有效范围。**地图先只进 events.jsonl,进 prompt 需单独一次对照 run。**

### 1.3 S2 的数据形状(定稿)

每个维度一条独立记录,**不合成、不投票、不取 max**:

```
{ dimension_id          例:dram_bandwidth_pressure / dram_latency_exposure /
                            compute_fp16 / occupancy / shared_capacity /
                            register_pressure / launch_overhead / peak_memory
  measured              实测值(可为 None)
  ceiling               本机实测天花板
  ceiling_provenance    哪次校准 / 精度 / 后端  ← 没有这个,读者无法判断可信度
  verdict               binding | near-binding | slack | not-applicable | unknown
  confidence            噪声底以下一律 unknown
  applicable            一等字段,见下 }
```

**`applicable` 为什么是一等字段而不是缺省值**:V100 没有 bf16 → 相关维度**不存在**,而不是「值为 0」。`applicable=false` 与 `measured=0` 必须永远可区分 —— 这不是新问题,`task_cost.py` 已经用 `notes` 解决过同一件事(「`flop_count = 0` 对 maxpool 是合法结果、对 matmul 是失败结果,只有这个字段能区分」),沿用那个已验证的做法。

**多维同时 binding 时,输出就是多份。** 这修的是 v2 缺陷本身:L3:21 的 20 份报告 19 份是 `resource_limited` —— 问题不是标签选错了,而是「必须选一个」这个要求强迫在同时绑定的维度之间做一个没有依据的选择。

**资源占用按 `(候选, structural_signature)` 键入,不按族。** 依据用户的判断:每次结构改动后占用率都会变。`families.py` 已有 `structural_signature`,直接用。

### 1.4 消化层的位置(硬约束)

```
原始向量 ──→ events.jsonl / report.md          ← 唯一出口
    │
    └──→ 消化层 ──→ agent prompt
              每维一条:{维度, 严重度, 根因, 排序建议, 预期Δ(可缺失)}
```

**代码层面要加一道门**:构造 prompt 的函数**不得访问原始向量对象**。依据是实测的:KernelPro 三臂对照里,原始计数器那一臂(1.77×)比**完全不给反馈**(3.35×)更差,单侧 Wilcoxon p=0.0007。

## 第二部分:缺口登记册

分四类。**每条标注它是「测量缺口」(不知道怎么测)、「设计缺口」(不知道该怎么定)、还是「功效缺口」(知道怎么做但证据不够)** —— 三者的处理方式完全不同。

**写这份清单时我核实掉了自己两条过时断言**(见 B-5),所以下面每条都是在当前 v3 checkout 或当前 run 的 events.jsonl 上复验过的,不是凭记忆列的。这一点很重要,因为 memory 里的「已修复/未修复」条目主语可能是另一台机器。

### A. 设计缺口 —— 最重要,因为它们无法靠多跑实验解决

#### A-1 ★ 多维同时 binding 时,agent 该先动哪一维?→ **2026-09-10:实测发现这个问题问反了**

**完整论证见 `result-a1-no-ranking-rule-survives-its-controls.md`(工具 `scripts/multibind_rule_check.py`,零 GPU)。**

**问题原本的形态**:原设计用合成回答它 —— 压成一个标量,最紧的那维就是要动的那维。撤回合成之后这个问题没有答案了,而它不是理论问题(L3:48 的候选同时是 DRAM 93.7% 与 occupancy 17%,两个方向的改写要求相反)。

**先去数据里看了一眼,三步**:

1. **A-1 确实是活的**:六个 run(box 1 + box 2,**已补进唯一 DRAM 真绑定的 L3:48**),n=**61** 个候选,**72.1% 在阈值 0.70 下多维绑定**(23.0% 在 0.85 下)—— 此数已剔除 `dram`/`compute` 两个 1/延迟的列(最初报 90%/45%,让延迟投了两票)。最常见组合 **occupancy + register_pressure**(27/61),其次加 shared(15/61):**三者全是编译期读数,与 S2c 所测维度完全重合**。补进 L3:48 后 0.85 阈值下**首次出现 `dram_bandwidth + register_pressure`(4 次)** —— 正是 A-1 关心的那类冲突,先前语料里一次都没有。
2. **没有规则打得过对照**(换了语料、换了维度集合、换了标签之后依然成立):最初 7.1% vs 21.4%;补进 L3:48 并只用编译期维度重新打分后 **R2 剩余空间最多 38.5% vs 最好对照 61.5%**,而 **R1 最紧的墙优先 7.7% 是全表最差**。**但那个 61.5% 的对照什么都没发现 —— 它只是叫出了摆幅最宽那一维的名字,见 A-3b。**
3. **原因在标签上 —— 但这一条的强度已两次下调**。最初:14 次成功改写里只有 4 次(28.6%)动得最多的那维是绑定的,且 8/14 什么都没缓解。**去掉延迟列并补进 L3:48 后(n=23):动得最多的那维是绑定的从 26.1% 升到 47.8%(几乎翻倍)**,而不做跨维度比较的问法给出 **10 缓解了绑定维度 / 11 什么都没缓解 / 2 只缓解非绑定 —— 大致对半**。所以正确说法是"**大约一半**的成功改写没在缓解绑定维度",不是"多数"。**这个较弱的版本仍然足以支撑"并列输出两类、不排序"这个可执行结论。**

> **A-1 问"该把哪一面墙推开";而数据说赢的改写里大约有一半没在推开任何「绑定」的墙。**(原文写"多数",已按补进 L3:48 后的 10 vs 11 下调)
>
> **⚠「赢的动作是填空隙」已收回,两个理由**:(1) 判据 5 个已知答案的 kernel 误判 2 个(纯 L2 kernel 读出 DRAM 屋顶 287%);(2) **更致命 —— `dram` 与 `compute` 两维就是 1/延迟**(byte_count/flop_count 是任务级常数,实测 `gpu_ms × achieved_tbs` 在 66 份判决上恒定到 0.07–0.36%),所以"朝墙推"与"变快了"是同一件事。**真正独立于延迟的只有编译期维度(occupancy/registers/shared)。** 见 `result-dram-and-compute-pressure-are-latency-restated.md`。

这也解释了规则为什么输:R1/R2 都在**绑定集合里**挑,而多数成功改写动的是集合**之外**的东西 —— 命中率被结构性压在 28.6% 以下,与规则好坏无关。

**定稿处理(取代原来的三个候选方向)**:S2 **并列输出两类维度,不排序、不加权**:

```
绑定的(墙在哪):    compute 0.93, occupancy 0.83   → 这些方向要付代价
有余量的(空隙在哪):dram 0.10, register 0.27       → 这些方向还能用
```

**v2 从来只报第一类。** 并且**记录 agent 的选择与实测结果的符合率**,让下一轮有前瞻证据。

**但"填空隙"不许变成新的机械规则**:n=14 太小(足以说明没有规则被支持,不足以立新规则);同一张表里已有反例(2/8 压强全平但吞吐涨 +34.97,更像减少了总工作量 —— 而候选真实流量正是 B-1 那个测不到的缺口);**因果方向未定**;以及**外部文献给了一个同样合理的替代解释**:Balakrishnan & Cheng(*IJPR* 38(6), 2000,已复核全文)的算例里利用率不满的资源反而影子价格更高($1.8 vs $0.6),所以我标成"有余量"的维度**可能本来就是真约束、只是利用率标签认错了** —— 那就不存在新机制。**两种读法可执行结论一致(都不按利用率排序、都并列报两类),但要分开须有正对照**(一个确知 DRAM 受限 + 一个确知占用率受限的 case)。**在那之前"填空隙"是候选解释。**

**这一条因此从「不做就走不下去」降级为「已有可执行的定稿处理」**,但它降级的方式是**问题被改写**,不是被解决。

#### A-2 维度集合「运行期发现」的机制未定

我写了「维度集合是运行期发现的产物」,但**没写发现机制**。目前只知道两端:
- 已知维度的 `applicable` 可由设备属性判定(V100 无 bf16 → false);
- 但「一个我们没预置的维度」怎么被发现,完全没设计。

**诚实的收缩**:v3 第一版恐怕只能做到「**预置维度集合 + 按设备/任务判定 applicable**」,而不是真正的运行期发现。**如果是这样,文档里必须这么写**,不能把「可扩展」说成「会自动发现」。

#### A-3 转化效率的分母跨维度不可比(量纲问题)

`Δlatency / Δresource_j` 在每个 j 上单位不同:字节 / 寄存器数 / 占用率百分点 / 启动次数。**同一维度内部比较是有意义的**(这次改动比上次改动划算),**跨维度比较没有意义**(省 1000 字节 vs 省 10 个寄存器,谁划算?)。

这与 A-1 是同一个困难的两个面。**当前的处理是「不跨维度比」,这是诚实的,但也意味着转化效率不能用来回答「该动哪一维」。**

#### A-3b ★ 新增(2026-09-10 晚):量纲问题已实际污染了 A-1 自己的证据基

**A-3 先前只登记为「转化效率不可跨维度比」。实测发现它还有第二个受害者:A-1 用来打标签的那个 `argmax |Δ压强|` 本身。**

23 次超噪声底成功改写上的实测摆幅:`shared_capacity` 中位 **0.162**、`register_pressure` 中位 **0.012**、`occupancy` 中位 **0.000**。**shared 的中位摆幅是 registers 的 13.5 倍** —— 而摆幅由归一化分母决定(`shared_bytes/101376` 一改 tile 就是几万字节;`n_regs/255` 动几个数),**与该维度是否真的是瓶颈无关**。

后果:重新打分后**「最佳对照」变成「永远挑 shared_capacity」= 61.5%**,它什么都没发现,只是叫出了摆得最宽那一维的名字。

**登记为硬纪律:禁止用跨维度的 `argmax |Δ|` 做任何判断** —— (a) 打标签、(b) 排序、(c) 报告给 agent。**替代**:每个维度只和**自己的历史分布**比("shared 降 0.16 = 该维度变化的第 50 百分位;registers 降 0.28 = 第 95 百分位")。这是 D-2(只有实测量进选择)与 A-3 的同一条纪律的第三次应用。

**对 S2c 无影响**(地图报 Δ 的原始量:字节数、寄存器个数,且只在同一维度内比较)—— 这次缺陷又一次说明了为什么 S2c 走原始量而非归一化压强。详见 `result-a1-evidence-base-had-two-defects.md`。

#### A-4 撤回 TMA 闭合后,没有等价的算错自检

原本有一个免费自检:`Σ分量 ≤ total` 且 `residual ≥ 0`,任何一处算错都会被抓住。**撤回后没有等价物。**

候选(均未验证):逐维度量纲/范围检查(利用率 ∈ [0, 1+ε],>100% 时 clamp 并打标记 —— Nsight 文档明写百分比可超 100%,我们已真的撞上 107.8%);`applicable`/`measured` 一致性检查;同配置重测两次比稳定性(抓得住随机错,抓不住系统错)。

**S2 的验收判据已包含「替代自检已确定并实现」,否则 S2 不算通过。**

#### A-5 异构卡的按维度比较办法未定

撤回 `Performance-Score` 后失去了跨卡可比的标量,而**不同卡上维度集合本身不同**(V100 无 bf16 维度),所以「逐维度比」会遇到「比什么」的问题。

候选:只比两卡都 `applicable` 的维度并显式报告被排除的维度;或者不比数值而比**判决模式**(哪些维度绑定)。**A100 测试的前置项。**

#### A-6 改写 agent 收到「多份并列判决」后的行为完全未验证

**外部有反向先例**:KernelBench 论文实测 few-shot 优化范例**降低** fast_1(o1 在 L1 上 10%→6%),因为模型「attempt more aggressive optimization strategies」而失败更多。给更多信息不保证更好。

**这是 S2 的最大风险**,判据 J2-5(终局不变差)就是为它设的,退路是回退消化层措辞而不回退向量。

| B-7 | **存储/容量只作布尔** | shared/regs 只有硬限检查(可行/不可行),不作可交换的软资源。而「用容量换流量」是最基本的交换之一 |
| B-8 | **谓词化维度不可测** | 会抓住 `if bn.training:` 死分支那类事故(31 个 trial 全测 fallback、零报错、全 run 最差)的信号是 warp-vs-thread 指令计数,**需要 counter → 被 `ERR_NVGPUCTRPERM` 永久挡住**。cubin 里能看到分支结构,看不到活跃线程数 |
| **B-9** | **改动的资源影响不可知 → 2026-09-10 已由实测给出可行解,降级为「已有对策,待实现」** | 用户点出的缺口 ③。三条前提已在 box 1 实测:一个资源点 **614.6 ms 中位 / 899 ms 均值 = 1/21~1/30 个计时 trial**;`n_regs`/`n_spills` **编译后 0/108,一次 0.4 ms 的 launch 后 96/96**;而**公式路线被否证** —— shared 线性拟合 0/96 精确命中(残差最大 121.4%),地图**不可分离**(1/8 一步移动增量一致,同一移动 shared 跨度 24576 B、寄存器跨度 127)。**对策 = S2c 局部资源地图**,详见 `v3-design-v2-resource-visibility-and-change-impact.md` |
| **B-10** | **num_warps / BK 的单调性未测** | §Q2 只有 BM/BN/num_stages 有 ≥3 个取值;两个取值的轴上单调性是**空命题**,而 **num_warps 恰好是寄存器跨度最大(127)那一条**。需扩到 ≥3 个取值重测。**这是我上一版把「monotone everywhere」写成一般结论时会漏掉的** |

### C. 功效缺口 —— 知道怎么做,证据不够

| # | 缺口 | 数字 |
|---|---|---|
| C-1 | **19 个 run 只有 1 个跑到墙钟** | 4 个用了 0-2/12 改写轮却「收敛」。**已翻转**:预算修好之后,最新 **5/5 跑完的 L3 run 全部由墙钟结束**,改写轮只用 1–2/5、族数 3–4/6 —— 现在的问题不是提前收敛,而是**墙钟不够** |

| C-2 | **Loop D 在 18 个 run 里零执行** | 论文四循环之一无证据;首次跑通后又暴露 D2(一次 novelty 失败结束整个 run,已修)。**最新 5 个 run 仍是 0,但原因换了**:族数 3–4 < 上限 6,门是开的;真因是 `orchestrator.py:568` —— Loop D 只在 `_rewrite_round` 无进展时才被调用,而改写一直有进展,墙钟先到。**这不是缺陷,是优先级;但意味着 D 在 12 h 预算下实际不可达** |

**C 类的共同处方是墙钟**,而这正是 S1 的价值:它把 18% 的 trial 预算还回来,是唯一同时改善「结果」与「统计功效」的一项。**C-1b 给了这句话一个上界**:trial 只占墙钟 43–46%,所以把 18% 的 trial 省下来最多还回墙钟的 ~8%;真正的大头(逐候选例行开销 23–29%)要动就得决定「是否每个候选都值得一份完整分析」,那是功效取舍不是缺陷修复 —— 而**看起来最便宜的那条路(只对一轮里更有希望的那个候选付例行开销)正是早停剪枝**,用户已否决,且 L3:21 的赢家族恰好来自四个 seed 里最差的那个、前两次调参完全持平。**留待全部实验完成后统一处理。**

### D. 已知但已决定不做的(记录以免重复讨论)

- 多目标 TPE / qEHVI(MOTPE 在 n=40 时只有 4 个点喂 `l(x)`,且 `multivariate` 静默变 False;qEHVI 在 M=4 时 acquisition 459 s = 25 个整 trial)
- 学习型代价模型(需 1.6M / 25k / 10M 次实测 = 827 年 / 5.2 天 / ~6 年)
- 构造取代搜索(Roller 小算子慢 50%、TC 与 cuBLAS 差 43%(即约 57% of cuBLAS);tritonBLAS 在真实形状慢 13.9%)
- 任何依赖 ncu counter 的方法(容器内永久不可用)
- 原始计数器进 prompt(p=0.0007 比不给更糟)
- 计数式取值黑名单(实测误杀 38.5%)
- 向量合成一个数(用户否决,三条理由)
- CUTLASS/CuTe(在 4090 上测不出收益;手写 CUDA 实测 0.874×;KernelPro 的 1.23× 来自 CuTe on Hopper)

## 第三部分:优先级建议

按「确定性 × 便宜 × 打中已实测缺陷」排:

1. **~~A-1~~ → 已由实测改写(2026-09-10)**,不再是 S2 的阻塞前置。定稿处理是**并列输出「墙」与「空隙」两类维度且不排序**。见 `result-a1-no-ranking-rule-...md`。**S2 现在可以在没有排序规则的情况下上线。**
2. **★ 修 `pct_of_dram_peak` 的 L2 缺陷(2026-09-10 已做完正对照,现在是一个确定的待修项)** —— 正对照已跑:5 个已知答案的 kernel **误判 2 个**,根因是该量分不清 L2 命中的流量与真到显存的流量,一个纯 L2 流式 kernel 读出 DRAM 屋顶 **287%** 并压掉真正的信号。**这不是设计缺口,是一个具体可修的度量缺陷,就在 v2 已上线的判决路径里**(`bottleneck.py:298`)—— **但今天还没伤到我们**:`byte_count` 是任务级的 `compulsory_bytes`,而三个真实任务全部远超 72 MiB L2(L3:21 307 MiB / L3:43 397 MiB / L3:48 1.351 GB)。**它是一个休眠缺陷,会随任务变小而醒来**,所以要在扩大任务范围之前修。两条修法都便宜且泛化:(a) 压强 > 1.05 报 unknown 而非 binding;(b) 工作集 vs L2 容量作为 dram 维度 `applicable` 的前置。**已列为 S2 的硬门 J2-8。** 见 `result-dram-and-compute-pressure-are-latency-restated.md`。
3. **B-2(峰值显存)** —— 一行代码(已复验全仓库零引用),外部有 28% 的实测支撑,可立即加。
4. **S1(编译期不可行声明出空间)** —— 唯一「确定 + 便宜 + 有外部实测支撑 + 打中 18% 浪费」的一项。
5. **S2c(局部资源地图)** —— 三条前提已全部实测(付得起 1/21~1/30 trial、字段一次 launch 后可读、公式与可分离性双双被否证),确定性与 S1 同级。它填缺口 ③(B-9),**并且与新的 A-1 处理互补**:判决说「哪些方向还有余量」,地图说「往那个方向走要付什么」。
6. **A-4(替代自检)** —— S2 的验收前置。**新增两条具体自检**:(a) 任何**跨配置恒为常数**的资源读数视为采集器故障(来自我自己的探针 bug:`n_regs` 读出常数 56 而非 None,「非 None」检查抓不住);(b) **每个维度必须显式声明「高还是低算绑定」** —— occupancy 是低算绑定,我把它当高处理过一次,结果 0 个多维绑定候选而催生 A-1 的那个案例就在输入里。
7. **B-6(per-backend 天花板)** —— 有外部实测数字(54% vs 96.5%),且它是 H/A 卡测试的前置。
8. **S1b 的历史重放** —— 零 GPU,回答「降权判据是否真的零误杀」。
9. **B-10(num_warps/BK 单调性重测)** —— 便宜,而 num_warps 是寄存器跨度最大那一条。
10. 其余按实施方案的阶段顺序。

**清单里现在唯一带 ★ 的是第 2 条(绑定判据的正对照)** —— 它不阻塞 S2 上线,但它决定 S2 输出的两类标签是否可信,而它便宜到没有理由不先做。

**要记清楚 A-1 是怎么"解决"的**:不是找到了排序规则,而是**发现问的方向错了**。真正的排序依据仍然不存在,只是现在知道不该去找它 —— 而这一点现在有外部依据:排队论/制造业与约束理论**两支文献在同一处断裂(多约束同时绑定)**,TOC 的产品组合工具在该情形下被证明 deficient,Meerkov 自承其规则"we do not have an analytical justification"。**没有已确立、经验证的方法能在不合成的前提下对同时绑定的约束排序。** 这对我们是双向的:确实是开放问题(可作新颖性的一部分),但也**不该期待去找到一个**。
