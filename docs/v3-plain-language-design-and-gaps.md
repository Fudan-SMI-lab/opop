## 第零部分:先讲清框架现在是怎么跑的

一次实验(一个 run)= 一个任务(比如 KernelBench 的 level3/48),目标是产出一个比 PyTorch 快的 GPU kernel。流程:

### 步骤 1:标定本机(`_calibrate`)
测出**这台机器实际能做到什么**:fp32/tf32/fp16/bf16 四档的算力上限、DRAM 带宽上限、一次 kernel 启动的最小开销。

**为什么不用规格书**:规格书是理论值。实测过 4090 上 tf32 只比 fp32 快 1.61 倍(88.1 vs 54.8 TFLOP/s),而 A100 上是 8 倍 —— 拿规格书当分母会得出完全错误的"还有多少余量"。

**为什么必须在候选编译之前测**:如果标定时 GPU 正在编译别的东西,测出的上限会系统性偏低。

### 步骤 2:测基线(`_baseline`)
跑四个 PyTorch 参考实现各 100 次:eager、eager+tf32、torch.compile、torch.compile+tf32。**最后一个是宣称加速比时唯一诚实的分母**(同精度对同精度)。

### 步骤 3:生成种子候选(`_generate_seeds`)
一个 LLM agent 读参考实现,写出 N 个不同结构的 Triton kernel。"不同结构"指算法思路不同,不是参数不同。

### 步骤 4:对每个候选跑四步流水线(`_candidate_pipeline`)

**4a. 参数化(含修复循环)** —— 另一个 agent 把候选改写成"所有可调项都走一个 `PARAMS` 字典",并声明每个旋钮的取值域。然后过**双见证门**:用默认配置和最小配置各跑一次,两个都得正确才允许进入调参。写坏了就交给 repair agent 修,最多几次。

**4b. 调参(`_tune`)** —— Optuna 的 TPE(贝叶斯优化)在这个参数空间里搜索,默认 40 个 trial。每个 trial:代入一组参数 → 编译 → 验正确性 → 计时 20 次。**这是墙钟的主要消耗者,一个 trial 约 18.6 秒。**

**4c. 统计与分析(`_stats_and_analysis`)** —— 先做确定性统计(每个旋钮的最优值曲线、是否顶在域边界、按取值的失败率),再让 analyst agent 读这些统计给出瓶颈判断。**这一步就是本项目要改造的核心。**

**4d. 扩域(`_maybe_expand_space`)** —— 如果某个旋钮的最优值顶在域的边界上,说明域给窄了,往外扩。

### 步骤 5:改写循环与新族循环
- **改写(Loop C)**:agent 拿着 4c 的瓶颈分析,对表现最好的候选做**结构性**修改(不是调参),然后新候选重新走一遍步骤 4。这是本项目最强的证据来源 —— L3:43 靠三代改写从 3.591 ms 走到 2.767 ms。
- **新族(Loop D)**:如果改写榨不出东西了,让 agent 写一个结构上足够不同的**新起点**。在 18 个 run 里从未执行过,这是个功效问题(见第三部分)。

### 步骤 6:定稿(`_finalize`)
θ_best 在一个**全新进程**里复测 100 次。**只有这个数字可以对外宣称** —— 调参过程中的 `tuned_ms` 系统性偏乐观。

## 第一部分:v3 要做的六件事(逐项白话)

我按"确定性 × 便宜 × 打中已实测缺陷"排序。**每项都写"不做会怎样",因为那才是它的价值。**

**六件事分别对着你点出的三个缺口**:

| 你点出的缺口 | 哪一项在填 |
|---|---|
| ① 完全没考虑**资源转化效率**(花掉的资源换到了多少性能) | 第 4 项(事后测交换比)+ 第 4b 项(事前查代价表) |
| ② agent 不知道**其他资源**的情况,甚至不知道撞到了哪个 | 第 2 项(每维一份判决)+ 第 4b 项(地图一次给全维度) |
| ③ agent 不知道**自己的改动会造成什么资源影响** | **第 4b 项(核心)** |

**并且**:第 1 项与第 5 项不直接对着这三个缺口,它们分别是"把浪费的墙钟还回来"和"补上缺失的维度与分母"—— 是前提条件而不是新能力。

### 第 1 项:让不可能跑起来的参数组合根本不进入搜索空间

**要解决的现象**:一个 Triton kernel 的 tile 越大,需要的 shared memory 越多。4090 的上限是 101376 字节。tile 开太大 → 编译得出来但**根本无法启动**。历史实测:**1004 个 trial 里有 180 个(18%)是这种必然失败**,而且是**编译期就能知道**的。

**当前已经做到什么(必须先说清,否则会夸大这一项的价值)**:
- `_prescreen_space`:调参前先批量问编译器"这些配置能启动吗"。批量是关键 —— 单独探测一个配置要 16.7 秒(和它替代的那个浪费 trial 的 18.6 秒差不多),而 48 个配置放一个进程里只要 11.02 秒,**每个摊 7 毫秒**。
- `tpe.py:69-71`:采样时如果 guard 说不行,**报 PRUNED 并重新抽**(PRUNED 会留在 Optuna 的模型里,FAIL 会被剔除)。
- box 1 最近这个 run 的实测效果:shared memory 失败只剩 **22 次(3.2%)**,远低于历史的 18%。

**诚实的增量**:所以"抽出再拒"**已经在做了**,而且有效。第 1 项真正的增量是更前一步 —— **让不可行的取值根本不出现在被抽的域里**(把约束表达成"给定 BLOCK_M 与 NUM_STAGES 之后,BLOCK_K 的合法取值只有这些"),这样连"抽了再拒"的那一轮循环都省掉。

**加在哪**:步骤 4a 的空间生成之后、4b 的调参之前。

**不做会怎样**:每次 ask 都要抽若干次才抽到合法点(`max_guard_rejects_per_ask` 上限是 64),浪费的是 CPU 与采样多样性,**不再是 GPU 墙钟**。所以它的价值比我上一轮说的小 —— **我之前把"18% 的墙钟浪费"当成这一项的收益,那部分收益 F5/P5 已经收了。**

**约束必须来自编译器,不能来自公式**:实测 agent 手写的 shared memory 约束中位只有真值的 32%,L3:43 那条 36/36 恒真、从不拒绝任何东西。**shared memory 的真值必须问编译器。**

### 第 2 项:瓶颈判断从"一个词"改成"每个资源维度各一份"(★ 核心)

**要解决的现象**:现在 `classify()` 返回一个词,8 种取值之一。L3:21 的 **20 份报告里 19 份都是 `resource_limited`** —— 几乎没有区分度,改写 agent 拿到的等于"资源不够",这句话不指向任何具体动作。

**而原料已经在了**:代码里 `evidence` 字段已经算出了 DRAM 占峰值百分比、算力占峰值百分比、占用率及其限制者、寄存器数、溢出数、shared 字节数、算术强度、ridge point、是否用张量核。**这些数已经存在,只是被 if-else 链压成了一个标签。** 另外四个 SASS 计数器(shared 读/写、64 位向量化、barrier)**已在采集但从未被任何代码读取**,躺在每个 run 的磁盘上。

**改成什么**:每个资源维度一条独立记录:

```
维度名          例:DRAM 带宽压力 / DRAM 延迟暴露 / fp16 算力 / 占用率 /
                    shared 容量 / 寄存器压力 / 启动开销 / 峰值显存
实测值
本机天花板
天花板来源      哪次标定、什么精度、什么后端 ← 没这个读者无法判断可信度
判决            绑定 / 接近绑定 / 宽松 / 不适用 / 未知
置信度          噪声底以下一律"未知"
是否适用        见下
```

**"是否适用"为什么必须是独立字段**:V100 没有 bf16,那么 bf16 相关维度**不存在**,而不是"值为 0"。这两者必须永远可区分。**这不是新问题** —— `task_cost.py` 已经用 `notes` 字段解决过同一件事:`flop_count = 0` 对 maxpool 是合法结果、对矩阵乘是失败结果,只有那个字段能区分两者。沿用已验证的做法。

**多个维度同时绑定时,就输出多份,不投票、不加权、不取最大值。** 这修的是缺陷本身:19/20 同标签的问题**不是标签选错了,而是"必须选一个"这个要求** —— 它强迫在同时绑定的维度之间做一个没有依据的选择。

**新增一条:资源占用是"结构特定"的。** 每次结构改写后必须重测,不能沿用父候选的数字。代码后果:资源记录要按 `(候选, 结构签名)` 存,**不能按族存**,否则改写会静默继承父代的数字。`families.py` 已有 `structural_signature` 可直接用。

**加在哪**:步骤 4c。

**不做会怎样**:改写 agent 继续收到"资源不够"这种无指向的输入,而 Loop C 是本项目最强的证据来源 —— 它的输入质量直接决定产出。

### 第 3 项:给 agent 的必须是"诊断",绝不能是数字(硬约束)

**这条是外部实测逼出来的,不是我们的偏好。** KernelPro 在 42 个 KernelBench 任务上做了三臂对照:

| 给模型什么 | 解决率 | 几何均值加速 |
|---|---|---|
| 什么都不给 | 32/42 | **3.35×** |
| ~50 个原始 ncu 计数器,不加解释 | 36/42 | **1.77×** |
| 消化后的工具建议 | 42/42 | **4.00×** |

单侧 Wilcoxon:**"什么都不给" 优于 "原始计数器",p=0.0007**。论文原话:"unstructured metrics actively degrade optimization quality"。

**注意那个非单调性**:原始计数器把解决率从 76% 提到 86%,却把速度**腰斩**。它让模型更擅长正确性、大幅更不擅长速度。

**所以第 2 项的输出必须先过一层"消化"**,每个维度产出四件事:严重度、根因(指向可改的旋钮或结构,不是现象重述)、排序建议(依据要写出来)、预期变化(**允许缺失,不允许编造**)。

**代码层面要加一道门**:构造 prompt 的函数**不得访问原始数值对象**,只能访问消化后的结果。原始数值的唯一出口是 events.jsonl 和 report.md。

**另一条同源约束:瓶颈必须我们自己算,不能问 agent。** 外部实测:给了剖析数据,agent 分类准确率 100%;只给源码,推理模型只到 **64%**。**64% 意味着 agent 自述的瓶颈永远不能当证据** —— 可以进证据栏,不能进判决。

**加在哪**:步骤 4c 的输出端、以及步骤 5 改写简报的输入端。

### 第 4 项:记录"这次改动花了什么、换来了什么"

**项目的核心思想**是:算子优化本质是在资源维度之间做交换(融合 = 花存储换启动和传输开销;降精度 = 花数值精度换算力和带宽)。要判断一次优化好不好,除了看它是否提升利用率,还要看**它的交换效率** —— 花的代价买到了多少性能。

**FlashAttention 是最好的例子**,它的论文在一张表里同时印出账本两侧(A100,seq 1024):标准实现 66.6 GFLOP / 40.3 GB / 41.7 ms;FlashAttention **75.2 GFLOP(多 13%)/ 4.4 GB(少 9.2 倍)/ 7.3 ms(快 5.7 倍)**。**它多花算力换流量。**

**这同时是一条警告:任何把 FLOP 当成要最小化的量的框架,都会否决 FlashAttention。** 所以评分对象必须是"每单位资源换来的延迟",不是资源最小化。

**具体做什么**:
- **改动前后各测一次**,记录成对观测 `(维度 i 变了多少, 维度 j 变了多少, 延迟变了多少)`;
- **只用于报告和给 agent 的信号**,不进任何选择逻辑。

**四条硬约束**:
1. **不作 TPE 的优化目标**(多目标会退化我们已有的 tuner:Optuna 的 MOTPE 在多目标下只把 10% 的 trial 喂给模型,40 个 trial 时是 4 个点,而且会静默关掉我们依赖的旋钮相关性建模);
2. **噪声底以下报"未知"**;
3. **不用来剪枝** —— 实测反例:L2:37 上**最慢**的种子所属的族改善最多(−30.5%),按效率剪枝会杀掉赢家;L3:21 领跑族的种子是四个里最差的;
4. **不把成对观测归约成一个交换率标量、不跨候选平均**。

**为什么第 4 条**:v2 已经用实测否决过"预测"版本。唯一一次尝试预测增益(`predicted_gain_pct`),n=21,**中位预测 5.0%、中位实际 1.8%、中位带符号误差 −5.0%,21 次里 8 次实际是负的**(预测 +16.4% → 实际 −16.5%)。那份文档的结论原话:"**Do not use it for allocation.**"

**所以边界是**:v2 失败的是**预测**;v3 做的是**事后测量实际发生了什么**。这是两件不同的事。

**加在哪**:步骤 4b 之后记录、步骤 5 的改写简报里使用。

### 第 4b 项(2026-09-10 新增,★ 与第 2 项并列为核心):在动手之前就知道"这样改会花掉什么"

**这一项填的是你点出的第三个缺口**:agent 不知道自己的改动会对资源使用造成什么影响。

**现在的实际情况**:agent 改一个 tile 大小,它靠先验猜"这大概会多用点 shared memory"。**实测这种猜有多不准**:改写后的资源占用漂移最多 **79.9 KB shared / 137 个寄存器**,全是没预料到的;而唯一一次让 agent 明确预测收益(`predicted_gain_pct`),21 次里 **8 次连符号都是错的**。

**v3 的做法:不猜,去测。** 在调参结束后,拿最好的那个配置,把**每个旋钮各往上下各挪一步**(约 30 个配置),批量编译一遍、每个 launch 一次(不计时),读出资源。产物是一张**局部代价表**:

```
把 BM 从 64 改到 128  →  多花 16384 字节 shared,多花 44 个寄存器
把 num_warps 从 4 改到 8 →  shared 不变,少花 42 个寄存器
...
```

于是"这样改会花掉什么"从**猜**变成**查表**。

**为什么这条现在是确定的,而不是一个想法** —— 三个问题都在 box 1(4090)上实测过了:

**问题一:付得起吗?** 一个资源点(冷编译 + 一次不计时 launch)**614.6 毫秒**(中位),整批算上编译长尾是 **899 毫秒**。一个计时 trial 是 **18.6 秒**。所以:

> **约 21 个资源点 = 1 个计时 trial。** 30 个配置的地图 ≈ 1.5 个 trial。一个 run 跑约 2000 个 trial,整套地图开销约占 **2.3%**。

对比它要修的浪费:编译期就注定失败的配置占了 **18%** 的 trial。

**问题二:数据拿得到吗?** 拿得到,但有一个关键分界:

| 读什么 | 编译完就能读吗 | 一次 launch 后能读吗 |
|---|---|---|
| shared memory、warp 数、stage 数 | **能(108/108)** | 能 |
| **寄存器数、spill 数** | **不能(0/108)** | **能(96/96)** |

**寄存器必须 launch 一次才能读** —— 而 launch 一次只要 **0.4 毫秒**。这一条正好对上 Roller 那篇论文的自述:它把寄存器上限硬编码打折到 **96/255 = 37.6%**(2.66 倍安全系数),原话是"**cannot detect implicit register allocation beforehand**"(无法事先探测隐式寄存器分配)。**一篇主张"用解析构造取代搜索"的论文,拿到完整表达式和硬件规格后,结论是寄存器无法从源码算出来。** 我们不是比它聪明,我们只是多一个它没有的选项:**launch 一次读一下,0.4 毫秒。**

**问题三:能不能写个公式省掉这一步?** **不能,而且两个方向都被否证了**:

- **shared memory 没有公式。** 用 `a·BM·BK + b·BK·BN + c·stages + d` 去拟合 96 个实测点:**0 个精确命中**,最大误差 **121.4%**。(理论上早该如此:Triton 是用活跃性分析 + 图着色 + 不动点迭代算的,没有闭式解。)
- **地图不能测一次到处用。** 同一个"把 BM 从 64 加到 128",在其他旋钮取不同值时,shared 代价的**跨度达 24576 字节**(接近 4090 上限的四分之一),寄存器跨度 **127 个**。8 种一步移动里,只有 **1 种**的代价是到处一致的。

**第二条恰好证实了你的判断**("每次算子结构改动后,算子本身的资源占用率都会发生改变") —— 而且把它从一条设计原则变成了一个**实测约束**:

> 地图必须**以当前配置为中心、局部测量**,带上"它在哪测的"这个有效范围;**结构改写之后必须重测,不能继承父候选的地图。**

**加在哪**:步骤 4b(调参)之后测,步骤 5(改写)的简报里查。

**风险与退路**:地图先**只写进日志、不进 agent 的 prompt**(零风险)。要不要进 prompt 需要单独一次对照实验 —— 因为"给 agent 更多信息会不会更好"本身完全未验证(见缺口 ⑥),而外部有反例。

### 第 5 项:补维度(峰值显存、per-backend 天花板)

**峰值显存**:目前**完全不存在**(已复验:全仓库零 `max_memory_allocated` 引用)。而外部实测 **28% 的 LLM 生成 kernel 会抬高峰值显存** —— 一个更快但吃更多显存的 kernel,在真实部署里可能是不可用的。**加一行 `torch.cuda.max_memory_allocated()` 即可。**

**per-backend 天花板**:现在拿 cuBLAS 能达到的算力峰值当所有候选的分母。但**Triton 发的是 WMMA 指令,不是 cuBLAS 的手工调优路径**。外部实测 V100:张量核经 cuBLAS 达理论峰的 **96.5%**,**经 WMMA 只有 54%**。**拿 96.5% 那个分母去衡量一个只能达到 54% 的后端,会让每个张量核候选都读出"利用率很低,还有大量空间",而那个空间结构上不存在。** 我们自己已经撞过一次同类的错:fp16 候选因为缺 fp16 天花板、被拿 tf32 当分母,读出 **107.8%"已到顶"**,实际约 54–60%,给出的指令方向完全反了。

**加在哪**:步骤 1 标定、步骤 4c 判决。

## 第二部分:缺口 —— 分三类,因为处理方式完全不同

我上一轮用 A/B/C 标号,那也是我的表达失误。这里按**"该拿它怎么办"**分类:

- **第一类:不知道该怎么设计** —— 多跑实验也解决不了,需要坐下来想清楚;
- **第二类:知道缺什么但不知道怎么测** —— 需要探索,可能测不出来;
- **第三类:知道怎么做但证据不够** —— 需要更多墙钟。

---

### 第一类:设计缺口(最要紧,因为无法靠跑实验解决)

#### 缺口 ①:多个维度同时绑定时,agent 该先动哪一维?→ **2026-09-10 实测:这个问题问反了**

**这个缺口原本是唯一"不解决就走不下去"的一条。** 原设计用"把向量合成一个数"回答它:压成一个标量,最紧的那维就是要动的那维。你否决了合成,这个问题就没有答案了。

**它不是理论问题,是眼前的问题。** L3:48 的获胜候选**同时**是 DRAM 带宽 **93.7%**(几乎撞满)与占用率 **17%**(限制者是寄存器),而两个方向的改写要求**相反**:减流量要**更大**的 tile(吃更多寄存器 → 占用更低),提占用要**更小**的 tile(复用更少 → 流量更多)。

**我本打算靠设计工作补上它。先去数据里看了一眼,结果发现前提站不住。** 工具 `scripts/multibind_rule_check.py`,零 GPU,只读历史日志。三步:

**第一步:这个现象确实很常见。** box 2 三个 run、40 个候选,按"压强"统计(每个维度归一到 `1.0 = 贴着墙`,**占用率要反向** —— 17% 占用是压强 0.83 不是 0.17):

| 阈值 | 多维同时绑定 |
|---|---|
| 0.70 | **36/40(90.0%)** |
| 0.85 | 18/40(45.0%) |

**所以这个缺口是活的。**

**第二步:没有任何排序规则打得过对照。** 在"父候选多维绑定 + 子候选提升超过噪声底"的 14 次改写上打分 —— 规则挑的那一维,是不是那次成功改写实际动得最多的:

| 规则 / 对照 | 命中率 |
|---|---|
| 最紧的墙优先 | 7.1% |
| 剩余空间最多优先 | 7.1% |
| **永远挑同一维(对照)** | **21.4%** |
| **均匀随机(对照)** | **21.4%** |

**两个规则都输给"永远挑同一维"。** 两个对照是这张表的全部意义 —— 一个规则拿 60% 毫无意义,除非知道随机能拿多少。

**第三步:原因在标签上,而这才是真正的发现。**

> **14 次成功改写里,只有 4 次(28.6%)动得最多的那一维是绑定的。**

"动得最多"这个判据本身脆(它是跨维度的 argmax,而各维度没有共同单位)。所以换一个**完全不做跨维度比较**的问法:这次改写有没有**缓解**任何一个原本绑定的维度?

| | n=14 |
|---|---|
| 缓解了至少一个**绑定**维度 | 6 |
| **什么都没缓解**(变快了但没有任何维度压强下降) | **8** |

**再看那 8 次到底做了什么**(正号 = 朝墙靠近):

| 子候选 | 提升 | ΔP_compute | ΔTFLOP/s |
|---|---|---|---|
| cand-490a9d76 | 58.9% | **+0.45** | **+70.61** |
| cand-25eb0110 | 57.3% | **+0.41** | **+70.34** |
| cand-71e51726 | 47.2% | +0.28 | +24.81 |
| cand-7760976a | 43.0% | +0.43 | +38.39 |
| cand-1cfac4a2 | 41.5% | +0.40 | +36.06 |

**8 次里 6 次把某个维度朝墙推了,同时吞吐大幅上升。** 它们不是在缓解约束,**是在把一个有余量的资源用起来。**

> **这个缺口问的是"该把哪一面墙推开";而数据说赢的改写多数没在推开任何"绑定"的墙。**

**⚠ 但"赢的动作是填空隙"这个解释我已经收回了(同一天)。** 我按下面第(3)条自己立的正对照去验证时发现:**利用率判据在 5 个我们按构造就知道答案的 kernel 上误判了 2 个**。根因是"DRAM 压强"分不清**L2 命中**的流量和**真到显存**的流量 —— 一个数据全在 L2 里的流式 kernel 读出了 DRAM 屋顶的 **287%**(物理上不可能)。

**所以"绑定/有余量"这两个标签本身不可信**,建立在它们之上的机制解释就没有证据。详见 `docs/result-binding-criterion-mislabels-l2-resident-kernels.md`。

**仍然站得住的三条**(它们不依赖标签对不对):没有排序规则打得过对照(规则和对照用的是同一套标签);不要按利用率排序(两条独立依据);并列输出多类维度而不选一个头条。

**而这恰好就是你说的"将算子的资源使用分布与硬件/环境的资源分布对齐"。** 规则输的原因也随之清楚:两个规则都在**绑定的那几维里**挑,而多数成功改写动的是**绑定集合之外**的东西 —— 命中率被结构性压在 28.6% 以下,与规则好坏无关。

**所以第 2 项的输出定稿为:并列给出两类,都不排序。**

```
绑定的(墙在哪):     compute 0.93, occupancy 0.83   → 这些方向要付代价
有余量的(空隙在哪): dram 0.10, register 0.27       → 这些方向还能用
```

**v2 从来只报第一类。** 这与第 4b 项的局部地图正好互补:判决说"哪些方向还有余量",地图说"往那个方向走要付什么"。

**但"填空隙"不许变成新的机械规则**,三条理由:
1. **n=14 太小** —— 足以说明"没有规则被支持",不足以立一个新规则;
2. **反例就在同一张表里** —— 另 2/8 是"压强全平但吞吐涨 +34.97",这连"填空隙"都解释不了(更像是减少了总工作量,而那正是缺口 ⑦ 测不到的东西);
3. **因果方向未定** —— 吞吐上升和延迟下降是同一件事的两种说法,在这份数据里分不开。

**处理**:记录 agent 的选择与实测结果的**符合率**,让下一轮有前瞻证据。

**这个缺口因此不再阻塞第 2 项** —— 但要记清它是怎么"解决"的:**不是找到了排序规则,而是发现问的方向错了。真正的排序依据仍然不存在,只是现在知道不该去找它。**

**完整论证**:`docs/result-a1-no-ranking-rule-survives-its-controls.md`。

#### 缺口 ②:"维度集合运行期发现"只写了目标,没写机制

我写了"维度集合是运行期发现的",但**没写怎么发现**。目前只知道两端:已知维度的"是否适用"可由设备属性判定(V100 无 bf16 → 不适用);但**一个我们没预置的维度怎么被发现,完全没有设计**。

**诚实的收缩**:v3 第一版恐怕只能做到"**预置维度集合 + 按设备/任务判定是否适用**"。**如果是这样,文档必须这么写** —— 不能把"可扩展"说成"会自动发现"。

#### 缺口 ③:交换效率的分母跨维度不可比(量纲问题)

`延迟变化 / 资源 j 变化` 在每个 j 上单位不同:字节 / 寄存器个数 / 占用率百分点 / 启动次数。**同一维度内部比较有意义**("这次改动比上次划算"),**跨维度比较没有意义**("省 1000 字节 vs 省 10 个寄存器,谁划算?")。

这和缺口 ① 是同一个困难的两面。当前处理是"不跨维度比",这是诚实的,但也意味着**交换效率不能用来回答"该动哪一维"**。

**不过缺口 ① 的实测让这个限制没那么要紧了**:既然赢的动作多数是"往还有余量的方向走"而不是"在几个绑定维度之间取舍",跨维度排序的需求本身就小了。量纲问题依旧无解,但它挡住的那件事已经不是必需的了。

#### 缺口 ④:失去了一个免费的算错自检

原设计要借 Intel TMA 的做法:选一个守恒的量作分母、把各分量加起来必须等于它、差额记为"未解释部分"。**这样任何一处算错都会被"加起来不对"抓住。** 撤回合成后,这个自检没有了,而**我们没有等价替代**。

候选(都未验证):逐维度的量纲与范围检查(利用率超 100% 时**截断并打标记而不是拒绝** —— Nsight 文档明写百分比可以偶尔超 100%,我们已经真的撞上 107.8%);"是否适用 / 实测值"一致性检查(标了不适用却带实测值 = 缺陷);同配置重测两次比稳定性(抓得住随机错,抓不住系统错)。

#### 缺口 ⑤:异构卡怎么按维度比较

撤回那个跨卡可比的标量之后,**不同卡上维度集合本身不同**(V100 没有 bf16 维度),所以"逐维度比"会遇到"比什么"的问题。候选:只比两卡都适用的维度并显式报告被排除的;或者不比数值而比**判决模式**(哪些维度绑定)。**这是 A100 测试的前置项。**

#### 缺口 ⑥:agent 收到"多份并列判决"后的行为完全未验证

**外部有反向先例**:KernelBench 论文实测,给 few-shot 优化范例反而**降低**成绩(o1 在 level1 上 fast_1 从 10% 掉到 6%),因为模型"attempt more aggressive optimization strategies"而失败更多。**给更多信息不保证更好。**

这是第 2 项的最大风险。判据是"最终结果不能变差",退路是回退消化层的措辞而不回退底层记录。

### 第二类:测量缺口(知道缺什么,不知道怎么测)

#### 缺口 ⑦(最难):候选实际搬了多少字节,从来没被测过

现在传给瓶颈分类器的是 `compulsory_bytes` —— **任务级的下界,对所有候选是同一个常数**。后果:一个融合掉一半中间张量的候选,和一个完全不融合的候选,在分类器眼里**流量完全相同**。而"DRAM 占峰值百分比"实际是"任务级分子 ÷ 候选级分母",**偏差在融合最差的候选上最大**,恰好在最需要准确判断的地方最不准。

**三条现成的路已经逐一在代码里证明不通**:
1. **数 SASS 里的 LDG/STG 指令** —— 那是**静态文本计数**。一个 K 维循环 100 次的矩阵乘,它的 LDG 可能只出现两三条。"指令数 × grid"得不到动态字节数。
2. **`TorchDispatchMode`** —— 它是 **aten 算子级**的。它能测出参考实现的流量是因为参考由许多 aten 算子组成;而**融合良好的候选只有一个自定义 Triton 算子**,dispatch 在它内部什么也看不见。**这个仪器会系统性低报,而且融合越好越低报** —— 方向完全错。
3. **静态转动态的换算** —— `ProfileRecord` 里**没有 grid 尺寸也没有启动次数**,连乘数都缺。

**所以这是探索项,不排进关键路径。** 第一步应该是给 `ProfileRecord` 补上 grid 和启动次数 —— 这个改动**独立有用**,不依赖整件事成功。

#### 缺口 ⑧:通信维度、多卡维度完全不存在
绑定多卡环境,现在没有硬件可测。

#### 缺口 ⑨:容量类资源只作布尔判断
shared memory 和寄存器现在只有"超限/不超限",不作为**可交换的软资源**。而"花容量换流量"是最基本的交换之一(tiling 就是它)。

#### 缺口 ⑩:线程谓词化不可测
有一类事故是这样的:`if bn.training:` 把优化挡在死代码一侧,**正确性过、计时正常、零报错**,31 个 trial 全在测 fallback 路径,拿到全 run 最差的成绩(25.0 ms)。能抓住它的信号是"warp 级指令数 vs 线程级指令数"之比,**但那需要硬件计数器,而计数器在租用容器里永久不可用**(`ERR_NVGPUCTRPERM`,需要宿主机侧的内核模块参数)。cubin 里能看到分支结构,看不到实际活跃的线程数。

## 第四部分:整体形态 —— 为什么是"多个算法 + 多个 agent"

你给的架构约束:

> 新增的这些缺口里会包含大量的资源/profiling/性能采集和分析的过程,**不能指望一个 agent 或是一个算法来完成这些工作**,可以通过**多个算法**来进行采集和信息提取,并由**多个 agent** 来进行分析和基于这些信息和分析结果来进行改进

**这条约束有实测依据,不只是分工偏好。** 外部有一个三臂对照实验:把**原始计数器数值直接喂给 LLM** 的那一臂拿到 1.77×,而**完全不给反馈**拿到 3.35×(单侧 Wilcoxon p=0.0007)。**给 agent 原始数值比什么都不给更差。** 所以采集与分析之间必须隔一层代码。

**三层的形状**:

```
第一层  采集器(多个独立算法,全是代码,零 LLM)
        每个只回答一个窄问题,各自有正对照,可以单独坏掉而不污染其他
                    │  产物:带出处的实测数字
                    ▼
第二层  提炼器(代码,不是 agent)  ← 这一层是硬约束,不能省
        把原始数字变成"每维一条判决 + 局部代价表",并做算错自检
                    │  产物:结构化的、有限的、可以被证伪的陈述
                    ▼
第三层  分析 agent(多个,各管一段,互不共享上下文)
                    │  产物:排序后的改写方向 + 理由
                    ▼
        harness 判定(接受/拒绝/继续 —— 永远由代码决定,不由 agent)
```

**第一层的采集器**(每个一个窄问题):局部资源地图(第 4b 项)、编译期可行域(第 1 项)、天花板标定、任务级下界、SASS 静态特征(**已经在采集,但从未被读过**)、成对变更观测、启动开销、占用率实测。**关键规则:每个采集器都必须能报"我测不出来",而不是猜一个数。**

**第三层的四个 agent**:

| agent | 只看什么 | 输出 | 不许看 |
|---|---|---|---|
| 资源分析 | 每维判决 + 天花板出处 | 哪些维度绑定、证据有多强 | 原始数字、其他 agent 的结论 |
| 变更影响分析 | 局部代价表 + 成对观测 | "往这个方向走要付什么" | 延迟排名(防它反推答案) |
| 转化效率分析 | 历史的"花了什么 → 换到什么" | 哪些资源花了却没换到东西 | 未来的建议(它只做回顾) |
| 改写提议 | 上面三个的**结论**(不是它们的原料) | 排序后的结构改动方案 | 任何原始测量 |

**"改写提议只看结论不看原料"就是第二层那道门的位置。**

**为什么多个而不是一个 —— 两条实测依据**:
1. **代码任务上,去掉任何一个角色代价都很大**:ChatDev 去掉角色后可执行率 0.88→0.58;AgentCoder 从"只有 programmer"的 61.0/47.9 到三个 agent 的 79.9/89.9;MapCoder 去掉 debugger 掉 17.5%。**专门反向查过,找不到任何代码域论文说 reviewer/tester/critic 可以省。**
2. **弱模型放分析位可行,放生成位不行**:实测 GPT-OSS-120B 当**评审**达 100% 正确率/1.364×,当**写代码的**掉到 96%;QwQ-32B 当写代码的只有 0.790×。

**成本核算(必须付得起)**:外部实测可负担范围是**每轮 2–3 次 agent 调用**(有一份工作在 3 次调用下拿到 1.978× geomean、每个算子 $0.21、不用计数器、非前沿模型)。我们现在每轮已经用掉 2 次。**所以四个分析 agent 不能每轮全跑** —— 转化效率分析是回顾量,**只在同一族连续两轮没进展时才触发**,这样每轮稳定 2–3 次,卡住时才到 3–4 次。

**两条必须记下的反向证据**(它们和上面的依据方向相反,我不打算藏起来):
1. **在匹配预算下,多 agent 未必赢**:MMLU-Pro/Llama-3.1-70B 上 debate 只 +1.3pp、mixture-of-agents +2.7pp,**而且低于约 3 倍 CoT 预算时朴素 self-consistency 反而胜**。我们是预算饥饿的,**按这条我们正落在"多 agent 不划算"的区间**。抵消它的是上面那条代码域证据,以及我们的任务是 planner/actor 型而非 debate 型 —— 调研里这两类的结论确实是分叉的。**结论:不建 debate 循环**(有 NeurIPS 2025 Spotlight 论证"多数投票本身就解释了通常归因于 debate 的大部分收益")。
2. **同一个结构性修复的效果极不稳定**:同样的拓扑改动,在一个基准上 25.0%→40.6%,在另一个上 89.6%→91.5%(几乎没有),换个底座模型则**统计不显著**(p=0.4 → 换模型后 p=0.03)。原文:"these seemingly straightforward solutions often prove inconsistent"。**所以第三层的 agent 数量与分工必须是可消融的配置项,不能写死进架构。**
