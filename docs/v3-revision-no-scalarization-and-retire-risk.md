# 两处修正:F-A 的过度拦截风险已量化(撤回),以及"不做向量合成"

**状态**:2026-09-10,基于用户的两条反馈。两条都接受,第二条改掉的东西比表面更多——它同时否掉了我原计划里另外两处。

---

## 一、F-A(N 次全败即摘掉取值):风险已量化,**按原样撤回**

### 1.1 用户的判断是对的,而且比"有风险"更严重

我原本推荐"某个 categorical 取值累计 N 次全失败后从后续采样域里摘掉",并说它"低风险"。**我用全部 7 个 L3 run 的历史数据做了这个提案自己的反向对照,结论是它在低阈值下会大量误杀。**

`scripts/retire_risk.py`:对每个 `(候选, 旋钮, 取值)`,按事件顺序数"首次成功之前有多少次连续失败";若该数 ≥ N 而该取值**后来成功过**,则阈值 N 会摘掉一个能用的取值。

| 阈值 N | box 1(4 个 run) | box 2(3 个 run) |
|---|---|---|
| **6** | 摘 43 个,**2 个后来成功(4.7%)** | 摘 13 个,**5 个后来成功(38.5%)** |
| **8** | 摘 36 个,0 个 | 摘 8 个,**2 个后来成功(25.0%)** |
| **12** | 摘 22 个,0 个 | 摘 3 个,0 个 |
| 20 | 摘 8 个,0 个 | 摘 0 个 |
| 40 | 摘 0 个 | 摘 0 个 |

**我原本建议的 N=12 恰好落在两箱都零误杀的位置——但这是事后挑的,不是先验的**,而 N=6/8 的误杀率高达 38.5%/25.0%。一个必须靠事后调参才安全的阈值,不是低风险机制。

### 1.2 被误杀的取值有多好——这是最关键的一组数字

| 被 N=6 摘掉的取值 | 该取值的真实通过率 | 说明 |
|---|---|---|
| `PJ_BC=64`(L3:21 box2) | **102/176** | 该 run 使用最多的取值之一 |
| `ATTN_BLOCK_N=128`(L3:43 r2) | **12/23** | best 3.929 ms |
| `ATTN_BLOCK_N=128`(L3:43 box2) | **25/55** | best 3.577 ms |
| `EXPAND_STAGES=4`(L3:21 box2) | 3/12 | |
| `RED_CB=128`(L3:21 box1) | 3/10 | |

**`PJ_BC=64` 通过 102/176。** 我的机制会因为开头 6 次不巧全失败就把它摘掉。这不是边缘案例,是把主力取值当垃圾扔掉。

唯一的安慰是"被摘掉的取值里没有一个落在该 run 最优的 2% 之内"——但这个安慰很弱:它只说明在这 7 个 run 的具体抽样顺序下没有酿成事故,而不是机制安全。

### 1.3 根因:失败几乎总是**条件性**的,而摘掉取值是**无条件**动作

`scripts/value_conditional.py` 把某个取值的通过率按其他旋钮的取值切开。`ATTN_BLOCK_N=128`(L3:43 r2,总计 12/23):

```
--- GEMM_BLOCK_K
    128    0/3   <-- 与这个搭档从不通过
    64     7/11
--- ATTN_STAGES
    1      9/11
    2      3/10
--- COMPUTE_DTYPE
    bf16  10/11
    fp16   2/9
```

**这个取值本身没问题,是某些组合有问题。** 摘掉 `ATTN_BLOCK_N=128` 等于因为搭档的过错而处决它。

**这正是用户直觉指向的东西**,也和我们已有的记录同向:[[opop-v2-K-retune...]] 系列反复出现的教训是"归因要看获胜配置到底用了什么",而"取值级别的黑名单"是比"点级别的 FAIL"更粗、而不是更细的工具。

### 1.4 那 tf32 呢——它是不是同一类?**不是,而且差别可测**

同一个脚本跑 `DOT_PRECISION=tf32`(L3:48 r2):

```
--- OUT_WARPS        1:0/2   2:0/3   4:0/10  8:0/6
--- STATE_BLOCK_P    16:0/2  32:0/1  64:0/14  256:0/1
--- STATE_NUM_STAGES 1:0/5   2:0/3   3:0/3   4:0/7
--- STATE_NUM_WARPS  1:0/2   2:0/9   4:0/5   8:0/2
(每一个搭档、每一个取值,全部 0 通过)
```

**tf32 是无条件失败:在每个旋钮的每个取值下都是 0。** 而被误杀的那些是条件性失败(有搭档下 7/11、10/11)。**这个区分是可测的,不需要猜。**

### 1.5 替代方案:判据从"N 次全败"改成"无条件性 + 已有充分反例"

**不做**:计数式黑名单(任何阈值)。
**改做**:只有当一个取值满足**全部三条**时才降低其采样权重(而非摘除):

1. **无条件性**:对每个其他旋钮的每个取值(样本 ≥3 的),该取值的通过数均为 0 —— 即失败不能被任何搭档解释;
2. **样本充分**:该取值自身试过 ≥ M 次(M 取该 run 中同旋钮其他取值的中位样本量,而不是一个猜的常数);
3. **有活着的对照**:同一旋钮至少有一个其他取值在同一批搭档下通过过 —— 排除"整个候选坏了"的情形。

**并且动作是"降权"不是"摘除"**:把它的采样概率降到该旋钮其他取值的 1/k(k 可配),**保留非零概率**,这样"我们错了"仍然可以被后续 trial 纠正。计数式黑名单没有这个性质。

**这个替代方案的验收判据必须是**:在全部 7 个历史 run 上重放,**误杀数必须是 0**(而不是"在某个 N 下恰好是 0"),同时 tf32 那 172 个 trial 里至少有 100 个被省下。`retire_risk.py` + `value_conditional.py` 就是这个重放的工具,零 GPU 成本。

**排期上它仍属 v3 阶段 1,并且降级为"需要先通过历史重放才能实现"的条目,不再标"低风险"。**

## 二、"资源向量合成一个数":取消,改为按维度独立处理

### 2.1 用户的立场

> 我不赞同直接采用其他工作的公式,而是应该开发/研究自己的一套算法(甚至可以说我从来没想过要把资源向量合成一个数,不同维度可以按不同维度去单独考虑,并且在不同设备上维度的数量也未必是固定的,在每次算子结构改动后,算子本身的资源占用率都会发生改变)

三条独立的理由,每条都否掉设计里的不同部分:

1. **不该照搬外部公式** —— 借来的公式携带借来的假设;
2. **合成本身不是目标** —— 各维度应当独立考虑;
3. **维度数不固定** —— 随设备变,且每次结构改动后占用率都变。

### 2.2 我接受,并且这否掉的比一处更多

**撤回 §零修订 5 的地位**:ECM 的 `T = max(T_nOL + T_data, T_OL)` 与 ERM 的 α 从"设计要采纳的合成规则"降为**调研记录里的先验工作**。原文档说它"回答了设计里悬空的问题"——**那个问题现在被取消了,而不是被回答了。**

**连带撤回三处我自己写进计划的东西**(它们都预设了"要合成一个数"):

| 原条目 | 为什么必须一起撤 |
|---|---|
| **S2 的 TMA 式闭合**(守恒分母 + 残差 `unexplained_ms`) | 把 `total_ms` 划分成具名分量、要求加和守恒,**本质就是合成**。它假定分量可比、可加、数目固定——三条都与"维度数不固定"冲突 |
| **S5b(α 作可测标量)** | 整条取消,不再是"若 S5 通了才有意义",而是不再需要 |
| **S3 的 `Performance-Score` 作头条量** | `Score = Achieved / min(Peak FP, Peak BW×AI)` **是把两维压成一个标量**。它可以留在报告里作参考,但**不作头条上报量、不作判据** |

**Gables 的四步排序自检也降级**:它检验的是"合成规则能否复现某个排序",而我们不再有合成规则。它作为"局部正确的资源移动会整体变差"的**动机例子**保留,不作验收判据。

### 2.3 替代设计:按维度独立,维度集合本身是运行期发现的

**核心转变:从"一个向量 → 一个数"改为"每个维度一份独立的判决 + 一份维度间的关系记录(不聚合)"。**

**(a) 维度集合不固定,由设备与任务共同决定**

不预声明固定的 N 维。每个维度是一条独立记录:

```
{ dimension_id, measured, ceiling, ceiling_provenance, verdict, confidence, applicable }
```

- `applicable` 是一等字段:V100 无 bf16 → bf16 相关维度**不存在**而非"值为 0";4090 上 tf32≈fp32 → 精度维的交换价值**结构性地小**。
- **`applicable=false` 与 `measured=0` 必须永远可区分**——这正是 `task_cost.py` 已经用 `notes` 处理过的同一个问题("`flop_count = 0` 对 maxpool 是合法结果,对 matmul 是失败结果,只有这个字段能区分")。**沿用那个已验证的做法。**

**(b) 每次结构改动后重测,不继承**

用户点出"每次算子结构改动后占用率都会改变"。这与我们已立的两条纪律合并:交换比是设备特定的(A100 +50.9% vs A4000 +5.8%),以及天花板必须实测。**新增第三条:资源占用是结构特定的,改写后必须重测,不得沿用父候选的向量。**

这有一个直接的代码后果:候选的资源记录必须**按 `(候选, 结构签名)` 键入而非按族键入**,否则 rewrite 会继承父代的占用数字。这一条要在 S2 实现时验证。

**(c) 维度间的关系:记录成对观测,不合成成标量**

用户说各维度可独立考虑。但"某维度花费换来另一维度缓解"这件事本身是**成对**的,不能真的完全独立。折中做法:

- 记录**成对观测** `(维度 i 的变化, 维度 j 的变化, 延迟的变化)`,来自同一次结构改动的前后对比;
- **不把它归约成一个交换率标量,不跨候选平均,不作为选择依据**;
- 它的用途是**给消化层提供一句可证伪的话**:"这次改动在 i 上多花了 X、在 j 上省了 Y、延迟变了 Z"。

**这与 §1.4 的既有边界一致**:进入选择/排序的数字必须是已实现的实测量。成对观测是实测的,而"平均交换率"是构造出来的——**后者不做。**

**(d) 判决保持多份,不投票**

每个维度输出自己的 `verdict`(binding / near-binding / slack / not-applicable / unknown)。**当多个维度同时 binding 时,输出就是"多个维度同时 binding"**,不选一个赢家、不加权、不取 max。

这恰好修掉了 v2 已实测的一个缺陷:20 份报告里 19 份是 `resource_limited`——**单标签的问题不是标签选错了,而是"必须选一个"这个要求本身**。

### 2.4 这样做失去了什么(必须诚实记下)

1. **没有单一头条数字**,报告与 prompt 都更长。消化层的工作量上升——它现在要处理"多个维度同时 binding"的表述。
2. **无法直接回答"这个候选整体处在天花板的百分之几"**。这个问题以后只能按维度回答。
3. **失去了一个免费的自检**:TMA 式闭合本可以用"分量和 ≤ total"抓住算错。**必须换一个自检**,候选做法是逐维度的量纲/范围检查 + `applicable` 与 `measured` 的一致性检查(例如 `applicable=false` 却带 `measured` 值 = 缺陷)。**这一条是本次修改留下的空缺,记入待办。**
4. **`Performance-Score` 的"跨卡稳定"这个优点用不上了**(它的稳定性正来自压成标量)。异构卡比较将需要另一套办法——按维度逐条比,且要处理维度集合本身不同的情形。**这也是空缺。**

### 2.5 新颖性上的影响:反而变强

原设计的可守地面是"没有人把维度间替代率当作按任务实测、并用于引导搜索的量"。**现在多了一条更硬的**:

调研的 §3.9 结论是——**现存所有多资源模型,无论 ERM 的向量还是 Gables 的 N 单元,最终都收敛到一张 2D 图或一个标量界**;ERM 用 α 合成、ECM 用重叠假设合成、Gables 用 `max` 合成、Nsight SOL 用维度间取 max。**"拒绝合成、维持多份并列判决、且维度集合本身是运行期发现的"在调研的约 120 篇里没有对应物。**

这条比原来那条更好守,因为它是一个**设计选择**而不是一个测量声明——审稿人无法用"某篇 2014 年的论文也有向量"来驳回它。
