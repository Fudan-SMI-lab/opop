## 0. 一句话

**在一次调参跑完之后,对"被硬件拒绝的参数取值"做一次逐 knob 的归因消融,
从而把"哪个 knob 被哪个资源顶住、顶住它值多少延迟"从 agent 的猜测变成 harness 的实测。**

## 1. 为什么需要它:现在这个信息是**猜的**

`BottleneckReport.parameter_limits`(`models/reports.py:62`)的字段形状恰好就是我们要的:

```python
class ParamLimit(BaseModel):
    param: str
    headroom_direction: Literal["increase", "decrease"]
    blocked_by: str          # "registers" | "shared_memory" | "oom" | ...
    predicted_gain_pct: float | None
    evidence: str = ""
```

**但它 100% 由 analyst agent 自己填**(`agents/modules.py:1126` 的 prompt schema),
harness 从不核对。实测两个 box2 run 的 179 条声明:

| | 数量 |
|---|---|
| analyst 的 `parameter_limits` 声明 | **179** |
| 其中 harness 的数据**也**认为该 knob 在边界 | **57 = 32%** |
| `blocked_by` 分布 | shared_memory 83、**none 57**、registers 27、compile_failure 6、其他 6 |
| 带 `predicted_gain_pct` 的 | 114/179 |

**68% 的声明说的是 harness 数据不认为在边界的 knob**,而 `predicted_gain_pct` 已被本项目
量过会高估。⇒ 这是一个未经核验的猜测字段,而它**可以被实测替代**。

## 2. 数据地基已经在,而且已经测过

真正的数据源不是 `at_boundary`,而是 **`CONFIG_SCREENED_INFEASIBLE`**
(`orchestrator.py:1477`),它记录**实测的、逐配置的资源拒绝**:

**box2(4090,shared 上限 101376 B):**

| 量 | 值 |
|---|---|
| 资源拒绝记录 | **402 条** |
| requested/limit 比值 | min 1.02、**p50 1.62**、max 11.64 |
| 在 1.5x 以内(一个 knob 步长可能就能装下) | **42% / 46%** |
| 形成"截断"的 knob(被拒值在已跑范围之外) | 6 |
| **其中延迟仍朝被拒值改善的** | **3** |

那三个案例:

| 候选 | knob | 已跑值 | 被拒 | 每值最优延迟 | 尾部增益 |
|---|---|---|---|---|---|
| cand-2dc6a2ff | BLOCK_M | 64,128,256 | **512, 1024** | 3.8221→3.3807→3.1836 | **+16.7%** |

**A800 上是 0**(上限 166912 B = 1.65x,22 条拒绝,一个 run 是 0)⇒ **可用性取决于卡有多紧。**

## 3. 唯一的缺口:一条拒绝命名的是**整个 param set**

`CONFIG_SCREENED_INFEASIBLE.params` 是**完整的 6–12 个 knob 的取值**。
所以从一条拒绝**无法断定是哪个 knob 造成的**。我在探针里用的是保守判据
(被拒值落在已跑范围之外),得到 6 个案例 —— 但那是**相关**,不是**归因**。

**2e 就是补上这一步。**

## 4. 做什么:具体算法

### 4.1 触发点

在 `_stats_and_analysis`(`orchestrator.py:1486`)里,**`STATS_DONE` 之后、
`BOTTLENECK_REPORTED`(analyst 调用)之前**。这个位置有三个理由:

1. 此时该候选的全部 trial 已在手,所以"已跑范围"和"每值最优延迟"都是完整的;
2. 它在 analyst **之前**,所以归因结果可以进 analyst 的 prompt(如果开了那个开关);
3. 它不在调参循环里,所以**不影响 trial 预算,也不影响 TPE 的采样**。

### 4.2 算法(五步,全部复用现有代码)

```
输入:crun(候选 + 源码 + space + trials)、该候选的 CONFIG_SCREENED_INFEASIBLE 记录
输出:一条 RESOURCE_WALL_ATTRIBUTED 事件

第 1 步 找候选墙(纯读,0 GPU)
  对每个有序数值域的 knob k:
    ran(k)     = 该 knob 在 status==complete 的 trial 里出现过的取值
    refused(k) = 该 knob 在 CONFIG_SCREENED_INFEASIBLE 里出现过的取值
    若 refused(k) 里存在落在 ran(k) 范围之外的值 v  =>  (k, v) 是一个候选墙
  跳过分类域:序数概念在列表顺序上没有意义

第 2 步 排序(纯读,0 GPU)
  对每个候选墙 (k, v),算尾部斜率:
    best[x] = 该 knob 取 x 时的最优延迟(median)
    tail    = 朝 v 方向的最后 3 个已跑取值
    monotone = best 在 tail 上单调下降
    tail_gain = (best[tail[0]] - best[tail[-1]]) / best[tail[0]]
  只对 monotone 且 tail_gain > 0 的墙做第 3 步 —— 其余的墙"顶住了但不值钱"

第 3 步 归因消融(这一步花 GPU,但只花 compile-only)
  取该候选的 best trial 的参数 θ*(不是随便一个 trial —— 见 §7 风险 3)
  对每个待归因的墙 (k, v):
    θ_probe = θ* 但把 knob k 改成 v          # 只动一个 knob
    src     = materializer.materialize(crun.source, θ_probe)
    probe   = evaluator.compile_screen(..., src, ...)   # 已有函数,已有缓存
    若 probe 拒绝  =>  ATTRIBUTED:k 单独就足以触墙,记下 max_shared / limit
    若 probe 通过  =>  NOT_ATTRIBUTED:拒绝需要 k 与其他 knob 共同作用
  代价:每个墙 1 次 compile-only 探针,中位 11.4-13.6 s

第 4 步 定量"值多少"(纯读,0 GPU)
  对 ATTRIBUTED 的墙,记录:
    over_ratio = max_shared / limit           # 超了多少,决定"能不能腾出来"
    tail_gain                                 # 顶住它损失多少延迟
    blocked_by = "shared_memory"              # 目前只有这一个资源有拒绝通道
  这两个数一起才有意义:over_ratio 1.05 且 tail_gain 15% 是最值得改写的;
  over_ratio 6.5 说明一次结构改写不可能腾出这么多

第 5 步 落盘
  RESOURCE_WALL_ATTRIBUTED { candidate_id, walls: [ {param, refused_value,
    ran_values, monotone, tail_gain_pct, attributed, over_ratio, max_shared,
    limit, kernel, probe_s} ], n_probes, probe_total_s }
```

### 4.3 复用了什么(几乎全部)

| 需要的能力 | 已有的实现 | 位置 |
|---|---|---|
| 把一组参数写进源码 | `materializer.materialize` | `paramspace/materializer.py:108` |

**新代码只有第 1、2、4、5 步的纯读逻辑,加一个 config 开关。** 没有新的测量机制。

## 5. 证明什么:三个可证伪的断言

| # | 断言 | 支持它的数字长什么样 | 否证它的数字长什么样 |
|---|---|---|---|
| **A1** | 资源墙**可以**被归因到单个 knob | ATTRIBUTED 占待归因墙的多数 | 大部分 NOT_ATTRIBUTED ⇒ 墙是多 knob 联合效应,单维度归因不成立 |
| **A2** | harness 的归因**优于** agent 的猜测 | 二者不一致的比例高,且不一致时 agent 那一侧无证据 | 二者高度一致 ⇒ 2e 只是加了一道核验,不是新能力 |
| **A3** | 被归因的墙**指向有价值的改写** | ATTRIBUTED 且 tail_gain > 0 的墙,其后的改写确实腾出了该维并改善延迟 | 改写腾出了该维但延迟没改善 ⇒ 墙不是真瓶颈 |

**A1 是承重的。** 若 A1 失败,2e 就退化成"我们试过按单 knob 归因,不成立"——
那仍是一个可发表的负面结果(**"资源墙是联合效应,不可归因到单维度"**,
与已有的「资源映射不可分离」三重否证同族),但**不能当主 contribution**。

**A3 需要一次实验才能答**,A1 和 A2 **可以在已完成的 run 上离线回答**(见 §8)。

## 7. 风险(五条,按严重度排序)

### 风险 1(中):探针机时不是零,会动可比性

**量化**:box2 两个 run 各有 6 个候选墙,过滤后 3 个待归因。
每个墙 1 次探针 × 中位 11.4–13.6 s ⇒ **每 run 约 34–41 s**。
相对 12 h 墙钟是 **0.08–0.09%**,远低于本项目的臂内跨度(4.72%)。
**但它不是零**,所以:
- 放在开关后面,默认关;
- 事件里记 `probe_total_s`,使它在报告里可减掉;
- 缓存复用现有 `_screen_cache`(同一源码不重复探针)。

**残余风险**:若某候选有很多墙(比如 12 个 knob 全被截断),代价线性增长。
**缓解**:上限 `max_wall_probes_per_candidate`(建议 8),超出的按 tail_gain 降序取前 8,
并在事件里记 `walls_skipped`。**这不是缩小搜索空间** —— 它不排除任何配置,
只限制**诊断**的深度(同「独立短超时是代价上限而非空间限制」的逻辑)。

### 风险 2(中):归因可能大面积失败(A1 否证)

**这是真实可能的**,因为 shared memory 的需求是多个 knob 的乘积
(`BLOCK_M × BLOCK_N × stages`),所以"只动一个 knob 就触墙"可能很少见。
本项目已审计过:`BLOCK_M * BLOCK_N * stages` 的 **failing-min 低于 passing-max,15/15**
⇒ 可行与不可行集合在任何这样的乘积上**重叠**。

**这恰好说明为什么要做实验而不是推理** —— 重叠说明**不能用公式判定**,
但不说明**不能用探针判定**:探针问的是"这一个具体点行不行",不是"这个乘积的阈值是多少"。
**若 A1 失败,产出是负面结果**(见 §5),不是白做。

### 风险 3(中):从哪个 θ 出发做消融会改变答案

若从一个**很差**的 trial 出发,把 knob 改大可能不触墙(因为其他 knob 都很小),
于是归因成 NOT_ATTRIBUTED —— 这是一个**假阴性**。
**决定**:从该候选的 **best trial 的 θ\*** 出发,理由是
"在 agent 关心的那个点上,这个 knob 是否单独触墙"才是它要回答的问题。
**必须在事件里记下 θ\***,否则这个选择不可复现。

**残余风险**:θ\* 本身是被墙塑造出来的(TPE 学会避开墙),所以从 θ\* 出发有轻微的
选择偏差。**缓解**:同时从 `space` 的**默认配置**出发做第二次探针(再 +1 次 11–14 s),
两个结果都记。若二者不一致,那本身是一个发现(**"墙的位置依赖于其他 knob 的取值"**)。

### 风险 4(低):只有 shared memory 有拒绝通道

`CONFIG_SCREENED_INFEASIBLE` 只覆盖 shared memory。寄存器不会产生拒绝 ——
本项目已测:**Triton 上编译器会 cap 寄存器而不是 spill**,所以 occupancy 才是会触发的信号,
而 occupancy 没有"拒绝"这个事件。
⇒ **2e 目前只能归因 shared memory 一个资源维度。** 这必须在论文里写明,
不能说"资源墙",只能说"共享内存墙"。
**可扩展性**:若将来加 register/occupancy 的墙,需要新的探针类型,不在 2e 范围内。

### 风险 5(低):A800 上没有输入

A800 只有 22 条拒绝、0 个截断 ⇒ **在 A800 上跑 2e 会得到一张空表**。
这不是 bug,是机制的适用条件。**但它意味着第 3 步的三臂不能全放在 A800 上**,
而且**臂之间必须同卡**(否则 2e 臂的输入量本身就不同)。

## 8. 能不能现在就做:能,而且分两段

### 8.1 第一段:**离线回答 A1 和 A2,0 GPU 机时,今天就能做**

**关键洞察:第 3 步的探针不需要跑实验才能做** ——
它只需要 (a) 候选源码、(b) 一组参数、(c) 一次 compile-only 探针。
这三样在**已完成的 run** 里全都有:源码在 artifacts 里,参数在 events.jsonl 里,
探针可以现在对着已完成 run 的源码跑。

**做法**:一个离线脚本,对 box2 两个已完成 run 的 6 个候选墙做归因消融。
- 代价:6 × ~13 s ≈ **80 秒的 GPU 时间**,在空闲的 box2 上
- 产出:**A1 的第一份答案**(资源墙能不能归因到单 knob)
- 产出:**A2 的第一份答案**(harness 的归因 vs agent 的 179 条声明)
- **不改任何代码,不影响任何 run 的可比性**

**若 A1 在这 6 个墙上大面积失败,2e 不值得实施** —— 省下全部实现工作。
**这是我建议的第一步。**

### 8.2 第二段:实施 6a/6b + 第 3 步实验(需要您批准)

| 阶段 | 内容 | 机时 |
|---|---|---|
| 实现 | 第 1/2/4/5 步 + config 开关 + 测试 | 0 |
| 验证 | 在两个已完成 run 上离线重放,复现 8.1 的结果 | 0 |
| 实验 | 第 3 步第三臂改为检验 A3 | 12 h × 1(增量) |

**两台机器都空着**(刚查:box2 RTX 4090 0% / 0 MiB;box3 A800 0% / 0 MiB,无相关进程),
所以第二段可以立刻排。

### 8.3 但有一个时序约束

**2e 若进第 3 步,第 3 步的第三臂就要在两件事之间选:**

| 选项 | 第三臂检验 | 主结果 | 离延迟的距离 |
|---|---|---|---|
| **现在 plan 里的** | 机制一(定向核验低准确率维度) | 逐维度声明准确率 | 远(元层面) |
| **改成 2e** | A3(墙归因 → 改写腾出该维) | 改写是否腾出该维 + 延迟 | **近** |
| **两个都要** | — | — | 需要**四臂**,即 4 × 12 h |

**我的建议**:改成 2e。理由是 A3 的主结果**离延迟更近**,而机制一的主结果是准确率,
审稿人会问"那延迟改善了多少"。机制一仍然实现(它是 2e 第 3 步探针预算的分配依据),
只是不占用第三臂。

| cand-d91a77cb | BLOCK_N | 32,64,128 → **256** | 163840 | −4.2% | 否 |
| cand-136dfbfb | ATT_STAGES | 1,2,3 → **4** | 212992 | −41.1% | 否 |
| cand-2d8eaf9a | GEMM_BK | 16…128 → **256** | 131072 | −54.8% | 否 |

⇒ **A1 成立。** 注意这与"公式判不了"并不矛盾:本项目已审计
`BLOCK_M × BLOCK_N × stages` 的 failing-min 低于 passing-max **15/15**,
即**任何这样的乘积上可行与不可行集合重叠**;但**探针问的是"这一个具体点行不行"**,
不是"阈值是多少",所以它能判。

**第 2 步的过滤是必需的,不是可选的**:6 个墙里只有 3 个尾部斜率为正。
不算斜率就会把 6 个墙全当成机会,而其中 3 个"顶住了但不值钱"(最差 −54.8%)。

### 10.3 A2:agent 的 53 条声明只有 **8 条**被确认

6 个被测候选共 **53 条** `parameter_limits`,harness 确认 **8 条**。三类典型误报:

| 误报类型 | 实例 |
|---|---|
| `blocked_by` 归错资源 | cand-b010505b 的 BLOCK_M 声明 `registers`,实测是 shared 墙 |
| 声明了不存在的墙 | cand-136dfbfb 的 5 条 `shared_memory`,该 knob 根本没有墙 |
| `predicted_gain_pct` 方向都反了 | ATT_STAGES 声称 **+1.0%**,实测尾部 **−41.1%** |

⇒ **A2 成立,而且差距远大于预期**(spec 原估"68% 与数据不符",实测确认率只有 15%)。

### 10.4 风险 3 实测:**第二 origin 只有 1/6 一致 —— 这是本次最重要的发现**

同一消融从**空间默认配置**(每维 `choices[0]`)出发:

| | θ\* 出发 | 默认配置出发 | 默认处 shared |
|---|---|---|---|
| cand-b010505b BLOCK_M | ATTRIBUTED | **ATTRIBUTED** | 135168 |
| 其余 5 个 | ATTRIBUTED | **not attributed** | 9216–100352 |

**机制清楚**:默认配置各维都取最小,单独放大一个 knob 装得下;
θ\* 处其他维已经很大,再放大一个就溢出。
⇒ **墙的位置依赖其他 knob 的取值。这不是探针的缺陷,是被测事实本身的性质。**

**两个后果,都必须落进实现:**
1. **归因文本必须带条件**:「**在该候选的最优参数点处**,单独把 X 改成 Y 即超出共享内存上限」。
   **不能**说"BLOCK_M 被 shared 顶住"(无条件读法会误导 agent 去做一次无效改写)。
2. **`RESOURCE_WALL_ATTRIBUTED` 必须同时记 θ\* 与第二 origin 的判定。**
   spec 原文只把第二 origin 列为"可选缓解措施" —— 1/6 这个数字把它升级为**必需字段**。

### 10.5 成本估计下修 20 倍

| | spec 原估 | 实测 |
|---|---|---|
| 每个墙 | 11.4–13.6 s | **0.49 s** |
| 每 run(3 个待归因墙) | 34–41 s | **~1.5 s**(含 6 个对照与第二 origin 共 18 个变体也只 8.8 s) |
| 占 12 h 墙钟 | 0.08–0.09% | **~0.003%** |

原因是**批处理**:`make_compile_probe_job` 的 `extra_kernel_src_paths` 让所有变体共享
一次进程启动(本项目已量过:一个探针独占进程要 16.7 s,48 个变体在一个进程里 11.02 s)。
⇒ **风险 1(可比性)基本消失**,但仍保留开关与 `probe_total_s`,因为"很小"不等于"零"。
