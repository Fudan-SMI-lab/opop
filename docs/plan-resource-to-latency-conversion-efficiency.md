# 「资源 → 性能转化效率」可实施方案

**日期** 2026-09-11 · **本文档的每个数字都来自三台机器上 events.jsonl 的落盘实测**,
probe 为 `scripts/probe_conversion_efficiency.py` 与 `scripts/probe_spill_threshold_vs_rate.py`,
语料 = box1 15 run / box2 5 run / box3 5 run,共 **5213 个 complete trial**。

---

## 0. 结论先行

**可以做,但只能做成三层,而且第三层只有一个维度撑得住。**

| 层 | 形态 | 证据 | 建议 |
|---|---|---|---|
| L1 **定性判决**(已实现) | `improved` / `no_conversion` / `regressed` / `flat` | 6 轮生产证据 | 保留,扩大样本 |
| L2 **每候选局部斜率** | 在**单一维度内部**回归 `d(ms)/d(resource)` | **本文档新增**,见 §2 | **实施** |
| L3 **跨候选/跨任务的转化率常数** | 一个可迁移的「每单位资源值多少 ms」 | **已否证**,见 §3 | **不做** |

**最重要的单一发现**:八个维度里**只有 `n_spills` 的转化关系是稳定的**,而且它**不是**
「溢出就慢」的阈值效应 —— 它是**真的斜率**。其余七个维度(含 `n_regs`、`shared_bytes`、
`occupancy`)的 r² 都在 0.10 以下且**斜率符号在候选之间翻转**。

---

## 1. 为什么现在没有这个数(不是遗漏,是被论证过)

`conversion.py` 的 docstring 明确拒绝合成一个数,理由是**跨维度无共同单位**:
`shared_bytes/101376` 一改 tile 就摆动上万,而 `n_regs/255` 只动几个,实测中位摆幅
0.162 vs 0.012 —— **13.5 倍的差距完全来自归一化分母**。

这个论证**是对的,而且本次实测再次证实了它**,但它只否证了**跨维度合成**。
**单一维度内部**单位是固定的,`d(ms)/d(n_spills)` 量纲上是合法的。这就是本方案的切入点。

---

## 2. L2:每候选、单维度的局部斜率 —— **实测支持**

### 2.1 八个维度的判决(box1 / box2 / box3 三家独立)

`series` = (candidate, dimension) 且该候选有 ≥8 个 complete trial;`usable` = 该维度在候选内
取到 ≥3 个不同值;`signflip` = 斜率为正/负的 series 数。

| 维度 | box1 usable | 中位 r² | 符号 | box2 usable | 中位 r² | 符号 | box3 usable | 中位 r² |
|---|---|---|---|---|---|---|---|---|
| **n_spills** | 43 | **0.733** | **43+/0−** | 51 | **0.573** | **49+/2−** | 5 | **0.800** |
| shared_bytes | 44 | 0.059 | 36+/8− | 51 | 0.046 | 39+/12− | 5 | 0.307 |
| n_regs | 43 | 0.083 | 13+/30− | 51 | 0.045 | 15+/36− | 5 | 0.053 |
| occupancy | 32 | 0.049 | 3+/29− | 51 | 0.029 | 11+/40− | 4 | 0.223 |
| threads_launched | 9 | 0.008 | 4+/5− | 9 | 0.015 | 1+/8− | 5 | 0.028 |
| peak_alloc_bytes | 2 | 0.083 | — | 1 | 0.006 | — | **0** | — |
| candidate_aten_bytes | 2 | 0.070 | — | 1 | 0.163 | — | **0** | — |
| candidate_aten_ops | 1 | 0.099 | — | **0** | — | — | **0** | — |

**读法**:
- `n_spills` 在三台机器上 r² = 0.57 / 0.73 / 0.80,**斜率符号 95/99 一致**。这是唯一一个
  「资源动一单位 → 延迟动多少」有稳定答案的维度。
- `n_regs` / `occupancy` **符号本身就翻转**(30/43 与 29/32 为负)—— 与 memory
  `resource-map-is-not-separable` 记录的「连符号都不可靠」完全一致,**这不是新发现,是复现**。
- 后三个维度**每候选恒定**(它们是候选级而非配置级的量),所以在候选内部**没有变化可回归** ——
  `usable` 几乎全为 0。**这三个维度永远拿不到 L2 斜率**,只能留在 L1 判决里。

### 2.2 关键排除:`n_spills` 的 r² **不是**阈值效应

高 r² 有一个平庸解释:如果 series 里只有 `0` 和 `一个大数`,那回归测的是「溢出的 kernel 更慢」,
这是已知常识而**不是效率**。三向拆分实测:

| | box1 | box2 | box3 |
|---|---|---|---|
| 混合 series(两种状态都有) | 44 | 51 | 2 |
| 中位 r²,spills 作**计数** | **0.733** | **0.573** | 0.845 |
| 中位 r²,spills 作 **0/1 阈值** | 0.072 | 0.055 | 0.438 |
| **计数比阈值多解释** | **+0.661** | **+0.518** | +0.407 |
| **去掉所有零之后**的 r²(纯溢出区间) | **0.745** | **0.594** | 0.762 |
| 该区间斜率符号 | **41+/0−** | **47+/2−** | 5+/0− |

**这三行是本方案的地基**:去掉零点后 r² **没有塌掉**(0.745 / 0.594 / 0.762),
说明**在溢出区间内部,多溢出一个 slot 就多花一点时间**是真实的连续关系,而非
「溢出/不溢出」的二值跳变。

**顺带的反直觉证据(必须写进论文)**:混合 series 中**溢出反而更快**的占
**9/44(box1)、17/51(box2)** —— 延迟比值范围 0.493x .. 4.869x。所以
**「消除 spill」不是一条无条件的优化建议**,这正是 L2 斜率要替代掉的那种"常识"。

## 3. L3:可迁移的转化率常数 —— **已否证,不要做**

同一个 run 内、不同候选之间的 `ms/spill` 斜率:

| run | 候选数 | 最小斜率 | 最大斜率 | **跨候选跨度** |
|---|---|---|---|---|
| run-l3-21-20260908-232211 | 10 | 0.01364 | 0.13019 | **9.5x** |
| run-l3-48-20260907-202457 | 9 | 0.00571 | 0.08817 | **15.4x** |
| run-l3-48-20260909-115701 | 7 | 0.00618 | 0.02986 | 4.8x |
| run-l3-43-20260911-053020 | 9 | 0.01026 | 0.03520 | 3.4x |
| run-l3-43-20260908-121539 | 3 | 0.03519 | 0.06627 | 1.9x |
| run-l3-43-20260910-083647 | 3 | 0.01379 | 0.03842 | 2.8x |

**同一任务、同一张卡、同一个 run 内,斜率相差最多 15.4 倍。**

我试过用候选自身的无溢出延迟归一化(`% of own no-spill latency per spill`),**没有变稳**:
pooled n=41,中位 0.543%,p10 0.187%,p90 1.155% —— **p90/p10 仍是 6.2x**,
单个 run 内仍达 18.2x。

**⇒ 斜率是「这个候选在这个局部的性质」,不是任务性质,更不是硬件常数。**
任何把它当先验喂给 agent 的设计都会**在 15 倍误差上做决策**。这与已记录的
`resource-map-is-not-separable`(只能局部实测)是同一个结论的第二个独立证据。

## 4. 混淆因素:一个参数会同时动好几个资源

**必须承认且不能靠回归消除**。联合拟合(所有变化维度一起)的 r²:

| | 候选数 | 中位联合 r² | 最小 | 最大 |
|---|---|---|---|---|
| box1 | 44 | 0.810 | 0.148 | 0.991 |
| box2 | 51 | 0.631 | 0.107 | 0.985 |
| box3 | 5 | 0.914 | 0.778 | 0.982 |

把它和 §2.1 的单维度 r² 并读:
- box1:`n_spills` 单维 **0.733** vs 联合 **0.810** ⇒ **n_spills 已经解释了联合模型的 90.5%**,
  混淆很小。
- box2:0.573 vs 0.631 ⇒ **90.8%**。同样的结论。
- 其余维度单维 r² < 0.10 而联合 0.63–0.81 ⇒ **它们的表观相关几乎全部来自与 spills 共变**。

**这直接给出实施上的取舍**:只为 `n_spills` 出斜率是**可辩护的**;为 `n_regs` 出斜率会把
spills 的效应错记到 registers 头上 —— 而这正是 memory
`pooling-register-classes-inverts-correlations` 记录的 Simpson 悖论的形状。

## 5. 可实施方案(三步,按依赖排序)

### 步骤 1 —— `ConversionRate`:每候选、仅 `n_spills`、随判决一起落盘

**在哪**:新模块 `evaluation/conversion_rate.py`,由 `conversion.py` 在已算出
`resource_deltas` 之后调用;**不改** `conversion_verdict` 的任何现有字段。

**算什么**(全部从该候选**自己的 trial 序列**拟合,不跨候选):
```
n, n_distinct, slope_ms_per_spill, r2, sign_consistent,
slope_pct_of_clean_latency,          # 便于跨候选阅读,但明确不是常数
regime = "mixed" | "always_spilling" | "never_spilled"
```
**四个拒答条件**(任一命中就返回 `None` 并写明原因,不给数):
1. `n < 8`(box3 那种一轮 run 会直接落进这里);
2. `n_distinct < 3`(两点连线不是回归);
3. `r2 < 0.4`(box2 的中位 0.573 高于它,box1 0.733 更高;这个门是**证据门**不是调参);
4. 去零后符号与含零不一致(§2.2 那 2/51 个反例)。

**为什么只做 n_spills**:§2.1 + §4。其余维度**不给数**,而不是给一个低置信度的数 ——
一个不可信的数比没有数更糟,因为它会被 agent 当成先验用。

### 步骤 2 —— 进 prompt,但**只作为该候选的局部实测**

在 vector 模式的资源段里,对拿到斜率的候选加**一行**:

> `n_spills`: 在这个候选上实测,每个 spill slot ≈ **0.021 ms**(占其无溢出延迟的 0.54%),
> r²=0.73,n=31,12 个不同取值。**这是这个候选在当前局部的斜率,不是硬件常数** ——
> 同一个 run 内不同候选相差可达 15 倍,别外推到你的新结构上。

**这一行必须带 r² 和 n**,否则它就变成 `handwritten-shared-memory-constraints-are-vacuous`
里那种「看起来精确、实际恒真」的数字。**必须带那句免责**,否则 agent 会把它当常数外推,
而 §3 已经证明外推错 15 倍。

**风险与门控**:这是 prompt 改动 ⇒ **改后 run 与改前不可比**。所以做成 config 门
`v3.diagnosis.conversion_rate: false`(默认关),**它是 E2 的一个臂,不是修复** ——
与 S2d(c) 的处理方式完全一致。

### 步骤 3 —— 报告里出「转化效率」小节

对每个族每轮,把已有的定性判决和新的斜率并排:
```
round 2: conversion=improved, latency -8.7%
  n_spills   26 -> 4    (-84.6%)  实测斜率 0.021 ms/slot ⇒ 预期 -0.46 ms, 实际 -0.52 ms
  n_regs    155 -> 168  (+8.4%)   无斜率(r²=0.04, 符号在候选间翻转)
```
**「预期 vs 实际」这一列才是论文要的东西**:它把「资源变了」和「性能变了」之间的
**倍率**变成一个**可被证伪的预测**,而不是一个事后叙述。而且它**天然承接 S2d** ——
声明给方向,斜率给量级,reconcile 给对错。

## 6. 这个方案没有解决什么(明确写清)

1. **七个维度里六个仍然只有定性判决。** 这不是实施偷懒,是 §2.1/§4 的实测结论:
   它们的斜率符号在候选之间就不稳定。
2. **`peak_alloc_bytes` / `candidate_aten_bytes` / `candidate_aten_ops` 永远拿不到斜率** ——
   它们在候选内部是常量。要给它们出转化率,需要**跨候选**比较,而 §3 已经证明跨候选不可比。
3. **斜率不能外推到新结构上。** 它描述的是「这个候选周围的局部地形」,rewriter 要去的
   地方恰恰在这个局部之外。所以它的价值在**解释刚才发生了什么**,而不是**预测下一步**。
4. **样本量仍然是主要瓶颈。** 拿到斜率需要每候选 ≥8 trial 且 ≥3 个不同 spill 取值;
   box3 那次 12 h run 只有 5 个 series 达标(3 个还是 always_spilling)。**E1/E3 跑完会
   把语料翻倍**,这是把它做扎实的前提。

## 7. 与 E 阶段的关系

| | 依赖 | 说明 |
|---|---|---|
| 步骤 1(落盘) | **无** | 纯新增字段,不进 prompt ⇒ **不影响 run 间可比性**,可以立刻做,并让 E1/E3 顺便产出数据 |
| 步骤 2(进 prompt) | **E1 完成** | 改 prompt ⇒ 必须在两次实验之间;而且它天然属于 E2 的第三臂 |
| 步骤 3(报告) | 步骤 1 | 纯读事件日志 |

**建议**:**步骤 1 现在就随 E1/E3 一起上线**(它只写事件,不改 prompt,不改搜索),
这样 E1/E3 跑完时,`n_spills` 斜率的语料就从现在的 99 个 series 增长到约 150 个,
步骤 2/3 才有底气。步骤 2 并入 E2 的臂设计。
