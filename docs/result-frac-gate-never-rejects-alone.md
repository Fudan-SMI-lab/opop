# frac 门单独否决:0 / 134,95% 上界 2.21%

**日期** 2026-09-11 · 语料 box2 四个 L3 run(131 次)+ 三个在跑的 run(3 次)· 脚本 `scripts/audit_which_correctness_arm_rejects.py`

## 起因:frac 门低于任务自身的噪声底

三个 L3 任务的参考自身 ieee-vs-tf32 `frac_within_tol` 分别是 **0.9554 / 0.9767 / 0.9778**,全部低于 0.99 的门限 ⇒ **参考自己过不了自己的门**。这意味着 frac 臂原理上可以否决一个比参考更自洽的候选。

box3 今天给了一个教科书式的实例:

```
候选 frac_within_tol   0.976029
参考自身两精度差       0.979825   <- 任务实测噪声底
门要求                >0.99
```

候选只比噪声底低 **0.39%**。若只看 frac 臂,这是一次误杀。

## 但 fp64 相对臂独立给出 6.786×

```
reference_rmse_vs_fp64  1.1144e+15
candidate_rmse_vs_fp64  7.5623e+15
multiplier 2.0  =>  threshold 2.2288e+15   ratio_to_reference 6.786
```

这个臂把候选的 rmse-vs-fp64 与**参考自己的** rmse-vs-fp64 相比,所以它**对噪声底免疫**。6.79 倍是真实的精度亏空,不是门的产物。**这次否决是正确的。**

**0 / 134,95% Clopper-Pearson 上界 2.21%。** 按本项目的规矩,零必须并列上界与分母,而不是说成"不会发生"。

**结论:frac 门低于噪声底这件事是真的,但它在实践中没有承担任何否决** —— 每一次否决都由 fp64 相对臂承担,而那个臂是免疫的。所以**门侧不需要改动**,这与 G37「真候选被门挡住是我的错误猜想,已否证」一致。

## 一个我自己的分类错误,以及它为什么值得留在这里

第一版脚本报出 l3-43(09-09)有 **1 次 frac-only**。查那一条,它是个 **`CompilationError`** —— kernel 根本没跑起来,既没有 frac 读数也没有 fp64 臂。`SPACE_REJECTED` 不等于正确性否决:空间可以死于编译错误、materialize 错误或越界见证,三者都到不了任何一个臂。

把它算进"仅 frac 臂"就等于报告了一次不存在的误杀 —— 而这正是**支持改动门限**的那类证据。现在的判据是"该行是否带真实的 `frac_within_tol` 读数",不带的单独列出而不是静默归类。

这是本次会话里第三个同形错误(前两个:`TRIAL_DONE` 载荷嵌套读成全 None、猜错事件名 `EXPECTATION_LEDGER_ENTRY`)。共同点是**读数错误产生的是一个可信的数字,而不是一个报错**。
