# v3 设计(第二版):资源可见性、变更影响、与转化效率

**状态**:2026-09-10。**这一版取代前一版的架构部分**,针对用户点出的三个缺口重新设计。前四份文档(`v3-design-resource-ratio-and-conversion-efficiency.md` 思路、`v3-implementation-plan.md` 阶段、`v3-prior-art-and-what-to-borrow.md` 调研、`v3-flow-and-gap-register.md` 流程与缺口)的**事实与纪律部分仍然有效**;本文档改的是**架构形态**——从"改进单个诊断步骤"改为"多个采集算法 + 多个分析 agent"。

## 零、用户的重新框定,以及它为什么改变架构

用户的原话把 v2 定位得比我之前写的更准确:

> 先前 v2 中的基于参数空间探索的结果进行瓶颈分析以及算子重构**事实上已经是一种将算子的资源使用分布与硬件/环境的资源分布对齐的一种方法**(但这几乎是全靠参数探索来撞到瓶颈后触发的算子重构来不断接近性能上限)

这句话的价值在于:**v2 并不缺少"对齐"这个机制,它缺少的是对齐过程中的信息。** 我之前的设计文档把 v3 写成"给 v2 加一个更好的诊断",这个定位错了 —— v2 的对齐机制本身是对的,问题在于它是**盲的**:

| v2 的实际行为 | 用户的三个缺口 |
|---|---|
| 调参撞到某个资源上限 → 触发改写 → 再撞 → 再改写 | **缺口 ①**:完全没考虑**资源转化效率**(花掉的资源是否换到了性能) |
| 诊断输出一个标签,agent 只知道"某个资源到顶了" | **缺口 ②**:agent 不知道**其他资源**的情况(甚至可能连撞到哪个都不清楚) |
| 改写凭 agent 的先验猜测资源影响 | **缺口 ③**:agent 不知道自己的改动**会对资源使用造成什么影响** |

并且用户给了架构约束:

> 新增的这些缺口里会包含大量的资源/profiling/性能采集和分析的过程,**不能指望一个 agent 或是一个算法来完成这些工作**,可以通过**多个算法**来进行采集和信息提取,并由**多个 agent** 来进行分析和基于这些信息和分析结果来进行改进

这条约束不是风格偏好,它有实测依据(见 §四):把原始计数器直接喂给 LLM 的那一臂,实测**比完全不给反馈更差**(1.77× vs 3.35×,p=0.0007)。采集与分析必须分层,中间必须有代码而不是 agent 在做筛选。

**"盲"这个词是可以量化的,不是修辞。** 下表是我在历史 run 上实测的(`scripts/blind_spots.py`):

| 缺口 | 实测 |
|---|---|
| ② agent 不知道其他资源 | 一个 run 里 **17 份诊断报告只产生 1 个标签**;跨 run 76% 的报告里**至少两个维度同时接近上限**,而输出只提一个 |
| ③ agent 不知道改动的资源影响 | 改写后的资源占用**实测漂移最多 79.9 KB shared / 137 registers**,全部是未预料的 |
| ① 转化效率从未被计算 | `predicted_gain_pct` n=21,中位偏差 −5.0%,**8/21 符号都是错的** |

## 一、四条新的实测结论(2026-09-10,box 1 空闲期测的)

这四条把架构从"可能"变成"确定",因为它们回答的是**这套东西付不付得起、以及能不能靠算式省掉**。

### 1.1 一个资源点 = 1/15 ~ 1/30 个计时 trial(**这是整个架构的地基**)

`scripts/probe_resource_read_cost.py`,108 个 GEMM 配置(M=N=K=1024,fp32 ieee dot),4090:

| 动作 | 中位耗时 | 换算成计时 trial |
|---|---|---|
| 冷编译(生成机器码) | **614.1 ms** | 1/30 |
| 热编译(同配置再读一次) | **0.1 ms** | 1/197000 |
| 一次不计时的 launch(拿到寄存器) | **0.4 ms** | 1/42000 |
| 一次正确性检查(单输入) | 0.2 ms | 1/78000 |
| **冷编译 + 一次 launch(= 一个全新资源点)** | **614.6 ms(中位)** | **1/30** |
| 一个计时 trial(20 采样 median + 正确性) | 18600 ms | 1 |

**但预算必须按均值算,不是中位。** 编译时间有长尾(最大 **4791 ms**,是中位的 7.8 倍),所以 `probe_resource_map.py` 实测**整张 108 点的地图墙钟 97.1 s = 899 ms/点 = 5.2 个计时 trial**。

**两个数字都要记,用途不同**:
- **中位 614.6 ms** 描述一个典型点的成本;
- **均值 899 ms(实测整批墙钟 ÷ 点数)** 是**排预算时唯一该用的数**——按中位算预算会低估 46%。

**含义:约 21 个资源点的成本等于一个计时 trial**(按窄扫均值 899 ms;按中位是 30 个;而 §1.5 的宽扫因含大 tile 是 1244 ms/点 = **15 个点**)。**排预算用最保守的那个:1244 ms/点。** 一个 12 小时的 run 跑约 2000 个 trial;拿出 5% 的预算(100 个 trial)仍能买到约 **1500 个资源点**。所以"给 agent 一张局部资源地图而不是一个点"是**付得起的**,这不是估算,是实测。

> **这里我差点犯的错**:先用中位 614.6 ms 算出"30 点 ≈ 1 trial",然后地图探针实测整批是 5.2 个 trial 而不是 3.6 个。**长尾的存在意味着"每点中位 × 点数"不是墙钟**,而排预算要的恰恰是墙钟。这与既有纪律同源(`opop v2 tuning objective must be median`:排名要用 median),但方向相反 —— **排名用 median,预算用 mean**,因为预算关心的是总和。

### 1.2 寄存器在一次 launch 后可读,但编译后不可读

同一份探针的字段可用性(n=108 编译 / 96 launch):

| 字段 | 编译后 | 一次 launch 后 |
|---|---|---|
| `shared` / `num_warps` / `num_stages` / `num_ctas` / `cluster_dims` | **108/108** | 96/96 |
| `n_regs` / `n_spills` / `n_max_threads` | **0/108** | **96/96** |

这条与 Roller 的自述完全对上 —— 它把寄存器上限硬编码 derate 到 **96/255 = 37.6%**(2.66× 安全系数),原文两句:"we reduce the register limit empirically to only 96 registers"、"**cannot detect implicit register allocation beforehand**"。**一篇主张解析构造优于搜索的论文,在拿到完整张量表达式与硬件规格后,结论是寄存器无法从源码预测。**

**但我们比 Roller 多一个选项:launch 一次只要 0.4 ms。** Roller 需要一个**闭式公式**因为它在构造阶段就要剪枝;我们不需要 —— 我们可以**编译 + launch 一次然后读**。这就是 v3 的核心工程判断:**不预测,去读。**

> **两个探针 bug 的记录**(比结论本身更值得记):
> 1. 第一版读 `device_caches[dev][0]`,拿回的是**缓存字典**而不是 kernel,于是每个字段都读成 `None` —— 这和"硬件不暴露这个字段"**长得一模一样**。
> 2. 修好后改成 diff 缓存键,但 `warmup()` 已经把缓存填好了,所以 diff 永远为空,fallback 对 108 个配置返回**同一个** kernel,`n_regs` 读出常数 **56**。`None` 明显是坏的;**常数看起来像一个结论**("寄存器不随 tile 变")。
>
> 正对照因此改成"n_regs 必须在这个 sweep 上取多个值",而不只是"非 None"。**这是纪律 `probe needs a positive control` 的第二次实战:一个坏探针最危险的形态不是报错,是报一个可信的常数。**

### 1.3 shared memory **没有**闭式公式(0/96 精确命中)

`scripts/probe_resource_map.py`,同一批 96 个成功配置,拟合 `shared ~ a·BM·BK + b·BK·BN + c·stages + d`:

| | |
|---|---|
| 精确命中(残差 < 1 字节) | **0 / 96** |
| 残差 | 中位 **4410 B(12.4%)**,最大 **21905 B(121.4%)** |

理论上早该如此:Triton 用**活跃性分析 + 图着色 + 不动点迭代**算 shared(`lib/Analysis/Allocation.cpp`),总量 = `max(offset + size)`,不存在闭式解。**但这一次是在我们自己的栈上实测的,而且它同时否决了两件事**:agent 手写的 shared 约束(实测中位只有真值的 32%),以及我们自己想写一条公式的念头。

**这条与已有的 `triton-flash-attn-shared-memory-formula` 记忆一致但更强**:那条记忆说三点标定的公式在 39 个实测点只中 1 个;这条说**任何**这种形状的线性模型在 96 个点上中 **0** 个。

### 1.4 资源地图**不可分离** —— 这条决定了地图必须"局部、每次重测"

同一批数据,对每个"只改一个 knob 一步"的移动,统计它在**其他 knob 的所有取值下**的资源增量是否一致:

| knob | 一步移动 | n | Δshared 中位 | **Δshared 跨度** | Δregs 中位 | **Δregs 跨度** |
|---|---|---|---|---|---|---|
| BM | 32→64 | 34 | +8192 | **20480** | +24.0 | **126** |
| BM | 64→128 | 28 | +16384 | **24576** | +44.5 | **127** |
| BN | 32→64 | 34 | +8192 | **20480** | +25.5 | **117** |
| BN | 64→128 | 28 | +16384 | **24576** | +48.0 | **125** |
| BK | 32→64 | 42 | +24576 | **40960** | +8.0 | **95** |
| num_stages | 2→3 | 34 | +24576 | **40960** | +0.0 | 24 |
| num_stages | 3→4 | 26 | +20480 | **24576** | +0.0 | **0** |
| num_warps | 4→8 | 48 | +0 | **0** | −42.0 | **127** |

**增量一致的移动:shared 1/8,registers 1/8。**

意思是:**"把 BM 从 64 加到 128 要多花多少 shared"这个问题没有唯一答案** —— 取决于 BN/BK/stages/warps 当时是多少,跨度达 24576 字节(接近 4090 的 shared 上限 101376 的四分之一)。寄存器更极端:同一个 `num_warps: 4→8`,中位省 42 个寄存器,但**跨度 127 个**。

**这直接印证了用户的判断**("每次算子结构改动后,算子本身的资源占用率都会发生改变"),并且把它从一个设计原则升级成一个**实测约束**:

- 资源地图**不能全局测一次然后复用** —— 同一个移动在不同位置代价不同;
- 资源地图**必须以当前配置为中心、局部测量**;
- 结构改写后**必须重测**,不能继承父候选的地图。

### 1.5 补测:把每条轴都扩到 ≥3 个取值后,"方向可预测"这条也被推翻了

上面 §1.4 我写过一条较弱的退路:寄存器在 **BM / BN / num_stages 三条轴上单调**,所以至少"方向"是可预测的。**但那句话只覆盖了三条轴** —— BK 与 num_warps 当时各只有 2 个取值,而**两点之间必然单调,单调性对它们是空命题**。我当时把这个限制写进了文档,现在把它补测了。

把 BK 扩到 `(16,32,64)`、num_warps 扩到 `(2,4,8)`,243 个配置(成功 225),结果:

| | 窄扫描(108 点,3 条轴可测) | **宽扫描(243 点,5 条轴全可测)** |
|---|---|---|
| 非单调切片 | 0 | **13** |
| 全部落在哪条轴 | — | **全部 13 条都是 BK** |
| shared 增量一致的移动 | 1/8 | **0/10** |
| 寄存器增量一致的移动 | 1/8 | 1/10 |

**BK 上的寄存器是 V 形或倒 V 形的**,最极端两例:

```
BM=128, BN=64, stages=3, warps=4:   BK 16 → 226 regs,  32 → 168 regs,  64 → 255 regs
BM=64,  BN=128, stages=3, warps=4:  BK 16 → 216 regs,  32 → 168 regs,  64 → 254 regs
```

**把 BK 从 16 加到 32,寄存器少了 58 个;再加到 64,又多了 87 个,直接顶到 255 的上限。** 一个 agent 推理"BK 更大 → 每次迭代载入更多 → 寄存器更多"在这两个点上是错的,而且错在**第一步**。

**三条后果**:

1. **"至少方向可预测"这条退路没了。** 现在 shared 没有闭式公式(0/96)、地图不可分离(0/10)、连符号都不可靠(13 条非单调切片)。**三条都被否证,查表是唯一选项** —— S2c 的必要性比 §1.4 写的时候更强。
2. **我上一版的措辞本身就是这个错误的实例。** 我写"monotone everywhere"(到处单调),而实际只测了 3/5 条轴,并且**恰好漏掉了寄存器跨度最大的 num_warps(127)与唯一非单调的 BK**。改成"在被测的三条轴上单调、另两条不可测"之后才暴露出这是个缺口 —— **这就是"未验证项被沉默地当成已验证"的又一例**,和 `L1 冒烟通过 ≠ 可跑 L3` 同一族。
3. **num_warps 反而是干净的**:扩到三个取值后仍无非单调切片,而它的寄存器**中位效应是负的**(2→4 少 54 个,4→8 少 41 个),跨度 138/127。方向稳定但幅度完全不可预测 —— 所以它仍然只能查表,只是理由是"幅度"不是"符号"。

**代价也补测了**:宽扫描 243 点墙钟 302.3 s = **1244 ms/点**(比窄扫描的 899 ms 高 38%,因为大 tile 编译更慢)。**排预算按这个数**:一张 30 点的局部地图 ≈ **37 s ≈ 2 个计时 trial**。仍然便宜,但不是我最初按中位算出的 1/30。

## 二、v3 的架构:三层,采集与分析分离

用户的约束("多个算法采集 + 多个 agent 分析")对应到三层。**分层的判据是"这一层的产物由谁生产、错了怎么被发现"**,不是模块图的美观。

```
第一层  采集器(多个独立算法,全部是代码,零 LLM)
        每个采集器只回答一个窄问题,各自有自己的正对照,可单独失效
                    │  产物:带出处的实测量
                    ▼
第二层  提炼器(代码,不是 agent)
        把原始量变成"每维一条判决 + 局部代价表",并做算错自检
                    │  产物:结构化的、有限的、可证伪的陈述
                    ▼
第三层  分析 agent(多个,各有专责,互不共享上下文)
        每个 agent 只看它需要的那一部分,输出建议而非决定
                    │  产物:排序后的改写方向 + 理由
                    ▼
        harness 判定(接受/拒绝/继续,永远由代码决定)
```

**第一层与第三层之间必须有第二层,这是硬约束。** 依据是实测的:KernelPro 三臂对照里,**原始计数器那一臂 1.77×,完全不给反馈 3.35×**,单侧 Wilcoxon p=0.0007 —— 给 agent 原始数值**比什么都不给更差**。

### 2.1 第一层:采集器(每个一个窄问题)

**设计规则**:一个采集器 = 一个窄问题 + 一个正对照 + 一个"我测不出来"的输出通道。**任何采集器都必须能报 `unknown` 而不是猜。**

| # | 采集器 | 回答的问题 | 成本(实测) | 正对照 | 状态 |
|---|---|---|---|---|---|
| **C1** | **局部资源地图** | 当前配置**邻域**里,每个 knob 一步移动的资源代价是多少 | **~21 点 ≈ 1 trial**(按均值 899 ms) | shared 与 n_regs 必须在 sweep 上**多值**(否则探针坏了,见 §1.2) | **新,确定可做** |
| **C2** | 编译期可行域 | 哪些配置编译期就注定失败 | 热编译 0.1 ms/点 | 至少一个已知超限配置必须被判不可行 | 已有判据,需前移 |
| C3 | 天花板校准(带 provenance) | 本机各精度/后端的实测上限 | 已有 | 每个天花板必须被至少一个候选逼近过 | 已有,缺 per-backend |
| C4 | 任务级下界 | 这个任务**至少**要多少流量/FLOP | 已有(`task_cost.py`) | `flop_count=0` 对 maxpool 合法、对 matmul 是失败 | 已有,承重 |
| C5 | SASS 静态特征 | shared load/store 强度、barrier 密度、向量化比例、是否用张量核 | 已在采集 | 必须能区分已知的标量 vs 张量核 kernel | **已采集,从未被读** |
| **C6** | **成对变更观测** | 这次改动实际改变了哪些资源、延迟怎么动的 | 0(改写前后各已有测量) | 父/子候选资源必须**不相等**(§1.4) | **新** |
| C7 | 启动开销 | cpu_issue vs gpu 时间 | 已有(P2) | 已实测 0.037 比值,判决正确不触发 | 已解决 |
| **C8** | 占用率实测 | 一次 launch 后的 n_regs/n_spills/occupancy | **0.4 ms** | 见 C1 | **新,§1.2 已验证可行** |

**C1 是这一版新增的核心采集器**,它同时回答用户的缺口 ② 和 ③:

- **缺口 ②(不知道其他资源)**:地图**同时**给出所有维度在当前点的值,不只是撞到上限那一个;
- **缺口 ③(不知道改动的影响)**:地图给出**邻域内每个方向的资源代价**,所以"把 BM 加倍会怎样"是查表而不是猜。

**而 §1.4 决定了 C1 的形态**:因为不可分离,C1 必须是**以当前配置为中心的局部地图**,每次结构改动后重测,**不得全局测一次复用**。这不是保守,这是实测跨度 24576 字节逼出来的。

### 2.2 第二层:提炼器(代码,不是 agent)

三个职责,每个都可单测:

**(a) 每维一条判决**(沿用前一版的定稿形态,不合成):
```
{ dimension_id, measured, ceiling, ceiling_provenance,
  verdict ∈ {binding, near-binding, slack, not-applicable, unknown},
  confidence, applicable }
```
多维同时 binding 时,**输出就是多份** —— 不投票、不加权、不取 max。修的是 v2 缺陷本身:17 份报告 1 个标签,问题不是标签选错,而是"必须选一个"这个要求。

**(b) 局部代价表**(C1 的产物,新增):
```
{ knob, from_value, to_value,
  Δresource: {shared: +8192, n_regs: +24, ...},
  Δlatency: 实测或 unknown,
  measured_at: 当前配置的完整签名 }   ← 因为不可分离,这个字段是必须的
```
`measured_at` 不是元数据,是**有效性范围**:这张表只在它被测的那个邻域成立。

**(c) 算错自检**(补 §A-4 的空缺):
- `applicable=false` 却带 `measured` 值 → 缺陷;
- 利用率 ∈ [0, 1+ε],>100% **clamp 并打标记而非拒绝**(Nsight 文档明写可超 100%,我们已真的撞上 107.8%);
- **新增,来自 §1.2 的教训**:任何**跨配置恒为常数**的资源读数视为**采集器故障**而非发现。这条自检恰好会抓住我把 `n_regs` 读成常数 56 的那个 bug,而原本的"非 None"检查抓不住。

### 2.3 第三层:多个分析 agent(各有专责)

**为什么是多个而不是一个**:除了用户的约束,有两条实测依据:

1. **代码域的角色消融全部显示"去掉那个角色代价很大"**:ChatDev 去掉角色 Executability 0.88→0.58;AgentCoder pass@1 从 61.0/47.9(只有 programmer)到 79.9/89.9(三个 agent);MapCoder 去掉 debugger 掉 17.5%。**调研里找不到任何代码域论文显示 reviewer/tester/critic 可以省掉**(这是在专门做了反向查询之后)。
2. **弱模型放分析位是可行的,放生成位不行**:CudaForge 实测 GPT-OSS-120B 作 **Judge** 达 100% 正确 / 1.364×,作 **Coder** 掉到 96%;QwQ-32B 作 Coder 只有 0.790×。

| Agent | 只看什么 | 输出 | 不允许看 |
|---|---|---|---|
| **A1 资源分析** | 每维判决 + 天花板 provenance | 哪些维度绑定、各自的证据强度 | 原始向量、其他 agent 的结论 |
| **A2 变更影响分析** | 局部代价表(C1) + 成对观测(C6) | "往这个方向走要付什么" | 延迟排名(避免它反推答案) |
| **A3 转化效率分析** | 历史成对观测:Δresource → Δlatency | 哪些资源在这个候选上"花了没换到东西" | 未来的建议(它只做回顾) |
| **A4 改写提议** | A1/A2/A3 的结论(**不是**它们的原料) | 排序后的结构改动方案 | 任何原始测量 |

**四个 agent 的上下文互不共享**(延续既定决策:不做跨候选报告/假设共享)。A4 看的是**结论**而不是**原料**,这就是第二层门的位置。

**代价核算**(按调研的实测封顶):可负担的范围是**每轮 2–3 次 agent 调用**,HTAM 实测 3 次调用达 1.978× geomean、$0.21/算子、无 counter、非前沿模型。我们现在每轮已经用掉 analyst + rewriter 两次。**所以四个分析 agent 不能每轮全跑** —— 见 §五 的分级触发。

## 三、三个缺口分别怎么被填上

### 3.1 缺口 ②:agent 不知道其他资源的情况

**填法:C1 局部地图 + 每维一条判决。** 地图天然是全维度的 —— 测一次 launch 就同时拿到 shared / n_regs / n_spills / num_warps / occupancy,不存在"只知道撞到哪一个"。

**这一条是确定的**,因为它的全部前提都实测过了:字段在一次 launch 后可读(§1.2,96/96),成本 0.4 ms(§1.1)。

**而 A-1(多维同时 binding 时先动哪一维)在 2026-09-10 被实测改写了,不再阻塞 S2。** 完整论证见 `result-a1-is-framed-backwards-fill-the-gap-not-push-the-wall.md`,三步:

1. **A-1 确实是活的**:n=40 个候选,阈值 0.70 下 **90%** 多维绑定(0.85 下 45%);
2. **没有排序规则打得过对照**:最好的规则 7.1%,**最好的对照(永远挑同一维 = 均匀随机)21.4%**;
3. **原因在标签上,这是真正的发现**:14 次超噪声底的成功改写里只有 4 次动得最多的那维是绑定的;换成不做跨维度比较的问法(有没有缓解某个绑定维度),**8/14 什么都没缓解**,而那 8 次里 **6 次反而把某维朝墙推**,同时吞吐上升最高 **+70.61 TFLOP/s**。

> **A-1 问"该把哪一面墙推开";数据说赢的动作通常是"该把哪个空隙填上"。**

**这恰好就是用户说的"将算子的资源使用分布与硬件/环境的资源分布对齐"** —— 而它与 A-1 的预设相反。规则输的原因也随之清楚:R1/R2 都在**绑定集合里**挑,而多数成功改写动的是集合**之外**的东西,命中率被结构性压在 28.6% 以下。

**所以 S2 的输出定稿为并列两类,不排序、不加权**:

```
绑定的(墙在哪):     compute 0.93, occupancy 0.83   → 这些方向要付代价
有余量的(空隙在哪): dram 0.10, register 0.27       → 这些方向还能用
```

**v2 从来只报第一类。** 这与 C1 局部地图正好互补:判决说"哪些方向还有余量",地图说"往那个方向走要付什么"。

**但"填空隙"不许变成新的机械规则**(四条理由):n=14 只够说"没有规则被支持";同一张表里有反例(2/8 压强全平但吞吐涨 +34.97,更像减少了总工作量 —— 正是 B-1 测不到的候选真实流量);**因果方向未定**(吞吐上升与延迟下降在这份数据里分不开);以及**第四条最要紧,是外部文献逼出来的**:

**"填空隙"有一个同样合理的替代解释,而现有数据分不开两者。** Balakrishnan & Cheng(*IJPR* 38(6):1459–1463, 2000,我已拉全文复核)的算例里,**利用率不满的资源 B 影子价格 $1.8,而被选中的资源 A 只有 $0.6** —— 即"看起来有余量的维度反而是杠杆更大的那个"。若这在我们这里也成立,那么我用利用率标成"有余量"的那些维度**本来就是真约束**,改写是在**正确地缓解真约束**,只是我的标签认错了是哪一个 —— **不存在新机制,只是我的绑定判据不可靠**。

**两种读法在可执行结论上一致**(都说不要按利用率排序、都说要并列报两类),这是它没有推翻设计的原因。**但分开两者需要一个正对照**:造一个确知 DRAM 受限、一个确知占用率受限的 case,看诊断能否各自判对。**在那之前,"填空隙"是候选解释而非已确立机制。** 完整论证见 `result-a1-is-framed-backwards-...md` §五b。

**顺带一条支持我们既有纪律的发现**:文献推荐的替代方案是"按梯度(影子价格)排序而非按利用率",但**影子价格在原问题退化时(即"多约束同时绑定",正是我们的情形)本身就不唯一** —— MIT 15.053 敏感性分析章:"if all righthand-side values in the final tableau are positive, then there do not exist alternative optimal shadow prices",反之则可能存在,且"any weighted combination…is also an alternative set of optimal shadow prices"。**所以解析推导的梯度在我们最需要它的情形下反而比实测的成对观测更弱** —— 支持 D-2(进入选择的必须是已实现的实测量)。

### 3.2 缺口 ③:agent 不知道改动的资源影响

**填法:C1 把"预测"换成"查表"。** 这是 v3 与 v2 最实质的差别:

| | v2 | v3 |
|---|---|---|
| "把 BM 加倍会怎样" | agent 凭先验猜 | **查邻域实测表** |
| 代价 | 0,但实测中位偏差 −5.0%、8/21 符号错 | 30 点 ≈ 1 trial |
| 错了怎么发现 | 不会发现(改写后从不回看) | 成对观测 C6 立刻对账 |

**这一条也是确定的**,而且 §1.3 与 §1.4 恰好是它的**必要性证明**:如果 shared 有闭式公式(§1.3 证否)或者地图可分离(§1.4 证否),那么查表就是浪费,一条规则就够了。**两个否定结果一起把"必须实测局部地图"从选择变成唯一选项。**

### 3.3 缺口 ①:资源转化效率从未被考虑

**这是三个缺口里最难的,因为它有一个量纲问题(A-3)而且我不打算假装解决。**

用户的表述是"资源转化效率"以及"每个优化步骤时的性能转化效率"。可实测的形态是 **Δlatency / Δresource_j**,来自 C6 成对观测。**它在单个维度内部有意义**(这次改动在 shared 上的换算比上次好),**跨维度没有意义**(省 1000 字节 vs 省 10 个寄存器谁划算,没有共同单位)。

**当前设计的边界,写清楚**:

| 用途 | 允许? | 理由 |
|---|---|---|
| 报告 + 喂给 A3 做回顾分析 | ✅ | 这是它的主用途 |
| 同一维度内比较两次改动 | ✅ | 单位一致 |
| **跨维度比较"该动哪一维"** | ❌ | 量纲不可比(A-3)。**而 A-1 的实测说明这个需求本身被高估了** —— 赢的动作多数是"往有余量的方向走",不是"在绑定维度间取舍" |
| 进 TPE 目标 | ❌ | 多目标会退化我们的 tuner(MOTPE 在 n=40 时只有 4 个点喂 `l(x)`,`multivariate` 静默变 False;qEHVI 在 M=4 时 acquisition 459 s = 25 个整 trial) |
| 作筛选剪枝 | ❌ | v2 实测反例:L2:37 上**最慢**的种子所属族改善最多(−30.5%);L3:21 领跑族的 seed 是四个里最差的 |
| 噪声底以下报数字 | ❌ | 报 `unknown`。L3:48 r2 最极端:126/371 trial(34%)在获胜者 1 个合并 SEM 内,带宽 5.01% 而 **SEM 5.51% —— SEM 比整个带还宽** |

**一个廉价的可证伪自检(值得做)**:LP 对偶的互补松弛说**非绑定约束的影子价格为零**。翻译成实验:**若某维被判 slack,则在该维上花资源应买到零延迟改善。** 若花了反而买到改善,**我们的判决是错的**。这个反向对照必须能大声失败。

### 4.1 一条外部独立复核:我们的 DRAM 屋顶是对的

调研带回一个同型号卡的独立测量,值得记,因为它给我们最重要的那个分母上了一道外部保险:

**Luo 等,"Benchmarking and Dissecting the Nvidia Hopper GPU Architecture"(arXiv:2501.12084v2),Table 5:RTX 4090 global memory = 929.8 GB/s**,原文并注明"our results reach 92%, 90%, and 91% of the theoretical performance on RTX4090, A100, and H800"。

**我们自己校准出的是 924.1 GB/s —— 差 0.6%(99.4%)。** 这条把"我们的带宽分母可信"从自证变成了外部复核过的。

**同一份工作里有一个 4090 专有的向量化陷阱,但我已复核它不影响我们**,记下来是为了防止以后误加一个不需要的"修复":

- 原文的陷阱是:"on the consumer-grade RTX 4090, using FP32 to access **L1 cache and shared memory** yields only half the throughput achieved with FP32.v4"(L1:63.7 vs 121.2 byte/clk)。
- **它的作用面是 L1/shared 吞吐,不是 global memory 带宽。** 我们**不测** L1/shared 吞吐天花板,所以现有的维度里没有一个会被它打中。
- 而我们的 DRAM 探针是 `torch.add(big, 1.0, out=out)`(`worker_main.py:1097`),PyTorch 的 TensorIterator 对齐时自带向量化访存 —— **并且 0.6% 的外部符合度本身就是它没被减半的证据**(若被减半会读出约 465 GB/s)。

**真正的可执行结论有两条**:
1. **不要为此改校准脚本** —— 这里没有 bug。误"修"一个正确的分母恰恰是曾经把指令反转的那类事故(fp16 分母缺失 → 读出 107.8%)。
2. **若将来新增 shared/L1 吞吐维度,那个新维度的微基准必须向量化**,并把"是否向量化"写进 provenance。这是 §一 的 provenance 要求的一个具体实例,不是新纪律。

**另一条可直接用的解析先验**:同一 Table 给出 4090 的 **L2:global 吞吐比 = 4.67×**(A100 是 2.01×)。这是"改善 L2 复用最多能买到多少"的上界,可以用来判断一个 L2 类改写建议值不值得做 —— 而它在异构卡上差别很大(4090 的 L2 杠杆是 A100 的 2.3 倍),正好是 A-5 那类跨卡差异的一个具体例子。

## 五、成本与分级触发(这套东西必须付得起)

**约束**:agent 调用每轮 2–3 次是可负担上限(HTAM 实测);资源点每个 614.6 ms。

| 触发时机 | 采集 | agent | 每次成本 |
|---|---|---|---|
| 每个候选调参前 | C2 可行域(热编译) | — | ~10 s |
| 每个候选调参后 | C1 局部地图(θ_best 邻域,~30 点)+ C5 + C8 | A1 资源分析 | **≈ 1.5 trial**(30 点 × 899 ms = 27 s)+ 1 调用 |
| 改写前 | C6 成对观测(免费,已有数据) | A2 变更影响 + A4 改写 | 2 调用 |
| **仅当同一族连续两轮无进展** | 全部 | + A3 转化效率回顾 | +1 调用 |

**A3 分级触发的理由**:转化效率是回顾量,连续改善时它不改变决策;只在**卡住时**才需要它回答"我们一直在往哪个方向白花资源"。这样每轮稳定 2–3 次调用,只在卡住时到 3–4 次。

**墙钟核算**(按均值,不按中位):C1 每个候选 30 点 × 899 ms ≈ 27 s ≈ **1.5 个 trial**。一个 run 约 10 个候选 × 平均 3 轮 = 30 次 C1 = **45 个 trial ≈ 2.3% 的 trial 预算**。对比它要修的浪费:S1 的编译期不可行占 **18%** 的 trial。

**一个可以省掉大部分成本的现成机制**:`orchestrator.py:1129-1194` 的 `_prescreen_space` 已经在做**批量编译探测**,其 docstring 记录 48 个配置在同一进程里 11.02 s(边际 **7 ms**)vs 单独 16.7 s。**C1 应当挂在这个已有的批量路径上而不是新建进程** —— 热编译实测 0.1 ms(§1.1),意味着凡是 prescreen 已经编译过的配置,C1 只需付 0.4 ms 的 launch。**这条能把 C1 的成本从 1.5 个 trial 压到接近零,但需要在实现时验证 prescreen 的覆盖面是否与 C1 需要的邻域重合。**

| 缺口 | 类型 | 为什么没解决 |

| **A3 的分析价值** | 功效 | 转化效率能否真的指导改写,零证据。分级触发降低了它的成本风险,不降低它的有效性风险 |

**另外两条调研带回的反向证据,必须记在设计里而不是埋在调研文档**:

1. **匹配预算下多 agent 未必赢**:MMLU-Pro / Llama-3.1-70B 上,debate +1.3pp、mixture-of-agents +2.7pp,**但低于约 3× CoT 预算时,朴素 self-consistency 反而胜**。我们是预算饥饿的,**按这条我们正处在多 agent 不划算的区间**。抵消它的是上面那条代码域角色消融证据(方向相反),以及我们的任务是 planner/actor 型而非 debate 型 —— 调研里这两类的结论确实分叉。**不建 debate 循环**(NeurIPS 2025 Spotlight:"Majority Voting alone accounts for most of the performance gains typically attributed to MAD")。
2. **同一个结构性修复的效果极不稳定**:MAST 的干预实验里,同样的拓扑改动在 ChatDev/ProgramDev 上 25.0%→40.6%,在 ChatDev/HumanEval 上 89.6%→91.5%(几乎没有),在 AG2/GSM-Plus 的 GPT-4 上**统计不显著(p=0.4)**、换到 GPT-4o 才显著(p=0.03)。原文:"these seemingly straightforward solutions often prove inconsistent"。**所以第三层的 agent 数量与分工必须是可消融的配置项,不是写死的架构。**
