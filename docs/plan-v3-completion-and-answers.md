## 1. D9 与 D8:问题、修法、风险、预期效果

### D9 — 单配置编译筛查借用了真 trial 的 1200 s 编译预算

**问题。** `compile_screen`(`evaluation/correctness.py:268`)把 `self.cfg.build_timeout_s`
(1200 s)传给 `run_job`,而它的姊妹函数 `prescreen_batch`(第 180 行)用的是专门的
`prescreen_timeout_s(cfg, n)`。**这是 `59d5a71` 修过的同一个缺陷,漏在了同文件 88 行外的另一个
调用点** —— 那次还专门写了 30 行论证「筛查的超时必须与 trial 的编译预算分开」,但论证没被延伸过去。

**证据。** box1 的四个 50.1 分钟 `TRIAL_DONE` 空档,job 目录给出确切成因:

```
04:12:07  compile-screen fe8e01e7.json   ← 写入,永远没有 .out.json
04:32:08  eval job 758c300e.json         ← 04:12:07 + 1200 s
05:02:11  compile-screen 781a63fa.json   ← 04:32:08 + 1800 s
```

1200 s(筛查)+ 1800 s(评测)= 3000 s。5 个挂起的筛查后面 5/5 都跟着一个超时的 eval。

三箱 1243 次单配置筛查:**p50 11.4–13.6 s,p90 26.5–28.5 s,p99 38.7–105.0 s** ——
**截止线是自身 p99 的 11 倍**。而且**长筛查连缓存都不预热**:唯一一次跑完的慢筛 991.0 s,
紧随的 eval 又花 978.8 s,编译整整付了两遍。

**修法**(方案已完整写在 `docs/fix-ready-d9-screen-deadline.md`):

```python
def screen_timeout_s(cfg: EvalConfig) -> float:
    return max(prescreen_timeout_s(cfg, 1), float(cfg.screen_floor_timeout_s))
```

`screen_floor_timeout_s: float = 120.0` 是新增的 config 字段。**120 s 由实测导出而非猜测**:
它仍能答出 99.0% / 99.6% / 99.7% 的「本来会答出来的」筛查。`prescreen_timeout_s(cfg, 1)` = 33 s,
比实测 p90 只低 4.5–6.5 s,**所以 floor 是必需的而不是装饰**。

**风险。**

| 风险 | 等级 | 说明 |
|---|---|---|
| run 间不可比 | **中(唯一实质风险)** | 改变哪些配置拿到筛查判决 vs 落到真 trial ⇒ 改后的 run 不能与改前合并比较。**必须在两次实验之间做** |
| 误杀正确候选 | **无** | 筛查只缓存答案,超时留空缓存 ⇒ `cached_shared_verdict` 返回 `None` ⇒ 该配置**照样**拿到完整 `build_timeout_s` 的真 trial |
| 判据被削弱 | **无** | 不动拒绝判据。实测两臂 225 次拒绝**没有一次是边缘的**(最紧的超限 5%,中位超 62%),**0 个漏判** ⇒ 逻辑对、只有期限错 |

**预期效果。** 按「超过 120 s 上限的时间」计:

| box | 可回收 | 占 12 h 预算 |
|---|---|---|
| 1 | **~2.1 h**(+1202 s 那次约 0.3 h) | **17–20%** |
| 2 | 0.02 h | 0.2% |
| 3 | 0.01 h | 0.1% |

代价是 1243 次筛查里最多丢 3 个判决,而它们本来就会落到真 trial 上。**注意它对 box1 的
0 轮改写解决不了** —— 那 6.10 h 主要是**答出来的**作业(见 D8)。

### D8 — 一个候选的病态 PTX 让 `ptxas` 跑到 25–44 GB / 20–50 分钟

**问题。** `cand-941ea454` 的某些配置产生 74474 行 PTX,`ptxas` 在其上做寄存器分配要跑
20–50 分钟(实测 RSS 12.2 → 37.6 → 41.0 → 44.2 GB,CPU 100% 忙,**不是挂死**)。
1800 s 的作业期限确实兜住了它,所以**成本有界但极高**。

**三次修正后的正确框架**(每次都是我先报错、再被逐条明细否证):

1. ~~"这个候选统一慢 14 倍"~~ —— 用**均值**得出,**错**;
2. "中位 1.1 min,成本集中在 5 个灾难 trial(233 min = 94%)" —— 对,单位是 **trial**;
3. **最终**:该候选的 K 扩展发了第二个空间,两个空间构成对照 ——
   **空间 1:40 trial / 5.99 h / 9.2 min每trial / 6 个挂起筛查;空间 2:34 trial / 1.43 h /
   2.6 min / 2 个挂起。相差 3.5 倍,同候选同设置** ⇒ **病态的单位是「配置」,不是候选**。

**这条否证了一整类修法**:任何按候选下手的机制(准入、按候选配额)都会连空间 2 一起卡掉,
而空间 2 和三个兄弟一样便宜,还是 K 扩展刚判定值得探索的对象。

**修法必须分两步,顺序不能颠倒**(方案在 `docs/fix-ready-d8-job-wall-clock.md`):

**第一步(硬前置):`worker_client.run_job` 的四个出口都落盘 `job_wall_s` + `job_timed_out`。**
为什么是前置而不是「最便宜的一步」—— 我去读现成的 `compile_s` 想定阈值,结果它在 198 个 profile
上是 **p50 0.3 s / max 1.6 s**,而同一 run 的 `ptxas` 实测 25:35。原因:`compile_s` 只在
**作业返回时**写入,而付了昂贵编译的 6 个 trial **全部超时、不写 `out.json`** ⇒ 没有 profile。
落盘验证:无 profile 的 trial 全是 fail,该候选的正好是 **6 timeout + 1 runtime_error +
7 infeasible**。**度量在它最该说话的样本上被删失了。**

**第二步(等第一步有语料后):按时间导出一个 per-compile 闸。** PTX 行数分布已测(11737 个
`.ptx`:p50 1378 / p90 4510 / p99 17908 / max 280124;40 k 上限拒 0.24%,60 k 拒 0.09%),
**但按行数设闸目前不成立** —— size→time 无法从事件日志证明,按行数选阈值就是给「代理的代理」
定阈值,与 10x `excessive_speedup` 同一个错误。

**风险。**

| 风险 | 等级 | 说明 |
|---|---|---|
| 第一步:改变搜索行为 | **无** | 纯增量落盘,不参与任何判决。用 grep 测试守住「排序/分配/接受三条路径都不读它」,与 `CONVERSION_RATES` 同一纪律 |
| 第一步:字段被静默丢弃 | **中,已识别** | `ProfileRecord` 只设 `frozen=True`,继承 pydantic 默认 `extra="ignore"` ⇒ **会静默丢掉新字段**。所以**不能走 `ProfileRecord`**,守卫必须断言它穿过真实模型往返后仍存在 |
| 第二步:误杀慢但正确的 kernel | **高 —— 这是必须挡住的方向** | 「便宜但慢」绝不能成为否决候选的理由。闸必须表现为**一次正常的 trial 失败并说明理由**,且**绝不降低 `build_timeout_s`** |
| run 间不可比 | 第一步无 / 第二步中 | 所以第一步可与 D9 同批,第二步须再等一批语料 |

**预期效果。** 第一步:每候选成本表进报告 + `JOB_COST_OUTLIER` 事件 ⇒ 「一个候选吃掉 50.8% 预算」
这件事不再需要临时脚本才能发现。第二步(待定阈):回收 box1 那 6.10 h 里的大部分。

## 2. 为什么会 0 轮改写 —— 根因

**不是**「改写试了没提升」,而是**根本没走到 loop C**。根因是**结构性的,不是这个候选特有的**。

### 根因:`_pipeline_batch` 是全阻塞的,loop C 在它之后

`orchestrator.py:656` 的执行顺序:

```python
self._pipeline_batch(list(self.runs))     # ← 把【所有】种子逐个跑完:参数化 + 40~80 个 trial
self._restore_family_control_state()
while True:                                # ← loop C 从这里才开始
    ...
    progressed = self._rewrite_round(round_no)
```

⇒ **任何一个种子的调参慢,后面所有种子和整个 loop C 都在它后面排队。**
`_pipeline_batch` 的墙钟检查是**按候选**的(第 2790 行),所以它只能在候选**之间**停,
不能在候选**内部**停。

### 落盘证据

box1 `run-l3-43-20260911-230217`:`AGENT_CALL_FINISHED`(analyst)**02:35:49** → 下一次 agent 调用
**08:41:46**,**6.10 h 零 agent 调用**。窗口内只有 40 个 `TRIAL_DONE`(全是 `cand-941ea454`)
+ 4 个筛查 + 2 个 quicktest + 5 个单次事件。**6.10 h = 12 h 预算的 50.8%,是一个候选的一次调参。**

四个族最终都是 `status: active`、`rewrite_rounds_used: 0`、`history` 只有一个元素。

### 三个因素叠加,缺一不可

| 因素 | 贡献 | 已有对策 |
|---|---|---|
| **A. 结构:全批阻塞在 loop C 之前** | 根因。慢候选把 loop C 推到预算之外 | **尚无。这是新问题,见下** |
| **B. D8:某些配置的 `ptxas` 20–50 min** | 把「慢」放大到 9.2 min/trial | D8 两步 |
| **C. D9:筛查再叠加 1200 s** | 每个坏 trial 多付 20 min | D9 期限 |

**为什么 B+C 修完还不够。** 假设 D9 全回收(2.1 h)、D8 把 5 个灾难 trial 压到正常水平
(省约 3.5 h),这一 run 能腾出约 5.6 h ⇒ loop C 够跑。**但因素 A 仍然在**:只要某个候选
恰好更慢一点,同样的事会再发生一次,而且**报告里表现为沉默**(零 agent 调用不是错误)。
所以 A 需要一个**独立的、泛化的**修法。

### A 的候选修法(尚未实施,需用户决定)

1. **给单个候选的调参阶段加一个墙钟份额**,例如「任一候选的一次调参不得超过剩余预算的 X%」,
   超出即**结束该空间的调参**(保留已测 trial,该族照常进 loop C)。
   泛化、不针对任何候选、不缩小可行域(不删任何取值,只是这一轮少测几个点)。
   **风险**:改变每候选的 trial 数 ⇒ run 间不可比;且需要一个 X 的取值依据。
2. **把 loop C 的第一轮提前到种子批完成之前**(例如首个族拿到 stats 就可以改写)。
   更贴近论文的「反馈闭环」语义,但改动大、改变调度顺序。
3. **只报告不干预**:先上 D8 第一步的 `JOB_COST_OUTLIER`,让这件事可见。
   最保守,但不解决问题。

我的建议是 **1 + 3**:3 无风险先上,1 的 X 用 `job_wall_s` 语料导出而不是猜。

## 3. 三个核心概念:当前实验够不够

**结论:概念一(资源维度对齐)已有充分生产证据;概念二(优化动作的资源转化)有证据但只是单臂;
概念三(资源→性能转化效率)基本上还没有实验证据。**

### 概念一:资源维度对齐 — ✅ 够了

已实现并在生产中承重:`evaluation/dimensions.py` + `digest.py`,`for_prompt()` 是**唯一**允许
产出 agent 可见资源文本的函数,入口第一行是 `assert_no_raw_vector(d)`。

**证据**:S2 的 J2-5 单边判决(vector 臂 2.84 ms vs label 臂 3.11 ms,**−8.68%,超噪声底 3.7 倍**);
本轮 box2 处理臂两臂都开 `mode: vector`,4/4 族靠改写改善。每个维度都声明自己的
binding polarity、不可测就说不可测、屋顶不可达就单独列为 caveat。

**还缺的**:一个「维度对齐 vs 不对齐」的**三臂**对照(E2),用来分离「结构化判断」与
「原始数值」的贡献。这是 E2 的事,不是缺口。

### 概念二:优化动作带来的资源转化 — ⚠️ 有证据,但单臂

已实现:S2d 的 declare→reconcile 账本(`ResourceExpectation` + `reconcile.py`)、
`conversion_verdict`(improved / no_conversion / regressed / flat / unknown)、
`FAMILY_ROUND_RECORDED` 携带 `conversion` + `latency_gain_pct` + `resource_deltas`。

**本轮拿到的**:box2 **58 命中 / 23 未中 / 7 空洞 = 71.6%**,名义单边 p=0.00006
(此前配对 run 只有 p=0.1585);6/6 族轮 `conversion=improved`。

**缺口 1 —— 显著性只是逐声明的。** 二项检验把 81 条声明当独立,而它们是 **6 轮 × 2 候选、
单任务、单 agent**。按**轮**保守计只有 **5/6 多数命中,p=0.109,不显著**。
⇒ **需要第二个臂或第二个任务**,不是同一 run 里更多声明。

**缺口 2 —— S2d(c) 的对照缺失,但处理臂本身首次真正生效了。**
这一条我先前说错了方向,落盘核实后必须改写:

`config.py:410` 的注释记载「历史上每个族都只拿到过恰好一轮改写,所以 `ledger_entries` 在
**有史以来每一次** rewriter 调用上都是 `[]`,两臂对 S2d(c) 完全等价」。
**本轮 box2 打破了这个记录** —— 落盘的族轮序列:

```
fam-75181090  1 轮
fam-a47a797a  2 轮   06:23 记录 → 10:09 第二次 REWRITE_PRODUCED
fam-d375b4d4  2 轮   07:34 记录 → 08:39 第二次 REWRITE_PRODUCED
fam-550b5696  1 轮
```

两个族拿到了**第二轮**,且第二轮的 rewriter 调用发生在该族自己的
`EXPECTATIONS_RECONCILED` **之后** ⇒ **共 4 次 rewriter 调用首次携带了非空账本**。
这就是 `reserve_round_for_reconciled: true` 的设计效果,**S2d(c) 的处理臂第一次真正被施测了**。

而且它有结果可看:`fam-a47a797a` 两轮 4.1938 → 3.3203 → **2.9471**(第二轮再降 11.2%),
`fam-d375b4d4` 4.8072 → 3.2840 → 3.1836(第二轮再降 3.1%)。**总冠军 `cand-eb28dbe5` 正是
`fam-a47a797a` 第二轮的产物** —— 即那次「拿到了自己上一轮账本」的改写。

**所以缺的只是对照**:对照臂 0 轮改写 ⇒ 没有「同样条件下、账本**不**进 prompt」的第二轮可比。
这正是第 5 问要补的东西,而且**补的价值比我原先估计的更高** —— 处理侧已经有信号了。

**注意**:rewriter 收到的 `ledger_entries` **不落盘**(`orchestrator.py:2694` 直接传参),
所以上面是从「族轮序列 + 时间先后」推出的,不是直接观测。
**这本身是一个缺口**:S2d(c) 的自变量是否真的送达,应该有一个事件记录。


### 概念三:资源→性能转化效率 — ❌ 基本没有实验证据

这是**最大的缺口**,而且缺的不是数据、是**通路**。

**已有的(只落盘,零消费)**:`evaluation/conversion_rate.py` 实现了 per-candidate 回归,
实测 5213 个 complete trial 后**只有 `n_spills` 撑得住**(三箱 r² 0.573/0.733/0.800,
符号 95/99 一致),且证明它是**真斜率不是阈值**(计数比 0/1 多解释 +0.661/+0.518/+0.407 方差;
去零点后 r² 仍 0.745/0.594/0.762)。**但同时证否了可迁移性**:跨候选 ms/spill 相差 **15.4x**,
归一化后 p90/p10 仍 6.2x ⇒ **L3 层(把速率当常数外推)已被否证**。

**通路缺口,落盘核对过:**

```
conversion_rate.for_prompt()   已实现,但【没有任何调用者】
CONVERSION_RATES 事件           已发射(本轮三箱共 45 条),但【没有任何消费者】
                                (由一个 grep 源码的测试刻意守住)
```

⇒ **agent 从来没有看到过任何「资源→延迟转化速率」的信息**,所以「给了速率会不会改变优化动作」
这个命题**一次都没被测过**。

**还差的,按依赖顺序:**

| # | 缺什么 | 为什么必需 | 成本 |
|---|---|---|---|
| C1 | 把 `n_spills` 的速率**接进 prompt**(受 config 门控的第三种 mode) | 否则概念三永远只是离线统计 | 小(渲染 + 开关 + 守卫) |
| C2 | **报告里的转化效率段**(每族:资源变了多少 → 延迟变了多少) | 让「效率」在结果里可读,不必写临时脚本 | 小 |
| C3 | **E2 三臂实验**:label / vector / vector+rate | 唯一能回答「速率进 prompt 有没有用」的设计 | 12 h × 3 |
| C4 | 第二个维度的速率(需重跑两个 probe) | 单维度的结论撑不起「多资源」的叙事 | 中,可选 |

**注意 C1 的护栏**:不能绕过 `assert_no_raw_vector`,必须是**受 config 门控的第三种 mode**;
且**必须排除** `pct_of_dram_peak` / `pct_of_compute_peak` —— 它们是 1/gpu_ms 的改写,
给进去等于把延迟本身喂给 agent。

**必须做完才能跑大批量:**

   使**不同任务的结果不可比**(有的跑到 loop C、有的没跑到)。
2. **因素 A 的对策** — 同上,而且它是**沉默失败**,大批量下我不会注意到有多少任务其实没跑完流程。
3. **每个 run 的「流程完整度」自检** — 现在报告不会说「这个 run 从未进入 loop C」。
   大批量下必须能一眼筛掉流程没跑完的 run,否则会把「没改写」当成「改写无效」。

**大批量本身还需要:**

4. **任务集选择依据** — 现在只有 3 个 L3 任务,且 21/43/48 的选择有明确理由
   (forward 内 randn 的 33/35/41 不可用于正确性比对)。要上量必须先筛出**哪些 KernelBench 任务
   可用**,这本身是一次扫描。
5. **单任务预算的下界** — 12 h/任务在大批量下不现实。需要用现有语料回答「多少小时能稳定走完
   四个循环」,而这个数字**依赖 1 和 2 修完之后**才有意义。
6. **并行度** — 三台机器,每任务 12 h ⇒ 一天 6 个任务。要上 20+ 任务需要重新规划或缩短单任务预算。

**不阻塞、但会让结果更有说服力:** C1–C3(概念三进 prompt + E2 三臂)。

### 我建议的推进顺序

```
第 1 步  E1 对照臂补跑(单卡 12 h,见第 5 问)   ← 立即可做,不依赖任何修复
第 2 步  D9 + D8第一步 + 因素A的方案3(可见性)   ← 一批提交
第 3 步  C1 + C2(概念三进 prompt + 进报告)      ← 概念三的通路
第 4 步  E2 三臂(label / vector / vector+rate)  ← 同时验证概念一与三
第 5 步  因素A的方案1(用新语料定 X)+ D8第二步
第 6 步  任务集筛查 + 单任务预算下界 → 大批量
```

**第 1 步与第 2 步可以并行**:补跑用的是**旧代码**(见下),所以它不受修复影响,反而必须在
修复**之前**跑完,否则它与 box2 那一臂不可比。

## 5. 能否单卡 12 h 补出对照臂 — **能,而且有一个更便宜的做法**

### 关键发现:`resume` 会直接进入 loop C

落盘核对 box1 `run-l3-43-20260911-230217`:

```
STEP_DONE 共 7 条,其中 pipeline:* 4 条 —— 覆盖全部 4 个已注册候选
   pipeline:cand-772ea591  pipeline:cand-e254236c
   pipeline:cand-fdfbcb59  pipeline:cand-941ea454
四个族:status=active, rewrite_rounds_used=0, explored=False, rounds_not_evaluated=0
```

而 `_candidate_pipeline`(第 906 行)开头就是

```python
key = f"pipeline:{cand_id}"
if key in state.steps_done:
    self._restore_pipeline(crun, state); return
```

⇒ **resume 时 `_pipeline_batch` 对四个候选全部是 no-op**,直接落到 `while True` 的 loop C。
而 `self.t0 = time.monotonic()`(第 532 行)在 resume 时重置 ⇒ **12 h 预算是 12 个全新小时,
全部给 loop C**。

### 两个方案对比

| | **方案 A:resume 原 run** | 方案 B:全新单卡 run |
|---|---|---|
| 命令 | `resume --run <run-l3-43-20260911-230217>` | `run --task level3:43 --config <control>` |
| 墙钟 | **约 4–6 h**(只跑 loop C) | 12 h |
| 与 box2 的可比性 | **种子/空间/trial 完全是原对照臂的** ⇒ 可比性**更强** | 新种子 ⇒ 只是「另一个对照 run」 |
| 风险 | resume 后 `elapsed_hours` 只从 resume 起算,墙钟对等**必须用事件跨度** | 无此问题 |
| 代码版本 | **必须用旧代码**(`842e2a6`,即两臂当时跑的那一版) | 同 |

**方案 A 明显更好**:它补的正是缺失的那一半(loop C),而且用的是**同一批种子与同一批
调参结果**,消除了「两臂种子不同」这个本来就存在的差异。box2 的种子与 box1 不同,
这是原设计接受的;而 resume 让对照臂的 loop C **建立在它自己已测的族之上**,正是自变量作用的位置。

### 必须遵守的三条

1. **用 `842e2a6`(两臂当时的代码),不要带 D9/D8 修复。** 否则补出来的 loop C 与 box2 那一臂
   不可比 —— 这正是「修复必须在两次实验之间」的同一条约束。
2. **墙钟对等用事件跨度,不用自报 `elapsed_hours`。** resume 的时钟从 resume 起算
   (box3 曾自报 7.5 h 而实际 8.75 h)。报告 E1 时应写「对照臂 = 12.506 h 种子阶段 + N h loop C
   阶段」,并明确它与 box2 的 12.346 h **不是同一种预算**。
3. **哪台机器都行,但优先 box1 本机** —— run 目录、trials、artifacts、标定文件都在那里,
   `resume` 需要它们。换机器要先同步整个 run 目录,而 `runs_dir` 里的 agent 沙箱
   **携带明文 API key**,搬运即泄漏。

### 这会得到什么 / 不会得到什么

**会得到**:对照臂的 loop C 行为,特别是 **`reserve_round_for_reconciled: false` 下的第二轮改写** ——
即「同一个族拿到第二轮,但 prompt 里**没有**它自己的账本」。
处理臂已经证明这条路走得通(4 次调用带账本,总冠军就是其中一次的产物),
所以对照臂要回答的是:**那 11.2% 的第二轮改善,有多少来自「拿到了账本」,
有多少只是「多给了一轮」**。这是 S2d(c) 的全部内容。

**不会得到**:一个「12 h vs 12 h」的干净配对。对照臂将是「12.5 h 种子 + ~N h 改写」,
处理臂是「12.3 h 全流程」。这个差异**必须在论文里写明**,不能含糊。
如果需要严格对等的配对,那就得两臂都重跑(24 h 机时),而这应该等 D9/D8/因素A 都修完再做 ——
否则很可能再撞一次同样的问题。

**一个前提要注意**:对照臂能否真的拿到第二轮,取决于 `active_families()` 的规则 1
(「每个从未改写的族优先」)。对照臂有 **4 个族全部 0 轮**,而 `max_families_active=3` ⇒
前几轮会先把四个族各喂一轮,**第二轮要等到所有族都有过一轮之后**。
按处理臂的实测节奏(每族一轮约 2 h),四个族一轮约需 6–8 h,第二轮再 2 h ⇒
**12 h 预算大概只够拿到 1–2 个族的第二轮**,和处理臂的 2 个恰好可比。
这是 resume 方案成立的关键,也是它不能压缩到 6 h 的原因。
