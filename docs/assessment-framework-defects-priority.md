## P0 — Loop D(novelty)从未执行过

### 情况

统计 18 个 run 的候选来源:

```
origin:seed       72
origin:rewrite   111
origin:novelty     0      ← 一次都没有
AGENT_CALL_STARTED module=novelty : 0
```

**不是"很少有用",是从未被调用。**根因是两个预算参数互锁,`orchestrator._novelty_round`:

```python
if len(self.deps.families.families) >= self.cfg.budgets.max_families_total:
    return False
```

`max_seed_candidates: 4` 让 generator 产出 4 个种子,每个注册自己的族;而 `max_families_total: 3`。
所以**第一次检查 loop D 时已经有 4 个族**,`4 >= 3` 恒真。17 个有效 run 全部 families=4。

### 举例

`run-l3-43-20260906-091019`:四个族分别从 18.6 / 18.5 / 19.4 / 16.7 起步,全部是 seed 出身。
如果某个任务的四个种子恰好都选错了大方向(例如全都写朴素 attention 而没人想到 flash),
loop D 本该在这里注入一个结构上不同的新族 —— 但它不会被调用,run 只能在四个已有方向里改写到底。

### 是否应该修

**应该。**这是论文声称的四个循环之一(A 修复 / B 调参 / C 改写 / D 新族),而它的机制
"结构差异化的新族是否优于改写现有族"目前**零证据**。论文里任何关于 loop D 的表述现在都无实验支撑。

### 如何修

两个方向,选一个即可:

1. **抬高 `max_families_total`** 到 `max_seed_candidates` 之上,例如 seeds=4 + total=6
   (`max_families_total_hard: 6` 已存在,是现成的上界)
2. **降 `max_seed_candidates`** 到 3,给新族留 1 个位置

### 风险

**低,但会改变搜索投入的分配**:
- 方向 1 增加总族数 → 每个族分到的墙钟变少;配合 P8 的 5 轮,12h 可能不够,需要接受 run 变长
- 方向 2 减少种子多样性 → 起始方向少一个,而种子质量方差很大(实测最差种子 110ms,最好 16.7ms)

**我的建议是方向 1**,因为种子多样性是已证明有价值的(`run-l3-43-20260906-091019` 的冠军来自
第二好的种子,不是最好的),而族数上限只是个未经检验的保守值。

**必须先验证的一件事**:loop D 从未跑过,意味着 `NoveltyGeneratorAgent` 的整条代码路径
(prompt、schema、`accept_novel_seed` 的相似度门)**从未在真实 L3 任务上执行**。
开启前应先用 `configs/smoke_l1_novelty.yaml` 做一次 L1 冒烟,否则可能在 L3 跑到一半才发现它崩溃。

## P1 — 见证门永久丢弃一半触发它的候选(**已由 fp64 相对门解决**)

> **2026-09-06 更正**:本节首版把 P1 列为"需要再跑一次实验确认"。核实结果:
> **已经确认了**。`run-l3-43-20260906-091019`(唯一启用 fp64 相对门的 run)剩余的
> 2 次 `witness_default_failed` 是 `cand-8c64ccc3` 和 `cand-9c8d066a`,两者
> `failure_kind` 均为 `runtime_error` —— **真 bug,拒得对**。精度误拒 0 次。
> 下面的分析保留作为"为什么不能改 `relaxed_pass_frac`"的记录。

### 情况

146 次空间拒绝中 **119 次(82%)是见证失败**,其余全部加起来 27 次。按候选统计恢复情况:

```
命中过 >=1 次拒绝的候选 : 52
  最终恢复(空间发布)  : 26  (50%)
  彻底丢失              : 26  (50%)

首次拒绝原因 witness_default_failed: 49 个候选,119 次拒绝 → 每个约 2.4 次 repair
```

`repair_attempts: 3`,所以**见证门几乎吃掉它碰到的每个候选的全部修复预算**。

连带效应在最大的 agent 成本上可见:

```
parameterizer 每候选调用次数     被参数化候选 : 74
  1 次: 15 个候选               额外重调用   : 81
  2 次: 42 个候选               总调用       : 155
  3 次: 12 个候选               重参数化占比 : 52%
  4 次:  5 个候选
```

**74 个候选里只有 15 个(20%)第一次参数化就过关。**parameterizer 占 8.2% 墙钟(最大单项
agent 成本),约 4% 的墙钟花在重新参数化被见证门拒掉的候选上。

### 举例

`run-l3-48-20260905-010737` 的 `witness_minimal_failed` 占 21/42 —— 一半的拒绝来自 P2 描述的
fp16 角问题,那些候选本身是正确的。而 26 个"彻底丢失"的候选中,我们**永远不知道**其中有没有
更快的方案,因为它们从未进入调参。

### 是否应该修

**应该,但要分两步、谨慎推进。**这是当前唯一会**永久删除可能正确的 kernel** 的机制,严重度最高。
同时它也是安全网:门放松过度会让错误 kernel 进入调参,污染全部结果 —— 所以不能一次改到底。

**已有的重要缓解**:fp64 相对门(`run-l3-43-20260906-091019` 首次启用)已经把同任务的 trial
失败率从 45.9% 压到 13.5%,见证拒绝从 10 降到 2,救回 663 个 trial(全部 `complete`)。
这说明"相对判据"的方向是对的。

### 如何修

1. **先做 P2**(minimal 见证的 fp16 角),它是 119 次里 42 次的原因,且修法明确、风险低
2. **`witness_default_failed` 的 83 次已按 `failure_kind` 拆开**(本次补测):

```
correctness_mismatch    60  (72.3%)
runtime_error           22  (26.5%)
static_check_failed      1  ( 1.2%)
```

`runtime_error` 那 22 次是真 bug,该拒。关键是 60 次 correctness —— 其中 19 次是 09-02 的旧格式
(只有 "Output mismatch",无数字,不可分析),**22 次带完整判据数字**,结果非常一致:

```
gate: frac_within_tol > 0.99 AND cosine >= 0.99985

被拒的 22 次:  cosine 全部 >= 0.9999997     ← 方向上几乎完全一致
                frac_within_tol 0.953-0.987  ← 只差这一项

cosine >= 0.99(可能是精度噪声): 22
cosine <  0.99(可能是真错)    :  0
```

**22/22 全部是"cosine 近乎完美、只有 frac 不达标"。**没有一个像真的算错。

再对上已测的参考自身噪声底(ieee vs tf32 的 `frac_within_tol`):

```
任务      参考自身 floor    被拒候选的 frac 区间
L3:21        0.9554           0.9533-0.9778   (n=6)
L3:43        0.9767           0.9639-0.9869   (n=3)
L3:48        0.9778           0.9758-0.9764   (n=13)
                                门要求 > 0.99
```

**被拒的值就落在参考自身的噪声底附近,而门要求 0.99 —— 对这三个任务而言这个门本就不可达。**
这正是 `docs/finding-unreachable-correctness-gate.md` 描述的现象,而你已明确指示
**该文档的改动现阶段不实施("危险性过大")**。

### 风险

**中到高,而且这一项我不建议现在动。**

测量结论支持"门过严",但**它同时说明为什么不能贸然放松**:
- 唯一可分析的证据只有 22 个样本,且全部集中在 3 个任务、4 个 run
- `frac_within_tol` 是唯一在拒绝这些候选的判据。放松它 = 直接放松正确性门
- 一个被错误接受的 kernel 会进入 40 个 trial 的调参,并可能成为 run 的"冠军",污染最终结论
- **已有的 fp64 相对门是更安全的同类修复**,而且实测有效(见 P1 情况段):它不放松绝对判据,
  而是新增一条"相对参考自身误差"的接受路径,只能增加接受、不能减少

**建议**:P1 的正确下一步**不是**调 `relaxed_pass_frac`,而是
**确认 fp64 相对门是否已经吸收了这 22 类情况**。`run-l3-43-20260906-091019` 是唯一开启它的 run,
它的 `witness_default_failed` 从 10 降到 2 —— 若在其余两个任务上重跑也能复现,那么 P1 无需
额外改动,已被 fp64 门解决。**这是一次实验就能回答的问题,不需要改任何代码。**

### 附带发现:一次真实的 harness 崩溃(**已修**)

> **2026-09-06 更正**:本条首版列为"待修",实际**已经修好了**。
> `worker_main.py:569-570` 现在是 `sample = flat` /
> `p99 = sample.sort().values[int(sample.numel() * 0.99)]`,并包在 try/except 里。
> 下面保留起因记录。

拆分过程中发现 1 次(123 次空间拒绝中)是我们自己的代码崩溃,不是候选的问题:

```
run-l3-48-20260905-010737  cand-eb910a18
RuntimeError: quantile() input tensor is too large
  worker_main.py:436 in _relaxed_metrics -> "p99_rel_err": rel.flatten().quantile(0.99)
```

`torch.quantile` 对超大张量会直接报错。L3:48 输出很大,所以**度量函数自己崩了,候选因此被判失败**。
只发生 1 次,不是系统性问题,但它是纯粹的误判。修法:大张量走采样或 `kthvalue` 而非 `quantile`。
**低风险、独立**,可以和 P5/P6 一批做。

## P2 — minimal 见证是 fp16 角,在大输出任务上必然失败(**已修**)

> **2026-09-06 更正**:本节首版列为"待修",实际**代码里已经有这个回退了**,
> 而且比我提出的方案更精细:
> - `validation.py:35 _looks_out_of_range(result)` —— 识别"非有限值 / 参考 absmax 崩塌"
>   这个**溢出指纹**
> - `validation.py:235` —— `if label == "minimal" and _looks_out_of_range(result):`
>   → 调 `self._next_witness(...)` 换一个见证点
>
> 比我的提案好在哪:我原本想让精度 knob 一律保持 default 值,那会**顺带掩盖**
> L3:21 / L3:43 上"便宜角落确实有真 bug"的情况;现有实现只在命中溢出指纹时才回退,
> 真 bug 仍然被抓住。**不需要改动。**下面保留起因记录。

### 情况

双见证机制取"默认配置"和"全最小配置"两个点。而"最小"= 每个 knob 的 `choices[0]`,
因为 choices 按"便宜→贵"排序,精度 knob 的第一个值就是 **fp16**。

fp16 最大值 65504。L3:48 的输出超过这个范围,所以**无论候选多正确,minimal 见证一定失败**。
实测 L3:48 的 42 次拒绝里 21 次是它。

### 举例

`witness_minimal_failed` 意味着 default 见证**已经通过了** —— 也就是说候选在正常配置下是正确的,
却因为一个必然溢出的角落配置被否决,然后浪费 repair 预算去"修"一个不存在的 bug。

### 是否应该修

**应该。**这是纯粹的机制错误,不涉及放松正确性判据:被拒的候选在 default 点已被验证正确。

### 如何修

把 minimal 见证从"每个 knob 的 `choices[0]`"改为**"在默认精度下最便宜的合法配置"** ——
即精度 knob 保持 default 值,其余 knob 取 `choices[0]`。这样它仍然测试"最小资源配置"这个
本来的目的(小 block、少 warp),但不再顺带切换到一个任务不支持的数值格式。

### 风险

**低。**它只会让门变宽,而变宽的部分恰好是"default 已通过"的候选。
**验证方法**:改完后用历史上 42 次 `witness_minimal_failed` 回放,确认它们现在通过,
并确认没有任何历史上被接受的候选变成拒绝(后者不可能,但应该断言)。

## P3 — 族抽象允许成员之间结构不一致,导致归属声明失真

### 情况

`run-l3-43-20260906-091019` 按 `kernel_names` 分类每个族的成员(H=自写注意力,D=委托 torch SDPA):

```
fam-6eea8eac   best  8.06   5 个候选   D D H D H     ← 血统内部翻转
fam-8fb9b2b8   best  9.43   4 个候选   H H H H
fam-e6706893   best 15.40   3 个候选   D D D
fam-94add40d   best 16.10   5 个候选   H H H H H
```

**最快的族在自己的血统内部切换了计算方法**,五个成员三个手写、两个委托,而**获胜的是委托那个**。

### 举例

这个 run 的头条数字 8.06ms(复测 8.37ms)来自 `cand-60fdcae9`,它的 `kernel_names` 是
`['_fused_qkv_projection', '_head_layout_projection']` —— **没有注意力 kernel**。
注意力核心是 PyTorch 的 `scaled_dot_product_attention`。我们的贡献是把 `c_attn` + QKV 打包
融进一个 Triton GEMM 并去掉输出转置,这是真实的,但**不是注意力 kernel**。

纯手写最优是 `cand-9f6af7bd` 的 9.43ms。两个数字都必须给 —— 只报 8.06 等于把 SDPA 的功劳
算进我们的搜索。

我自己在这上面错过两次:先说 `fam-e6706893`(16.7ms)是最好的手写结果(错,该族全程委托),
又说 `cand-e29aa508`(16.1ms)是委托型(错,它有 `_flash_causal_attention`)。
**按族归属推断会出错,必须读 `kernel_names`。**

### 是否应该修

**应该修报告,不要改搜索。**委托 SDPA 对延迟是好棋,搜索找到它是正确行为,不该禁止
(而且"禁止委托"属于你已排除的 dtype-ban 类干预)。问题只在于报告没有区分两类。

### 如何修

在 report 里增加一行:按获胜候选的 `kernel_names` 判定是否自写核心算子,同时给出
**"纯自写最优"和"含委托最优"两个数字**。判定逻辑已在
`scripts/verify_report_against_events.py` 里实现并验证过。

### 风险

**极低**(只读 profile 元数据,不改判决)。唯一的注意点:"核心算子"的关键词判定
(`attention|flash|score|softmax|probab`)是任务相关的,换任务需要换关键词 ——
所以应该实现为"候选启动的 Triton kernel 是否覆盖了参考实现的主要算子",
而不是硬编码注意力关键词。

## P4 — 空间扩展朝已经在失败的边界瞄准

### 情况

扩展方向取自获胜 trial 的位置,**不看该边界的失败率**,而 `failure_rate_by_value` 早已在
`TuningStats` 里算好。`run-l3-43-20260906-091019` 实测 24 个被拓宽的 knob:

```
10 个(42%)推向了失败率 >=25% 的边界
  新增值在失败边界后 : 16/37 = 43% 失败
  新增值在健康边界后 : 13/84 = 15% 失败
```

近 3 倍差距,而失败 trial 不返回任何延迟数据。

全部 67 次扩展的产出分布:

```
完全无变化(|增益|<0.5%)          26  (39%)
边际(0.5–2%)                      19  (28%)
改善且获胜 trial 用了新增值        12  (18%)   ← 机制真正生效
改善但只靠重调原有域               10  (15%)
```

**只有 18% 通过它存在的理由获益**,67% 没有产生有意义变化,每次 40 个 trial。
按 19s/trial 估,约 9.5 小时 GPU 时间花在没移动任何东西的扩展上。

### 举例

`cand-60fdcae9` 八个 knob 里七个推向失败率 24–40% 的边界 —— 整次扩展瞄进了父空间已经证明
不友好的区域。

反例(机制正常工作):`cand-9c8d066a` 的 `ATTN_BLOCK_M` 加了 256,采样 2 次得到 166.0ms
(差 8.7 倍),TPE 正确留在 128 —— **花 2/40 个 trial 买到一个真实阴性结论**,这是合理产出。
差别在于那个边界是健康的。

### 是否应该修

**应该。**代价明确,数据现成,且不改变任何正确性判据。

### 如何修

在选扩展方向时读 `failure_rate_by_value`:边界取值失败率超过阈值(建议 30%)则**跳过该 knob 的
拓宽**,或改试反方向。

### 风险

**低。**最坏情况是少做几次本来也大概率无收益的扩展。

**一个必须避免的错误**:不要把它"升级"成资源模型。我测过 —— 汇总层面 `shared_bytes`
随失败率单调上升,看着像完美预测量:

```
失败率     knob-value 数   regs 中位   shared 中位
0%               974          255       40960
50%+             619          255       86016
```

但 `n_regs` 每桶都是 255(硬上限,零信息),而在**单候选单 knob 内部**(veto 实际需要的粒度)
"shared 最高的取值失败率也更高"只占 **458/935 = 49%,等于抛硬币**。
汇总趋势是跨候选聚合的假象。**只用直接测到的 `failure_rate_by_value`。**

## P5 — 无 `tl.dot` 的 kernel 被标成 `precision: unknown`

### 情况

`_detect_candidate_precision` 的兜底分支是 `if "tl.dot" in text: return "tf32"`,否则
`return "unknown"`。L3:48 的获胜 kernel 是纯 elementwise/reduction 的顺序扫描,
grep 全部精度信号:

```
tl.dot 0   input_precision 0   float16 0   bfloat16 0   .half( 0   tf32 0
float32 1
```

**零个点积**,于是落到 `unknown`。它实际是 `ieee_fp32`。

### 举例

`run-l3-48-20260905-010737` 报 `precision: unknown`,`_honest_verdict` 因此默认对比
`torch_compile`(fp32)—— **恰好是正确的比较基线,但纯属运气**,代码并不知道原因。
影响所有 scan / 归约 / 逐点融合类 kernel。

### 是否应该修

**应该。**修法明确、纯报告层。

### 如何修

无点积且无低精度构造 ⇒ 不使用张量核 ⇒ 算术精度就是存储精度,归类 `ieee_fp32` 而非 `unknown`。

### 风险

**极低**(仅影响报告里的对比基线选择,不改运行)。

## P6 — 报告把跨精度加速比印在诚实判据之前

### 情况

三个任务的参考实现**全是纯 fp32**(已读源码:无 tf32 标志、无 autocast、无 dtype 参数),
而每个获胜候选都用更低精度。选错基线的收益:

```
任务     vs torch_compile   vs c_tf32(诚实)   仅选基线就虚高
L3:21          3.09×              2.27×            1.36×
L3:43          4.23×              2.21×            1.91×
L3:48          9.49×              9.13×            1.04×
```

**L3:43 上光是选基线就值 1.91×**,几乎等于全部诚实加速。

### 举例

诚实判据已经在承重:三个历史 run 被它判为 `FAILS` —— 在自己精度下比基线**更慢**,
却对 fp32 基线显示 1.08–1.86× 的"胜利":

```
run-l3-21-20260904-013056  fp16  vs_compile 1.08×  vs_compile_tf32 0.79×  FAILS
run-l3-43-20260903-145357  tf32  vs_compile 1.72×  vs_compile_tf32 0.87×  FAILS
run-l3-43-20260904-093730  fp16  vs_compile 1.86×  vs_compile_tf32 0.95×  FAILS
```

机制是好的,问题在于报告把四个原始加速比印在诚实判据**上方**,读者先看到的是虚高的数字。

### 是否应该修

**应该。**纯呈现顺序。

### 如何修

把同精度判据移到四个原始加速比之前,并给原始那组加标注"跨精度,不可直接比较"。

### 风险

**极低。**

**注意一个不修的相关项**:`torch_compile_tf32` 对 fp16 候选并非真正同精度
(tf32 和 fp16 都是张量核路径但精度不同,而没有 fp16 基线)。详见
`finding-same-precision-baseline-is-not-same-precision.md`。加 fp16 基线等于改变任务定义
(参考是否允许换 dtype),**这是需要你决定的事,不是可以直接改的缺陷**。
