## 适配器边界实验

这些是开发者启动的独立对照，不是 Agent 自主优化。原实验、原 adapter 和
原参考输出均未覆盖；每个端点使用新 worker，正序/逆序各一次，每次15个样本，
并与历史完整输出参考比较两个连续步骤。18个端点、22个 rank、44次输出检查
全部通过。[完整结果](adapter-boundaries/result.json)

| 对照 | 原 adapter | 隔离改变后 | 解释 |
|---|---:|---:|---|
| ResNet latency：统计/额外同步移出 run | 4.3948 / 4.4590 ms | 4.2323 / 4.2478 ms | 这批配对端点相差约0.16–0.21 ms |
| ResNet memory：同一边界改变 | 4.4080 / 4.4272 ms | 4.2283 / 4.2273 ms | 显存峰值始终282,103,808 B；吞吐计时有变化 |
| ResNet latency：保留原始图片 fixture | 280,297,472 B | 282,103,808 B | 精确增加1,806,336 B；不是模型计算变化 |
| DDP：移除 reset 中额外的清梯度，保留 run 内源操作 | 149.1521 / 145.8136 ms | 143.4181 / 137.3658 ms | 数值检查通过，状态/内存生命周期影响可测；不能简单归因于清梯度调用本身的耗时 |

Qwen 使用同一次调用的内外计时之差判断边界：四个端点的中位差约
0.198–0.224 ms，相对差约0.028–0.031%。跨进程的总时长波动明显更大；
不把不同端点的吞吐差归因于计时指标替换。

上述结果说明：既有候选相对各自 adapter 的改进不等同于原项目的完全同边界
改进。后续需要生成并检查遵守原始边界的 adapter，再做共同 evaluator 下的
目标比较。当前没有新增一套按项目名硬编码的修补器。

## 通信协议核实

六个独立进程端点均通过完整的两步梯度/参数检查。此筛选开启了
`NCCL_DEBUG=INFO` 和 TUNING 日志，端到端时间包含该诊断设置；
若筛出有利方案，还需关闭诊断日志的独立确认。

| 控制 | 正序 step_ms | 逆序 step_ms | 28.35 / 157.54 MB 梯度通信的实际调优选择 |
|---|---:|---:|---|
| 默认 auto | 138.110 | 137.954 | RING / SIMPLE |
| 显式 Simple | 139.905 | 133.489 | RING / SIMPLE |
| 显式 LL（诊断控制） | 195.782 | 201.074 | RING / LL |

**默认基线已经为这些梯度载荷选择 SIMPLE。** 强制 LL 明显变慢不构成
相对默认基线的优化收益；目前不能把“切到 Simple”当作有力的正例。
见[端点结果](communication-screen/result.json)和[调优日志证据](protocol-evidence.json)。

三个控制的 profiler kernel 入口名称均包含 `RING_LL`。名称与实际调优协议
并不一一对应，NVIDIA 维护者也明确说明了这一点：
[NCCL issue 1595](https://github.com/NVIDIA/nccl/issues/1595)。
因此已修正上一阶段基于入口名称的解释；历史候选本身仍需对应日志核实。
累计 NCCL kernel 时长包含等待，不能解释为线速、纯传输时间或关键路径下界。
