# 生成对照与独立验证

本目录记录完整七案例批次之前的开发实验。它们由开发者发起，不能计为从原项目入口开始的自主优化。
完整批次使用冻结版本 `187617ce316403ea627c0d33392cc020bca2cb63`，结果另行记录。

## 最小信息调整

| 实验 | 独立新会话数 | 观察 | 判断 |
|---|---:|---|---|
| 通信 calibration 解释 | 对照 3、处理 3 | 对照均把合成 collective 时间解释成纯传输下界；处理组两次仍有矛盾表述，一次明确承认下界未知；六次都选择 CPU rendezvous | 未证明策略改善，不合入该候选提示 |
| ResNet 测量边界 | 对照 1、处理 1 | 对照在 run 内查询/重置统计；处理移至 metrics；两者均遗漏原 images fixture | 边界说明有用，但不能保证完整语义一致 |
| ResNet fixture 说明 | 对照 1、处理 1 | 两者都保留 images fixture | 生成有随机性，不能把结果全部归因于新增文字 |
| DDP reset 说明 | 对照 1、处理 1 | 两者都只在 run 内清梯度 | 本次对照已正确，不能声称处理产生因果收益 |

每次仅替换一个明确的输入片段；模型、工具设置和同批次框架版本一致，均使用新会话。
完整 prompt、输入 SHA-256、实际候选和用量见各 `*-generation-ab` 目录。
`snapshot-artifacts/` 按 SHA-256 去重保存对应输入。快照只涵盖声明的输入，未冻结整个外部文件系统。
通信候选和 DDP evaluator 的历史输入是事后重建，已标记为 historical；不是当时采集的完整状态。
跨源码版本重放显式允许源码变化；同一 A/B 内版本不变。

通信六个 proposal 均通过结构检查。原 selection 本身包含“纯传输下界”和排除重分桶的断言，
候选阶段小提示无法证明能修复这个更上游的决策。不能根据 Agent 重述了 caveat 就认定理解正确。

预先选定 repeat 0 的两组候选，再通过现有参数搜索执行真实 GPU 验证：

| 组别 | rendezvous_stride | step_ms | 原基线约束上限 | 结果 |
|---|---|---|---|---|
| 对照 | 2 / 3 / 1 | 241.847 / 232.104 / 235.504 | 148.377 ms | 全部拒绝 |
| 处理 | 13 / 1 | 281.669 / 242.138 | 148.377 ms | 全部拒绝 |

两组均为 `no_valid_parameter_candidate`；对应 NCCL 时长下降不构成通过完整目标约束。
只在独立分支验证，未修改原运行的 accepted revision。

## 适配器与结果生命周期

- 测量边界 A/B：四个 AB/BA 端点均通过完整 logits/top-1 对照。对照 4.246922 / 4.238059 ms，
  处理 4.215958 / 4.228771 ms；两者显存峰值均为 280,169,472 B。样本不足以支持通用收益结论。
- fixture 后续 A/B：四个端点均通过，峰值均为 281,975,808 B。两组都保留了 fixture。
- DDP reset：两组、两个 rank、连续两步的完整梯度和参数检查均通过。
- 固定历史 ResNet adapter，只切换 evaluator 输出生命周期：legacy 为 282,103,808 B，
  invocation 为 281,975,808 B，差值精确为 128,000 B，均通过数值检查。
  新入口选择 invocation；已有结构化请求仍默认 legacy。
- 原脚本实测峰值最小值为 281,975,808 B，中位数为 282,264,064 B。
  仅运行 offline 配置也有这一区间，因此“之前的 online 工作负载导致差异”没有得到证实。
  adapter 与原脚本的绝对峰值尚有分配历史差异，不能宣称完全相同。

这些检查用于定位实际差异，没有增加按模型名匹配的 adapter 修补器，也没有自动语义一致性保证。

## 通信机会筛选

通道实验八个端点均通过质量检查：

| 控制 | 正序 step_ms | 逆序 step_ms |
|---|---:|---:|
| auto | 143.904 | 140.962 |
| 4 channels | 151.436 | 136.171 |
| 8 channels | 141.363 | 141.633 |
| 16 channels | 146.868 | 142.598 |

没有相对同块 auto 的稳定收益。实际通道选择保留在 NCCL 调优日志。

共享内存 CUDA memcpy 模式 1/2/3 均发生真实 collective watchdog 超时，未建立质量通过；
首个 auto 端点为 138.237 ms。开发者在第一块四个结果完成后中断重复筛选，记录见
`shm-screen/developer-stop.json`。这是开发实验监督，不是框架中的失败类型路由。

新可选 `nccl_tuning` collector 已通过实际双卡 worker 验证。观测到 9 种调优决策；
主要梯度通信选择 SIMPLE。采集范围包含该诊断进程的初始化/预热，不能逐事件归因到算子组。
不能从 kernel 入口名称中的 `RING_LL` 推断实际协议。

当前仍没有发现强通信优化正例，也未通过人为强制 LL 来制造较弱基线。
