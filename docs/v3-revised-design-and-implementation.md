# v3 修订版设计与实施方案(2026-09-10 第三版)

**状态**:**当前有效版本**。本文档取代 `v3-implementation-plan.md` 与两份设计文档中与之冲突的一切早期措辞。被取代的部分在文中逐处点名,原文档保留作论证与调研出处。

**本版的由来**:用户对前一版设计提出三条纠正。它们改的不是措辞而是架构 —— **删掉一个已排期的阶段(S2c)、重写另一个阶段的形状(S4)、并新增一个当前完全不存在的机制(动作级预期与对账)**。同时,前一版里我自己判定「无解」的两个缺口(A-3 量纲不可比、A-1 排序规则不存在)在新框架下**不再是缺口** —— 不是被解决,是被绕过。

**方法**:本文档每一条状态断言都在当前 checkout 复验过,或来自当天的实测。凡是「没有」的,写出做了哪个检索。跨机断言带 host。

# 第 0 部分:本版相对前一版改了什么

## 0.1 三条纠正的原文与后果

| # | 用户的纠正 | 前一版的设计 | 后果 |
|---|---|---|---|
| **纠正 1** | 「资源之间的转化率具体是指的**每个优化动作**对应的资源转化,每个优化/修改动作都会引起不同维度上的资源消耗进行变动,**资源与资源之间没有明确的『交换率』**,因为每种动作对应的交换率都不一样」 | 把转化效率定义为 `Δlatency/Δresource_j` 的资源对属性,并因量纲不可比而**放弃**跨维度 | **问题被重新定位**。前一版在找一个不存在的量,所以只能报「做不到」;本版按**动作**记账,这是做得到的 |
| **纠正 2** | 「不需要把工具版本归为需要考虑的维度,**仅需知道不同版本工具的环境上,结论不能照搬**」 | 把 triton/torch 版本列为可能要建模的环境维度 | 收窄为缓存隔离 + 文档纪律。**但复验查出一个真缺陷**(§0.3) |
| **纠正 3** | 「**不应该存在明文的『代价表』**……不同方法/参数变动在不同的 task 上所引起的资源变化率都是不一样的,而且几乎无法被量化(只能事后重测反推);需要的是让 agent 能在知道现有算子以及环境在各个维度上的**完整信息**时,能**自己推理/分析**出什么样的动作应该对应什么样的资源变化趋势,以及最后应该要选择什么方法才符合现状」 | **S2c**:θ_best ±1 步邻域实测局部代价表,进 prompt | **S2c 整条删除**。省 2–3 天编码、**一整对 12h 对照 run**、每 run 约 2.3% 的 trial 预算 |

## 0.2 一个我自己的推理错误,必须记下

前一版用三重否证论证「所以必须给 agent 一张实测局部表」:

| 否证 | 实测 |
|---|---|
| shared 有闭式公式? | **0/96** 精确命中,残差最大 121.4% |
| 地图可分离? | **0/10** —— 宽扫里没有一对一步移动的增量一致,跨度 **32768 B / 138 regs** |
| 至少符号可靠? | **连符号都不可靠** —— 13 条非单调切片**全在 BK 上**:BK 16→32 寄存器 **−58**,32→64 又 **+87 顶到 255** |

**从这三条推出「所以要查实测表」,推错了一步。** 不可分离意味着表**只在被测邻域成立**(所以前一版给它加了 `measured_at` 作有效性范围)—— 而一个只在自己邻域成立的表,**对「下一步该往哪走」几乎没有外推价值**,那恰是它唯一的用途。

**所以这三条现在的角色变了**:它们不再是 S2c 的必要性证明,而是**「为什么不能给 agent 任何变化率」的实测证据**。第三条(符号不可靠)尤其关键 —— **连人工规则都推不出方向,凭什么把一张局部表当通用先验喂给 agent**。

**同向的自家实测(G9,2026-09-10)**:三臂 A/B,`none`(不给分析)/ `verdict`(给判决)/ `rich`(判决 + 候选级实测量)。

| arm | best_ms | vs 起点 5.4472 ms | 臂内跨度 | agent_s | cost |
|---|---|---|---|---|---|
| `none` | 7.8679 | **+44.4%(更差)** | 255.6% | 1075 | $0.024 |
| `verdict` | **4.5670** | **−16.2%** | 4.7% | 1108 | $0.026 |
| `rich` | 4.7585 | −12.6% | 1.6% | 1565 | $0.056 |

- `none` 与另两臂**分离得极清楚**:逐候选 **7/7**,`verdict`+`rich` 的每个候选都优于 `none` 的每个候选;`none` 是唯一比起点更差的臂;
- **`verdict` 与 `rich` 没有分离**:差 4.19% < `verdict` 臂内跨度 4.72%,而 `rich` 贵 **2.1×**。

**读法:「有没有结构化分析」有效;「分析里塞多少实测量」边际收益已饱和。而代价表正是「塞更多量」的极端形式。**

## 0.3 纠正 2 顺带查出的一个真缺陷

按纠正 2,「结论不照搬」的机制有两处已在执行:

1. **标定缓存按环境身份键入**:`Calibration.identity()` = `device_name + capability + sm_count + torch_version + driver_version`(`calibration.py:214`)。身份不符 → 缓存作废、重测。
2. **文档级共变因素**:`box-a800-setup.md §7.2` 记「Triton 3.4 与 3.5 生成不同代码,寄存器数、shared 用量、乃至一个 tile 能不能编译都可能不同 —— 任何 box-1-vs-box-3 比较必须把工具链当作共变因素」。

**缺陷:`triton_version` 不在 `identity()` 里。**

这在我们的场景下承重:`fp32/tf32/fp16/bf16_triton_tflops` 这四个天花板**是通过 Triton 测出来的**(G10),而 Triton 就是代码生成器。目前两台机 torch 与 triton 恰好共变(box 1 = 2.9.1/3.5.1,box 3 = 2.8.0/3.4.0),所以缓存事实上没串;但**在同一台机上单独 `pip install -U triton` 会静默复用旧天花板** —— 那正是纠正 2 要防的「结论被照搬」。

**登记为 G32。修法泛化且低风险**:`identity()` 加 `triton_version`,并 bump `CALIBRATION_SCHEMA_VERSION`(现为 4 → 5)。这与「加新测量必须 bump schema」是同一条纪律 —— 上次 `l2_bytes` 因为没 bump,差点被 36h 的 L3 链继承成 0。

## 0.4 被绕过(不是被解决)的两个缺口

| 缺口 | 前一版的判定 | 本版为什么不再需要它 |
|---|---|---|
| **A-3 跨维度量纲不可比** | 「量纲问题,无解;当前处理是不跨维度比」 | **按动作记账不需要跨维度比较。** 一个动作在 shared 上 `up`、在 n_regs 上 `down`,这两条各自与自己的实测对账,从不相除 |
| **A-1 多维同时 binding 时先动哪一维** | 「实测证否:最好的规则 7.1% vs 最好的对照 21.4%。排序依据仍不存在,只是现在知道不该去找它」 | **本版不需要排序规则。** 「该动哪一维」交给 agent 推理,而正确性由**事后对账**保证,不由事前规则保证 |

**这是本版最实质的收益**:准确性的来源从「我们替 agent 算出变化率」换成「agent 自己推理 + 被实测追责」。前者已被三重否证证明不可行,后者只要求 agent **说清预期**。

# 第 1 部分:修订后的设计

## 1.1 核心思想(不变)

一个算子在每个资源维度上有自己的**消耗向量**;一台硬件在每个维度上有自己的**供给向量**。两者方向不一致时,某个维度先撞顶而其余闲置 —— 这就是瓶颈。**算子优化的本质是在资源维度之间做交换,把消耗向量的方向转向供给向量的方向。**

**文献佐证这个抽象是对的**:FlashAttention(arXiv:2205.14135)在一张表里同时印出账本两侧 —— A100 / GPT-2 medium / seq 1024:标准实现 66.6 GFLOP、40.3 GB HBM、41.7 ms;FlashAttention **75.2 GFLOP(+13%)、4.4 GB(−9.2×)、7.3 ms(−5.7×)**。它**多花 13% 算力换 9.2× 流量削减**。

**同一个例子也是设计约束**:一个把 FLOP 当作要最小化的量的框架**会否决 FlashAttention**。所以评分必须是「每单位资源换来的延迟」,不是资源最小化。

**但「利用率均衡」不是目标。** 严格讲最优是延迟最小。一个打满带宽、算力空转的 kernel,若已达该任务的物理下界,它的「比例失衡」是**物理性质而非缺陷**。已实测反例:**L3:48 固定 1.351 GB 流量,1.64 ms 已达实测 911 GB/s 屋顶的 90.4%**,三次 run 复现(8/10 候选、跨 4 个不同族全在 2% 内)—— 平台期是物理不是噪声。

## 1.2 本版的核心机制:四步循环

```
第 1 步  状态           每个维度:算子用了多少 / 环境有多少 / 哪些到顶了 / 哪些有余量
                        ↓
第 2 步  agent 选动作    读完整状态,自己推理该用什么优化动作去对齐各维度
                        ↓
第 3 步  声明方向预期    "这个动作会让哪些维度变多、哪些变少" —— 方向,不是数值
                        ↓
第 4 步  双段对账        (a) 实际资源变动是否符合预期?
                        (b) 资源变动是否真的换来性能提升?
                        ↓
        回灌下一轮       两段结果都进 agent 的下一次输入
```

**第 4 步是两段而不是一段,这是本版的关键。** 前一版只有 (b);(a) 完全不存在。两段分开把失败拆成**三种可区分的原因**:

| (a) 预期 vs 实测 | (b) 资源 vs 性能 | 说明什么 | 该怎么办 |
|---|---|---|---|
| 符合 | 换到了 | 方法对、执行对 | 沿这个方向继续 |
| 符合 | **没换到** | **执行对,但那个维度不是限制** | **判决错了** —— 改判决,别改 agent |
| **不符合** | 没换到 | **agent 对这个动作的资源效应理解错了** | 可在下一轮 prompt 里纠正 |
| **不符合** | 换到了 | **偶然收益**,不可复现 | 不得当经验沿用 |

**v2 和前一版都只能看到第 2 列,所以第 2 行和第 3 行长得一样。** 这正是本版要补的能力。

## 1.3 三层架构(不变,但第二层的职责改述)

```
第一层  采集器(多个独立算法,全部是代码,零 LLM)
        每个采集器只回答一个窄问题,各自有正对照,可单独失效
                    │  产物:带出处的实测量
                    ▼
第二层  提炼器(代码,不是 agent)                      ← 硬约束,不可绕过
        把原始量变成"每维一条判决"并做算错自检
                    │  产物:结构化的、有限的、可证伪的陈述
                    ▼
第三层  分析 agent(各有专责,上下文互不共享)
        每个 agent 只看它需要的那一部分,输出建议 + 方向预期
                    │  产物:改写方向 + 逐维方向预期 + 理由
                    ▼
        harness 判定(接受/拒绝/继续,永远由代码决定)+ 对账
```

**第二层为什么是硬约束**:KernelPro 三臂对照 —— **原始计数器那一臂 1.77×,完全不给反馈 3.35×**,单侧 Wilcoxon **p=0.0007**。**给 agent 原始数值比什么都不给更差。**

### 1.3.1 消化层的职责改述 —— 这一处前一版写错了方向

前一版把消化层描述成**压缩层**。按纠正 3(agent 需要「各个维度上的完整信息」),这个描述会导致实现时**砍掉维度** —— 而砍维度正是 v2 的原始缺陷。

**「完整」与「原始向量不进 prompt」不冲突,因为它们在不同的轴上:**

| | 覆盖面 | 形式 |
|---|---|---|
| KernelPro 那条有害的臂 | 完整 | **原始数值,无判决、无天花板、无出处** |
| **v2 现状(也有害)** | **只报一个维度**(L3:21 的 20 份报告 **19 份**同标签) | 有判决 |
| **本版要的** | **完整 —— 每个维度都在** | **每维带判决**:`{measured, ceiling, ceiling_provenance, verdict, applicable, confidence}` |

**所以消化层的职责是:每个维度都给,但都给成判决形态。它是「改形式」层,不是「减内容」层。**

## 1.4 维度词表:闭合,逐维声明极性

`conversion.py:38-50` 已定义 8 个维度并逐个声明极性。**本版把它提升为全框架的唯一词表**(状态、预期、对账、报告都用它):

| 维度 | 单位 | 改善方向 | 候选级真实量? | 来源 |
|---|---|---|---|---|
| `n_regs` | registers/thread | 降低 | ✅ | 一次 launch 后可读(96/96) |
| `n_spills` | local-memory slots | 降低 | ✅ | 同上 |
| `shared_bytes` | bytes | 降低 | ✅ | 编译后可读(108/108) |
| `num_warps` | warps | 无方向 | ✅ | Triton launch 属性 |
| `occupancy` | fraction | **提高** ← 唯一反极性 | ✅ | 一次 launch 后可读 |
| `peak_alloc_bytes` | bytes | 降低 | ✅ | 跨候选跳度实测 **9.6–41.3%** |
| `candidate_aten_bytes` | bytes | 降低 | ⚠️ **仅下界** | aten 级,**融合越好越低报** |
| `candidate_aten_ops` | aten ops | 降低 | ⚠️ 同上 | 同上 |
| `threads_launched` | threads | 无方向 | ✅ | S5 第 1 步已完成 |

**逐维声明极性不是冗余。** 代码注释记着:统一按「低=好」处理会把 occupancy 的每一份判决**反转**,而且**表格依然干净** —— 那个错误曾报出 **0 个多维绑定而反例就在输入里**。

### 1.4.1 两个不能算作独立维度的「维度」

`pct_of_dram_peak` 与 `pct_of_compute_peak` 的分子(`compulsory_bytes` / `flop_count`)是**任务级常数**(`orchestrator.py:1421` 一带),所以除以 `gpu_ms` 后**就是 1/延迟**。实测:**66 份判决 `gpu_ms × achieved_tbs` 恒定到 0.07–0.36%**,而同期 `gpu_ms` 在候选间变化达 4.6×。

**处理(两条同时成立,缺一不可)**:

- ✅ **可以**用于「离物理屋顶还有多远」—— L3:48 的 94.6% 是有意义的判断,而且它是 `task_cost.py` 刻意的设计(任务下界,回答「该任务能否算力受限」),**不得改动**;
- ❌ **不可以**算作多维绑定里的两个独立维度 —— 否则**延迟被算两票**;
- ❌ **不可以**进动作对账账本的维度列表 —— 一个动作让延迟下降,这两「维」的压强**必然**上升,那是恒等式不是观测。

**多维绑定率 72.5%(n=51,阈值 0.70)这个数字里凡有 dram/compute 参与的组合,都必须按这条重算。** 幸运的是最常挂在一起的一对是 **occupancy + register_pressure(20/51)**,两者都是真独立维度。

## 1.5 第 1 步:状态视图

### 1.5.1 供给侧(环境持有多少)—— 已是实测的向量

`Calibration`(`calibration.py:152-194`)不是数据表抄来的:

| 供给维度 | 字段 | box 1 (4090) | box 3 (A800) |
|---|---|---|---|
| DRAM 带宽 | `dram_tbs` | 911–924 GB/s | **1686 GB/s** |
| 算力 × 4 精度 × **2 后端** | `fp32/tf32/fp16/bf16_tflops` + `*_triton_tflops` | 54.8 / 88 / 158 / 164 | **19.0 / 111.8 / 229 / 234** |
| L2 容量 | `l2_bytes` | 72 MiB | **40 MiB** |
| shared/block | `max_shared_bytes_optin` | 101376 B | **166912 B** |
| SM 数 | `sm_count` | 128 | 108 |
| 启动地板 | `empty_launch_floor_ms` | 已测 | 已测 |
| 判决阈值 | `thresholds` | 由本机基准工况派生 | **未缓存**(见第 3 部分) |

**这一半为什么可信**:每个天花板要求「至少被一个候选逼近过」作正对照,并带 provenance。**G10 是它承重的证据** —— Triton/cuBLAS 比值在两张卡上**方向相反**(4090 fp16 Triton 反超 9.6%;A800 fp16 Triton 只到 80.8%),所以屋顶取**本机所有实测路径的最大值**,任何硬编码比值在其中一台机上必错。

**A800 的 tf32/fp32 = 5.9×,4090 只有 1.6×** —— 这正是「供给向量方向不同」的实测实例:同一个 `input_precision="ieee"` 的候选,在 A800 上放弃的东西是 4090 的 3.7 倍。

### 1.5.2 消耗侧(算子用了多少)—— 分三层,可信度不同

**不能把三层混在一起给 agent**:

| 层 | 内容 | 可信度 | 能否进接受判定 |
|---|---|---|---|
| **层 1 直接实测** | §1.4 词表的 9 个维度 | 高 | ✅ |
| **层 2 实测 ÷ 实测天花板** | `pct_of_dram_peak`、`pct_of_compute_peak`(**必须按精度**) | 中,**分母是已知弱点** | 只作「离屋顶多远」(§1.4.1) |
| **层 3 静态推导** | SASS 派生的 shared 强度、barrier 密度、`vectorized_frac`、访存模式墙坐标 | 低 | ❌ **只作排序先验** |

### 1.5.3 每维一条独立记录(定稿形态,不合成)

```
{ dimension_id, measured, ceiling, ceiling_provenance,
  verdict ∈ {binding, near-binding, slack, not-applicable, unknown},
  confidence, applicable }
```

四条规则:

1. **`applicable` 是一等字段,不是缺省值。** V100 无 bf16 → 该维**不存在**,而非「值为 0」。`applicable=false` 与 `measured=0` 必须永远可区分 —— 沿用 `task_cost.py` 已验证的 `notes` 做法(「`flop_count=0` 对 maxpool 合法、对 matmul 是失败」),**不要另发明**。
2. **判决保持多份,不投票。** 多维同时 binding 时输出就是「多个维度同时 binding」—— 不选赢家、不加权、不取 max。**这修的是缺陷本身**:问题不是标签选错,而是「必须选一个」这个要求。
3. **资源占用是结构特定的,改写后必须重测。** 按 `(候选, structural_signature)` 键入,**不得按族** —— 否则 rewrite 静默继承父候选的向量。`families.py:79` 已有 `structural_signature`,直接用。
4. **屋顶的可达性按任务推导,不作常量。** Roofline 原文自己在 SpMV 上推翻了自己的 ceiling 顺序,且其高位 ceiling 定义里就含「inherently lacking in a kernel」。**这正是我们 L3:48 的事故**:张量核这条「高阶」屋顶在那任务上天生不可用,框架仍拿它当目标 —— **8/8 张量核候选被拒、7/7 标量候选被收**,最终 2.09 ms / 8.90× 完全没用上张量核。

### 1.5.4 输出并列两类,不排序

```
绑定的(墙在哪):     compute 0.93, occupancy 0.83   → 这些方向要付代价
有余量的(空隙在哪): dram 0.10, register 0.27       → 这些方向还能用
```

**v2 从来只报第一类。** 而 A-1 的实测说明第二类才是赢的改写多在动的地方:14 次超噪声底的成功改写里只有 4 次「动得最多的那维」是绑定的;**8/14 什么都没缓解**,其中 **6 次反而把某维朝墙推**(吞吐上升最高 **+70.61 TFLOP/s**)。

**但「填空隙」不许变成新的机械规则**,四条理由:n=14 只够说「没有规则被支持」;同一张表里有反例;**因果方向未定**;以及 Balakrishnan & Cheng(*IJPR* 38(6):1459–1463, 2000)的算例里**利用率不满的资源 B 影子价格 $1.8,而被选中的资源 A 只有 $0.6** —— 若这在我们这里也成立,那么「有余量」的标签本身就认错了约束,**不存在新机制,只是绑定判据不可靠**。两种读法**在可执行结论上一致**(都说不要按利用率排序、都说并列报两类),这是它没推翻设计的原因。

**顺带一条支持既有纪律的发现**:文献推荐「按梯度(影子价格)排序而非按利用率」,但**影子价格在原问题退化时(即多约束同时绑定,正是我们的情形)本身就不唯一**(MIT 15.053:「any weighted combination…is also an alternative set of optimal shadow prices」)。**所以解析梯度在我们最需要它的情形下反而比实测的成对观测更弱。**

## 1.6 第 2 步:agent 选动作

**这一步刻意不给规则。** 依据是 A-1 的实测:没有排序规则打得过对照(最好规则 7.1% vs 最好对照 21.4%)。所以框架的职责止于**给完整状态**,选择交给 agent 推理。

**但两条边界必须由代码守住:**

1. **瓶颈由我们算,不问 agent。** 外部实测:给了剖析数据分类准确率 **100%**,只给源码推理模型只到 **64%**。**64% 意味着 agent 自述的瓶颈永远不能当证据** —— 它可以进 evidence,不能进判决。
2. **接受/拒绝/继续永远由代码决定。** agent 只建议。

## 1.7 第 3 步:方向预期(本版新增)

### 1.7.1 形态:闭合词表,只有方向

agent 每提一个改写动作,必须对它**预期会动的每个维度**给一条:

```
{ dimension: <§1.4 词表中的一个>,
  expect: "up" | "down" | "unchanged" | "unknown",
  why: <一句话,指向具体机制> }
```

**为什么必须闭合词表**:对账要可机械执行。若允许自由文本,「shared 可能会有一些变化」既不算命中也不算未命中,账本就失效了。

**`unknown` 允许,但计数。** 所以一个永远答 `unknown` 的 agent 会留下一份**可见的零信息记录**,而不是隐形地逃过检查。

**只要方向,不要数值。** 这是纠正 1 和 3 的直接落地:变化率「几乎无法被量化」,所以不问。

### 1.7.2 这不违反 D-2,而且是 D-2 精神的正面实现

D-2 是「进入选择/排序/分配的数字必须是已实现的实测量,不得是预测」。它的证据是 `predicted_gain_pct`:n=21,中位预测 5.0%、中位实际 1.8%、**中位带符号误差 −5.0%**,**21 次里 8 次实际为负**(预测 +16.4% → 实际 −16.5%)。原文建议:「**Do not use it for allocation.**」

**前一版把这条误用了。** 两处区别:

1. **那次失败预测的是「延迟增益的数值」,本版要的是「资源维度的方向」。** 后者是**结构性得多的推断**(「加大 tile → shared 变多」不需要知道多少字节),而且**编译期就能验证**。用一个关于延迟幅度的失败去否决一个关于资源符号的声明,是把两件事混为一谈。
2. **方向预期不进入选择。** 它进入的是**对账账本**,而且**总是会被实测检查**。D-2 防的是「用未验证的预测去分配预算」;这里的预测是**被检查的对象**,不是分配依据。

**硬边界(写进代码)**:方向预期**不得**参与候选排序、族分配、trial 预算、接受判定。它只有两个出口:账本,和下一轮的 prompt。

## 1.8 第 4 步:双段对账

### 1.8.1 第 (a) 段:预期 vs 实测(本版新增,当前零代码)

对每个维度,把 agent 声明的 `expect` 与实测方向比:

```
{ dimension, expected: up|down|unchanged|unknown,
  actual: up|down|flat,           ← 由 conversion.py 已有的 direction 推出
  match: hit | miss | vacuous,    ← vacuous = expected 为 unknown
  before, after, delta, rel, unit }
```

**逐轮汇总**:`{hits, misses, vacuous, dimensions_unpredicted}`。最后一项是「实测动了但 agent 没提」的维度 —— **它与 miss 不同,是「没想到」而不是「想错了」**,两者对下一轮的提示不一样。

**实质阈值沿用现有的 `_MATERIAL_RESOURCE_DELTA = 0.05`**(`conversion.py:53`):资源必须动过自身前值的 5% 才算真动过。这不是物理量,它存在的目的是让「1 个寄存器 / 128 字节」的差别不被当成一次资源变动并挂上延迟判决。

### 1.8.2 第 (b) 段:资源 vs 性能(已实现,零消费者)

`conversion_verdict()`(`conversion.py:76-149`)已算出逐维 `direction ∈ {improved, worsened, flat, changed}` 与轮级判决:

| 判决 | 含义 |
|---|---|
| `improved` | 延迟降幅超噪声底 |
| **`no_conversion`** | **某资源实质改善而延迟没动 —— 那个资源不是限制** |
| `regressed` | 延迟上升 |
| `flat` | 延迟与资源都没实质变动 |
| `unknown` | 延迟无法比较 |

**`no_conversion` 正是本设计要的第二段对账,而它已经在代码里。** 模块 docstring 自己写着它为什么可靠:

> 某资源实质改善而延迟没动,是**那个资源不是限制**的直接证据 —— 这比任何利用率标签都可靠,**因为它是同一族两次真实测量之间的受控比较,而不是与一个假定天花板的比值**。

**并且模块已明确拒绝跨维 argmax**(`conversion.py:21-26`):shared 的中位摆幅是 registers 的 **13.5 倍**,纯粹来自归一化分母;任何「跟维度 argmax |Δ|」的规则会退化成「**永远挑 shared**」(实测 61.5%),什么都没发现。**替代是每个维度只和自己的历史分布比。**

**唯一缺的是消费者。** 复验:`report.py` 里 `conversion` **0 次命中**;它的输出只进 `FAMILY_ROUND_RECORDED` 事件,而该事件的**三个消费者只读 `best_ms` / `family_id`**(`orchestrator.py:1817`、`report.py:62`、`run_store.py:152`)。**没有消费者的判决等于没实现。**

### 1.8.3 回灌:替换现在的 `failed_hypotheses`

当前 `failed_hypotheses` 每条只有 `{id, change, round}`(`orchestrator.py:1983`)。rewriter 因此只能看到「H1 试过、没帮上」,**看不到「H1 说 shared 会降,实际升了」**。

**本版把它扩成账本条目**(同一个通路,加字段):

```
{ id, change, round,
  expectations: [{dimension, expect, why}],
  reconciliation: {hits, misses, vacuous, unpredicted, per_dimension: [...]},
  conversion: improved|no_conversion|regressed|flat|unknown,
  latency_gain_pct,
  caveat: <见 1.8.4> }
```

**必须小。** G9 已实测信息量边际收益饱和 ⇒ 每维每轮**一行**,不许膨胀成第二份原始向量。渲染进 prompt 时的形态是**每轮一段、每维一行**,不是 JSON dump。

### 1.8.4 一个真实的归因混淆,账本必须带警告

`conversion_verdict` 比的是**父/子各自的 θ_best**(`families.py:307-309` 记着:轮级判决需要改写两侧的资源状态)。而**改写后会重新调参**,所以「预期未命中」可能是因为 tuner 走到了别处,而不是 agent 判断错。

**这不是假设,是代码事实。** 账本每条必须带这个 caveat,否则会冤枉 agent —— 而冤枉 agent 的后果是它下一轮据错误反馈调整,比没有反馈更糟(KernelPro 那条 1.77× 的臂就是这个形状)。

**可减轻但不可消除**:同时记一份「在**父** θ 上编译**子**结构」的读数作对照。热编译实测 **0.1 ms**,近乎免费,而它把「结构造成的资源变化」与「重新调参造成的」分开。**这是可选项,不是硬要求** —— 若实现,必须验证它真的能分开两者(反向对照:构造一个只有 θ 变、结构未变的对子,断言该对照读数不变)。

## 1.9 环境(纠正 2 的落地)

**不做维度。** 只做两件事:

1. **缓存隔离**:`Calibration.identity()` 必须包含**每一个会改变代码生成或可达上限的环境要素**。当前含 `device_name + capability + sm_count + torch_version + driver_version`,**缺 `triton_version`(G32,§0.3)**。
2. **文档纪律**:任何跨机比较必须把工具链列为共变因素,并在结论里写明。已在 `box-a800-setup.md §7.2` 执行。

**判据**:在同一台机上升级 triton 后,标定缓存必须失效并重测。**反向对照**:只改 `triton_version` 字段,断言 `identity()` 变化;不改任何字段,断言不变。

## 1.11 新颖性位置(修订)

前一版的新颖性主张被调研收窄过两次:**多资源向量被 ERM(2014)占据**(它已有资源向量 + 三层利用率分解 + 显式重叠系数),**gap 高度被 Roofline(2009)占据**。前一版留下的可守主张是「替代率作实测量引导搜索」,以及「拒绝合成本身是一个设计选择」。

**本版新增一条更强的,而且它直接来自纠正 1:**

> **动作级的方向预期 + 强制事后对账。**

**位置**:KernelPro 的工具建议携带「expected improvement estimates」,**但从不回头验证它是否实现**。前一版把这条记成新颖点却**没有对应机制**;本版把机制补上,而且比它强三处:**逐维度**、**方向化(不假装能给数值)**、**双段(预期符合性与性能转化分开)**。

**这比「多资源向量」和「gap 高度」都更难被前人占位**,因为它不是一个量而是一条闭环纪律。

**论文上必须同样诚实的地方**(否则会被按 A-1 那组数字攻击):

- 「转化效率引导」**不是**「用交换率驱动搜索」。必须写清:交换率不存在统一形式,框架提供的是状态 + 对账,方向选择由 agent 推理。
- A-1 的负面结果要**主动报告**(没有排序规则胜过随机对照),而不是等审稿人发现。
- 基线警告要**前置**:KernelBench-Verified 已复验 —— 最好的模型在 TF32 基线 + 四分布隐藏测试下从 **1.43× 掉到 0.88×**(比 PyTorch 慢)。**任何对 eager 基线宣称的加速比现在都可被攻击。** 我们已在用 `torch_compile_tf32` 作同精度基线,应明确前置而不是放附录。

## 2.5 S1b:无条件失败降权 —— **判据已于 2026-09-10 整段重做**

> **本节的判据被实测取代过一次。** 原判据(median-M + 活对照,见 §2.5.4 保留的记录)前瞻重放下**取值级误杀 67.5%**,比它要取代的计数式黑名单(N=6,2.3%)差 **29 倍**。这是对我自己设计的否证,详见 `docs/decision-s1-not-worth-building.md` §二。以下是实测过的那一版。

### 改什么

**规则(全部四条,缺一不可)**:

> **2026-09-10 二次修订。** 首次修订写的是「跨空间汇总 + 下限 8」。风险分析(`docs/result-s1b-risk-analysis.md`)实测发现**「跨空间」在这份语料里等于「跨候选」**(N=8 的 4 条规则里 3 条混了多个候选,`DOT_PRECISION=tf32` 混了 10 个),而根因是候选自己的代码性质 ⇒ **原理性错误**。以下是三条独立判据(原理 / 证据强度 / 阈值稳定性)一致指向的那一版。

1. 证据按 **`(candidate_id, knob, value)`** 汇总,跨该候选的**多个空间**(每候选中位 2 个),**不跨候选、不跨 run**;
2. **触发**:累计 ≥ **7** 次失败(`correctness_mismatch`)且 **0** 次通过。**7 是留一选出的**(用 4 个 run 选最小零误杀 N,五次一致),不是我挑的常数;
3. **撤回**:一旦出现**任何一次**通过,**永久**撤回该规则并恢复权重;
4. **动作是降权到 1/4**,保留非零概率。**k 不能取 8** —— 实测 k=8 时该取值期望仍被采到中位 **0.8 次 < 1**,等于摘除。

**为什么必须跨空间(而不是每空间独立)**:单空间内收益有**算术天花板**。旋钮域中位 4 个取值 ⇒ 一个取值在 40-trial 预算里只出现约 10 次,要求看到 7–8 次失败才动手等于**等它的 trial 花光**:

| 下限 N | 触发 | 该取值总出现 | 触发前已花 | 触发后可省 | 可省份额 |
|---|---|---|---|---|---|
| 3 | 70 | 561 | 233 | 328 | 58.5% |
| 6 | 35 | 332 | 213 | 119 | 35.8% |
| **8** | 26 | 267 | **208** | **59** | **22.1%** |
| 12 | 8 | 107 | 96 | 11 | 10.3% |

**安全与收益在单空间内直接对冲,调参解决不了。**

**为什么必须有撤回**:全 hindsight 判定下,在 ≥2 空间出现且 ≥1 空间全败的 18 个 (knob,value) 里,**只有 4 个真的在每个空间都全败,14 个在某些空间活着**。撤回把这 14 个变成「先误触发、见第一次通过即退回」,代价是几个 trial 的采样份额而非丢掉配置。

**实测(前瞻式、全局顺序、先判后学)。三种汇总范围,并列置信上界**:

| 汇总范围 | N | 规则 | **省下失败 trial** | **误杀通过** | **误杀率(0 时给 95% 上界)** |
|---|---|---|---|---|---|
| 每空间独立 | 8 | 32 | 63 | 0 | 0% (**≤8.9%**, n=32) |
| **每候选(跨其空间)** | **8** | **33** | **206** | **0** | **0% (≤8.7%, n=33)** |
| 整个 run(跨候选) | 8 | 4 | 249 | 0 | 0% (**≤52.7%**, n=4) |
| 每候选 | 12 | 20 | 105 | 0 | 0% (≤13.9%, n=20) |
| 整个 run | 12 | 3 | 237 | 0 | 0% (≤63.2%, n=3) |

**这张表推翻了首次修订的选择。** 跨候选那档的 249 只由 **4 条规则**支撑,0/4 的 95% 上界是 **52.7%** —— **数据完全无法排除「真实误杀率高达一半」**。per-candidate 用 33 条规则拿到 206,上界 **8.7%**,证据强度差一个数量级。**「误杀 0」在 n=4 时几乎不是证据**,这是首次修订报「省 249、误杀 0」时漏掉的部分。

**误判概率随阈值的完整曲线**(直接测,不依赖挑定的阈值):k=1 → **78.5%**、k=3 → 26.7%、k=4 → 13.5%、k=6 → 2.3%、**k=7 → 0%**、k=12 → 0%。

**阈值稳定性(对 S1b 自己用一次「N=12 是事后挑的」那条判据)**:用 4 个 run 选最小零误杀 N,在第 5 个上验 ——

| 汇总范围 | 五次选出的 N* | 稳定性 |
|---|---|---|
| 每空间独立 | [7, 7, 7, **6**, 7] | **不稳定**(那次留出 run 误杀 1) |
| **每候选** | **[7, 7, 7, 7, 7]** | **稳定,五次全零误杀** |
| 整个 run | [**5**, 7, 7, 7, 7] | **不稳定**(那次留出 run 误杀 1) |

**原理、证据强度、阈值稳定性三条独立判据一致指向 per-candidate。**

**余量只领先 1 步,这是最脆弱的一点**:后来真的通过的取值,首次通过前累计失败数**中位 0、最大 6**(≥5 的只有 2 个,≥8 的 0 个)。所以 N=7 = 观测到的最长失败前缀 + 1。**一个连败 7 次后通过的取值就会造成一次误判** —— 不是「不会发生」,是「2776 个取值里没发生过」。

**绝不能按 dtype 值汇总**:同一个精度词在不同旋钮下行为相反 —— `DOT_PRECISION=tf32` 是 **0/164**,而 `COMPUTE_DTYPE=tf32` **通过 209 次**。

### 过度拦截的两个层次

**会拦,幅度已量化**:per-candidate N=7 下 33 条规则,一条中位吃掉该空间剩余预算的 **18.9%**(触发后该键中位还出现 6 次、最大 20 次)。其中 **0/33 条是错的**。

**最坏后果 —— 最优点有没有被挡住**:误杀率不是最贴切的指标(误杀一个平庸的通过点几乎无代价,**挡住最优点才是灾难**)。直接检查 64 个空间的最优 trial:

```
0 / 64 个空间的最优点用到了会被降权的取值
```

**这是 S1b 与已撤下的 S1 风险结构的根本差别。** S1 删的是**条件失败**的组合,而那些组合的成员**正出现在最优点里**(`DOT_PRECISION=fp16` 曾持有一个空间的最优 2.6286 ms)。S1b 只动**从未通过**的取值,所以它**在结构上**碰不到最优点。

### 机制可命名,所以阈值不是事后挑的

N=7/8 触发的规则集中在精度类旋钮(`DOT_PRECISION=tf32`、`COMPUTE_DTYPE=bf16`、`BC_CACHE_DTYPE=bf16`、`GEMM_PRECISION=bf16`)。**这与已知根因吻合**:低精度 100% 失败的两个成因(未补偿的 `dot`;`PREC` 门控整个算法)都让该取值在**该候选的每个空间**里无条件失败,而**不影响**其他候选 —— 这也正是 §上文「不得跨候选」的机制依据。

**但判据必须保持通用** —— 规则是「per-candidate 无条件 + 可撤回」,**不得**写成「只对精度旋钮生效」。精度类只是当前语料里满足该判据的集合;硬编码进去就是针对单一 case 的特化修改。

## 2.6 S2:按维度独立的多份判决 + 消化层

### 改什么

**现状**:`classify()`(`bottleneck.py:223-256`)返回**单个** `BottleneckVerdict`,`kind: str` 一个字符串,9 个 return 点各给一个标签。实证代价:**L3:21 的 20 份报告里 19 份 `resource_limited`**。

**但分量大多已算出来了**:`evidence` 已有 31 个键(实测枚举),含 `occupancy` + `occupancy_limiter`、`n_regs`、`n_spills`、`shared_bytes`、`pct_of_dram_peak`、`pct_of_compute_peak`、`arithmetic_intensity`、`ridge_flop_per_byte`、`uses_tensor_cores`、`at_limit`、`peak_alloc_mib`、`candidate_aten_mib`、`threads_launched`、`backend_reachable_frac` + `basis`、`compute_ceiling_used`、`candidate_precision`。**向量已经存在,只是被 if-else 链塌缩成标签。**

**三件事同时做**:

**(a) 判决改形状** —— 每维一条 §1.5.3 的记录;多维同时 binding 输出多份。

**(b) 消化层(四元组)** —— 每维一条:

```
{ dimension, severity, root_cause, ranked_recommendation, expected_delta }
```

- `severity`:**三档**(binding / near-binding / slack)。二分会把中间情形误路由 —— L3:48(带宽 90.4%)与 L3:43(融合头寸 69×)在三区下才分得开;cuPilot 同样用三个 roofline 区。

## 2.8 S2b:访存模式墙

### 改什么

Instruction Roofline(Ding & Williams, PMBS@SC19)的指令强度被限死在 `[1/32, 1]`,若干位置有已知名字的墙:

| 模式 | 强度 |
|---|---|
| stride-0(广播) | 1 |
| 单位步长 FP32/INT32 | 1/4 |
| 单位步长 FP64 | 1/8 |
| stride-8(FP32)/ stride-4(FP64)/ 随机 / gather | 1/32 |
| shared 无 bank 冲突 | 1 |
| shared 32 路冲突 | 1/32 |

**候选相对这些墙的横坐标就是其访存模式的直接读数,而它可以从 Triton 的 tile/stride 配置静态推出来** —— 不需要 counter、不需要跑。**这是某一维自己的坐标而非合成量,也不是变化率**,所以不受纠正 3 影响。

**原料已在**:`statics.py:66-77` 已数 STS/LDS/BAR/vec_128;两台机 `nvdisasm` 都在(`/usr/local/cuda/bin/nvdisasm`),且 Triton 自带 vendored 副本。

| **J2b-1** 映射正确 | 手工造已知模式的 Triton kernel(单位步长 / gather / bank 冲突各一) | 🟡 **正对照必须存在**:**至少一个 kernel 必须落在 1/32 墙上**,否则推导器恒返回好结果。依据是纪律 `probe needs a positive control` —— 我曾把探测器自身故障读成五个阴性结果 |

### 改什么

我先前写「剩下的里有**真候选被门挡住**的情况(三任务噪声底全部低于 `relaxed_pass_frac`)」——**这个猜想已被实测否证**。逐条分类全部 537 个失败:**门归因 0 例,537/537 是候选自己的问题**。噪声底低于 `relaxed_pass_frac` 是真的,但绝对门**不是**唯一判据 —— `fp64_relative_gate: true` 在三个 L3 配置里都开着,它按候选距 **fp64 真值**的 RMSE 独立判决,并已实测救回 **2790** 次正确性检验。这 537 个是它**放过之后仍然**被拒的,最小 **3.04 倍**、中位 **6.48 倍**参考自身误差,近 15% 超出 **1000 倍**。乘数选择也无缺陷(537/537 与参数精度一致,且两个乘数之间的带子为空)。

**所以门侧不做任何改动** —— 放宽只会把 3.04–3766 倍误差的 kernel 收进来。**真正的杠杆在候选生成侧**:未补偿的 `dot`(三项分裂过 12/12,单次全灭 11/11)与 `PREC` 门控整个算法(非 fp16 落到未稳定化的 `else`)。参考量级:L3:48 上 8/8 张量核候选被拒、7/7 标量候选被收,最好成绩完全没用上张量核。**这仍是独立一项,不许并进 S1b。** 详见 `docs/result-gate-not-at-fault.md`。
